# Lessons from running GEAR by hand

While GEAR cannot run itself, its captain (Claude) runs the process manually with real lanes. Every mistake made there is one a future captain — another model, another team — will also make. Each entry names the mistake, why it happens, and the GEAR rule or mechanism that prevents it. A lesson is closed only when that rule/mechanism exists (doc, skill, script now; engine later).

| # | Mistake | Why it happens | Prevention in GEAR |
|---|---|---|---|
| L-1 | Typed a shell `export` into panes that already hosted agents; it was submitted as a prompt and both agents started working on it | Assumed a pane's occupant instead of looking | SOP (`agent:<kind>` "Before anything"): read the occupant first. Engine: `pane_run` only into a pane observed as a plain shell (design/03) |
| L-2 | Started agents without the CLI's auto-approve flag | Did not know the flag was essential | Profile `unattended_args` is mandatory; a profile without it is never verified (design/04) |
| L-3 | Started an agent and would have dispatched before choosing its model | "Agent started" felt like "agent ready" | Onboarding = start → choose model for the role → `/model` → check status bar → dispatch (SOP, 17 §8 model rule). OpenCode resumes the last-used model, not the config |
| L-4 | Created worktrees with plain git at invented paths | Did not check what Herdr provides | Worktrees only via Herdr; paths from Herdr config (17 §4) |
| L-5 | Gave every task its own worktree for long-lived lanes | Did not separate lane vs temp | Lanes hold one worktree for life; only temps get one per task (17 §4) |
| L-6 | Named lanes `lane-a`/`lane-b` | No naming rule | Duty first; names `<project>-<duty>`; temps `<project>-<task>` (17 §1–§2) |
| L-7 | Cut tasks of 40–90 min / 1000-line diffs | Planned like BMAD stories | Size rule ≤ 30 min, ≤ ~300 lines, ≤ 3 checklist items (decompose skill) |
| L-8 | Queues forced lanes to wait for review (T-1 → T-3) | Planned sequential layers | Each lane's first ready tasks independent; contract first across lanes; `lowready` trigger (17 §6a) |
| L-9 | Captain did acceptance + code review itself | Old rule "captain reviews" | Reviews by temp reviewers; captain only decides (17 §8) |
| L-10 | Doorbell rang once for an idle lane; captain got pulled into other events and forgot it for ~15 min | Single-shot notification + captain attention | Doorbell re-rings while a lane with work is stopped or its queue is short; silent only on standby. Captain wake checklist: idle/low-ready first, then the triggering event (ops/CAPTAIN.md step 0). Engine: review triggers `idle_lanes`, `low_ready` (design/11) |
| L-11 | Marked T-3 `ready` without a packet | Board and packets edited separately | `gear plan apply` refuses `ready` without a packet and with an unmet size/dependency rule |
| L-12 | Made the reviewer a long-lived lane that would need `/clear` before each review | Chose convenience over role fit | Lane vs temp rule: clean-per-task work is temp, pushed to a fresh session; no "clear before dispatch" lanes (17 §8a) |
| L-13 | Treated Herdr `done` as "agent finished" when the provider quota had run out | Status ≠ outcome | Always read the screen on stop; quota markers in the profile (SOP pitfalls) |
| L-14 | A watcher event fired on every push of a reviewed branch | Keyed events on commit sha | Events key on status changes (ops/bin/watch.sh) |
| L-15 | Captain asked the user to approve fixes for problems the user had pointed out | Over-cautious after an earlier rebuke | Captain decides within the conventions; asks only for user-owned decisions (release, money, scope, destructive acts on others' things) — captain skill |
| L-16 | Reviewer skeleton signature lacked an input it needed (`reconcile` without profiles) | Signatures written before the call sites | Contract-first tasks include a throwaway implementation that exercises the signature before lanes get it |
| L-17 | Spawned two research subagents for a few files and made the user wait | Delegation reflex | Captain reads small material itself; delegates only large mechanical work |
| L-18 | A reviewer created its own git worktree in a temp dir to check out the reviewed commit | The review rules did not say how to look at another branch | Reviewers check out the reviewed commit inside their own worktree (`git switch --detach`); never create worktrees (ops/REVIEW.md) |
| L-19 | Captain put not-yet-implemented contract tests on `dev`, turning it red; other tasks' "still passes" checks failed and a lane reordered its queue to unblock itself | Contract-first without keeping the integration branch green | `dev` always green: contract tests for unmerged tasks are `#[ignore = "T-n"]`; the task runs them with `--include-ignored`; the captain removes the ignore at merge |
| L-20 | The doorbell nagged "stopped with work" for a lane that had correctly stopped at the review cap | Work counted without the cap | The watcher counts ready tasks as work only below the review cap |
| L-21 | One fresh agent per review cost ~20 s plus a ~1 min cold Rust build per review (15–25 % of review time) | Clean context was equated with a fresh worktree | Clean context = new session; warm reviewer seats keep shell and build cache (17 §8a, ops/bin/start-reviewer.sh) |
| L-22 | All three reviews finished but nobody decided them; the data lane sat at the review cap with two ready tasks | The captain's doorbell was not re-armed after a context compaction, and a lane stopped at the cap was (correctly) not "stopped with work", so nothing rang | Watcher heartbeat; `board.sh` prints `WATCHER OFF`; captain never ends a turn without it armed; new `capped` event when a lane is stopped at the cap with ready tasks (ops/bin/watch.sh). Engine: the doorbell is part of the engine loop, not something a captain re-arms |
| L-23 | `dev` still had the slice-1 acceptance test red (7 tests panicking on `todo!`) after L-19's fix | L-19 was applied only to the tests just written, not swept across `dev` | Rule applies to every test that targets an unmerged task, including end-to-end acceptance tests; the captain's merge step runs `cargo test --workspace` on `dev` and any red not owned by the merged task is fixed before pushing |
| L-24 | Captain created a scratch git worktree to peek at `origin/dev` (removed at once) | Quick-check reflex; L-4 only stated where lanes' worktrees come from | To look at another commit use `git show <rev>:<path>` / `git log`; no worktree for reading. Engine: worktrees only through the Herdr adapter |
| L-25 | A reworked task's second hand-in did not ring the doorbell | The watcher re-armed a packet event only when the pushed packet went back to `running`; the lane went straight `review → review` | Re-arm on the captain's own decision: board `rework` clears the packet key (ops/bin/watch.sh). Engine: events key on (task, attempt), not on status text |
| L-26 | A lane ended its turn right after handing in, with a rework and two ready tasks waiting, and reasoned from its memory of the queue ("merge T-16 first, it is ready") | The rule "go to step 1" was one clause among many; the lane's picture of its queue was stale | Lane rule: end the turn only when the inbox prints "none for now" (ops/CONVENTIONS.md step 4). Watcher: `stopped with work` re-rings; reviews counted against the cap ignore tasks the board sent back to rework (else a false `capped`). Engine: the home page, not the agent's memory, is the queue |
| L-27 | A task handed in that no longer merged into `dev` (another task had landed in the same import block); a full review round was spent to find it. Also the watcher went silent on a rework hand-in while the board said `rework` | Lanes checked only their own tests; the earlier L-25 fix cleared the event key but skipped the rework state entirely | Lanes run `git merge-tree` against `origin/dev` before every hand-in and merge `dev` in on conflict (ops/CONVENTIONS.md); the watcher reports a rework hand-in when the packet says review on a branch newer than its review record. Engine: refuse a hand-in whose branch does not merge, before starting a reviewer |
| L-28 | A packet asked for "one query" while its allowed changes excluded the store that would provide it; the lane built a workaround and the review spent a question on it | Captain wrote the goal from the ideal design without checking the public API the lane may use | Packet self-check (decompose skill): every goal item must be reachable with the allowed files and the existing `pub` API; otherwise the captain adds the API first (contract-first) or drops the item |
| L-29 | Switched both lanes to "DeepSeek V4.1 Flash" and the picker chose the free OpenCode tier ("DeepSeek V4.1 Flash Free"), which hit its own limit within minutes; the status-bar check passed because it matched a prefix | Filter and check used a name prefix shared by two providers | Model switch uses the full label (incl. the variant/provider), and the check matches the full label; quota markers include `usage limit reached`. Profile: models are named by provider/model id, not display prefix |
| L-30 | Reviewer model check failed (wrong picker filter `deepseek-v4-pro`), and after the manual fix the review prompt vanished into a second "Select variant" dialog | The alternate model was configured without being tried once in the picker | Any model in a chain is tried in the picker at kickoff (label + whether it has variants) and recorded; scripts handle the variant dialog; a prompt counts as delivered only when the agent is seen `working` |
| L-31 | A re-review resumed on another seat kept working in its original seat's directory, which another reviewer had switched to a different branch; it worked around it in a temp export and left a staged stray edit behind | An OpenCode session is bound to the directory it was created in; `-s` from another directory does not move it | Re-review runs on the seat whose directory the session records (`opencode session export` → `directory`); if that seat is busy the job waits (start-reviewer.sh exits 4). Engine: a temp worker's session and its worktree are one resource |
| L-32 | Nearly every review spent a P3 on stale `Branch:`/`Diff:` numbers in the writer's Result | The format asked the writer to state its own hand-in commit and final diff, which the hand-in commit itself changes — impossible to get right | Result names the last code commit and carries no diff counts; reviewers take both from git and do not flag it (ops/CONVENTIONS.md, ops/REVIEW.md). Engine: hand-in facts (sha, diff) are recorded by GEAR, not typed by the agent |
| L-33 | A hand-in merged into `dev` without a textual conflict but did not compile (two tasks each added `const T0` to the same test module); only the reviewer caught it | `merge-tree` checks text, not meaning | Lanes merge `origin/dev` into the task branch and run acceptance on the merged result before every hand-in (ops/CONVENTIONS.md). Engine: the pre-review gate builds the trial merge, not just merge-tree |
| L-34 | Captain committed and pushed a merge with conflict markers to `dev` (a chained `git merge && …; … git add -A && git commit`) | Merge steps were typed ad hoc; the `;` let later commands run after the merge failed | One checked merge operation, `ops/bin/merge-task.sh`: `set -e`, aborts a conflicted merge, refuses conflict markers, builds and tests before pushing (CAPTAIN step 4b). Engine: merge is a single op with a verify gate |
| L-35 | The captain's own task branch also edited `ops/PLAN.md`, so it conflicted with `dev` before review | Board writes and task work mixed on one branch | The board is written only on `dev`; a captain task branch touches only its allowed files, like any lane's (start-reviewer's merge gate caught it) |
| L-36 | A packet's acceptance (`cargo test -p <crate> -- --include-ignored`) went red because of other unmerged tasks' contract tests in the same crate | The acceptance command was wider than the task | Acceptance = crate tests without ignored + the task's own ignored contract tests by file and name (decompose skill self-check) |
| L-37 | A new packet was made by copying a merged one and kept its `Status: review` and lane record | The merged packet on `dev` contains the lane's state | New packets start from `ops/tasks/TEMPLATE.md`. Engine: packets are rendered from the store, never copied |
| L-38 | Twice a new contract made an older contract test wrong (`not_yet_commands` vs `plan apply`; T-36's "any Staff is rejected" vs T-55) and the lane had to stop and ask | When the captain changes behaviour it did not search for tests asserting the old behaviour | Writing a contract that changes behaviour includes grepping existing tests for the old assertion and updating them in the same commit (decompose self-check). The lanes' questions were right |
| L-39 | A lane sat idle with a ready task (T-54). Cause: it had correctly ended its turn when its inbox was empty; the captain then made T-54 ready (T-53 merged) without waking it, and the watcher — which would have nagged "stopped with work" — was off because the captain had not re-armed it after a foreground merge. The captain first blamed an OpenCode auto-compaction; the user had compacted the session by hand, which does not affect the flow | (1) unblocking a task did not include waking its lane; (2) re-arming the watcher depended on the captain remembering; (3) a cause was stated without evidence | (1) whenever a task becomes ready, wake its lane if it is stopped (CAPTAIN); (2) a Claude Code Stop hook (`ops/bin/watch-guard.sh`) refuses to end the captain's turn while the watcher heartbeat is stale; (3) state a cause only with evidence from the screen/log, otherwise say "unknown". Engine: `gear run` keeps the doorbell loop running itself |
| L-40 | The first real run had the engine in a foreground pane printing tick lines, and the design put it in a plugin tab the user must open; the user asked why they should run and watch a process that never talks to them, and why its output was not kept for debugging | The design traded the user's daily experience for an ops worry (stray background processes); engine output went only to a terminal | The engine is a background process started by any `gear` call; its output goes to a timestamped `engine.log`; the user sees only the board (design/14). Judge a design by what the user has to do and look at |
| L-41 | First self-hosted dispatch: all three deliveries stayed unconfirmed and were flagged, although the lanes were working | The delivery text pointed at `gear --show T-n`; the lanes ran exactly that, and only the home page `gear` records a view | The delivery text says "run `gear` first". The captain's home page should also show flagged seats (it showed nothing) — goes to the board task |
| L-42 | The captain's doorbell rang again for the same two items it had already shown (both waiting on reviews the captain had started) | The doorbell fires while the inbox has unresolved items and the captain is idle, regardless of whether the captain already saw them | Ring only for items the captain has not been shown (the view record has `shown_msgs`); seen-but-open items wait for the captain's own next `gear`. Goes to the runtime lane |

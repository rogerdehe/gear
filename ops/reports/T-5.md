## How a result becomes a review

1. The task is `Verifying`, its last attempt is `Submitted` with a candidate, and no temp seat is bound to it.
2. The seat `r-<n>` is created `Queued` and bound to the task (`seat.task_id`), in one transaction.
3. A temp slot is free (`[quota].temps` counts Starting/Active/Releasing/Unknown, design/10) → the worktree of `review/t<n>` (opened if it exists, else created with the candidate as base), the environment line (`GEAR_CTX`, `GEAR_DB`, plus the model when the CLI takes one in the environment), the `[temps]` agent, then the seat `Active`.
4. One Deliver op carries the review packet. The reviewer runs `gear`, then reviews on that branch and hands the verdict in with `gear send --kind review --task … --attempt … --verdict pass|fail "ops/reviews/T-…md"`.
5. No free slot → the seat stays `Queued`, the captain gets one open item for the task, and the lane is not blocked.

The reviewer's model is the first of `[models].review` that differs from the writer's (the lane's primary model) — for this project `gpt-6.1-sol` on codex, so writer and reviewer never share a model.

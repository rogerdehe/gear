## What landed

### `gear queue [--json]` (design §8.3)

The queue is a new module, `crates/gear-app/src/queue.rs`, and the command
itself is in `crates/gear-cli/src/main.rs` (`Cmd::Queue { json }`). It is
captain-only and read-only: it starts no engine and writes nothing.

Everything is read from the store, never from the plan file:

```
hull  working T-143 38/60m  · left 3 (125m): T-148 35m, T-153 30m needs T-143, T-160 60m
deck  working T-144 22/45m  · left 4 (175m): …
keel  idle: next T-150 waits for T-142 (hull, review) · left 1 (40m)
mast  idle: nothing left planned · left 0
review-1 reviewing T-142 · review-2 standby 3m
```

- **The lanes** — one line each, in seat order. A lane that works says what
  it works on and how long that has taken against the estimate
  (`working T-143 38/60m`); the task is the one the lane has an attempt in
  flight for.
- **An idle lane says why**, through the one function the board uses
  (`gear_board::idle::idle_reason` and `gear_board::idle::describe`,
  design §8.2): `next T-150 waits for T-142 (hull, review)`, `nothing left
  planned`, `quota until 15:12`, `held: …`, `parked until …`.
- **What the lane has left** — the count and the minutes of estimate, and
  the tasks themselves (three at most, then `…`), each with its estimate and
  the dependency it waits for (`T-153 30m needs T-143`).
- **The reviewers are on the last line** — the task each one reviews, or how
  long it has been standing by (`review-1 reviewing T-142 · review-2 standby
  3m`).

`--json` prints the same facts as JSON: the lanes with their working task,
their idle reason, their left tasks and their minutes; the reviewers with
their task and their standby time.

### `gear plan show T-n` (design §8.3)

`crates/gear-app/src/plan.rs` gained `show` (the command is
`gear plan show T-n`). It prints one task's block as it would stand in the
plan file — the header (`## T-7 [must] lane=heat milestone=M2 required`),
then the fields the task carries: `goal`, `accept`, `evidence-files`,
`evidence-due`, `estimate`, `deps`, `followup-of` and `issue`. The captain
edits a block without reading the whole file.

The block is the one the draft parser reads back, so a block that `plan show`
prints parses to the same task (the test proves it: the block goes through
`gear_app::draft::parse` and every field comes back the same).

## Attempt 2 — the review's F1–F3

The review of attempt 1 (`ops/reviews/T-163.md`) failed it with three
blocking findings. Each is fixed with the smallest fix the finding names,
plus the test the finding names.

- **F1 — the elapsed minutes of a task that is in flight.** The attempt's
  last recorded step was used as the end of the round, so a running task's
  clock froze at its start. The end is now the merge, or the clock while the
  round runs.
- **F2 — a lane that is idle for a reason is not working.** The idle reason
  is computed first (through the board's own function); the lane's task is
  only shown as its work when the lane is not idle for a reason. A held, a
  quota-parked and a declared-waiting lane now says why, in the text and in
  the JSON alike, and its unfinished task stays in its left list.
- **F3 — only the available reviewers.** A released or a retired reviewer
  (its agent and its pane are gone, design §3.6) is not in the queue at
  all; the wording `standby` belongs to a seat that really stands by, and
  every other live state is named as it is.

## Notes for the reviewer

- `crates/gear-app/src/queue.rs` is a new module of this lane; the lane owns
  `crates/gear-app/src/{plan,home,mail}.rs` and the CLI. The idle reasons
  come from `gear-board`'s one function (design §8.2), as §13.6 says: the
  board, `gear queue` and the imbalance item use it.
- The queue's "working" is the lane's attempt in flight — the same rule the
  board's idle function uses, so a lane that works is never called idle.
- The task list of a lane's line names three tasks at most and then `…`, as
  the design's own line shows (`deck … · left 4 (175m): …`).
- An idle lane's line carries the count and the minutes but not the list:
  its reason already names the next task (design §8.3's own line).

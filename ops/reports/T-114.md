## The change

**1. A pi lane takes its model as a start flag.** `model_start("pi", model)` gives
`--model <provider>/<id>` and no environment line, next to the other CLIs that
take the model as a flag (claude, grok, codex) — deck's T-113, in `dev` now.
Nothing else of the OpenCode path is used: the session API (`session.create`)
and the status-bar model gate are both keyed on `opencode`, so a pi lane asks
no session and needs no `[models.switch]` labels — it has no model picker GEAR
drives.

**2. A quota stop on pi is a restart, not an in-place switch.** The decision
"in place or restart" follows the **CLI**, not the model: an in-place switch
needs a model picker GEAR drives, and OpenCode is the only one today
(`switch::switches_in_place`). Every other case — another CLI, or the same CLI
without a picker (pi) — is the restart of T-35: the agent is closed with its
profile's exit keys, the CLI of the chain entry starts again in the **same
pane** and worktree, and the lane's task is delivered again in the new session
(`Continue T-1: run 'gear' first`).

Before this change the same-CLI case was an in-place switch whatever the CLI
was, so a quota stop on pi was flagged with "no `[models.switch]` labels" and
the lane stopped; a quota stop on codex or claude was flagged the same way.

**3. An exhausted chain parks the lane**, as for every other CLI: the seat
goes to `Parked` until `[models].quota_reset_h`, and the captain is rung with
an urgent item. At the reset the lane is started again on the first model of
its chain (the same restart path).

## The identity proof on a live pi (T-104)

The proof must hold for pi: a caller may act only as the seat of the pane it
really runs in. Checked live on 2026-10-26 (pi 1.4.0, Herdr 0.19.1, macOS), in
a scratch workspace `pi-ancestry` with `pi --model opencode-go/deepseek-v4.1-flash`:

The bash tool's own ancestry (the script the tool ran printed it):

```
25445 25308 25445 bash
25308 24605 25308 pi
24605 22912 24605 -zsh
22912     1 22912 /Users/roger/.local/bin/herdr
```

What Herdr reports for that pane (`herdr pane process-info --pane w9G:p1`):

```json
{"shell_pid": 24605, "foreground_process_group_id": 25308,
 "foreground_processes": [{"pid": 25308, "name": "node", "argv0": "pi"}]}
```

The pane's shell pid (24605) **and** its foreground process (25308, the pi
process) are both in the caller's ancestry: `claims_pane` is true, so the
real-pane proof of T-104 holds for pi as it is. **No change is needed in the
OpenCode service case** (`gear_app::identity`): pi runs its tools under its own
process, in the pane, unlike OpenCode's shared service.

A `gear` run from pi's bash tool therefore proves the pane it runs in, exactly
like a lane on OpenCode.

## Two more live facts (for deck's profile)

- pi takes the model as the engine sends it: the start above ran
  `pi --model opencode-go/deepseek-v4.1-flash`, and pi's status line showed
  `(opencode-go) deepseek-v4.1-flash • high` — the "provider/id" form works.
- **pi exits on `ctrl+d`, not on `ctrl+c`**: with a live pi in a scratch pane,
  `ctrl+c` left the agent running (it only clears the input — pi's own startup
  line reads `escape interrupt · ctrl+c/ctrl+d clear/exit`), and `ctrl+d` made
  the agent go: `agent.get` answered `agent_not_found` and the pane's
  foreground was the shell again. The engine sends the profile's exit keys, so
  the pi profile has to carry `ctrl+d` (or an exit command) — with `ctrl+c` the
  quota restart would wait and flag the lane.

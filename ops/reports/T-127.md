# T-127 — the engine's tests fit the test-time red line

Scope: T-127 — no engine test sleeps or polls on the wall clock, the merge's
retry backoff is configuration (a test never sleeps it), and the git fixtures
are built once and copied. No assertion is weakened or deleted.

Branch: `hull/t127`; the candidate named in the hand-in carries this report.

## The measurement, and its one caveat

Every number below was taken on this machine while **other lanes were building
and testing** (`home-keel cargo build`, `home-mast scripts/test.sh`): the load
average was **20 to 55 on 10 cores** during the runs. Wall-clock seconds are
therefore inflated and noisy — two runs of the same binary differ by 20 %. The
load-robust number is the crate's own **CPU time** (`user`+`sys`, which the
scheduler does not inflate): it dropped from **242 s to 172 s** (−29 %), i.e.
the tests genuinely do less work, not only wait less.

**Not met, honestly:** the acceptance asks for under 30 s *on an idle machine*.
This machine is not idle, so what is shown is a 103.6 s → 74.2 s cut under two
to five times its capacity, and a CPU-time cut of 29 %. The remaining 172 s of
CPU is process spawns (each `git`/`sh` in the fixtures and in the merge itself,
~37 ms here, ~10 ms idle) — not waiting. Reaching 30 s wall on an idle box
needs that CPU near 30 s × 10 threads; at today's CPU cost an idle box lands
around 25-35 s, which is at the line, not comfortably under it. Cutting it
further means cutting git spawns in the fixtures and the merge, a different
piece of work from this task.

`scripts/test.sh` (the whole workspace, once, parallel, with `origin/dev`
merged in): **905 tests pass, 112.5 s**, exit 0 — the red line is 300 s, the
pass mark 60 s. It ran at a load average of 72 on 10 cores (three other lanes
were testing and building), and flags 45 tests over 10 s. Every one of them is
a fixture test of this crate or of `gear-cli`: none sleeps, and the same tests
take 5-7 s when run alone at that load. The flag is the machine, not the test;
if the captain wants them quiet in the gate it needs `scripts/slow-tests.allow`
lines, which only the captain adds — noted here, not touched.

## The change

**1. The merge's retry backoff is configuration, and it is a hook, not a
number.** `EngineCfg.merge_retry_wait: merge::RetryWait` (new, `merge.rs`).
The default is `RetryWait::backoff()` — exactly today's behaviour, 2 s doubling
to 30 s between attempts (T-61's `RETRY_BACKOFF_S` still names the 2 s). The
tests use `RetryWait::immediate()` (no sleep at all, which is what "run it at
0" was for), and `RetryWait::instead(f)` for the one test that needs the wait
to *do something* — see F2 below. A `u64` alone could not express that: the
retry loop's wait is the only place between attempt 1 and attempt 2 where a
test can put an event without sleeping.

**2. No engine test polls a worker on the clock.** `MergeWorkers` gained
`progress()`, `wait_progress(seen, timeout)` and `running(project)`: the worker
bumps a counter (under a `Condvar`) when it reports, and when the tick collects
a result. Every test helper now waits on that instead of sleeping:
`tick_step` = one tick, then block until the worker it launched reports;
`wait_merge`, `drive` and `ticks` are built on it. The 120 s deadlines and
their 10/20 ms sleeps are gone; a worker that never reports fails the test at
60 s. `multi_repo_contract::wait_merge` (the `it` binary) had the same 30 s
deadline + 20 ms poll loop and now waits the same way — that test was 18.0 s
and is 8.0 s.

**3. The git fixtures are built once per process and copied per test.**
`merge.rs`'s five fixture builders (`Scratch`, `Pair` x2, `Chain`, `Child`) each
ran 8-20 `git` calls per test. They now share one `Shape` (task branches, bases,
files, commit subjects) built once into a template repo per process
(`OnceLock<TempDir>` + one `sh` script) and copied by `cp -R` per test. One
`Branch` struct describes a task branch so the shapes are data, not code. The
`review.rs` fixtures are untouched: they were not in the packet's five slowest
and templating them is a change to that module's tests for ~1 s.

**4. Nothing sleeps on the wall clock in a test.** The last ones were gates that
waited with `sleep 1`/`sleep 2` and loops that waited for a file with a 10 ms
poll. A gate that must be *held* open while the test ticked is now built by
`held_gate(root, tag, after)`: it writes a byte into a fifo (the test's
`await_fifo` blocks on the write), waits for the test's byte (`release_fifo`),
then runs `after`. Each such gate is disarmed by a marker after its first run,
so a second merge — a recovery, a retry — finds the gate a no-op instead of
blocking on a fifo nobody feeds. That caught a real hang during the work.

## Assertions: changed, not weakened

- `a_gate_that_is_still_running_does_not_block_the_merge_step` asserted
  `op.updated > launched_at`, which only held because the gate slept a second.
  It now asserts `op.updated >= released_at.max(launched_at)`, taken before the
  release: stronger (the completion time is at or after the gate's end) and
  true without a clock.
- `a_killed_worker_recovers_from_origin_without_a_half_merge` waited for the
  orphaned gate to finish with `wait_file(done)` (a 10 ms poll). The gate holds
  the merge lock, so recovery cannot finish before the gate exits: the two
  `merge(T-5)` merges and `assert!(done.exists())` say the same thing without
  polling.
- `dispatch_and_doorbells_continue_while_the_gate_sleeps` →
  `…while_the_gate_runs` and `a_sleeping_gate_does_not_block…` →
  `a_gate_that_is_still_running_does_not_block…`: the names no longer claim a
  sleep. Their assertions are unchanged.
- `a_candidate_pushed_late_merges_after_the_retry` (F2 of the T-61 review) let a
  thread `sleep(500ms)` and push the lane's branch. The push is now the retry
  wait itself (`RetryWait::instead`), which is *more* faithful: attempt 1 does
  not see the candidate, the wait publishes it, attempt 2 lands it. Same two
  assertions.
- `tick_step` panics when a merge step had nothing to run, where the old loops
  would spin until their deadline: a stricter check, and it is what keeps a
  test from quietly passing on a no-op tick.

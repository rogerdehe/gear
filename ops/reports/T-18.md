## The shape

- **Seat** `k`: `<project>:review-<k>`, one Herdr worktree on `home/review-<k>` (label `<project>-review-<k>`, cut at the integration branch when first needed — `worktree_open` first, `worktree_create` only if it is not there), and its path kept in the store so a later job uses the pane without asking Herdr again.
- **Job** on a seat: a new generation (a fresh binding on the same pane), the checkout `git fetch origin && git checkout -f -B review/t<n> <candidate> && git clean -fd`, then a new agent `<project>-review-t<n>` (per task) with the review packet as before.
- **Free seat**: a `Released` one. Nothing free and the quota unspent → a new `review-<k>` seat; nothing free and the quota spent → the job waits and the captain is told (as before).
- **Release**: exits the agent and leaves the seat `Released`; the worktree and its `target/` stay for the next job.

## The real-environment proof (for the captain)

After merging, on the engine's first two reviews in a row (any two tasks, e.g. T-12 then T-15's reworks), watch the second start:

```bash
# the seat's workspace is long-lived; the second job reuses it
herdr worktree list | grep -E 'home/review-1'
# when job 1's verdict is in, the seat is released (agent gone, worktree kept):
herdr pane list | grep -E 'review-1'          # the pane survives, agent_status unknown
# when job 2 starts, the seat's pane shows the checkout line, then the agent:
herdr pane read <seat pane> --source recent-unwrapped --lines 20 | grep -E 'checkout -f -B review/t'
herdr agent get <project>-review-t<second>     # the new agent's name
# and the second build is warm: in the pane the first `cargo` line is fast,
# because <worktree>/target is the one the first review built
```

The one-line check that nothing went cold: the second job's first `cargo build` should not recreate `target/` from scratch — compare `du -sh <worktree>/target` before and after the second start (it stays, not resets).

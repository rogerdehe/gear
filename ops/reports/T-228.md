# T-228 — `gear admin init --check` validates a config and changes nothing (contract v1)

Branch: `mast/t228` (cut from `origin/dev`, the integration branch)

Scope: `crates/gear-app/src/admin.rs`, `crates/gear-cli/src/main.rs`,
`crates/gear-cli/tests/it/admin_init_contract.rs`,
`skills/gear/references/captain.md`, plus this report.

## The problem

`init` was the only validator of a `gear.toml`, and it registers the project:
a captain who only wanted to know whether its toml parsed started the engine,
which onboarded every lane. Another project's captain started its fleet nine
times just to check a file.

## The change

`crates/gear-app/src/admin.rs`

- New `pub fn check(config_text: &str, home: Option<&std::path::Path>) ->
  GearResult<config::ProjectConfig>`: exactly the checks `init_with_home` ran
  before its first `store.write` — `config::parse`, `config::validate` and the
  `field: problem` issue list, `config::profile_table` plus the unattended-args
  check for every seat, and the GEAR-skill check of every kind the project can
  start (with the `home` resolution: the caller's, else the process's `HOME`).
  The errors and their texts are the ones `init` gave; nothing was reworded.
  It opens no store, reaches no Herdr and writes nothing.
- `init_with_home` calls `check` where its step 2 started and keeps the
  caller-context checks (step 2b: `GEAR_CTX` seat/project and, on a read, the
  registered seat's role and generation) after it — those read the store, so
  they cannot move. Registration itself (`register` / `re_register`, one
  `store.write`) is unchanged. `init`, `init_with_home` and `init_checked`
  keep their signatures and their behaviour; the one visible consequence is
  that on a config that is invalid *and* called from the wrong seat, the
  config issue is now reported first — the same two errors, in the order the
  packet asks for (store checks after the config checks).

`crates/gear-cli/src/main.rs`

- `AdminOp::Init` gained `#[arg(long)] check: bool`.
- `cmd_admin_init(config, check_only, json)`: with `--check` it reads the file,
  calls `gear_app::admin::check(&text, None)` (so the skill check uses the
  caller's `HOME`) and prints
  `config ok: project <id>, <n> lanes, <m> reviewers` — `n` the config's
  lanes, `m` `[quota].temps`, the reviewers the project has. With `--json`:
  `{"ok":true,"project":"…","lanes":n,"reviewers":m}`. It runs before
  `env_from_process`, so no `GEAR_ADMIN` is needed; it opens no store and
  calls no Herdr. Errors are the usual `GearError` (exit 1, `ERROR <CODE>: …`
  on stderr), so the issue text is byte-identical to `init`'s.
- The non-check path is unchanged, including its order: `GEAR_ADMIN` is still
  checked before the config file is read (the read moved into the small
  `read_config` helper, used by both paths).
- `starts_engine` returns false for `AdminOp::Init { check: true, .. }` and
  stays true for a plain `init`, so `--check` starts no engine.

`skills/gear/references/captain.md` — step 4 ("Write the config") now says:
"Check it with `gear admin init --check gear/gear.toml` until it passes; that
starts nothing."

## The tests

`crates/gear-cli/tests/it/admin_init_contract.rs` (same helpers, one new
`check_cmd` that installs the skills in the scratch home and runs the real
binary):

- `check_validates_a_config_and_opens_no_store` — a valid config with one lane
  and one reviewer prints exactly `config ok: project p, 1 lanes, 1 reviewers`
  and exits 0 with **no** `GEAR_ADMIN`; the same with `--json` gives
  `ok/project/lanes/reviewers`; a `GEAR_CTX` of another project's lane also
  passes. After all three runs `GEAR_DB`'s file does not exist.
- `check_reports_the_issues_init_reports` — two lanes owning `src/`: exit 1,
  `ERROR BAD_FORMAT`, `lanes[1].owns`, no store; `init` on the same config
  produces a byte-identical stderr, and the project is not registered.

Existing init tests are unchanged and pass.

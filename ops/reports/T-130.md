# T-130 — A message for a lane reaches it while it works

Scope: T-130 — an urgent message, and every captain instruction to a lane whose
agent queues input while it works (pi, claude), is typed into the pane at once;
the doorbell names the message ids and says "run `gear` now"; one doorbell per
message; and `gear send` types the doorbell itself before it returns.

Branch: home/keel · contract v2 · cut from `origin/dev` e5082d8.

Files:
- `crates/gear-engine/src/doorbell.rs` — the pure model is now a list of
  `DoorbellItem { id, urgent, at_once }` (`waiting`) instead of the
  actionable/unshown split. `at_once(urgent, kind, from_captain, queues_input)`
  is the one rule: urgent always, a captain `instruction` when the agent queues
  input. `reaches_while_working(message, seat, agent_kind, captain)` binds it to
  stored rows (a seat counts only as a **lane** whose binding kind queues), used
  by the tick and by `gear send` so the two cannot drift. `text(items)` is
  `GEAR: <n> item(s) waiting for you[ (<u> urgent)]: <ids>. Run \`gear\` now.` —
  ids, not bodies. `decide`: an `at_once` message bypasses the idle check and
  the cooldown (urgent must not wait), never the slot check (the T-71 swallow);
  a **working** agent is told only about the messages that must reach it now,
  an idle one about everything.
- `crates/gear-engine/src/lib.rs` (`doorbell_inputs`) — each waiting message
  carries its own `at_once` (captain = the project's captain seat, agent kind =
  the active binding's kind). One doorbell per message: ids named by an earlier
  doorbell op of the seat (`payload.covers`) are dropped before `decide`, even
  after the cooldown and even when that doorbell was never confirmed; a **voided**
  op never reached the pane and covers nothing.
- `crates/gear-engine/src/ops.rs` (`deliver_doorbell_now`) — the send's own
  path. It re-reads seat/generation/reachable/active binding (a stale or closed
  pane is never typed into), calls `herdr.prompt`, and records the doorbell op —
  `Intended → Executing → Submitted` in one transaction, plus the T-40 reminder
  clock — **only when Herdr took the text**. A refused or uncertain prompt
  records nothing, so the engine rings it on its next tick.
- `crates/gear-herdr/src/lib.rs` (`queues_input(kind)`) — pi and claude queue
  text typed while a turn runs; opencode and codex take it into the running
  turn. A function, not a `Profile` field: `model.rs` records why that public
  type must not grow.
- `crates/gear-app/src/mail.rs` — `SendResult.project` (additive, serde
  default), so the CLI can find the message, its seat and its kind after the
  send transaction commits.
- `crates/gear-cli/src/main.rs` — `run_send` takes a `HerdrAct` and, after a
  non-replayed send, calls `ring_recipient_now`: it types the one-message
  doorbell when the message must reach a working recipient. The plain output
  gains `; doorbell typed into <pane>` when it did.
- Tests: `crates/gear-engine/tests/it/doorbell_contract.rs` rewritten for the
  new model (9 tests: the at-once rule, only-at-once-when-working, idle-told-all,
  ids in the text, urgent without cooldown); new
  `crates/gear-engine/tests/it/doorbell_while_working.rs` (4 tests, registered
  in `main.rs`): a working pi lane gets the captain's instruction's doorbell in
  the same tick, a working codex lane gets a normal one only when idle and an
  urgent one at once, and the same message is never rung twice (a second tick
  480 s later, cooldown long past, adds no prompt and no op). CLI (4 tests in
  `main.rs`, fake Herdr): an urgent send types the doorbell before returning and
  the next tick sends no second one, a captain instruction reaches a working pi
  lane, a normal one to a working codex lane waits for idle, and a refused
  prompt leaves the message stored with no op so the engine rings it.
- Docs: `docs/design/07-mail.md` (the doorbell conditions, the at-once rule, one
  doorbell per message, the sender typing it), `docs/design/04-herdr.md` (which
  kinds queue input), `docs/PRD.md` §7 (send and doorbell lines — the user
  changed that requirement), `ops/reports/T-130.md` (this brief).

## Open questions

none — four decisions worth naming:
- **The captain keeps its stale reminder.** `feed_contract`'s
  `a_twenty_minute_old_viewed_item_rings_urgently_once_per_period` (T-40)
  requires the same captain item to be reminded once per configured period; a
  literal "never twice" for every seat would delete that feature. So per-message
  dedupe is for lanes and reviewers, where the contract's problem lives; the
  captain's reminder clock stands, and `docs/design/07-mail.md` says so.
- **A reviewer is not a lane.** A captain instruction reaches a **lane** whose
  agent queues input, literally as the packet says; a pi/claude **temp reviewer**
  still waits for idle (`reaches_while_working` checks the role). One line to
  widen if the captain wants it.
- **"Herdr fails" means the prompt.** A `gear send` with no reachable Herdr
  socket fails before storing, as it did before: since T-104 the sender's
  identity is proven through Herdr, so no seat and no write. A prompt Herdr
  refuses or leaves uncertain stores the message, records no doorbell and the
  engine rings it on the next tick — the CLI test covers the refused case.
- **The send's doorbell holds the seat's slot** until a view confirms it or the
  existing expiry frees it, so an unrelated message for that seat waits a tick.
  That is the unchanged slot rule (design/07, /09) and the reason the T-71
  swallow does not come back.

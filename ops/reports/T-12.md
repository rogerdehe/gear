## Round 1 — the merge step

### How a pass becomes a merged task

1. The task is `Verifying` or `Done` and its attempt has a passing verdict (the candidate the verdict names).
2. No merge op exists for it yet → one `merge` op is queued with the task branch, the review branch and the candidate in its payload.
3. The execution re-checks the task (a cancelled one voids the op), opens or creates `home/merge` (Herdr, created once), resets it to `origin/<integration>`, merges the two branches with `--no-ff`, refuses conflict markers, runs the gate, pushes `<integration>`, then deletes the two branches on origin.
4. The op records `Confirmed` with the merge line, or `Failed` with the output tail and one open item for the captain; either way nothing reached the remote integration branch unless the push happened.

## Rework (round 2, captain scope only)

The five items the captain kept:
- **P0 — the approved candidate, not the branch tip.** The candidate in the op is pinned and checked against `origin/<task branch>` after the fetch; a branch that moved past it is refused with "a new verdict is needed", and the merge itself takes the candidate's sha.
- **P0 — a missing branch is not proof of a merge.** The op is only Confirmed without merging when `origin/<integration>` already contains the candidate (`merge-base --is-ancestor`); a gone branch whose commit is not on the integration branch fails without touching dev.
- **P1 — only the current attempt's pass authorizes a merge.** `passed_tasks` takes the latest attempt and requires the passing verdict to name that attempt, that candidate and that contract; the execution re-checks both before any git runs and voids the op otherwise.
- **P1 — merge `origin/dev` first.** Done; `lib.rs` keeps the review step and the merge step, in that order.
- **P1 — both output streams on a failed gate.** The stdout tail is kept together with the stderr tail (cargo reports test failures on stdout).

One new regression: `a_branch_that_moved_past_the_candidate_is_refused` — dev unchanged, both branches still on origin, the unreviewed commit nowhere.

## Round 3 (captain scope)

- **F1** — the candidate and the branch head are both resolved with `rev-parse` before they are compared, so an abbreviated candidate matches its full sha.
- **F2** — `git fetch --prune origin` before any remote-tracking ref is trusted.
- **F3** — a pass counts on the task's **current contract** (what `tasks::settle` allows), for the current attempt and candidate.
- **F4** — current `origin/dev` merged; the tick keeps the release step and then the merge step.

## Round 4 (F5)

The merge ops that `tasks::settle_review` queues (the dev code that settles a passing review) carry `branch` and `candidate` but **no `review`** — and my code found that op, so it never created its own payload, defaulted the review branch to an empty string and ran `git merge --no-ff origin/`, recording Failed for a clean pass.

Fix: the review branch is derived from the task when the payload does not name one, and it is merged only when `origin/<review>` exists — a task whose review branch is already gone merges the approved candidate alone. One regression seeds an op exactly as `settle_review` produces it (`branch` + `candidate` only) and expects a clean merge.

## Round 5 (F6)

Round 4 made the merge work for the ops that `tasks::settle_review` queues (payload: `branch` + `candidate`, no `review`) by deriving the review branch — but it also made the review branch **optional**: `rev-parse --verify origin/review/t<n>` was checked with `is_ok()`, and a missing ref was silently left out of the merge. That publishes the approved candidate *without* its review branch — a partial merge on dev, which the goal and `ops/bin/merge-task.sh` do not allow.

Fix: the review branch is **required**. When `origin/<review>` is gone, the merge fails before it touches anything, with the git diagnostic:

```
T-5: the review branch origin/review/t5 is missing on origin
git rev-parse --verify origin/review/t5: fatal: ambiguous argument 'origin/review/t5': unknown revision or path not in the working tree.
a merge publishes the approved candidate and its review branch together
```

The integration branch stays where it was, the op is `Failed`, and the captain gets one open item — the same path every other merge failure takes. The derivation of the review branch stays (the settlement ops need it), and the already-integrated replay path (the candidate is already on the integration branch) is untouched.

Two regressions:
- `a_missing_review_branch_does_not_publish_a_partial_merge` — over a scratch repo with a bare origin: only `refs/heads/review/t5` is deleted, the task branch and the candidate are intact. The merge fails, `dev` is byte-identical to before, the task commit is not on dev, the task branch is still on origin, and the worktree is back at `dev` (nothing half-merged for the next run).
- `a_missing_review_branch_fails_the_op_and_tells_the_captain` — the public path: the op is `Failed` with the git diagnostic, `dev` is untouched, and the captain's inbox holds exactly one item. (The fake can now register a worktree that Herdr already has open, so this test runs against a real repository.)

The successful missing-payload-key case (`a_settled_review_op_without_a_review_key_still_merges`) still passes: the review branch is derived from the task and both commits land on dev.

## The restart rule

The merge sequence starts with `git reset --hard origin/<integration>`, so it can safely run again: a second run either redoes the same merge from a clean base (nothing double-merged) or finds the task branch already gone from origin — the push went through before the engine died — and records the op `Confirmed` without touching anything. An op left `Executing` becomes `Unknown` on engine start and is picked up by the same path.

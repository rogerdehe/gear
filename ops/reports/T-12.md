## How a pass becomes a merged task

1. The task is `Verifying` or `Done` and its attempt has a passing verdict (the candidate the verdict names).
2. No merge op exists for it yet → one `merge` op is queued with the task branch, the review branch and the candidate in its payload.
3. The execution re-checks the task (a cancelled one voids the op), opens or creates `home/merge` (Herdr, created once), resets it to `origin/<integration>`, merges the two branches with `--no-ff`, refuses conflict markers, runs the gate, pushes `<integration>`, then deletes the two branches on origin.
4. The op records `Confirmed` with the merge line, or `Failed` with the output tail and one open item for the captain; either way nothing reached the remote integration branch unless the push happened.

## Rework (round 2, captain scope only)

The five items the captain kept:
- **P0 — the approved candidate, not the branch tip.** The candidate in the op is pinned and checked against `origin/<task branch>` after the fetch; a branch that moved past it is refused with "a new verdict is needed", and the merge itself takes the candidate's sha.
- **P0 — a missing branch is not proof of a merge.** The op is only Confirmed without merging when `origin/<integration>` already contains the candidate (`merge-base --is-ancestor`); a gone branch whose commit is not on the integration branch fails without touching dev.
- **P1 — only the current attempt's pass authorizes a merge.** `passed_tasks` takes the latest attempt and requires the passing verdict to name that attempt, that candidate and that contract; the execution re-checks both before any git runs and voids the op otherwise.
- **P1 — merge `origin/dev` first.** Done; `lib.rs` keeps the review step and the merge step, in that order.
- **P1 — both output streams on a failed gate.** The stdout tail is kept together with the stderr tail (cargo reports test failures on stdout).

One new regression: `a_branch_that_moved_past_the_candidate_is_refused` — dev unchanged, both branches still on origin, the unreviewed commit nowhere.

## The restart rule

The merge sequence starts with `git reset --hard origin/<integration>`, so it can safely run again: a second run either redoes the same merge from a clean base (nothing double-merged) or finds the task branch already gone from origin — the push went through before the engine died — and records the op `Confirmed` without touching anything. An op left `Executing` becomes `Unknown` on engine start and is picked up by the same path.

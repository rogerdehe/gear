# T-243 — one project's failure does not stop the other projects' tick

Branch: hull/t243 (code @ the hand-in commit; `origin/dev` merged before
verification, `make check CRATE=gear-engine` green on the merged result)

What changed (`crates/gear-engine/src/lib.rs`, one engine test):
- `TickReport::project_failed: Vec<String>`: one line per project whose
  per-project step failed this tick, `<project>: <code>: <detail>` (the line
  comes from a small `project_error` helper next to `tick`).
- The four per-project loops before the observation push and go on:
  `plan::reconcile_rebinds`, `parallel::check`, `gear_forge::sync` and the
  station checkpoints (the latter two via `if let Err` / `match`). The
  parallel scan still collects the opened ids and the problems it did read for
  a project that succeeded.
- The body of the main `for project in projects { … }` loop (from step 0d,
  the names restore, to step 12, the merge) moved into an inner closure
  `one_project(store, report, id) -> GearResult<()>` that is called once per
  project; its `Err` is pushed to `report.project_failed` and the next project
  runs. Nothing in the body used `continue` against that loop: the four
  `continue`s in it belong to the inner `for (id, state) in &executed` loop
  inside the `store.write` closure, so no `continue` had to become
  `return Ok(())`. The closure's own end is `Ok(())`.
- Steps that run once for all projects are untouched: `rebind::tick`,
  `onboard::onboard_queued`, `settle_reviews`, the first `waits::tick`, the
  observation, `rounds::tick`, the second `waits::tick`, `overrun::tick`, and
  the end-of-tick flag/stall sweeps.

Contract gap (sent as a question M-4125; the captain chose A in M-4127):
- The packet's acceptance names "one project's `config_toml` is invalid TOML".
  With the code as it stands no per-project step raises a config-parse error
  for such a project: every per-project reader tolerates it
  (`config::latest` fallback at the top of the loop, `delivery_grace` via
  `unwrap_or`, `restart::reconcile_config`, `review::start_reviews`,
  `quota::apply_quota_policy`, `merge::merge_passed`, `parallel::check`,
  `attention`, `busy`, `quiet`, `session`). The reachable per-project config
  failures are `config::profile_table(...)?` and `captain_quota`'s config read.
  So the fixture is a config whose TOML parses but whose `[profiles.codex]`
  block is refused by `config::profile_table` (`tail_lines = "many"`) — the
  step the packet's item (3) turns into a reported failure. That is what the
  captain chose (A) over "make the loop's config read a `?`" (B), which would
  also turn the empty `config_toml` of every seeded test store into a failing
  project and break existing tick tests (`silent.rs` full-tick test).

Tests (`crates/gear-engine/tests/it/project_failure_contract.rs`):
- `a_project_whose_config_the_engine_refuses_does_not_stop_the_tick`: two
  projects in one store, `p` (sorts first) with the refused profile block and
  `q` with a ready task and an idle lane. One tick is `Ok`, `q`'s task is
  delivered (`New task T-1` in the lane's pane, attempt `Delivered`), and every
  `project_failed` line names `p` with `BAD_FORMAT` and the profile.
  Verified to fail without the fix: with the closure's `Err` propagated
  (`one_project(...)?`) the same fixture returns `BadFormat: profile codex is
  not a valid profile …` and delivers nothing.
- `a_project_whose_config_is_not_toml_does_not_stop_the_tick`: the same store
  with `p`'s config not TOML at all — the tick is `Ok`, `q` is delivered, and
  `project_failed` is empty, because every reader tolerates that text (this is
  the literal acceptance fixture, kept as the tolerated case).

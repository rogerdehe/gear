# T-22 — A milestone is a voyage with a bar

Scope: T-22 — a plan's `# Milestone <id>: <title>` block must carry `done:` (the one checkable sentence of the phase), `bar:` (the quality line) and `eta:` (the planned landing); `gear plan apply` rejects a block without them (naming the milestone), stores them as a voyage with its departure (the first task's creation) and the task count there, and the captain's home page and the task packet show it. A milestone the draft does not mention keeps applying.
Branch: data/t22 (code @ pending, see the hand-in)
Files:
- crates/gear-app/src/draft.rs — `milestone_parts` (id + title of a block header) and `milestone_fields` (the `done:`/`bar:`/`eta:` lines of its body), read by the apply.
- crates/gear-app/src/plan.rs — `record_voyages`: every block in the draft is validated (`BadFormat` naming the milestone and the missing field), then stored; the departure (apply time, i.e. when the milestone's first task is created) and the task count are fixed on the first apply and never move; `voyage_line` renders the one line both views use; the task packet shows the task's voyage under the identity line.
- crates/gear-store/src/schema.sql + lib.rs — the `voyages` table (project, milestone, title, done, bar, eta, departure, departure_tasks, updated) with `upsert_voyage` (`COALESCE` keeps the first departure), `get_voyage`, `voyages_of_project`. A new table rather than extra columns on the old `milestones` table: the store has no migrations and `CREATE TABLE IF NOT EXISTS` is applied on every open, so an existing store gets it.
- crates/gear-app/src/home.rs — the captain's snapshot lists the project's voyages (max three, then a count) after the totals and before the inbox.
- crates/gear-app/tests/voyage_contract.rs — 4 tests: the field readers; a block missing done/bar/eta is rejected (named) and stores nothing; a voyage is stored with departure/count and shown in the packet and the home page, and a later apply never moves the departure; a task on a milestone with no block still applies.

Verification:
- `cargo build --workspace --all-targets` → clean, zero warnings and zero errors.
- `cargo test --workspace` → green (62 suites; 4 new tests).

Open questions:
- The departure is the time of the apply that first gives the milestone a task (its first task is created then), and the task count is the milestone's size at that apply; a milestone block with no tasks yet stores no departure. Say so if the count should instead be the plan's queue count or rise with later tasks.
- The three fields are one line each (`done:`, `bar:`, `eta:`); a longer sentence wraps in the view but the parser reads one line.
- `milestones` (the old, unused table) is left alone; `voyages` is the new home. A store without migrations gets the new table on its next open.

Out of scope:
- Milestone-level acceptance gates (the bar as a blocking check) and ETA tracking over time — this task records and shows them.
- Editing a stored milestone without a plan block (the plan is the only writer).

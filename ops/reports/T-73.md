# T-73 — `init` freezes where each repo may be pushed

Attempt 1, contract v1.

Branch: `course/t73`; the candidate named in the hand-in includes this
report. Base: `origin/dev` at 208ca54 (the M3 kickoff), merged with the
current `origin/dev` (e613a04) before the hand-in.

## What shipped

`gear admin init` reads, for the project root and for every `[[repos]]`
entry, the destinations the repo's own `origin` remote resolves to —
`git remote get-url --push --all origin`, after git's own
`url.*.insteadOf` and `url.*.pushInsteadOf` rewrites — normalises them as
host + path and stores them. Every init reads them again, so a project that
moves its remote moves with it. Git runs before the transaction (the store is
never held while a subprocess runs) and the list is written with the
registration, so a project never exists without the destinations it was
registered with.

`gear_app::push::check(store, project, repo, url) -> Result<(), Refusal>`
answers the one question a push asks: may this repo be pushed to this
destination? `repo` is the `[[repos]]` name, or `""` for the project root.
A refusal names the repo and the normalised destination and says why: an
unknown repo, a repo with no destination, a destination that is not
registered, a project that is not registered, or a store that cannot be read.

The destinations live in a new `push_destinations` table: the store's schema
version moves to 3, and the step from 2 creates the table and keeps every
row of the store. `InitResult` carries the frozen destinations, so
`gear admin init --json` shows where the project may push.

## The API the other lanes call

- steady's **T-72** (the engine's merge push): `gear_app::push::check(store,
  project, repo, url)` before the push. `repo` is
  `config.repo_of_lane(lane).name` (`""` for the project root), `url` is
  `git remote get-url --push origin` in the merge worktree.
- base's **T-74** (`gear push-check`): the same call with the pre-push
  hook's `$2` (git hands the hook the location the push goes to) and the
  repo the working directory belongs to. `push::push_urls(dir)` resolves a
  repo's push URLs when the hook needs them itself.

One rule the callers must keep: the URL is compared as git resolved it.
The frozen list holds the destinations the rewrite points at, so a raw
remote address (`git@github.com:owner/repo.git` that a rewrite sends to
`https://ext.example.com/owner/repo.git`) is refused on purpose — it names a
place the push does not go to.

## Acceptance evidence

- `push_contract::init_freezes_the_destinations_of_every_repo`: a real repo
  with a pushurl (`git@github.com:owner/parent.git`) and an `insteadOf`
  rewrite to another host freezes `ext.example.com/owner/parent` — the place
  the push goes, not the address the remote is written as. The child repo
  freezes its own local origin; the repo with no remote freezes nothing.
- `push_contract::the_check_passes_the_registered_destination_and_refuses_the_others`:
  the registered destination passes; another host (`gitlab.com/owner/parent`),
  the rewritten external URL (`git@github.com:owner/parent.git` and
  `ext.example.com/owner/other`) and an unknown repo are refused, each with
  the repo and the normalised destination in the refusal; a repo with no
  destination is refused; a project that is not registered is refused.
- `push_contract::every_init_reads_the_destinations_again`: moving the
  pushurl and initing again moves the frozen list; a repo that leaves the
  config leaves nothing behind and is refused as an unknown repo.
- `push::tests` (three): the normalisation of the URL forms (https, scp,
  ssh with a port, file, local path), the case of the path, and a URL that
  names nothing.
- `gear-store`: `the_push_destinations_of_a_repo_are_replaced_and_cleared`
  (the rows are per project and repo, a new list replaces the old one, a
  cleared project leaves nothing) and
  `a_store_of_v2_gains_the_push_destinations_of_t73` (a store of v2 is
  carried up, the table is there and the rows are kept).

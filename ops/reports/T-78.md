# T-78 — the forge layer: `crates/gear-forge`, GitHub through `gh`

Scope: T-78 — a new crate that is the one edge to a project's issues and pull
requests: the `Forge` trait, `GitHub` over the `gh` CLI (JSON, explicit repo,
no prompts, bounded, typed errors), `Local` doing nothing, and the ORCHESTRATE
marker lines.

Branch: base/t78 (code @ the hand-in commit; origin/dev merged before
verification, gate green on the merged result)

Files:
- `Cargo.toml` — `crates/gear-forge` is a workspace member and a
  `[workspace.dependencies]` entry, so T-80/T-81 can depend on it.
- `crates/gear-forge/Cargo.toml` — the crate: serde, serde_json, thiserror;
  tempfile for the tests. No dependency on the store or the engine: the forge
  is an edge and knows nothing of GEAR's own model.
- `crates/gear-forge/src/lib.rs` — the `Forge` trait and its types: `Issue`
  (number, title, body, label names), `Filter` (labels, limit; 0 = the forge's
  default), `PrRef` (repo, number, url, plus `none`/`is_open` so "nothing was
  opened" is a value and not a variant), `MergeMethod` (`Squash`/`Merge` and
  the `gh` flag each means), `MergeResult`, and the typed `Error` — `Tool`
  (cannot run), `Timeout` (ran past its bound), `Failed` (the tool said no),
  `Unreadable` (an answer this crate cannot read). `Issue`'s labels accept
  both shapes `gh` can answer (`[{"name": …}]` and `["…"]`).
- `crates/gear-forge/src/github.rs` — `GitHub`: every call names its repo
  (`--repo`), asks for JSON where `gh` has it, passes nothing on stdin and
  sets `GH_PROMPT_DISABLED`, `GH_NO_UPDATE_NOTIFIER`, `GH_PAGER=cat`, so a
  prompt fails at once instead of hanging a lane. One bounded runner for all
  five calls: the default bound is 30 s, past it the child is killed and the
  call answers `Timeout`; stdout and stderr are read on their own thread while
  the call runs, so a large answer cannot fill the pipe and deadlock the child.
  `open_claim` creates a **draft** and reads the number from the URL `gh`
  prints.
- `crates/gear-forge/src/local.rs` — `Local`: every call succeeds and does
  nothing, so a local-only project behaves exactly as before the forge
  existed; `open_claim` answers `PrRef::none`, `merge` answers "not merged,
  the project has no forge".
- `crates/gear-forge/src/marker.rs` — the two ORCHESTRATE markers:
  `claim(agent, issue)` and `completion(reviewer, rounds, ci)`, each one
  hidden HTML comment with one word per value.
- `crates/gear-forge/tests/it/{main,github_contract,local_contract,marker_contract}.rs`
  — 15 tests: 10 for `GitHub` against a fake `gh` on the child's `PATH`, 2 for
  `Local`, 3 for the markers.
- `ops/reports/T-78.md` — this brief.

Verification:
- `env -u GEAR_DB -u GEAR_CTX cargo build --workspace --all-targets` — exit 0,
  zero warnings.
- `env -u GEAR_DB -u GEAR_CTX cargo test --workspace` — 729 passed, 0 failed,
  0 ignored, zero warnings. Includes the 15 new tests.
- The fake `gh` is a shell script in a scratch directory, on the child's
  `PATH` only (`GitHub::with_path` replaces it, so no test can reach the real
  `gh`); it records its argv and replays recorded JSON. The tests pin each
  command line exactly: `issue list --repo … --state open --json
  number,title,body,labels --limit 5 --label must`; `pr create --repo … --head
  … --base … --title … --body … --draft`; `pr comment <n> --repo … --body …`;
  `pr merge <n> --repo … --squash|--merge`; `issue close <n> --repo …
  --comment …`.
- Typed errors, each tested: a missing tool (`Tool`), a non-zero exit with
  `gh`'s own message (`Failed`), a nonsense answer (`Unreadable`), and a fake
  `gh` that never returns (`Timeout`, with a 250 ms bound and a wall-clock
  assertion that the bound was respected).
- The flags were checked against the installed `gh 2.97.0`'s own help. That
  check caught a real defect in my first version: `gh pr create` has **no**
  `--json` flag (a recorded-JSON fake cannot catch a flag the real tool does
  not have); the number now comes from the URL `gh` prints on success, which
  its help states it does.

Decisions worth the captain's eye:
- `Local` never fails: it answers with "nothing opened / not merged" rather
  than an error, so the engine calls one signature in both modes (T-80's
  "local-only projects do nothing").
- The bound is 30 s per call (`GitHub::with_timeout`).
- The COMPLETION marker's fields are `reviewer`, `rounds`, `ci` in that order,
  with one word per value. The protocol's CLAIM line is the one the task names
  exactly; the COMPLETION line follows the same shape. Nothing in the repo or
  the linked material pins COMPLETION's field order, so the markers' exact
  text is pinned by tests and can be changed in one place (`marker.rs`) if the
  external protocol says otherwise.
- `issues` reads open issues only (the import path of T-79/T-81); a filter for
  closed issues is not in this task.

Open questions: none.

Out of scope: `gear_forge::sync` and the engine's per-tick call (T-80), the
`[github]` config and `issue_block` (T-79), `gear plan import-issues` and the
`github` skill (T-81), and reading CI's state — the completion marker's `ci`
is the caller's word, not a forge call.

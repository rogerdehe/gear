# T-23 — The captain's gate in the automatic flow (core)

Scope: T-23 — the engine's review packet carries the task's milestone `done:`/`bar:` and the blocking-or-logged rule; `gear send --kind review` takes `--blocking <ids>`; settlement sends back only the blocking findings (the rest are one information item for the captain); a fail without a blocking finding settles as a pass; rework rounds are capped by `[conventions].review_max_rounds` (past the cap: one captain action item, the task stays Verifying).
Branch: data/t23 (code @ pending, see the hand-in)
Files:
- crates/gear-engine/src/review.rs — the review packet: `Done (the milestone's sentence)` and `Bar (the quality this phase needs)` from the task's voyage (T-22), the rule (every finding is blocking — naming the part of the done-sentence or bar it breaks — or logged; fail only for a failed mechanical fact, a P0 or a blocking finding), and the hand-in command with `[--blocking <ids>]`.
- crates/gear-store/src/schema.sql + lib.rs — `review_blocks` (project, task, attempt, ids, created) with `set_review_blocking` / `review_blocking`: the ids a reviewer named as blocking. A new table, since a store without migrations gets it on its next open.
- crates/gear-app/src/review.rs — `Review.blocking`; `submit_review` stores the ids with the verdict (same transaction).
- crates/gear-app/src/mail.rs — `SendArgs.blocking` carried into the review.
- crates/gear-cli/src/main.rs — `gear send --blocking <ids>` (comma separated).
- crates/gear-app/src/tasks.rs — the settlement: `blocking_ids` + `split_findings` (a finding's id is the first word of its line: `F1: …`, `P1: …`); a fail with blocking findings → rework with only those findings in the note and the logged ones as one information line; a fail without a blocking finding → settles as a pass; `rework_rounds_over_cap` (`[conventions].review_max_rounds`, default 3, compared with the review round = the attempt) → `tell_captain_cap` writes one action item and the task stays Verifying (the attempt stays handed in).
- crates/gear-app/tests/settle_review_contract.rs — the rework note carries only the blocking finding; a fail without blocking settles as a pass with one information item; the cap (four rounds → one action item, task Verifying, a second settlement adds none); a restart between the review and the settlement does not double-settle (no second merge/info/rework).
- crates/gear-engine/src/review.rs (tests) — the packet carries the voyage, the rule and `--blocking`.

Open questions:
- A finding's id is the first word of its line (`F1: …`, `P1: …`), which is what the packet asks the reviewer for; a line without an id is logged. Say so if the ids should be a separate syntax.
- "A failed mechanical fact" is expressed by naming it blocking (the packet's rule: a fail must name what it breaks). A fail that names nothing blocking therefore settles as a pass — the logged findings still reach the captain.
- The round cap counts review rounds as the attempts of the task (round N = attempt N) and is read from the project config each settlement; the captain's action item is idempotent per task (the same body is not written twice).

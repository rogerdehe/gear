# T-91 — GitHub driven from the store (`gear_forge::sync`)

Scope: T-91 (the reopened T-80) — a project in GitHub mode is driven from
`gear_forge::sync(store, project, now)`, which the engine calls once per tick;
a task's first delivery opens its draft claim pull request, a hand-in and a
verdict comment on it, the merge comments the merge commit (`push`) or merges
the pull request (`pr`), and the issue is closed. Every call is an op; a forge
outage queues the calls and never stops local work. Local-only projects do
nothing.

Branch: base/t91 (code @ the hand-in commit; origin/dev merged before
verification, gate green on the merged result)

How it decides (all of it from the store, no new store API):
- **the event**: the attempt timestamps — `delivered_at` (the claim, first
  attempt only), `handed_in_at` (a COMPLETION comment), `verdict_at` (the
  verdict and the findings the store holds), `merged_at` (the merge and the
  close);
- **the pull request**: the confirmed claim op's result (`{repo, number, url}`),
  so every later call names it;
- **the branch**: `<lane>/t<n>`, the same rule as `dispatch::task_branch` (this
  crate cannot call the engine, which calls it);
- **the title**: the first words of the task's contract goal, then `(#issue)`;
- **the body**: `Closes #issue` and the CLAIM marker with the lane's seat.

The ops (T-91's "every forge call is an op"):
- one `OpKind::Forge` op per call, seat `<project>:forge` (the engine acts for
  the project), payload `{forge, key, attempts}`; the key is the dedupe:
  `T-1:claim`, `T-1:1:completion`, `T-1:1:verdict`, `T-1:1:merge`,
  `T-1:1:close`;
- a call is tried at most `MAX_ATTEMPTS` (3) times, once per tick;
- a failed call (the forge said no, or could not be reached) is `Failed` and
  retried on the next tick — that is how an outage "queues them" and catches
  up;
- a call the engine found `Intended`/`Executing` is a crash between the intent
  and the answer: it becomes `Unknown` and is never repeated, so a restart
  cannot post a comment twice; a call that ran past its bound is `Unknown` for
  the same reason.

Decisions worth the captain's eye:
- **The config is read here, not through `gear-app`.** `gear-app` depends on
  this crate for `Issue` (`gear_app::github::issue_block`), so the reverse
  dependency would be a cycle. `sync.rs` parses the part of the project config a
  GitHub mode needs (`[github]`, `[[repos]]`' `[github]`/integration, the lanes'
  repo, `[conventions].integration`) from the store's TOML; a shape it cannot
  read is local-only, never a guess. The two readers must agree on the shape.
- **`merge = "pr"` merges the pull request, but the engine's own merge still
  runs.** `merge.rs` (steady's) is what updates the local integration branch
  and runs the gate; the packet did not ask to change it. In `pr` mode GitHub
  merges the PR (the GitHub-side landing) on the merge event, and the two agree
  on the branch and content; `push` mode keeps today's merge and comments its
  commit. Both close the issue.
- **The COMPLETION marker's fields**: the hand-in comment names the lane (the
  work is complete from its side), the verdict comment names the reviewer's
  seat, both carry the attempt number as `rounds` and `ci=pending` — GEAR does
  not read GitHub's checks, and a made-up CI state would be worse than a
  pending one.

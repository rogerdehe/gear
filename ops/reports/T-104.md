# T-104 — A seat claim is proven by the caller's real pane, and the captain can be handed over

Attempt 1, contract **v2**.

Branch: `course/t104`; the candidate named in the hand-in includes this report.
Base: `origin/dev` merged into the branch before the hand-in.

## The hole

`gear` took a caller's seat from `GEAR_CTX` and cross-checked `HERDR_PANE_ID` —
both ordinary environment variables: any agent could export the captain's
context and pane id in its own shell and act as the captain.

## Identity: the real pane (v2)

`GEAR_CTX` and `HERDR_PANE_ID` now say only **which seat is claimed**. The pane
the caller really runs in is found from OS and Herdr facts:

- the caller's process ancestry — its own pid and its parents, walked with `ps`
  (`identity::process_ancestors`; no environment variable changes a parent pid);
- Herdr's `pane.process_info` (`shell_pid`, `foreground_processes`, `tty`) for
  each pane of the session — the trait gains `pane_process_info` and `panes`
  (`pane.list`), so agent-free panes (the user's own terminal) are seen too;
- `identity::claims_pane(info, ancestors)` matches a pane when its shell or one
  of its foreground processes is one of the caller's ancestors;
- `identity::real_pane(herdr, ancestors)` is that pane.

`identity::observe(env, herdr, ancestors)` refuses (`NotRegistered`) unless the
claimed pane **is** the real pane, naming both (`pane w1:p1 is claimed as a seat,
but this process runs in pane w1:p2 …`). `require_seat` then binds that pane to
the seat's binding as before, so a claim holds only when the real pane is the
seat's bound pane. A refusal raises **one urgent captain item** naming the real
pane (`identity:w1:p2`, deduplicated while open) and the command still fails.

**Role** is the store's binding, never a process: a captain restarted in the
same pane (a new agent session) is still the captain — asserted in the tests.

## Handover (v2)

`gear captain handover --pane <id>` rebinds the captain seat to another pane at a
new generation (`gear_app::captain::handover`):

- allowed from the **captain's own real pane**, or from a shell whose real pane
  hosts **no agent** (the user's own terminal; with no `GEAR_CTX` the project is
  the one whose checkout holds the working directory);
- a lane or reviewer asking is refused `Forbidden`, the binding does not move,
  and the captain gets **one urgent item** (`handover:<pane>`) naming the asking
  pane and the panes involved (deduplicated while open);
- the old bindings are voided, the seat keeps its role and profile, the new
  binding is `Active` on the target pane with the kind the agent there reports
  (the target must already host the captain's CLI), and the generation advances
  so an old session cannot write;
- the command never starts the engine (`starts_engine`).

## Acceptance (tests)

`crates/gear-app/tests/it/app_identity.rs` and
`crates/gear-app/tests/it/captain_handover_contract.rs`, with `FakeHerdr` and a
**fake process table** (every test names the pids its caller runs under; the fake
Herdr says which pids each pane runs, so nothing depends on this machine):

- a lane caller (its own pids) claiming the captain's `GEAR_CTX` and pane id →
  refused, names `w1:p1` and `w1:p2`, one urgent item `identity:w1:p2` naming the
  real pane, a repeat adds nothing;
- the caller in its own pane → accepted as `p:heat`;
- the captain's own caller → accepted as `p:captain`, and again after the agent
  restarted in the same pane (new session, same seat);
- handover from the captain's pane → binding moves to `w1:p3` at generation 2,
  the old binding is `Void`, the new pane is accepted as the captain, the old
  pane is refused;
- handover from a lane → refused `Forbidden`, one urgent `handover:w1:p2` item
  naming both panes, the captain stays at generation 1, a repeat adds nothing;
- handover from the user's own shell (agent-free pane) → allowed; a shell outside
  every project cannot name one (`BadFormat`).

## Notes / out of scope

- A process that detaches from its pane (`setsid`) is refused: it is in no pane's
  process tree. The skill has agents run `gear` in their pane.
- The real-pane search asks every pane of the session (one `pane.process_info`
  each) only when scanning; the normal path reads the claimed pane first.
- `pane.process_info` is Herdr 0.9.0's method; an older daemon fails the read,
  which refuses the identity (fail closed).
- The `push-check` hook keeps its best-effort identity read (its decision is the
  allow-list, not a seat action).

# T-79 — The config and the plan carry the GitHub mode

Attempt 1, contract v1.

Branch: `course/t79`; the candidate named in the hand-in includes this
report. Base: `origin/dev` at c17af11, merged into the branch before the
hand-in.

## What shipped

**Config (`crates/gear-app/src/config.rs`).** An optional `[github]` section
at the project level and inside a `[[repos]]` entry:

```toml
[github]
repo = "owner/name"
merge = "pr"                 # or "push" (the default: local, as today)
merge_method = "squash"      # or "merge"

[github.issues]
labels = ["gear", "triage"]  # empty = every open issue
```

The resolved `Repo` (`root_repo`, `repo_of_lane`, `repos`) carries
`github: Option<Github>`: a repo's own section replaces the project's, and
`None` means local-only. Validation refuses a section that names no repo or
one that is not `owner/name`, and a blank issue label; an unknown `merge` or
`merge_method` fails to parse. A GitHub mode is opt-in at both levels — a
project without the section behaves exactly as before.

**Plan (`crates/gear-app/src/draft.rs`, `plan.rs`; `crates/gear-store`).** A
queue block gains `issue: #<n>` (a `#` and a number; anything else is a
`BadFormat` naming the line). A `## NEW` block creates the task with the
issue; an existing task's block sets it when named and **keeps** it when the
block says nothing ("kept across applies"). The issue lives in a new
`tasks.issue` column — store schema **v4**, with a step from v3 that adds the
column and keeps every row.

`Priority` now also knows the GitHub labels: `priority/now|must|should|could|
wont` ↔ the queue's priorities (`Priority::from_label`, `Priority::label`).

**`gear_app::github::issue_block` (`crates/gear-app/src/github.rs`).** One
`## NEW` block per issue, for `gear plan import-issues` (base's T-81) to
print and the captain to paste and edit:

```markdown
## NEW [should] lane=<lane> milestone=<M>
goal: The board shows the lane twice
accept: When two lanes share a name the board lists it twice.
estimate: 30
deps: -
issue: #42
```

The goal is the title (flattened to one line), the accept the body's first
line (or a line naming the issue when the body is empty), the priority from
the labels (`must` when none names one), and the last line ties the task to
the issue. The lane, milestone and estimate are the captain's to fill in: an
issue says what is wanted, not who does it.

## Acceptance evidence

- `github_contract::a_project_github_section_parses_and_resolves_on_the_root_repo`:
  the section parses, validates, and reaches the root repo and a lane's repo
  (repo, labels, `merge = pr`, `merge_method = merge`).
- `github_contract::a_repo_github_section_replaces_the_projects_and_absent_means_local_only`:
  a repo's own `[github]` wins; without any section both repos are
  `github: None` (local-only); the defaults are `push` + `squash`.
- `github_contract::a_github_section_without_a_repo_or_with_a_bad_repo_is_refused`:
  no repo, a URL, a bare name, two slashes, a space → `github.repo` (and
  `repos[0].github.repo` for a repo's section).
- `github_contract::an_unknown_merge_mode_or_method_is_a_parse_error` and
  `a_blank_issue_label_is_refused`.
- `github_contract::the_priority_labels_name_the_queues_priorities`: the five
  labels, both directions, and non-priority labels ignored.
- `github_contract::an_issue_round_trips_through_apply_and_is_kept_when_a_draft_omits_it`:
  `issue: #12` on a NEW block lands on the task, a later block without it
  keeps 12, and a block with `#34` moves it.
- `github_contract::an_issue_that_is_not_hash_number_is_refused_at_its_line`:
  `12`, `#x`, `#-1`, `#` → `BadFormat` at the field's line.
- `github_contract::issue_block_renders_a_valid_new_block` and
  `issue_block_defaults_the_priority_and_handles_an_empty_body`: the rendered
  block parses as a queue block with the issue's goal, accept, priority and
  `issue: #<n>`; without a priority label it is `must`, and an empty body
  gets a line naming the issue.

## Notes on the shared interface (T-80, base)

T-80 drives the forge from `gear_forge::sync(store, project, now)`. What it
needs from this task:

- `config::ProjectConfig::repos()` → each `Repo.github: Option<Github>` with
  `repo` (`owner/name`), `issues_labels`, `merge` (`MergeMode::Pr|Push`),
  `merge_method` (`MergeMethod::Squash|Merge`);
- `gear_store::TaskRow.issue: Option<i64>` — the issue a task came from, so a
  merge can close it;
- `gear_app::github::issue_block(issue)` for the import path.

## Out of scope

- The `gh` calls, the claim/completion comments, the PR merge and closing the
  issue: base's `crates/gear-forge` and T-80/T-81.
- A `[github]` section's repo is written by the captain; it is not derived
  from the repo's git remote (a remote can be several URLs, and the config is
  the one place that says where a project lives).
- The draft's rewrite keeps an `issue:` line the captain wrote; it does not
  add one for a task whose issue came from an earlier apply (the store keeps
  it, and a block without the line does not clear it).

# T-150 — Delivery confirmation (design §10.3) and the taskless doorbell (§10.4) — attempt 2

Attempt 2 is the rework the review of attempt 1 asked for: **F1 and F2**.

- **F1** — a contract update for an attempt that already started was still
  sent as a Deliver op (the dispatch's `Adopt` action ran before the new
  "no second packet" guard). The contract change now goes as an **at-once
  instruction message** through the doorbell path; a started attempt never
  gets a delivery again.
- **F2** — a check-in that arrived after an unconfirmed delivery had been
  retried left the captain's stall item open: the retry confirmed the attempt
  first, so the failed op's late-check path had nothing to start and skipped
  the cleanup. The stall item now closes whenever the attempt is `Started` —
  in the confirmation path and in the late-check path.

Three rules of the design and one line of text, in the engine:

- **The confirmation window is wall clock.** A delivery used to be "unconfirmed"
  after three checks of four seconds — twelve seconds in which a lane that was
  busy, or that read its packet a minute later, could not be shown to have got
  it. The window is now `timing.delivery_grace_s` (default 180 s) of wall clock:
  a check-in view that shows the task and the attempt confirms the delivery
  whenever it arrives inside the window.
- **A late check-in counts.** A view that shows the attempt *after* its delivery
  op failed confirms the attempt anyway (`Delivered → Started`) and closes the
  stall item: the lane is not stuck any more.
- **One packet per round.** An attempt that already started got its packet and
  the lane checked in — the engine never delivers it a second one.
- **A lane with no open attempt is told so.** Its doorbell says it has no task
  and tells it to stop working on earlier things.

## What changed

**The window (`crates/gear-engine/src/ops.rs`, `crates/gear-engine/src/lib.rs`).**
`confirm_pending_with(store, project, budget, grace_s, now)` replaces the
check budget for a **lane** delivery: with no evidence yet, the op waits while
`now - op.created < grace_s` and fails with the reason when the window is over
(the seat is flagged once, as before, and the attempt is delivered again in a
new agent session). A **review** delivery is still settled by the reviewer's
verdict and spends no window at all, and a doorbell keeps its own check
budget. `confirm_pending(store, project, budget, now)` stays as the wrapper
with the default window (`DEFAULT_DELIVERY_GRACE_S`, 180 s), so no caller
outside the engine's tick changes.

The window's value is `EngineCfg::delivery_grace_s` (default 180), the same
shape as `doorbell_check_budget`: the project's `timing.delivery_grace_s` is
parsed by the config (hull's T-147) and feeds it when that lands. **This is
the one decision the captain should look at** (sent as a progress note).

**The late check-in (`crates/gear-engine/src/ops.rs`,
`crates/gear-engine/src/stall.rs`).** `ops::confirm_late_views` walks the
failed Deliver ops of the project: one whose seat shows the task and the
attempt in a view at or after the op was created confirms the attempt
(`Delivered → Started`, the task `Ready → Running`) and closes the seat's
stall item (`stall::resolve`). The tick calls it right after the confirm step,
and the tick report names the late confirmations (`TickReport::late_confirmed`).

**One packet per round (`crates/gear-engine/src/dispatch.rs`).** An attempt in
state `Started` gets no delivery any more: the dispatch returns `None` for it.
A `Delivered` or `Stopped` attempt is still nudged as before. In M4 the "no
progress" nudge is the overrun question of design §5.2 (an at-once message,
T-151's task), not a second packet.

**A contract update for a started attempt is a message (F1).** The dispatch's
`Adopt` action (the contract changed, the lane has not adopted it) used to
become a Deliver op — also for an attempt that had already started, which the
design forbids. It now depends on the attempt:

- `Started` → **no delivery at all**. The contract change is written as an
  instruction message (`contract:<task>:<version>`, urgent, so the doorbell
  rings it even while the lane works) with the same text as before ("T-n
  contract changed to v2: run `gear` and `gear --show T-n`"). The lane adopts
  the new contract at its next view (T-8) — the pending update and the view
  adoption are unchanged. One notice per task and version: the notice stays
  open until the lane answers it, so the engine does not write one every tick.
- `Delivered` or `Stopped` → the delivery, as before.

**The stall item closes with the recovery (F2).** `stall::resolve` takes the
time the item must predate: an item that is newer belongs to a later failure
and is not closed by an old delivery op. The confirmation path
(`confirm_pending_with`) closes the item of the seat whose delivery confirmed
the attempt, and the late-check path (`confirm_late_views`) closes it whenever
the attempt is `Started` — also when a retry confirmed it first, which is the
case the review reproduced.

**The taskless doorbell (`crates/gear-engine/src/doorbell.rs`,
`crates/gear-engine/src/lib.rs`, `crates/gear-engine/src/ops.rs`).**
`doorbell::text(items, no_task)` takes the new flag: with a task the text is
unchanged, without one it is the design's line, word for word:

```text
GEAR: <n> item(s) for you: <ids>. Run gear, answer them, then end your turn. You have no task now: do not continue earlier work.
```

`no_task` is true for a **lane** with no open attempt (`open_attempts_of_seat`
empty). The captain and the reviewers keep the usual text: they have no attempt
of their own by design. Both callers know it: the tick's doorbell inputs and
the sender's own doorbell (`gear send`).

## Verification

- `scripts/test.sh` on the merged result (`origin/dev` bb9d0ff, T-138 in) →
  **1010 tests run: 1010 passed, 0 skipped** (99 s; inside the 300 s red
  line). `cargo build --workspace --all-targets` → clean.
- The acceptance, in `delivery_grace_contract.rs`:
  - `a_view_after_a_minute_confirms_the_delivery` — three checks later the
    delivery is still on its way (the window is 180 s, not three checks); a
    view 100 s after it was sent confirms it and starts the attempt.
  - `a_late_check_in_confirms_the_attempt_and_closes_the_stall` — the window
    is over, the op fails and the seat is flagged; a view that arrives after
    that starts the attempt and resolves the captain's stall item.
  - `a_started_attempt_never_gets_a_second_deliver` — the dispatch gives a
    started attempt nothing, while the same lane with an attempt that waits
    for its check-in is still nudged.
  - `the_taskless_doorbell_text_says_so` — the exact text of the design, and
    the unchanged text for a lane that has a task.
- The review's two regressions (`delivery_grace_contract.rs`, both failed
  against attempt 1):
  - `a_contract_update_for_a_started_attempt_is_no_delivery` — a Running task,
    a Started attempt with `adopted_version = 1` and `pending_update = 2`, an
    idle lane, no pending op and an expired cooldown: `decide` returns
    `Adopt`, and the whole `decide → intend_dispatch` path writes **no
    Deliver op** — the contract change reaches the lane as an instruction
    message in the thread `contract:T-7:2`.
  - `a_late_check_in_closes_the_stall_after_a_retry` — the delivery times out
    and opens the stall, the agent is restarted in the same generation so the
    attempt goes again, and the lane checks in: the retry confirms the attempt
    and the captain's stall item is `Resolved` (the failed op's late check
    finds the attempt already `Started` and closes it too).
- The old rules, updated where they said what changed: a started attempt is
  not nudged any more (dispatch_contract, captain_quota_contract), the
  doorbell of a lane without a task says so (doorbell_while_working,
  gear-cli), and the delivery fails after its **window** instead of after its
  budget (undelivered_delivery_contract, with `delivery_grace_s: 8` so the
  test stays quick).

## Open questions

none — the review's two findings are fixed as it asked (F1: the contract
update of a started attempt is a message, never a delivery; F2: the stall item
closes with the recovery, in the confirmation path and in the late-check
path), and three decisions worth naming:

- **The window's value.** The engine's knob is `EngineCfg::delivery_grace_s`
  (default 180 s), the same shape as `doorbell_check_budget`. The design names
  the project's `timing.delivery_grace_s`; the config parses it in hull's
  T-147, which had not landed when this task was done — the project's value
  feeds the knob with one line when it does.
- **The window starts at the op's creation** (the intent of the delivery), not
  at the moment the text reached the pane: the two are the same tick, and the
  op's creation is the one time the store keeps.
- **The contract update still reaches a working lane.** "No Deliver op for a
  started attempt" is about the packet: the one-line contract bump (T-8) is
  not a second packet, so it goes as an instruction message the doorbell
  rings (F1).

## Out of scope

- **A hand-in for an attempt that is still `Delivered`** (design §10.3's third
  bullet: `Delivered → Started → Submitted` in one transaction) is hull's
  T-147 (gear-app `tasks.rs`).
- **The overrun question** (design §5.2: the at-once message that replaces the
  nudge of a lane that makes no progress) is T-151 (`overrun.rs`).
- **The seat's session bookkeeping** (`attempts.session_ref`, `sent_at`) is
  hull's T-147/T-151; this task only moves the attempt from `Delivered` to
  `Started` when a check-in proves the packet was read.

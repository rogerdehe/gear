# T-256 — two projects in one repo cannot share branch names

Scope: T-256 (contract v1, revised by the captain's answer M-4255) — task and
review branch templates default to `{lane}/t{n}` and `review/t{n}`, so two
GEAR projects registered on the same repository would both cut `hull/t12` and
`review/t12`. A project that shares a repository with another one must name
`{project}` in `conventions.task_branch`, `review_branch` and `seat_branch`.

Branch: mast/t256 · candidate 626380ff (origin/dev 68feb446 merged in).

## What changed

- `crates/gear-app/src/admin.rs`
  - New `pub fn branch_clash(config: &ProjectConfig, others: &[(String, String)])
    -> Option<String>` — the one comparison, as the captain's answer asked.
    `others` are the store's projects as `(id, config_toml)`; one that does not
    parse is skipped. Every repo path of both configs is canonicalized with
    `std::fs::canonicalize` (the text when it does not exist), and the first
    project of `others` (other than this config's own id) that works in one of
    this config's repositories whose own `task_branch`, `review_branch` or
    `seat_branch` has no `{project}` yields
    `project {other} also works in {path}: put {project} in
    conventions.task_branch, review_branch and seat_branch so the two
    projects' branches cannot collide`.
  - `check_other_projects(tx, config)` reads `tx.project_ids()` +
    `tx.get_project(...).config_toml` and refuses with `ErrorCode::BadFormat`
    and that text; `register` and `re_register` call it as their first
    statement, before any write.
  - `fn check` stays store-free (T-228): its signature and behaviour are
    unchanged; the doc names `branch_clash` as the cross-project part.
- `crates/gear-cli/src/main.rs`
  - `gear admin init --check` calls `gear_app::admin::branch_clash` after
    `check`. The other projects come from `other_projects()`: no `GEAR_DB`, or
    no file at `GEAR_DB`, → `None` and the command prints
    `cross-project check skipped: no store` (stderr, so `--json` stdout stays
    one object); otherwise the existing store is read. A clash is reported
    through the ordinary error path, so it prints as
    `ERROR BAD_FORMAT: <the same text init gives>`.
  - New `Store::open_read_only` is used for that read instead of `Store::open`:
    `Store::open` creates the directory and applies/migrates the schema, and
    T-228 (and the M4.2 goal) say a check writes nothing. `open_read_only`
    opens with `SQLITE_OPEN_READ_ONLY` and a busy timeout only — no file
    created, no schema applied, no migration, so `Path::exists` guards the
    file and nothing is written even for a store of another schema version.

## Tests

- `crates/gear-app/tests/it/admin_init_contract.rs` —
  `a_second_project_on_one_repo_needs_project_in_its_branch_templates`:
  project alpha on repo R; beta on R with the default templates is refused with
  exactly the contract's text, naming alpha and R (canonicalized), and nothing
  is written; beta on R with `{project}` in all three templates registers; a
  third project on another repository keeps the defaults; and gamma, already
  registered elsewhere, re-registering onto R with the defaults is refused
  (the `re_register` path) leaving its config version and text untouched.
- `crates/gear-cli/tests/it/admin_init_contract.rs` —
  `check_refuses_a_second_project_on_the_same_repo`: with no store the check
  passes and says `cross-project check skipped: no store`, creating no file;
  after `p` is registered on R, `--check` of `q` on R exits 1 with
  `ERROR BAD_FORMAT: project p also works in <R>: …`, the store file is the
  same size afterwards (a check writes nothing), and `q` on another repository
  passes with `config ok: project q, 0 lanes, 0 reviewers`.

## Out of scope

- The seat branch default already carries `{project}`, so a clash on that
  template alone cannot happen by default; the check still refuses a project
  that removes it, as the contract says.
- The review branch of a task and the "F1: branch names are compared as text,
  so two spellings of one path (a symlinked parent) collide only when
  canonicalization succeeds" — canonicalization covers it when the path
  exists; a path that does not exist compares as text, which is the contract's
  fallback and not a finding.

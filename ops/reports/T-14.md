# T-14 — the dependency view on the board

Scope: T-14 — `gear board --deps` draws the open tasks as a dependency tree, and the key `d` toggles between the tree and the queues of the lanes in the live board.

Branch: board/t14, based on board/t3 (the board crate is there) with origin/dev merged in; the hand-in commit carries the code and this brief — the candidate sha in the result names it (a brief inside a commit cannot name its own sha).

Files:
- `crates/gear-board/src/deps.rs` — the tree: every open task with its state, a task drawn under the first dependency that is still open, a task whose dependencies are done is a root, and the dependencies that are not done are what the task waits for. Every open task is drawn exactly once, even with a cycle in the plan.
- `crates/gear-board/src/lib.rs` — the two views (`View::Lanes`, `View::Deps`), the `d` toggle in the frame loop (drawn at once, not at the next tick), and the tree in the JSON.
- `crates/gear-board/tests/deps_contract.rs` — the contract: a small DAG (the diamond T-1 → T-2, T-3 → T-4 plus the independent T-5) checks the rendered lines; a finished task leaves the tree and its children come up; the two views show one thing at a time; `d` toggles; the JSON carries the tree.
- `crates/gear-cli/src/main.rs` — the `--deps` flag on `board` only.
- `bin/gear` — the P3 of the T-4 review: the wrapper follows a symlink, so a link at `~/.local/bin/gear` runs the plugin's binary instead of looking for `~/.local/target/release/gear`.

What the tree looks like (the contract fixture):

```
Dependencies
  T-1 queued
    T-2 queued · waits T-1
      T-4 queued · waits T-2 T-3
    T-3 queued · waits T-1
  T-5 queued
```

Verification:
- `cargo test --workspace` → 300 tests, all ok; `cargo build --workspace --all-targets` → no warnings.
- `GEAR_DB=~/.local/state/gear/gear.db gear board --deps` → the live plan as a tree (the gear project has one dependency: T-5 on T-1; T-1 is done, so T-5 is a root with nothing to wait for — the plan's only edge is met).
- In a pty: the first frame is the lane view, `d` redraws at once with the tree, `q` leaves; 0 bare LF (the T-3 P1 stays fixed).
- A symlink to `bin/gear` in a temporary directory runs the release binary (the P3).

Open questions:
- **The tree replaces the lane list rather than adding to it.** The board has one middle section; `d` switches it (queues ⇄ tree). Showing both would double the frame length on a real plan. If the captain wants both at once, it is one more `match` arm.
- **The `waits` marker lists every dependency that is not done, including the parent the task is drawn under.** The tree position already says the parent; the marker repeats it so that a queued line is never mistaken for "ready to start" — it reads `T-2 queued · waits T-1` under `T-1 queued`.
- **A dependency that is done is not drawn.** A task whose dependencies are all done is a root, and it has no `waits` marker: that is how a task becomes startable.

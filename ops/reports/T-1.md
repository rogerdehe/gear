## What was verified live

OpenCode has no `--model` flag. The model comes from its config, and the only config source a *client* can carry is the environment variable `OPENCODE_CONFIG_CONTENT` (a JSON object). Three starts in a scratch pane, wanted model `deepseek/deepseek-v4-pro`:

| Start | Model carried by | Result |
|---|---|---|
| `opencode --auto` (shared background service) | the environment line | **ignored** — status bar stayed `Build auto · MiniMax-M3.1-Flash MiniMax (minimax.cn)` |
| `opencode --standalone --auto` (private server) | the environment line | **applied** — status bar `Build auto · DeepSeek V4 Pro DeepSeek · high`; the session record shows `providerID: deepseek`, `model: deepseek-v4-pro` |
| `opencode --auto` (shared background service) | `opencode.json` in the working directory | **applied** — status bar `Build auto · DeepSeek V4 Pro DeepSeek · high` |

Why the first row fails: the config is loaded by the *server* process (`role=server` in `~/.local/share/opencode/log/opencode.log`), not by the TUI client. The shared background service was started long before the export, so its own environment does not carry the variable — a client cannot add it. A private server (`--standalone`) inherits the environment of the pane it is started in, which is where GEAR exports the model. A project `opencode.json` is re-read by the server when the file changes, so it works with the shared service too.

Resume was checked as well: `opencode --standalone --auto -s <id>` came back with the same context counter (12.1K) and the same model, so the model survives a resume and the session id is still found by `opencode session list` (the private server writes to the same database).

## What the engine does now

`onboard_seat` reads the lane's primary model — the first entry of the lane's own `models`, else the first entry of `[models].lanes` — and, when the lane's kind has a verified way to take a model, appends to the environment line:

```
export GEAR_CTX=<project>:<seat>:<generation>; export GEAR_DB=<db>; export OPENCODE_CONFIG_CONTENT='{"model":"<provider/model>"}'
```

and `--standalone` to the start args, so the agent reads the model from the environment it was started in. Without a model chain nothing changes: the environment line stays exactly as before and the start args stay `["--auto"]` (the existing onboarding contract test still holds).

A CLI without a verified mechanism gets nothing — its model is not managed by GEAR.

## For the captain: the one open decision

`--standalone` gives every model-managed agent a private OpenCode server (~260 MB RSS each, measured). The alternative is to let the model come from a project `opencode.json` written into the lane's worktree: it works against the shared service (verified above) and the server re-reads it when it changes, which also makes a quota fallback a file rewrite — but it puts an untracked file into the user's checkout, where a lane could commit it by accident.

Both are one line in `model_start` (in `crates/gear-engine/src/onboard.rs`); this hand-in takes the first, because it keeps the model in one place (the environment line) and writes nothing into the user's repository.

# T-41 — the store has a schema version

Scope: T-41 — the store stamps its schema version in `meta.schema_version` when it is created; a binary that opens a store of an older version migrates it up (one step per transaction, the version moving with the step); a store of a newer version is refused for writing with the new `SCHEMA_TOO_NEW` error, before anything is written (the schema only migrates up, never down). The lane's tests never touch the production store: every `gear` a test starts gets a scratch `HOME` and no `GEAR_DB`, and the engine's gate runs without `GEAR_DB`.

Branch: base/t41 (rebased on `origin/dev` 37501c0; the code and this report are in the hand-in commit)

Files:
- `crates/gear-store/src/migrate.rs` (new) — the version scheme and the steps. `SCHEMA_VERSION = 2`; `STEPS` is the list of steps, each a function that runs inside the caller's transaction. The one step (v1 → v2) brings a store to the canonical shape: the v2 tables a v1 store may not have yet are created, the shapes that `CREATE TABLE IF NOT EXISTS` cannot fix are repaired (`voyages` of T-22 attempt 1 is rebuilt with its rows, `seats.slot` becomes `seats.worktree`, `resources` gets `branch` and `workspace_id`), and the dead `slots` table of the skeleton is dropped. A column the old table never had stays empty; the rows are carried over.
- `crates/gear-store/src/lib.rs` — `Store::open` reads the version **before** the pragmas: a store of a newer version is refused with `SCHEMA_TOO_NEW` before a single byte of it is changed (the old code applied the schema first — that is how a lane's build wrote its own table version into the production store). A new store is created (schema + stamp in one transaction), a store of an older version is migrated up (one transaction per step), a store of the current version is left alone. `Version` says what the store claims; `set_version` writes the stamp.
- `crates/gear-model/src/error.rs` — the new `SchemaTooNew` code (`SCHEMA_TOO_NEW`).
- `crates/gear-store/tests/it/migration_contract.rs` (new) + `tests/it/v1_schema.sql` (new) — the contract: a fresh store has the current version; a store of v1 (the schema of the first release, with the `voyages` of T-22 attempt 1 and rows in it) is migrated up, keeps its rows and ends with the shape of a fresh store; a store of a newer version is refused for writing and nothing is written (the version and the rows are still there); a store without a version is migrated up; a store of the current version is opened as it is.
- `crates/gear-store/tests/it/contract.rs` — two assertions of the old contract changed, because this task is the new contract: the version of a fresh store is now the current one (was the literal `1`), and a newer store is refused with `SchemaTooNew` (was `BadFormat`).
- `crates/gear-cli/tests/it/scratch.rs` (new) + `skill_contract.rs`, `install_skill_contract.rs`, `readonly_no_engine.rs` — every `gear` a test starts gets no `GEAR_DB` **and** a scratch `HOME`, so the store it would fall back to (`$HOME/.local/state/gear/gear.db`) is a scratch one. New test: the store of a test lives under its scratch home.
- `crates/gear-engine/src/merge.rs` — the gate (the project's build and test command) runs without `GEAR_DB` and `GEAR_CTX`, like the lanes run it (`env -u GEAR_DB cargo test`). New test: the gate's command removes them.

```
$ sqlite3 real-copy.db "update meta set value='3' where key='schema_version'; …"
$ GEAR_DB=…/real-copy.db HERDR_SOCKET_PATH= cargo run -q -p gear-cli --
ERROR SCHEMA_TOO_NEW: the store at …/real-copy.db has schema version 3, but this binary writes
version 2; the schema only migrates up — upgrade GEAR and try again
$ sqlite3 "file:…/real-copy.db?mode=ro" "select value from meta where key='schema_version'"
3                                    # nothing was written: the version and the rows are as they were
```

Open questions:
- **v1 is the shape of v0.1.0, but the stamp never told the shape.** A store stamped 1 may have been written by a development build that created a table in an older shape; that is why the step repairs the shape instead of trusting the stamp. A store stamped 2 is the canonical shape. If the captain prefers v1 to mean "the shape of the first release, exactly", the step would have to be split into one step per release — more code, the same guarantee.
- **The refusal is on opening, not on writing.** The design says "refuse to run on version mismatch" (02), so a binary that meets a newer store stops there instead of reading it. If the captain wants an older binary to read a newer store (and refuse only the writes), that is a different contract and a different error path.
- **`slots` is dropped.** The table of the skeleton has not been read since the first release; its rows are lost with it. Nothing in the code refers to it.

Out of scope:
- The `milestones` table (the old, unused shape of `voyages`) is still there; v2 does not touch it.
- The engine's `engine.log` and the `~/.config/gear/targets.tsv` registry are untouched by this task.
- The other lanes' test suites (gear-app, gear-engine, gear-store) run in-process against in-memory or temporary stores; they never reach a store path. Only the CLI tests start a process, and those are the ones that got the scratch home.
- `docs/lessons.md` is not touched: L-59 names this task as its root ("the store stamps its schema version and a binary with another version refuses to write (or migrates up); lanes run tests with GEAR_DB unset") — the captain closes the lesson, the lane does not edit the shared log.

# T-6 — Change the project config mid-run

Scope: T-6 — `gear admin init <config>` on a registered project applies the config as the next config version: a lane that the config adds becomes a queued seat, a lane that it drops is refused by name, and the store hands the latest config (its models included) to whoever reads it.
Branch: data/t6 (code @ 484c9ef, branch head 8cd5e63)
Files:
- crates/gear-app/src/admin.rs — `init` registers a new project or applies a changed one: the next config version and the quotas, a new lane as a queued seat, the profiles that follow the config; a dropped lane, a changed Herdr session and a changed captain pane/kind are refused, each naming what cannot change.
- crates/gear-app/src/config.rs — `config::latest(store, project)`: the one reader of a project's config, so the engine and every command read the same (latest) version.
- crates/gear-store/src/lib.rs — `update_project` (the next config version and the quotas) and `set_seat_profile`.
- crates/gear-engine/src/onboard.rs — the engine reads the config through `config::latest`, so it reads the latest version every tick.
- crates/gear-cli/src/main.rs — the output is `project <id> (config v<n>)`: a re-init is a config change, not a registration.
- crates/gear-app/tests/config_change_contract.rs — 7 tests: the models chain, a new lane, a dropped lane, an invalid config, the session and the captain, the lane profile, a lane that would take another role's seat id.
- crates/gear-app/tests/admin_init_contract.rs — the "a second init is already registered" line of the T-57 contract is now "a re-init is the next config version": T-6 replaces that behaviour.
- crates/gear-engine/tests/onboard_run_contract.rs — a lane that a config change added is onboarded by the engine, with the repo of the latest config.
- crates/gear-store/tests/contract.rs — the project row takes the next config version; a seat profile is written and read back.

Verification:
- `cargo build --workspace --all-targets` → clean, zero warnings and zero errors.
- `cargo test --workspace` → green (48 test binaries; 10 new tests).
- Live smoke test of the binary against a scratch store: `gear admin init` → `project toy (config v1)`; the same command with a changed config → `project toy (config v2)` and the new lane `toy:pricing` queued; with a config that drops a lane → `ERROR BAD_FORMAT: the lane heat (seat toy:heat) is not in the new config: retiring a lane is a later task`; the stored config holds the new `[models]`.
- `git merge origin/dev` into the task branch twice (T-2 landed in between); the build is warning-free and the whole suite is green on the merged result.

Open questions:
- A re-init with the *same* config stores it as the next version: the "already registered" error is gone, as the packet asks. Say so if an unchanged config should stay a no-op (the old contract line in `admin_init_contract.rs` would come back).
- Design/01 ("repeated init") wants a replaced captain to go to NEEDS_CHECK through design/03's re-registration. That path does not exist yet, so a config edit that changes the captain's pane or kind is refused by name instead of half-applied. Same for the Herdr session of a project: the agents and their bindings live in it.
- A lane's `kind` needs no write — the engine reads it from the config when it onboards the lane. A lane's `profile` is stored on the seat, so the config wins for it; the seat keeps its id, generation, state and bindings.
- A lane that the config drops is refused (BadFormat, the seat is named). Retiring a lane is a later task, as the packet says.

Out of scope:
- The plan, the tasks and the attempts are untouched: a config change is not a plan change (`gear plan apply` is the captain's).
- `docs/design/01-config.md` still describes the old behaviour (the NEEDS_CHECK path for a replaced captain); the design docs are the captain's.

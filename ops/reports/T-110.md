# T-110 — an upgrade guide in the v0.3.0 release notes

Scope: T-110 — `docs/releases/v0.3.0.md` gets an upgrade guide in three cases
(user, 2026-10-26): new users, users of 0.2.x with no voyage running, and an
upgrade during a running voyage; the README links to it.

Branch: base/t110 (code @ the hand-in commit; origin/dev merged before
verification, gate green on the merged result)

What changed:
- `docs/releases/v0.3.0.md` — a new `## Upgrading` section at the end, one
  short line per step and copyable commands:
  - **New to GEAR** — the README's install section, then start a project.
  - **From 0.2.x, with no voyage running** — `gear admin stop`; replace the
    binary (`herdr plugin install rogerdehe/gear --ref v0.3.0`, whose build step
    fetches the release binary or builds it; from a checkout instead
    `git pull && cargo build --release && herdr plugin link <checkout>`); install
    the skill for every CLI in use (it changed in 0.3.0); restart the agents so
    each loads it; the store migrates up on the first `gear` call, and a store
    from a newer GEAR is refused with `SCHEMA_TOO_NEW`.
  - **During a running voyage** — wait until nothing is merging (no task in
    review); stop, replace, install skills; start the engine again with any
    `gear` call; lanes and reviewers keep their tasks, and each agent picks up
    the new skill when it is restarted — between tasks, never mid-task.
  - **What changes on upgrade** — the push allow-list and its pre-push hooks are
    gone (a hook left in a worktree is removed when that seat comes online); a
    seat sees only the messages addressed to it; an agent's claim is checked
    against its real pane, not an environment variable.
- `README.md` — one line after the install list: "Upgrading from 0.2.x?" with
  the link to `docs/releases/v0.3.0.md#upgrading` and the three cases named.
- `ops/reports/T-110.md` — this brief.

Every command and claim was checked against the code on dev:
- `gear admin stop` — `cmd_admin_stop`, "signal the engine named in its lock
  file"; it refuses when an agent runs it.
- `gear admin install-skill --agent …` — parses exactly
  `claude | codex | opencode | grok` (`SkillAgent::parse`).
- The plugin's build step — `herdr-plugin.toml`'s `[[build]]` runs
  `scripts/fetch-or-build.sh`: the release binary (SHA-256 checked) or a build
  from source. A *linked* plugin is not built by Herdr, so the checkout variant
  runs `cargo build --release` first (the manifest says so).
- The store — `Store::open` migrates an older schema up on open (the first
  `gear` call), and refuses a newer one with `ErrorCode::SchemaTooNew` before
  writing a byte.
- The engine — every command except `run`, `admin stop`, `admin kickoff`,
  `admin install-skill`, `board`, `report`, `plan import-issues` starts it
  (`starts_engine`), so any ordinary `gear` call restarts it.
- "in review" is the board's own word for a task in `Verifying` (the merge runs
  right after a pass, so no task in review means no merge in flight).
- `GEAR_DB` needs no mention: when it is unset the CLI defaults it to
  `~/.local/state/gear/gear.db` (`default_store_path`).

Verification:
- `env -u GEAR_DB -u GEAR_CTX cargo build --workspace --all-targets` — exit 0.
- `env -u GEAR_DB -u GEAR_CTX cargo test --workspace` — 844 passed, 0 failed.
- The three sections are present; the README link resolves to the `## Upgrading`
  heading's anchor (`#upgrading`).

Open questions: none.

Out of scope: the `SCHEMA_TOO_NEW` advice is one line (upgrade the binary); a
store downgrade is not supported and the guide does not pretend otherwise.

# T-90 — A review fail is settled where it can be

Attempt 1, contract v1.

Branch: `course/t90`; the candidate named in the hand-in includes this
report. Base: `origin/dev` at 3ad02a0, merged into the branch before the
hand-in.

## What shipped

The captain's home page names the `# Verdicts` line for an inbox item that
only a verdict settles, with the real values filled in —

```
next: gear plan apply gear/voyages/M3.md (# Verdicts: T-1 attempt=1 contract=1 candidate=abc1234def5678 fail rework="…")
```

— instead of `gear reply M-1 --resolve`. `gear reply --resolve` on such an
item is refused with that same line, so the item cannot be closed while
nothing is settled (M3: the captain resolved two fails by reply and the tasks
stayed verifying).

Which items need a verdict (`tasks::verdict_hint`):

- a **review fail** — the attempt is still handed in and the task still
  verifies (a fail *with* blocking findings is settled by the engine; a fail
  without them, or one over the rework cap, is the captain's decision);
- a **failed merge** — the attempt passed but its work is not in the
  integration branch. The captain's fail reopens the task for a rework on a
  new attempt: the accepted attempt keeps its state, only the task goes back
  (`settle`; `Done → Ready` is the model's "explicit reopen with reason").

An information line (a pass, a result) is bookkeeping and a reply still
closes it. The engine's merge item now names the task and attempt it is about
(`merge.rs`), so the page can fill the line in; before it carried neither.

## Acceptance evidence

- `verdict_item_contract::the_home_page_names_the_verdicts_line_not_a_reply`:
  a project on M3 with T-1's attempt handed in and a review fail in the
  captain's inbox → the page shows
  `next: gear plan apply gear/voyages/M3.md (# Verdicts: T-1 attempt=1 contract=1 candidate=abc1234def5678 fail rework="…")`
  and no `gear reply M-1 --resolve`.
- `verdict_item_contract::resolving_the_fail_by_reply_is_refused_and_leaves_it_verifying`:
  the reply is refused (`BadFormat`) with that line in the detail; the task
  is still Verifying, the item still Open and no verdict was written.
- `verdict_item_contract::after_the_plan_settles_it_resolving_works`: the
  captain writes the line → the attempt is rejected, the task is Ready with
  the rework note → the item is an ordinary one and a reply resolves it.
- `verdict_item_contract::a_failed_merge_is_settled_by_a_verdict_too`: a
  passed task whose merge failed → the page names the same line; the plan's
  fail reopens the task (Ready) and the accepted attempt keeps its state.
- `tasks_contract::pass_and_fail_settle` (contract extended with T-90): a
  fail then a pass on one attempt is still a conflict; a pass then a fail
  reopens a Done task (the failed merge) instead of being a conflict.

## Out of scope

  when they have acted.
- The hint names the fail form — the one that fits a fail and a failed

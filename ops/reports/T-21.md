# T-21 — a review's findings live in the store

Scope: T-21 — `gear send --kind review ... "<findings>"` stores the **text** of the findings: an argument that names a file in the reviewer's working directory is read (bounded at 64 KiB, with a note when cut), anything else is the text itself, and a path that names no file is `BAD_FORMAT` before anything is written. `settle_review` puts that text into the rework note (no more `git show origin/review/t<n>:<path>` pointer) and `gear --show T-n` shows the latest review's findings, so rework never depends on a reviewer's worktree or branch.

Files:
- `crates/gear-app/src/review.rs` — `findings_text` (a path is read, text is kept, a missing file is `BAD_FORMAT`), the path classification, the 64 KiB bound with its cut note, and six unit tests.
- `crates/gear-app/src/mail.rs` — a review's findings are resolved inside the request closure, so a missing file rolls back and stores nothing.
- `crates/gear-app/src/tasks.rs` — `settle_review` uses the findings text directly (the `findings_pointer` git-show helper is gone).
- `crates/gear-app/tests/review_contract.rs` — a path is stored as its text, the rework note and the packet carry it (and no review-branch pointer), a missing path stores nothing (`BAD_FORMAT`), the regressions of the review (F1, F2, F3).
- `crates/gear-app/tests/settle_review_contract.rs`, `crates/gear-cli/src/main.rs` — the findings fixtures are text now (a path would be a file read).
- `ops/reports/T-21.md` — this brief.

## Rework after the review of attempt 1 (round 1, fail)

The review (F1 P0, F2 P1, F3 P2) is in `ops/reviews/T-21.md` on the review branch; its findings are repeated here with what changed.

**F1 (P0) — a missing path was stored as findings.** The old rule only knew `.md`/`.txt`/`.markdown` and no spaces, so `"ops/reviews/T-1 draft.md"` and `"./ops/reviews/T-1"` were stored as findings text, and the rework note and the packet showed a path that does not exist. The path classification now asks whether the argument is *written like a path*:

- an explicit path — `./x`, `../x`, `/x`, `~/x` — whatever the extension;
- a text extension (`.md`, `.txt`, `.markdown`, `.rst`, `.log`);
- a directory part and a file-like last part (`ops/reviews/T-1`, `crates/app/src/lib.rs`);
- a last part with a space in it (`ops/reviews/T-1 draft.md`): the first word is already a path, or it names a file itself.

Prose stays prose: `n/a`, `and/or is broken`, `see ops/REVIEW.md`, `P1 — the header drifts`. The rule leans to the loud mistake: an argument that looks like a path but names no file is refused (`BAD_FORMAT`, nothing stored), because storing a path is silent, while refusing prose is recoverable — the reviewer hands the text in. A findings sentence that *starts* with a path (`crates/app/src/lib.rs:12 is wrong`) is refused too; that is the price of the safe direction, and the error says what to do.

**F2 (P1) — the retry of a lost receipt read the file again.** The findings were resolved before the request's replay check, so a repeated request id re-read the reviewer's file: with the file gone the retry failed with `BAD_FORMAT` instead of replaying the stored success. The review (and its findings) is now built inside the request closure, after the replay check; the request key still holds the original argument, so the same id with the same argument replays.

**F3 (P2) — the whole file was read before the bound.** `std::fs::read` read the entire file inside the store's write transaction; only the stored string was bounded. The file is now read with a bounded reader (at most 64 KiB + one byte, so a cut is still detected), and the size of the whole file comes from its metadata for the cut note.

## Real proof (round 2)

A scratch store (`/tmp/gear-t21-r2/store/gear.db`), the built binary, a temp reviewer bound to a **fake Herdr socket** (a Python script in the scratch dir — no real pane is touched, and the scratch store is not registered for any Herdr session, so no engine runs on it). The counts are `review_verdicts / messages / requests`:

```
$ gear send --kind review --task T-1 --attempt 1 --verdict fail --request-id proof-missing-spaces "ops/reviews/T-1 draft.md"

exit=1
counts: 0/0/0

$ gear send --kind review --task T-1 --attempt 1 --verdict fail --request-id proof-missing-no-ext "./ops/reviews/T-1"

counts: 0/0/0
```

Verification:
- `cargo build --workspace --all-targets` → clean, no warnings; `cargo test --workspace` → 399 tests, 0 failed (the six unit tests of the classification, the review contract's 14 tests — the path/text cases, the missing-path regressions of F1 with zero verdict/message/request rows, the replay of F2, the bounded read of F3 — and the settle test asserting the note and the packet carry the text).
- The proof above: the verdict row holds the file's text (not its path), the packet and the rework note carry it, a missing path stores nothing, a repeated request id replays without the file, and a huge file is read bounded.

Open questions:
- **Path vs text** is decided by the shape of the argument (see F1 above). The direction is deliberate: a path that names no file is refused loudly; prose is kept. A single-line findings text that starts with a path is refused as well — the reviewer hands it in as prose instead.
- The bound is 64 KiB with a note naming the file and its size, so the store never carries a whole book, and the read inside the write transaction is bounded too.

Out of scope:
- The reviewer's own packet rendering (unchanged); the engine's settle cadence (unchanged).
- A separate flag for a findings file (the contract is one argument: a path or the text).

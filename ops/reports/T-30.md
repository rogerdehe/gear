## Rework after the review of attempt 1 (contract v2)

The review of attempt 1 (`git show origin/review/t30:ops/reviews/T-30.md`) found two blocking issues; this hand-in answers F1 and F2 and takes the contract-v2 additions (agent:grok, install for four CLIs).

**F1 (P1, blocking) — the review handoff must describe the shipped binary.** The packet and the review guide promised that GEAR keeps the findings text and that the reviewer's file may vanish — that is T-21 (M2), not in this candidate or dev. Both now say what the binary does today: the review is written on branch `review/t<n>`, committed and pushed; `gear send --kind review … "<the path to your review file>"` records the verdict and the path; the writer's rework note names the `git show origin/review/t<n>:<path>` command that reads the findings, so the branch must stay pushed. The packet no longer promises missing-path rejection or 64 KiB truncation either.

**F2 (P1, blocking) — the captain guide must teach the milestone format integration accepts.** Every `# Milestone` block must carry `done:`, `bar:` and `eta:` lines (T-22's `record_voyages` rejects a block without one). The kickoff now agrees all three with the user, the guide shows all three, and the complete example below is applied on current dev as the real proof.

**F3–F5 (logged) — the complete example, the separate verdict rule and the review branch convention.** F3: the guide now has one concrete `base=0` plan with `NEW` work (no pre-existing ids, no phantom evidence) and shows the verdict and review-conclusion forms separately with the "not in this cut" caveat. F4: the verdict rule reads `done:` and `bar:` separately. F5: the review guide and the packet carry the `review/t<n>` branch/artifact convention (write, commit, push; the candidate stays untouched).

## Attempt 2 — the review's F1, F2 and F3

The review of attempt 1 (`ops/reviews/T-165.md`) failed it with three
blocking findings. Each is fixed with the smallest fix the finding names,
plus its regression. Six commits: the fix and its regression are separate
commits, fix first.

### F1 — the attribution that arrives after the pass

*Finding.* A pass that names the merge that landed the work did nothing when
the attempt was **already accepted**: `settle` returned at the "the same
verdict again settles nothing" line before the attribution was written. That
is the normal path after an auto-settled review or a failed merge, so the rule
was acknowledged but not performed.

*Fix* (`crates/gear-app/src/tasks.rs`). The marking moved into one helper,
`mark_integrated_by` (the attempt's merge time and the `integrated-by:<project>:<task>`
attribution), and the "same verdict again" line now performs the marking when
the verdict is a pass that names a merge — before it returns. No second
verdict row, no second state change: the attempt keeps its accepted state and
the task its done state. The helper is written once (the store's merge time
keeps the first reading), so the replay of the same plan changes nothing.

*Regression* (`crates/gear-app/tests/it/integrated_by_contract.rs`).
`an_attribution_added_after_the_pass_marks_the_merged_time`: the first plan
carries an ordinary pass (the attempt is accepted, nothing says which merge
landed the work), the second plan carries the same pass plus
`integrated-by=T-2` (the attempt then carries T-2's merge time and the
attribution, with one verdict row), and a third apply of the same plan changes
nothing.

### F2 — a task merged by another task is not merged again

*Finding.* A task marked merged by another task's merge still got a merge op
of its own: `passed_tasks` and the launch path never looked at the attempt's
merge time, so the engine ran a second gate and push over work that was
already on the integration branch.

*Fix* (`crates/gear-engine/src/merge.rs`, the file the captain named as an
allowed edit for this rework). Two guards:

- `passed_tasks` leaves out an attempt that already carries a merge time — the
  work is on the integration branch, so no merge of its own is queued.
- the launch path voids a queued merge op of such an attempt instead of
  running it (`void_merged_op`: Intended → Void, Unknown → Failed). A merge
  that is already running is left alone: its worker finishes on its own and
  the completion is kept.

*Regression* (`crates/gear-engine/src/merge.rs`, the file's own test module).
`a_task_already_merged_by_another_task_is_not_merged_again`: an accepted
attempt with a merge time, a merge op queued in an earlier tick, and one
`merge_passed` call — the op ends Void, no worker is launched
(`cfg.merges.running` is false) and no second op is queued for the attempt.

### F3 — whoami diagnosed a different identity rule than the commands

*Finding.* `whoami` wrote its own rules instead of the ones the commands
use: a stale generation was reported as "nothing is wrong", and a caller
without `GEAR_CTX` in a bound pane was told "no GEAR_CTX in the environment"
even though `resolve_env` recovers that seat.

*Fix* (`crates/gear-app/src/identity.rs`). `whoami` now

1. resolves the effective environment with `resolve_env` — the same
   resolution every command does (a caller in a bound pane without a context
   **is** the seat of that pane);
2. observes the pane read-only (`observe`) and
3. asks the same seat check the commands ask (`require_seat`), turning the
   error it returns into the reason.

`prove_seat` is never used: it writes a claim report, and `whoami` only
reports. The pane and the seat are still reported; the reason now names the
real refusal (a stale generation says so), and the seat of the pane is added
when the claim was for another seat.

*Regressions* (`crates/gear-app/tests/it/app_identity.rs`).
`whoami_reports_the_stale_generation_of_a_restarted_seat` (generation 0 for a
seat at generation 1: the reason names the generation) and
`whoami_resolves_a_context_free_bound_pane` (no `GEAR_CTX` in a bound pane:
the seat is named and there is no reason).

## What landed

### B03-08 — a rework keeps the work the reviewer read

A rework hand-in (attempt n > 1) must build on the attempt before it: the new
candidate has to contain the candidate that was reviewed. When it does not, the
hand-in is refused and the refusal names the commit that is missing, so the
lane knows what to merge in:

> the rework candidate `abc123` does not contain `def456`: a rework keeps the
> work the reviewer read (merge `def456` into your branch)

- `crates/gear-app/src/base.rs` — `contains`: the git question
  (`git merge-base --is-ancestor base candidate`) in the lane's worktree. Git
  that cannot place a commit is an error, never a silent "no" (the rule of the
  hand-in gate, T-19).
- `crates/gear-app/src/tasks.rs` — `rework_base_candidate`: the candidate of
  attempt n−1 that the rework has to carry, and `require_rework_contains`: the
  refusal that names it.
- `crates/gear-app/src/mail.rs` — the hand-in gate asks the question before the
  store transaction, so a refused hand-in leaves the attempt as it was.

### B03-01 — a pass may name the merge that landed the work

A pass verdict may say `integrated-by=T-m`: the work was already landed by
T-m's merge, so the task is marked merged by that merge instead of waiting for
a merge of its own. The verdict is refused unless both hold:

- T-m is merged (its attempt carries the merge time), and
- the candidate's tree is in the integration branch — the work is there, even
  when the merge rewrote the commit that carried it.

When it is accepted, the attempt carries T-m's merge time and the merge that
landed it is recorded (`integrated-by:<project>:<task>`), so the board and the
report can say which merge did it.

- `crates/gear-app/src/base.rs` — `tree_on_integration`: the tree of the
  candidate against the trees on the fetched integration branch.
- `crates/gear-app/src/tasks.rs` — `merged_at` / `require_merged_at` (the
  store's answer: is that task merged?) and the marking in `settle`.
- `crates/gear-app/src/plan.rs` — the check runs before the write transaction
  (git runs outside the store transaction, like the cancellation check).

### B9 — `gear whoami`

`WhoAmI` carries the real pane, the seat bound to it, the store and the reason
a claim fails; its `Display` prints all four. `whoami(store, env, herdr,
ancestors)` in `crates/gear-app/src/identity.rs` answers it: the pane comes
from the process ancestry (T-104), the seat from the store's bindings (T-126),
the store from `GEAR_DB`, and the reason says what a claim lacks (no
`GEAR_CTX`, no pane, no seat bound to the pane, or a claim of another seat's).

The packet says *mast* adds the CLI subcommand — that is this lane, so
`gear whoami` is here too:

- `crates/gear-cli/src/main.rs` — the `whoami` subcommand: it reads only (no
  engine, no write), prints the `WhoAmI` (or its JSON form).
- `crates/gear-cli/tests/it/whoami_contract.rs` — the command starts no engine
  and names its store.

## Signature deviation (captain's decision, M-2640)

The packet names `whoami(store: &Store, env: &Env, herdr: &mut dyn HerdrRead,
ancestors: &[i32])`. `Store::read` needs a mutable borrow
(`pub fn read<T>(&mut self, …)`), so a `&Store` cannot answer the seat
binding. The captain's answer (M-2640) was to commit what builds: the
function takes `&mut Store`. Everything else follows the packet.

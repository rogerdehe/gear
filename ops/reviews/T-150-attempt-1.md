## Findings
F1 [P1, blocking] A Started attempt with a pending contract update still gets a Deliver op — `crates/gear-engine/src/dispatch.rs:159` (also `:147` and `:436`). Reproduce with a Running task, Started attempt, adopted_version=1, pending_update=2, an idle lane, no pending op and expired cooldown: `decide` returns Adopt before reaching the new guard, and `intend_dispatch` puts that text through `intend_deliveries`, creating a second Deliver. The writer's report calls this an exception, but contract v1 and §10.3 bullet 4 explicitly prohibit any Deliver op for Started. This breaks the STABLE bar's normal-use correctness requirement: a normal contract edit still enters delivery timeout/retry bookkeeping for an already-started round. Smallest fix: in dispatch's Adopt handling, route the contract-change notice for a Started attempt through the existing message/doorbell path rather than Deliver, retaining pending_update and view adoption; ensure every packet-producing dispatch path excludes Started (about 25–40 lines plus a regression). Verify the full decide→intend_dispatch path produces zero Deliver ops for Started with pending_update while the contract-change notice still reaches the lane.
F2 [P1, blocking] A check-in after an unconfirmed delivery was retried leaves its stall item open — `crates/gear-engine/src/ops.rs:665` (normal confirmation at `:540`, tick ordering in `crates/gear-engine/src/lib.rs:294`). Reproduce: let a Deliver time out and open the stall; restart the agent in the same generation so a retry Deliver is Submitted; record a view showing the same task/attempt; run confirm_pending_with then confirm_late_views, as tick does. The retry confirms and moves Delivered→Started first. The failed original op's late-check path then gets false from start_confirmed_attempt and skips stall::resolve. My regression confirms the attempt is Started but the captain's stall message remains Open. This breaks §10.3 bullet 2 and the STABLE bar's normal-use usability requirement: the captain keeps an urgent false stall after the lane recovered. Smallest fix: in confirm_pending_with, when start_confirmed_attempt returns true for a lane delivery, call stall::resolve for that seat in the same transaction, just as the late path does (about 5 lines plus a regression). Exercise timeout→retry→view with the real tick confirmation order. Tie cleanup to that successful transition rather than repeatedly resolving unrelated future stalls from historical failed ops.

## Findings

F1 [P1, blocking] Count the first Codex total against zero — `crates/gear-usage/src/lib.rs:184`. `codex_rollout` unconditionally discards the first nonzero total. A fresh session containing one token_count inside the window returns `Some(Usage { input: 0, output: 0, records: 0, ... })`; a record with input=1000, cached=200, output=100 should contribute input=800, cache_read=200, output=100. Every new session loses its first request, breaking the STABLE bar for normal-use errors and the v0.4.2 tokens/cost-per-round done clause. Smallest fix: in `codex_rollout`, use an all-zero predecessor for the first valid total, still updating the predecessor before filtering by the window (~8 lines). Change the existing Codex expectations that deliberately omit the first total, and add a one-count fixture plus a window whose first total precedes `from`.

F2 [P1, blocking] Preserve the last assistant context across repeated Codex totals — `crates/gear-usage/src/lib.rs:227`. `codex_last_context` returns None for a single valid count and overwrites context with zero when the last two totals are identical. The synthetic sequence totals (input=1000,cached=200), (1500,300), (1500,300) returns `Some(0)`; its last assistant input is 500, not zero. Repeated token-count notifications must not make a large session appear empty. This breaks §13.2/§3.5 and the STABLE bar; the follow-up keep/compact decision in the v0.4.0 done clause depends on this value. Smallest fix: in `codex_last_context`, establish context on the first valid total and retain the last actual assistant context across unchanged totals; where `info.last_token_usage` is present, use that request's input/cache values instead of a notification delta (~15–25 lines). Add fixtures for one count and a duplicate total after a nonzero delta; also check cache-write inclusion.

F3 [P1, blocking] Ignore null Codex info before changing the baseline — `crates/gear-usage/src/lib.rs:569`. `CodexTokens::of` accepts `info: null` as an all-zero total because `.or(Some(info))` falls back to null and `number` supplies zeros. After totals (1000,200,100) and (1500,300,120), a null-info token_count in its own window yields input=-1200, cache_read=-300, output=-120, and `last_context` becomes -1500. §4.3 explicitly excludes null info. This breaks the STABLE bar, the v0.4.2 accounting clause and the v0.4.0 context decision. Smallest fix: make `CodexTokens::of` reject non-object/null info and require an object `total_token_usage` (~4–6 lines), without changing the previous total or last context for rejected events. Add valid/null/valid and trailing-null fixtures verifying that no negative record is introduced and the baseline/context survives.

F4 [P1, blocking] Read OpenCode completion time from JSON data — `crates/gear-usage/src/lib.rs:366`. `opencode_messages` requires a SQL `time_completed`/`completed`/`time_complete` column and never reads `data.time.completed`, which is the timestamp specified by §4.3. A readable `session_message(id, sessionID, data)` table containing an assistant with `data.time.completed=1793019600000` and tokens returns None from both APIs. Even with a completion column present, the window uses that column instead of the contracted JSON timestamp. This breaks the OpenCode reader contract and the STABLE bar, and prevents the v0.4.2 per-round tokens/cost report. Smallest fix: select the session's JSON data without requiring a completion column, parse `data.time.completed` through the existing timestamp conversion, and order the parsed completed records by completion time for `last_context` (~15–25 lines). Replace the synthetic SQL-time fixtures with JSON `time.completed` fixtures, including out-of-order inserted completions, boundary records and an unreadable database.

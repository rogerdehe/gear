## Findings

Nothing wrong lands (the candidate was approved), but the cancel is ignored. Logged; not worth a re-check before push under this bar.
- [P3] A gate that leaves a background process holding stdin keeps the merge lock forever — `merge.rs:554-560` — every tick then spawns a worker and calls `worktree_open`, gets `Ok(None)` and stays Unknown with no captain alert. It needs a gate that daemonises, which is a stacked coincidence. Logged. If it ever appears, tell the captain once after N busy results.
- [P3] After a restart, a merge whose push had already landed is recorded as "already merged" with the recovery time as `merged_at`, not the true push time — `merge.rs:499-503`. The real time is lost with the dead process. Logged.
- [P3] `fail_merge` is not idempotent. If `tell_captain` errors after the op is already Failed, the retained result re-enters `fail_merge` next tick, and Failed→Failed is probably rejected, so the tick keeps erroring — `merge.rs:274-285`. It needs a store error at one exact point, so it is a stacked coincidence. Logged.

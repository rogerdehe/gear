## Findings
F1 [P1, blocking] A refused land can never be retried by the advertised `- remerge T-n` command — `crates/gear-engine/src/merge.rs:1913`. Remerge creates another Merge op for the same accepted attempt, but `insert_land_op` returns as soon as any `{task}:{attempt}:land` exists, including Failed. Forge sync never retries a Failed land. Even when the PR-head push succeeds, the new Submitted Merge immediately fails again with the old land's message, without another forge merge call. This breaks §11.3 row 2's recovery instruction, done clause (4), and the STABLE bar for a normal temporary required-check refusal. Smallest fix: in `insert_land_op`, deduplicate live/Confirmed land ops but permit a new Intended land op after Failed/Void, with the current head and method and the existing attempt key; newest-op selection already exists in engine and forge (about 10-15 implementation lines). Add a refusal → captain remerge → successful fake-forge confirmation regression, checking a second forge call and final merged time.
F2 [P1, blocking] Restart-recovered Merge ops never become Submitted after a successful PR-head push — `crates/gear-engine/src/merge.rs:276`. Startup changes Executing to Unknown; the launch path changes only Intended back to Executing. Consequently this new completion handler skips the Submitted/result write for Unknown while still inserting its land op. `confirm_pr_merges` only processes Submitted, so the Merge keeps rerunning or fails on a subsequent push and cannot confirm even if its forge land succeeds. One engine restart during an in-flight merge is normal use; this breaks done clause (4) and the STABLE bar. Smallest fix: transition both Intended and Unknown merge ops to Executing before launching their worker (the existing launch check near line 369, about 2-4 lines), then retain the completion guard. Add a recovered-Unknown PR merge regression asserting Submitted JSON, one land op, and Confirmed/merged time after forge confirmation.
F3 [P1, blocking] Replaying a successful PR-head push creates a sibling merge commit and fails non-fast-forward — `crates/gear-engine/src/merge.rs:1841`. `pr_head` always resets to the original candidate and creates a new candidate+review merge. If the engine stops after the push but before collecting its result, or a successful push loses its response, the retry in a later second generates a different SHA with the same parents/tree. The already-pushed PR head is not its ancestor, so every ordinary push is rejected; retries cannot land the task. The same issue obstructs remerge after a land refusal independently of F1. This breaks the STABLE bar's single-restart/network-fault case and reliable PR landing in done clause (4). Smallest fix: before rebuilding/pushing in `pr_head`, recognize and reuse the fetched PR head when it is the engine's candidate+review merge (verify the expected parents and tree so unrelated extra branch commits are still refused); otherwise retain the normal fast-forward push and do not force-push (about 25-40 implementation lines). Add a deterministic fake-remote regression for a successful head push followed by recovery/retry with a different commit timestamp, asserting no non-fast-forward failure and reuse of the first head SHA.

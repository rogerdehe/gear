## Findings
F1 [P1, blocking] Real merged PR responses never deserialize — `crates/gear-forge/src/lib.rs:127` and `crates/gear-forge/src/github.rs:332`. `PrState.merge_commit` is `Option<String>`, but gh returns `"mergeCommit":{"oid":"sha99"}`, not `"mergeCommit":"sha99"`. Consequently an actual successful land becomes Unknown when its post-merge read returns Unreadable, and every later reconciliation remains Pending forever. This breaks done clause (4), landing a fixture GitHub task through its PR, and the STABLE bar. Smallest fix: in github.rs deserialize a gh response DTO with `mergeCommit: Option<{oid: String}>` and map its oid into the existing public `PrState` (about 15-25 lines); change the fake-gh state fixture in github_contract.rs to the actual object shape and cover null for OPEN. Keep the stored land result as `{"merge_commit":"sha99"}`. GitHub CLI's own [PullRequest and Commit types](https://github.com/cli/cli/blob/trunk/api/queries_pr.go) define this object shape.

F2 [P1, blocking] An OPEN PR is recorded as a successful landing — `crates/gear-forge/src/sync.rs:426`. After any Ok from `forge.merge`, `merge_and_record` confirms the land op without checking `state.is_merged()` or requiring a merge commit. A fake returning OPEN/same head after the merge produces Confirmed with `{"merge_commit":null}`. This is reachable on GitHub: [gh pr merge](https://cli.github.com/manual/gh_pr_merge) can successfully enqueue a PR or enable auto-merge for a required merge queue, while it remains OPEN. The engine would then treat unfinished work as landed and clean up branches. This breaks done clause (4) and the STABLE bar. Smallest fix: in merge_and_record and the MERGED branch of reconcile_land, confirm only a MERGED state with a nonempty commit; keep the op Unknown/Pending when the merge has been accepted but is not yet observable as merged (about 10-20 lines). Add a regression for successful merge command followed by OPEN/null, then a later MERGED/commit tick that confirms it; also reject/keep pending a MERGED response with no commit.

F3 [P1, blocking] A process death during land cannot enter the promised restart reconciliation — `crates/gear-forge/src/sync.rs:416`. `merge_and_record` calls gh without first persisting Executing. If the process dies during or after that call, the op remains Intended; `recover_on_start` only changes Executing ops to Unknown (`crates/gear-engine/src/ops.rs:932`), so the next tick blindly invokes merge again instead of reading PR state first. The explicit Unknown fixtures do not exercise the state actually left by a crash. This breaks design section 11.3 and the STABLE bar's single-restart recovery. Smallest fix: persist Executing immediately before invoking `forge.merge`, including when retrying an Unknown OPEN/same-head op (about 2-5 lines). Add a fake that stops/panics in merge and assert that persisted state is Executing and that restart recovery with a now-MERGED PR confirms without a second merge.

F4 [P1, blocking] Lane rebinding redirects an existing task's PR landing to the new repository — `crates/gear-forge/src/sync.rs:334`. The confirmed claim already contains its original repo, but land_op_of replaces it with `fact.github.repo`, which facts resolves from the lane's current config. For a task pinned to old repo owner/name with confirmed PR #7, rebind heat to owner/other and sync sends `merge owner/other#7`, despite the old claim. The same head guard ordinarily makes this fail; it cannot land the old task on its own repo. This directly breaks done clause (4)'s two-repo rebind requirement and the STABLE bar. Smallest fix: preserve the confirmed claim's `pr.repo` when constructing LandOp (one line), and use that LandOp PR for merge and reconciliation as already done. Add the two-repo regression with an old task pinned to old, a confirmed old-repo claim, and the lane now bound to new; assert both merge and pr_state use old.

F5 [P1, blocking] Recovery lookups bypass the per-tick call budget — `crates/gear-forge/src/sync.rs:289` and `crates/gear-forge/src/sync.rs:380`. Neither adopt_claim nor reconcile_land checks/decrements MAX_CALLS_PER_TICK; post-merge pr_state also bypasses it. A backlog of ten Unknown claims makes ten lookups in one tick even though the advertised cap is eight. After an outage/restart, each lookup may consume the 30-second gh timeout, so an arbitrarily large backlog can hold the engine tick and other work for minutes. This breaks the STABLE bar's normal outage/restart responsiveness. Smallest fix: thread the shared budget into adopt_claim and reserve one call before each new pr_by_head/pr_state invocation, returning Pending/None when exhausted; retain a recoverable Unknown state if the post-merge read must wait (about 15-25 lines). Add recovery-backlog tests exceeding eight Unknown claims and land ops, assert calls never exceed eight and later ticks continue the backlog.

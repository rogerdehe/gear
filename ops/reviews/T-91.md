## Findings

F1 [P1, blocking] PR mode runs only after the local push has consumed its PR head — `crates/gear-forge/src/sync.rs:276` and `:293`. The forge merge is gated on `attempt.merged`, but the engine sets that only after its existing merge worker pushes integration and calls `close_branches` (`crates/gear-engine/src/merge.rs:1031`–1040), deleting the task head on the ordinary path. Thus `merge = "pr"` still lands through a local push, and the later PR merge sees work already integrated and its head deleted; protected integration branches that require PRs never even reach this call. This breaks done (4), the specified PR merge mode, and the DELIVERABLE bar in normal use. Smallest fix: in `merge.rs`'s successful gate path, branch on the resolved repo's GitHub merge mode; for PR mode persist readiness for the forge instead of pushing/deleting, let `sync.rs` drive the PR merge from that readiness, then record the merged timestamp and do cleanup only after confirmed forge success. Preserve the existing push path and gate; roughly 60–100 lines of mode-specific wiring plus an engine/forge lifecycle test. Do not use an already-completed local merge as the PR merge trigger.

F2 [P1, blocking] Later events run even when their predecessor failed — `crates/gear-forge/src/sync.rs:184`. `run_task` ignores `None` from `run_call` and continues. With a confirmed claim and a forge that rejects only `merge`, this tick still calls `close_issue`; with a failed completion comment the verdict can appear first, and the completion is posted out of order on recovery. This breaks acceptance's ordering and done (4)'s merge-then-close behavior under one ordinary transient failure. Smallest fix: stop processing this task's later calls on pending/failed/unknown predecessors, while allowing confirmed predecessors through; return a small explicit outcome (already done / newly done / pending) or consult persisted state, about 15–25 lines in `run_task`/`run_call`. Add a fake that fails only the merge once: no close until the retry succeeds; also fail one completion once and assert completion precedes verdict after recovery.

F3 [P1, blocking] An outage lasting three ticks permanently drops queued work — `crates/gear-forge/src/sync.rs:342`. After three failures every later tick returns without attempting or scheduling anything, even when the forge recovers; no captain notification or retry mechanism exists. Reproduction: deliver, keep Fake.down true for ticks 2 through 5, set it false, tick 6: no claim is opened. This also makes initial PR creation brittle: delivery precedes the worker's first push, so an unavailable head can consume the entire retry budget before hand-in. This breaks the explicit outage catch-up requirement, done (1)/(4), and the DELIVERABLE bar for a routine service outage. Smallest fix: keep failed events pending with a persisted retry deadline/back-off and bounded work per tick/call, rather than a lifetime three-failure tombstone (about 20–35 lines in `run_call` and op payload handling). Prove recovery after more than three unavailable ticks, including a claim whose branch becomes available later, with exactly one successful event and ordered later comments.

F4 [P2, logged] An interrupted or timed-out claim is quarantined forever without reconciliation or notification — `crates/gear-forge/src/sync.rs:334`, `:351`, `:375`. One unfinished intent or timeout becomes Unknown; with no confirmed PrRef the whole task's later PR lifecycle is silently skipped forever. Suppressing blind duplicate writes is reasonable, but this is not lifecycle recovery across a restart. Logged as an interruption edge case at this bar; future work should reconcile an existing PR/comment using its identity/marker or surface a concrete captain action.

F5 [P2, logged] Confirmed comment/merge/close events are reported as newly done every tick — `crates/gear-forge/src/sync.rs:185` and `:336`. The confirmed result is returned as Some, so subsequent sync results repeatedly contain those event keys despite no new forge call. The engine currently discards the vector, so it does not block landing. Return a distinct already-done outcome when addressing F2.

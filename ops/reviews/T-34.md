## Findings

### R1 — [P0, blocking] NEW prose consumes task IDs and causes duplicate tasks

`crates/gear-app/src/draft.rs:793` — `rewrite_applied` treats every `## NEW` line as a queue block, even inside the free-text Goal or Milestone sections. The parser only creates tasks from Queue. Apply this valid first plan:

```markdown
<!-- gear-plan project=p base=0 -->
# Goal
## NEW
Ship the NEW format.
# Queue
## NEW [must] lane=heat
goal: A
accept: a
deps: -
```

The first apply creates T-1, changes the goal's heading to `## T-1`, and leaves the actual queue header as `## NEW`. The independent second apply succeeds with `plan version 2`, `created T-2`, `not mentioned T-1`; the store now has two tasks instead of one. The canonical file has also lost the original prose.

Smallest fix: in `rewrite_applied`, track the current top-level section with the same section-name parsing as `parse`; consume created IDs and replace NEW headers only while in Queue (about 8–12 lines). Add a regression with a NEW subheading in Goal or Milestone before Queue; assert the prose is unchanged, the queue receives T-1, and a second CLI apply creates no task. Do not rewrite unrelated free text.

### R2 — [P1, blocking] A compact valid plan header loses its closing comment delimiter

`crates/gear-app/src/draft.rs:827` — the parser strips `<!--` and `-->` before reading header tokens, but the rewrite splits the complete comment and replaces the entire token starting with `base=`. For a valid header `<!--gear-plan project=p base=0-->`, the closing delimiter is part of that token and is discarded. With the normal Queue from R1 (without Goal), first apply succeeds and writes `<!--gear-plan project=p base=1` as line 1. The next apply fails BAD_FORMAT: `line 1: the first line must be ...`.

Smallest fix: in `rewrite_applied`'s header replacement, strip the comment delimiters before tokenizing and restore them explicitly around the updated inner header, or replace only the numeric base span while retaining both delimiters (about 8–12 lines). Add the compact-header regression and assert the rewritten text parses at the applied base and a second CLI apply succeeds without task or contract changes.

### R3 — [P1, blocking] Accepted extra whitespace in a NEW header produces an invalid task header

`crates/gear-app/src/draft.rs:800` — detection uses split_whitespace, while extraction assumes exactly the six bytes `## NEW`. The parser accepts `##  NEW [must] lane=heat`. First apply creates T-1, but rewrite produces `## T-1 W [must] lane=heat`. The next apply fails BAD_FORMAT: `line 3: unknown priority "W"`. A tab between `## ` and NEW has the same problem.

Smallest fix: derive the suffix by stripping `## `, trimming leading whitespace, then stripping the complete NEW token, rather than slicing at `"## NEW".len()` (about 2–4 lines). Preserve the priority and remaining header fields. Add a double-space/tab regression and assert successful parsing and a second apply with no created tasks or changed contracts.

### R4 — [P2, nonblocking] Verdict-section detection disagrees with accepted whitespace

`crates/gear-app/src/draft.rs:848` — `parse` splits the section name on any whitespace; `is_section_named` accepts only end-of-line or a literal space after Verdicts. A valid `# Verdicts\taccepted` heading (a literal tab before `accepted`) survives the rewrite. The independent probe confirms the section remains. Identical existing verdicts are already idempotent in `tasks::settle`, so this is logged under the FASTEST bar rather than made a rework requirement. A small optional correction is to compare the first whitespace-delimited section-name token with Verdicts, matching the parser (about 2 lines), and test the tab heading.

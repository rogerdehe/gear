## Findings
F1 [P1, blocking] A NEW task submitted with an idle rebind captures the old repo — `crates/gear-app/src/plan.rs:587` (Staff processing after queue insertion and the config snapshot at line 367). Reproduce with the supplied fixture: apply `# Staff\n- rebind wire repo=api owns=[src/new/]\n# Queue\n## NEW [must] lane=wire\ngoal: new repo work\naccept: done\nestimate: 10\ndeps: -\n`. Apply succeeds and says applied; the lane config resolves to `/repo/crates/api`, but the new task permanently stores repo `/repo`, base `dev`, and gate `make test`. A captain moving a dry lane and supplying its next work in one plan therefore creates work for the wrong repository. This breaks the STABLE bar's normal-use usability/correctness requirement and the intended v0.4.3 lane move. Smallest fix: in `apply_queue`, process rebind Staff items in a prepass before loading `existing` and the queue's config snapshot, keep their warnings/decision records, and skip them in the later Staff loop (roughly 20 moved/adjusted lines). This preserves old tasks while NEW blocks see an immediately applied rebind. Add a regression combining an idle rebind with NEW and assert its repo/base/gate are the destination's while a pre-existing task retains its original target.
F2 [P1, blocking] Pending requests can reserve conflicting ownership and permanently abort engine ticks — `crates/gear-app/src/plan.rs:1112` and `crates/gear-app/src/plan.rs:1156`. Reproduce with heat in api and wire in root, each with an open attempt, plus an unused named engine repo. Apply `- rebind heat repo=engine owns=[src/]` and `- rebind wire repo=engine owns=[src/]` in Staff. Both are accepted because validation considers only the live config, not pending requests. Once both attempts become terminal, every call to `reconcile_rebinds` returns `line 0: lanes[1].owns: overlaps the paths owned by lane "heat"`; its transaction rolls back the first lane too and leaves both pending markers. The probe confirmed the identical error and rollback twice. `engine::tick` propagates this error at its start (`crates/gear-engine/src/lib.rs:181`), so all remaining engine work is skipped on every tick. The conflicting pending request cannot be replaced through rebind either. This breaks the STABLE bar's normal-use error handling and stability requirement. Smallest fix: in `request_rebind` validation, include the target repo/owns reservations of other pending requests (including earlier lines of this apply), rejecting a conflicting request atomically before recording it; a projected config checked with the existing validator is sufficient (about 20–40 lines). Add same-apply and separate-apply regressions proving the conflict is refused and the remaining valid request reconciles without error after its attempt closes.

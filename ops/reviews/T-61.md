## Findings

F1 [P1] BLOCKING — A transient remote push error permanently fails the merge — `crates/gear-engine/src/merge.rs:761–765`. Only errors containing `non-fast-forward`, `fetch first` or `cannot lock ref` are classified Clear. A connection failure or temporary remote-side rejection during push is classified Stuck, so `merge_with_retries` returns immediately and the op becomes Failed; later ticks do not retry it. Reproduced with the existing real-Git Scratch fixture: install an executable `origin.git/hooks/pre-receive` containing `#!/bin/sh`, `rm -- "$0"`, `echo 'temporary service unavailable' >&2`, `exit 1`; invoke `merge_retried` for the approved task candidate. It returns Stuck on the first push, with no backoff. Invoking exactly the same operation again succeeds, proving that the failure cleared. This violates M3 done (1), no hand fix/store reset, and the DELIVERABLE bar requiring normal-use errors to be fixed: a single temporary remote outage leaves the voyage stuck. Smallest fix: in `merge_one_locked`, route retryable transport/remote-service push errors through `Failed::clear`; the simplest bounded implementation is to classify push failures as Clear, retaining the race prefix where appropriate (about 3–8 production lines). The existing retry limit still rings once for permanent rejection. Add a real-Git one-shot rejecting-hook regression through `merge_passed`, asserting eventual Confirmed/merged with no captain item, plus an always-rejecting case asserting exhaustion and one item without a store reset.

F2 [P1] BLOCKING — Pending candidate pushes bypass retry when the object exists locally — `crates/gear-engine/src/merge.rs:650–654`. Missing local objects return Clear, but the same not-yet-pushed commit returns Stuck if it exists in the repository's shared object database. Lane and merge worktrees share that database, so this distinction depends on local object availability rather than whether the push can still land. Reproduced using Scratch: create a new commit on `heat/t5-delayed` without pushing it; start a thread that pushes it after one second; invoke `merge_retried` immediately with its SHA. The function returns Stuck before the push lands. After joining the pushing thread, the identical operation merges successfully. The worker's terminal result nevertheless makes the real op Failed, requiring intervention. This breaks the task's explicit candidate-not-yet-fetchable retry requirement, M3 done (1)'s no-store-edit chain and the DELIVERABLE normal-use recovery bar. Smallest fix: classify the no-pushed-ref result as Clear too, preserving its clear diagnostic and letting the existing bounded retry loop distinguish a pending push from one that never arrives (one production-line change). Update the existing never-pushed test to expect retries followed by one terminal ring, and add the delayed-push regression asserting automatic success without any store reset (about 20–35 test lines).

F3 [P2] LOGGED — A candidate reachable only from a pushed tag is reported as unpushed — `crates/gear-engine/src/merge.rs:613` and `:646`. Fetch/reachability enumerate branch refs only.

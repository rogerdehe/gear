## Findings
- [P2] `max_threads = 0` returns one thread: the reserved slot is pushed before any cap check, so a batch with a non-urgent thread has length 1 while an all-urgent batch correctly has length 0 — `crates/gear-app/src/mail.rs:139-144` (the only cap check is at `:150`) — the function's contract is "at most `max_threads` threads"; a caller that derives the limit from remaining home-page space (T-17) would get a thread where it asked for none, and the result depends on whether a normal thread happens to exist. Verified with a temporary probe test (not committed): `BatchLimits { max_threads: 0, per_sender: 2 }` with one non-urgent thread → 1 view; with one urgent thread → 0 views; probe removed, branch untouched. Fix: reserve only when `limits.max_threads > 0`, or `selected.truncate(limits.max_threads)` after the display sort.
- [P3] `last_reply_is_newest_reply` cannot distinguish "newest Reply in the thread" from "newest Reply among candidates", because `msg()` defaults to `MsgState::Open` and the two Reply rows are inserted as Open, so they are themselves candidates; real replies are stored `info` (design/07) — `crates/gear-app/tests/app_select_batch.rs:105-107` — an implementation that only scanned `actionable_for` would also pass. Build the replies row with `state: MsgState::Info` (or add one newer Info reply) so the whole-thread read is actually exercised.

## Set aside
- `per_sender` is attributed to the sender of the thread's oldest unhandled message (documented judgement in the progress notes). Multiple senders per thread are possible only when the captain instructs another lane inside an existing thread; the common lane-question case is covered — see the question below.
- `last_reply` tie at equal `created` broken by message id lexicographically (`M-9` > `M-10`), which matches the store's own `ORDER BY created, id`; no writer creates two replies in the same second in one thread today.
- One `thread_messages` query per candidate thread plus cloning each thread's messages: unselected threads are queried too, but the batch default is 6 and SQLite is local; no measured problem in slice 1.
- `messages.first().map(...).unwrap_or_default()` for `oldest`/`senders` is dead defensive code (groups are non-empty by construction); harmless.
- `per_sender = 0` yields an empty batch, consistent with a zero cap and deliberately documented; only the `max_threads = 0` asymmetry is a finding.
- `cargo test -p gear-engine --test slice1_messaging` not run: `mail::send`, `mail::reply` and `home::build` are still `todo!()` on `dev` (T-14/T-15/T-17 unmerged), and the packet says the scenario only passes once the engine is done.
- Display order "urgent first, then oldest" (which puts the reserved normal thread after urgent ones) is asserted by `urgent_first_then_oldest` and the writer documents it as deliberate; design/07 does not specify the batch's display order beyond "urgent first", so not a finding.

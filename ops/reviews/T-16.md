## Findings
- [P1] F1 — Reassigning a task transfers another lane's historical hand-ins and rejections — `crates/gear-board/src/lib.rs:283` (current-lane grouping starts at line 263). The reader sums every attempt of every task currently assigned to a lane, without checking `attempt.seat`. A supported captain plan edit changes `TaskRow.lane` (`crates/gear-app/src/plan.rs:295`), so merely moving a task rewrites both lanes' performance history. On the scratch fixture, both T-1 attempts retain `seat = demo:data`. Updating only T-1's lane to runtime changes data from `rework 1/2` to `rework 0/0` and runtime from `rework 0/0 · no task yet` to `rework 1/2 · no task yet`, in both text and JSON. Runtime has never handed anything in or received a Deliver op. This makes the advertised per-lane rework measure report the wrong lane's work during normal replanning. Attribute lane-owned attempts using their recorded lane seat rather than the task's mutable current lane; retain current-lane grouping for the queue, and count each hand-in once in the project totals. Add a regression that hands in/rejects work on data, reassigns the task to runtime, and checks that the historical lane numerators/denominators stay with data in both rendering and JSON. If a later attempt is handed in by runtime, only that later attempt belongs to runtime.

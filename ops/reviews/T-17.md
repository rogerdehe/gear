## Findings
- [P1] A Reply/Instruction created in the same second as the recorded view is never shown — `crates/gear-app/src/home.rs:42` (`since` = the latest view's `ts`), `crates/gear-app/src/home.rs:68` (`messages_to_since(..., since)`), with `crates/gear-store/src/lib.rs:759` using `created>?3` — `Ts` is Unix epoch seconds (`crates/gear-store/src/schema.sql:2`). A message created after the view but in the same second is not `> since`; the next build records a new view with a larger `ts`, so the message stays below every later cutoff and is lost from the page for good. The doc comment's "latest view that **listed it**" is the intended guard; the implementation only compares times. Impact: a lane never sees that reply, so the engine's doorbell for it can never be confirmed (design/07: judgement from view records; design/08: CONFIRMED needs a view). Verified with a scratch driver: view recorded at `NOW` with nothing shown, reply inserted at `created = NOW`, builds at `NOW+1` and `NOW+2` show neither the id nor the body. Fix: decide "unshown" from the ids the views listed — e.g. read `views_since(..., 0)`, union `shown_msgs`, and filter the messages to those whose id is not in the union (query from `since - 1` and drop listed ids also works). Add a test where the reply's `created` equals the recorded view's `ts`.
- [P2] An Instruction addressed to the captain is printed twice and recorded twice — `crates/gear-app/src/home.rs:48-63` (batch) and `crates/gear-app/src/home.rs:68-75` (unshown) — `select_batch` candidates are all Open messages (`crates/gear-app/src/mail.rs:250`), and `mail::send` stores an Instruction as Open (`crates/gear-app/src/mail.rs:135-136`), so the same message is printed under INBOX and again under UNSHOWN; `shown_msgs` ends up with the id twice. Verified with a scratch driver: the body appears twice and the view is `["M-1", "M-1"]`. Fix: collect the ids printed in the batch and skip those ids in the unshown loop; add a test with an Instruction to the captain asserting one occurrence and a unique `shown_msgs`.
- [P3] The generation is not really asserted in the identity test — `crates/gear-app/tests/app_home.rs:101` — `assert!(home.text.contains("1"))` is satisfied by any digit anywhere in the page (the seat id and message id already contain it), so a missing or wrong `generation` field would still pass. Assert the line, e.g. `contains("generation 1")`.
- [P3] The Result claims a test count that does not exist on this commit — `ops/tasks/T-17.md:77` — `cargo test -p gear-app` on `21fbfb2` runs 54 tests and has no `app_reply` target (T-15 is unmerged), while the Result claims 57 with "8 reply". Re-run and paste the real output.

## Set aside
- `ThreadView.last_reply` and a task summary are not printed; packet item 1 lists only thread ids, message ids, original bodies and `+N more`, and the rest of design/07's thread columns belong to the full page/`--show`, not this packet.
- `Home.text`'s "≈120 lines max" is not enforced and the unshown list is unbounded; the overflow marker in design/13 needs `gear --show`, which is outside this packet — raised as a question rather than a finding so truncation does not silently starve old messages.
- The footer strings are a judgement call (captain: `gear reply <first> --resolve`; lane: `gear send --kind progress`); the packet only asks for "footer: suggested next command" and specifies no text.
- Bodies are printed verbatim, newlines included; the writer flagged this and the packet has no truncation rule.
- On a generation change, views of the old generation are ignored, so all earlier Reply/Instruction messages are shown again; regeneration semantics belong to design/03 and the store has no per-generation message query.
- `views_since(..., 0)` loads every view (and its JSON id list) on each `gear` call; a `latest_view` store method would be cheaper, but the store is outside the allowed changes and this is not a correctness bug.
- The store's strict `created > since` in `messages_to_since` is the data lane's fixed contract; the correct compensation belongs in `home.rs` (see P1), not in the store.

## Findings
- [P3] Repeated ids in one call are not deduplicated: the pre-check pushes a row per occurrence, so `handled` reports the same id twice and the row is updated twice (a second `Resolve` re-stamps `resolved` with the same `now` instead of meeting the closed-state guard) — `crates/gear-app/src/mail.rs:387-411`, `crates/gear-app/src/mail.rs:442` — the "handling result for each ID" the CLI prints can overstate what happened, and the Open-or-Waiting guard is evaluated on a pre-write snapshot so it cannot catch the repeat. Deduplicate in the pre-check (or reject duplicates) and report each id once.
- [P3] The captain state list includes `Standby`/`Retiring`, states a captain can never hold (the model's captain transitions are Starting/Active/Unknown/Unavailable/Handover) — `crates/gear-app/src/mail.rs:360-366` — copied from `send`; the entries are dead and suggest a captain may write from states the model forbids. Keep only the captain states the design cares about.
- [P3] The Result's full-suite line is wrong: it claims `49 tests pass (8 reply + 9 send + 15 identity + 8 config + 3 unit + doc)`, but the run is 53 tests, `app_send` has 10 (not 9), `app_select_batch` (9) is omitted, and the listed numbers sum to 43 — `ops/tasks/T-15.md:74` — a merge record that hides a suite and miscounts the rest; the two acceptance suites it names separately are correct.

## Set aside
- `downgrade` is accepted but has no effect (design/07:62 wants urgency-only handling): `gear-store` has no method to change a message's `urgent` flag and `crates/gear-store` is outside T-15's allowed changes; the writer disclosed it. Needs a store task or the CLI task, not this one.
- `next_check` (design/07:64) has no field in `ReplyArgs`; the public signature is captain-owned and the CLI's `cmd_reply` is still `todo!()`, so the recheck record cannot be written here.
- A bare `--wait` (both fields `None`) stores a Waiting row with `wait_until IS NULL`, which `actionable_for` never selects until a slice-2 release event; design/07:61 says wait records whom and when, but an event-driven indefinite wait is legitimate and only the full case is tested — asked as a question.
- An "instruction requiring action" is answered with a Reply, never an Instruction (design/07:63); slice 1 hardcodes `needs_ack=false` for every message (T-24), so no such instruction exists yet.
- When one sender's ids span several threads, only the first listed id gets a `reply_to`-linked answer and the answer is written in that first thread; the packet's `one_reply_per_sender` deliberately encodes one answer for two threads, and ReplyResult documents "one per original sender", so this matches the spec as written — but the thread choice is unstated (question).
- A captain in HANDOVER is rejected here; handover delivery is slice 2/4 and the `reply` doc comment names no state carve-out.
- The generation-change annotation on the recipient (design/07:22) is absent; seat generations do not move in the slice-1 scenarios.
- Empty `ids` are accepted and recorded as a successful no-op request; the CLI declares `ids` required, and the packet names no error for an empty list.
- The `args_key` is order-sensitive: the same id set in a different order is a `RequestConflict`, not a replay. The CLI passes argv order; harmless today.
- Empty `text` is not validated; the CLI requires `--message`, and `send` does not validate bodies either.
- Red-first is not verifiable: tests and implementation share commit `61250ff`. The tests read rows back from the store (`get_message`, `messages_to_since`), so they are not vacuous.
- `gear_herdr::fake::FakeHerdr` is not used in `app_reply.rs`; `reply` takes a `Fingerprint`, not a Herdr handle, so producing one through `observe` belongs to `app_identity.rs`.
- The Result names `@ 61250ff` and `+450/-6` (the code commit) rather than the hand-in tip `bb3d256` (`+464/-7`); read as conventional (same as T-14 and T-12), no action.

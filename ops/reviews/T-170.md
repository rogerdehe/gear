## Findings

F1 [P1, blocking] Landing user corrections become notes with a false warning — `crates/gear-app/src/decision.rs:130` (`parse`). Apply `# Decisions` containing `- 2026-10-27 user: keep the promised export`: it stores kind `note`, loses the written date as its timestamp, and emits the unstructured warning. Design §7.1 explicitly gives this form without `why:`; listing `user` in KINDS does not bypass the general why requirement. This breaks the STABLE normal-use usability/correctness bar during the milestone's user landing review. Smallest fix: recognize the dated `user:` special form before the general structured-line/why check, storing its date and text with kind `user`, no why and no warning (about 15–20 local lines). Add an apply regression using exactly the documented form, reapply it, and assert one user entry with the written date and no warnings.

F2 [P1, blocking] Cancelling T-1 can record T-10's reason — `crates/gear-app/src/plan.rs:2274` (`why_naming`). Create T-1, then cancel it in a plan whose Decisions first says `2026-10-27 10:05 cut: T-10 is cut | why: ten reason` and then `2026-10-27 10:06 cut: T-1 is cut | why: one reason`. The automatic `T-1 cancelled` entry gets `ten reason` because substring matching treats T-1 as naming T-10. Multi-digit task numbers are normal use (including this voyage); this violates §7.4 and the STABLE correctness bar. Smallest fix: match complete task identifiers, with identifier boundaries on both sides rather than `contains`, in `why_naming` (about 10–15 lines). Add cancellation tests with T-10 preceding T-1, and with only T-10 present; assert `one reason` and `(no why written)` respectively, and reapply to assert the automatic cut is not duplicated.

F3 [P1, blocking] A successfully applied staff line can disappear from the log — `crates/gear-app/src/plan.rs:658` (`apply_queue`). Apply `hold heat reason=first reason`, then a distinct `hold heat reason=second reason` while heat is Held. The second apply succeeds, but the early continue skips decision recording, so only the first staff entry exists. The same applies to new park instructions targeting an already Parked lane. §7.4 promises an entry for a Staff line applied, including valid no-op target declarations; omitting a captain action violates the STABLE normal-use audit/usability bar. Smallest fix: record the staff decision on the already-target branch as well, after successful validation and before continuing (about 10–15 lines, preserving existing seat transition behavior). Add an apply test for two different hold lines and for replay of the second; assert two automatic entries, each once.

F4 [P1, blocking] Incremental apply orphans the voyage's decisions — `crates/gear-app/src/plan.rs:2174` (`voyage_of`). First apply a valid Milestone M1 and create a task on it; then apply only Decisions with a new starred structured line at the current base. The second apply succeeds but stores the line with voyage `""`, so `decisions_of("p", "M1")` returns no entry. Partial plans are supported (old milestones keep applying), and staff/verdict-only applies have the same defect. This breaks done clause (3), which needs `gear report voyage` to show that voyage's starred decisions, and the STABLE normal-use correctness bar. Smallest fix: pass the transaction/project to the resolver and fall back to the existing current departed voyage when the draft has no milestone block, using the same current-voyage rule as config logging (about 15–25 local lines). Add a regression for a real M1 departure followed by Decisions-only and Staff-only applies; assert entries belong to M1 and stay idempotent on replay.

F5 [P1, blocking] JSON apply silently drops the required fallback warning — `crates/gear-cli/src/main.rs:1184` (`run_plan`). After serializing ApplyResult (including its new decision warnings), the JSON branch replaces `warnings` with idle-lane warnings. Thus an unstructured decision is stored as a note but its required §7.2 warning is absent under `--json`; only text output combines the two sources. This violates the STABLE normal-use usability bar for the supported JSON interface and the acceptance requirement for the note warning. Smallest fix: combine result.warnings and idle-lane warnings once and use that list for both output branches (about 3–6 lines). Extend the existing CLI JSON warning test with an unstructured Decisions line and assert both warning types survive.

F6 [P2, logged] Arbitrary date text is accepted as a structured timestamp — `crates/gear-app/src/decision.rs:126` (`parse`). `yesterday scope: export added | why: user asked` is accepted as kind scope with at=`yesterday`; a leading star would survive too. §7.1 requires YYYY-MM-DD HH:MM and §7.2 otherwise requires a note without a star plus warning. Validate the date/time shape before accepting the ordinary structured form, with a parser/apply regression. Logged as malformed-input handling outside normal documented use; it does not block this STABLE review.

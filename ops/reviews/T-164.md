## Findings

F1 [P1, blocking] Valid RFC3339 fractional seconds reject the entire plan apply — `crates/gear-app/src/plan.rs:1644` (`parse_rfc3339`). Reproduce by applying `# Decisions` / `- tail: heat until=2026-10-26T18:00:00.123Z` with an existing heat lane: apply returns BAD_FORMAT, claiming the valid timestamp needs an RFC3339 time. The seconds field is parsed directly as `i64`, so timestamps routinely emitted by timestamp serializers are unusable. This breaks B6's RFC3339 input contract and the STABLE bar's normal-use usability requirement. Smallest fix: in `parse_rfc3339`, parse and validate the optional fractional seconds component, accepting both Z and offset forms; map to the existing seconds clock without ending the tail before the requested instant (round a nonzero fraction up if retaining second precision). About 15–25 lines plus regression cases for `.000Z`, nonzero fractions and an offset; check the second before/at the effective expiry.

F2 [P1, blocking] An ended task tail silently reactivates when the target task is reopened for rework — `crates/gear-app/src/plan.rs:1400` (`tail_is_over`; also `record_tail_decisions`). Reproduce with the actual app APIs: apply `tail: heat until=T-1`, start/submit T-1, settle pass so T-1 becomes Done, verify `lane_in_tail_at` is false, then settle the accepted attempt fail with a merge-conflict rework reason. T-1 becomes Ready and `lane_in_tail_at` becomes true again without a new tail decision. Thus a normal failed merge/rework silently restores suppression of refill/idle warnings after the tail already ended. This breaks B6's ending behavior and the STABLE bar's normal-operation stability requirement. Smallest fix: persist that this task-tail declaration has expired when its task first reaches its ending state, and consult that persisted end when reading the tail. Preserve the end across replay of the same retained Decisions line on subsequent applies; only a genuinely new declaration should reset it. Limit the change to the tail metadata/helpers and task completion integration as needed (roughly 25–40 lines), with a regression covering pass → Done → fail/reopen and a subsequent unrelated plan apply retaining the historical tail line.

F3 [P2, logged] Impossible calendar dates are accepted and silently normalized to another date — `crates/gear-app/src/plan.rs:1626` (`parse_rfc3339`). Applying `tail: heat until=2026-02-31T18:00:00Z` succeeds: the parser checks only day <= 31 before civil-date conversion. This can schedule expiry in March despite an invalid February input. Logged as malformed-input edge behavior outside normal use. Fix locally by validating day against the month's length and leap year before conversion, with February/non-leap and 30-day-month rejection cases (about 10 lines plus tests).

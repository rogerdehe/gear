## Set aside

- `--to` accepts any slice-1 kind, while design/07:21 reads as `--to <seat>` ⇒ kind INSTRUCTION. A captain `--kind question --to heat` stores an Open question in the lane's inbox, and the lane home page (design/13:31) lists only replies/instructions, so it can go unseen. Not covered by the packet, and the `send` doc comment only says `--to` is captain-only; raised as a question instead of reworked.
- A lane can send `--kind instruction` without `--to`; it lands in the captain's Open inbox. Design implies instructions are captain→lane via `--to`, but states no explicit ban, and the stored message is truthful and visible; same root as the question below.
- `needs_ack` is hardcoded false, including for Instruction (`mail.rs:165`). design/07:38 gives the flag meaning for instructions requiring action, but nothing reads it before the slice-2 ACK path; the writer documented the simplification. Question below.
- `--reply-to` does not check that the caller received M-x; design/07:22 only says "back to M-x's sender". Slice 2 can tighten when instruction/ack ownership checks land.
- A progress message without a task opens its own `<seat>:<seq>` thread instead of a per-task progress stream (design/07:24). Progress is Info, never a batch candidate, and the brief aggregates it per lane, so there is no slice-1 effect.
- A captain in HANDOVER is rejected by the allowed seat states, while design/07:23 says "stored as usual, doorbell paused". The `send` doc comment names Active/Standby/Retiring and the paused-doorbell rule needs the handover work (slice 2/4).
- The `--reply-to` generation-change annotation (design/07:22) is absent; seat generations do not move in the slice-1 scenarios.
- `gear_herdr::fake::FakeHerdr` is not used in `app_send.rs`; `send` takes a `Fingerprint` directly, so producing one through `observe`/FakeHerdr belongs to the identity tests (`app_identity.rs`), which cover that path.
- Red-first is not verifiable: the tests and the implementation share one feature commit. The tests assert rows read back from the store (`get_message`, `actionable_for`, `M-2` absence), so they are not vacuous.
- The Result's `Branch: … @ 05e3d2c` names the code commit rather than the hand-in tip `1f8dfe0`; read as conventional (same as T-12), no action.
- Empty bodies and non-existent `--task` ids are not validated; neither is required by the slice-1 packet.

## Questions for the captain

- Thread id: the packet and the `send` doc comment say `<task or seat>:<M-id>`, design/07:24 and the CLI example (`thread T-31:2`) say `<prefix>:<seq>`, and the implementation uses seq. Within T-14 it cannot be `<M-id>` (the store allocates the id inside `insert_message`; no thread update API). Should the doc comment/packet be amended to `<seq>`, or should a gear-store task add an insert-with-chosen-id path?
- Should `send` require (or force) `kind=Instruction` when `--to` is present, per design/07:21? As delivered, a captain question sent with `--to` is stored Open for a lane whose home page may never list it.
- Should `needs_ack` be true for Instruction in slice 1, or stay false until the slice-2 ACK path gives it a reader?

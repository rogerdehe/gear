## Findings
- [P1] An obsolete review permanently stops dispatch for the whole engine — `crates/gear-engine/src/lib.rs:144` (also the unconditional settlement at line 82). Reproduction on the merged result: submit T-1, submit its pass review through `mail::send`, cancel T-1 through `plan::apply`, restart, then tick with the lane idle and T-2 Ready. The tick returns `BAD_TRANSITION: task: cancelled -> done` before observation/dispatch, with no FakeHerdr calls or operations. Restart and tick again: the identical error recurs and T-2 still receives no attempt. `reviews_to_settle` keeps selecting T-1 because its attempt remains Submitted, and the propagated error prevents every later project from running too. Consume or exclude obsolete verdicts for cancelled/otherwise terminal tasks and prevent a single such settlement from aborting unrelated tick work. Add a cancellation-during-review regression with a restart and unrelated ready work.
- [P1] Automatic acceptance completes the current contract using an older-contract attempt — `crates/gear-app/src/tasks.rs:406`, `crates/gear-app/src/tasks.rs:419`. Reproduction: submit T-1 under contract v1; use `plan::apply` to change its goal/acceptance to v2; submit a pass review on attempt 1; restart and tick. The task becomes Done at contract_version=2, the attempt becomes Accepted at adopted_version=1, and a merge is queued for the v1 candidate. On the same fixture, the existing `tasks::settle` with a v1 pass correctly returns `BAD_FORMAT: a pass needs the task's current contract 2, not 1`. The new function bypasses that guard and records v1 as the acceptance verdict, violating `docs/design/06-tasks.md`'s rule that an old-version result cannot complete a new contract. Preserve the version check before accepting or queuing the merge; stale reviews need a version-safe rework/review path that also leaves unrelated dispatch working.
- [P1] Repeated review submissions leave the captain an action item after settlement — `crates/gear-app/src/tasks.rs:530`. The `.find(...)` resolves only one matching message. Reproduction through public `mail::send`: send the identical pass review twice for the same task/attempt with distinct request IDs, then restart and tick twice. T-2's existing review submission API permits this: it preserves one stored verdict but creates two inbox messages. Settlement produces one Accepted attempt and one merge, but leaves messages `(Review, Resolved)`, `(Review, Open)`, `(Reply, Info)`. The next tick settles nothing, so the Open review remains indefinitely. The built board reports `captain_waiting.count=1` although T-1 is Done. Resolve all matching review action items when settling, and handle later duplicate submissions without recreating captain work. Cover a duplicate before settlement and a duplicate after a restart/settlement, while retaining the single merge and information line.

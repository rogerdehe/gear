## Findings
- [P2] `cmd_home` opens the store and Herdr **before** `run_show` validates the target, so an unsupported `--show` target no longer always fails with `BadFormat` naming it: it fails with whatever the environment is missing. Verified on the reviewed commit: with `GEAR_DB` unset `gear --show queue` → `ERROR NO_TARGET: GEAR_DB is not set`, where on dev the same command said `ERROR BAD_FORMAT: --show is not supported in slice 1` (`reject_slice2(show, …)` was the first statement of `cmd_home`); with `GEAR_DB` set and no socket `gear --show queue` → `ERROR NOT_REGISTERED: cannot reach herdr at /Users/roger/.config/herdr/herdr.sock`. `--diff`/`--all` are unaffected — `reject_slice2` still runs first. Why it matters: rejecting an argument must not depend on unrelated infrastructure, and a lane (or the user in their own shell, design/13 ops commands) chasing `cannot reach herdr` for `gear --show queue` is sent to fix the wrong thing; exit code is 1 either way, so only the code/detail in the message is wrong — hence P2, not P1 (with a healthy store + socket the covered behaviour is correct, and all four new tests pass). Fix inside the Allowed changes: reject the non-task target in `cmd_home` before `open_store()`/`open_herdr()`, keeping the single error message in one place, e.g. build the error in a small `fn unsupported_target(target: &str) -> GearError` used by both `cmd_home` and `run_show` (or keep `reject_slice2`'s old three-argument shape and pass `show` again). The unit tests call `run_show` directly, which is why this ordering in the glue was not caught — `show_other_target_is_bad_format` stays as it is, the fix is in `cmd_home`'s dispatch. — `crates/gear-cli/src/main.rs:271-272` (the `open_store()` / `open_herdr()` calls that precede `run_show`, which only validates the target at `main.rs:306`)
- [P3] `--help` still advertises `--show <ID/thread/queue/draft>` while only a task id is supported, so `gear --show queue` fails after `gear --help` said it was a valid target. — `crates/gear-cli/src/main.rs:20` — narrowing that doc comment is outside this packet's Allowed changes (only `cmd_home` dispatch, `run_show` and its tests); raised as a question below, not a rework item.
- [P3] `is_task_id` is a verbatim copy of `gear_app::draft::is_task_id`. — `crates/gear-cli/src/main.rs:325-330` vs `crates/gear-app/src/draft.rs:319-324` — two copies of the task-id grammar will drift if it ever widens (e.g. suffixed ids); sharing it would need a `pub` item, i.e. a captain decision, not a lane fix.

## Set aside
- `run_show` printing through `println!` instead of an injected `&mut dyn Write` (T-30's `run_home` takes one) — the packet asks for "everything injected", which `store`/`env`/`herdr` satisfy for testability; `println!` matches `cmd_send`/`cmd_reply`/`cmd_plan` in the same file, and only `run_home` needs the writer because a failed write must record no view. At most a consistency nit, not a rework item.
- The extra blank line at the end of the output (the rendered text ends with `\n` and `println!` adds one) — `run_home` does exactly the same with `writeln!`; pre-existing convention, not introduced here.
- No CLI test that an unregistered seat is refused by `--show` — `run_show` delegates to `require_seat` unchanged, and every rule of that function is covered by `crates/gear-app/tests/app_identity.rs`; the CLI layer adds no identity logic of its own.
- `is_task_id` accepts `T-007`, `T-000` and arbitrarily long numbers — the store then answers `NoTarget` ("no task T-007 in project p"); harmless, and `draft.rs` behaves the same.
- Whether `--show` should later record a view record (evidence that the packet was read) — out of scope here (design/13 ties the view record to the home page); a captain/product decision, not a finding.

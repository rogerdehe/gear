## Findings

- [P3] A lane named `captain` collides with the captain's seat id and the user gets a raw SQLite message — `crates/gear-app/src/admin.rs:82-83` — `config::validate` accepts `name = "captain"` (it matches `[a-z][a-z0-9-]*` and is unique among lanes), so `insert_seat` for `<project>:captain` fails on the primary key and the error detail is `UNIQUE constraint failed: seats.id`, naming neither the lane nor the cause. Not blocking: nothing is written (I checked — the project row is absent afterwards, the transaction rolls back), the config is refused, and the user can fix it; `captain` is the reserved seat name in 17 §2's naming table. The rule belongs in `config::validate` (add "a lane may not be named `captain`" to its documented rule list, T-7's file), which this packet may not touch — so I list it rather than require it of the writer.
- [P3] `config_version: 1` is written twice — `crates/gear-app/src/admin.rs:72` (the row) and `crates/gear-app/src/admin.rs:103` (the returned `InitResult`) — as two independent literals. A one-line bump could leave the row and the reported value disagreeing, and nothing would notice. A private `const CONFIG_VERSION: i64 = 1;` (or building the result from the row's value) ties them.

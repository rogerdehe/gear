## Set aside

- **An orphaned worktree when `begin_onboard` fails** — `worktree_create` runs first (doc step 3), so a
  store error at step 4 leaves `home/<lane>` checked out while the seat is still Queued; the next tick
  retries, is refused `worktree_exists`, and parks the seat in NeedsCheck. That is the order the doc comment
  prescribes, the fake's `Inject::Refuse { code: "worktree_exists" }` in the contract exists precisely for
  that refusal, and the outcome is a parked seat with a clear reason — no wrong write, no lost work.
- **A parked lane never re-onboards itself** — `onboard_queued` only picks Queued seats, so NeedsCheck /
  Missing are left to a human even though `begin_onboard` would accept them. Exactly what the packet's
  "never retried automatically" asks for; the restart path belongs to the task that owns handover/restart.
- **`lane.kind` from the config combined with the profile looked up by `seat.profile`** — a lane
  configured with `kind != profile` would start the config's kind with the other kind's args. Every shipped
  config and design/01's example sets the two equal, and the doc comment prescribes exactly this split, so
  this is a gap in config validation (`crates/gear-app/src/config.rs:237` validates name/duty/owns only),
  not an engine defect.
- **One Herdr session, every project** — `gear run` connects a single socket, but `onboard_queued` walks all
  projects and `begin_onboard` records `project.herdr_session` in the binding. A lane of a project bound to
  another session would get a binding naming a session that is not where the agent lives. Pre-existing to
  `tick`'s single-session model (observe and dispatch assume it too) and out of scope for this packet.
- **The captain and temps are not onboarded** — the doc comment and the contract test both say so, and the
  test pins that the captain stays Queued. Correct for this cut.
- **The M-9 merge resolution** (the writer's note) — verified above; `gear-model`'s `(Queued, Starting)` /
  `(Queued, NeedsCheck)` edges are already on `dev`, so the branch depends on nothing unmerged.

## P3 (listed, never blocking)

- `crates/gear-engine/src/onboard.rs:2` — the module doc still says "This module only *plans* the steps
  (pure); executing them through Herdr is a later task", which is now false: the module drives
  `worktree_create`, `pane_run` and `agent_start`. The packet's Allowed changes line names only
  "`onboard_queued` and private helpers", so see the question below before touching it.
- `crates/gear-engine/src/onboard.rs:271` — `step_failure`'s `Outcome::Ok(_)` arm formats `"{step}: succeeded"`.
  Unreachable today (every call site is a non-`Ok` arm), but if a refactor ever passes an `Ok` through, a
  seat gets parked in NeedsCheck with the reason "worktree_create: succeeded" — actively misleading for the
  human triaging it. `unreachable!()` would turn that into a loud failure.
- `crates/gear-engine/src/onboard.rs:192` — `.ok_or_else(|| "a lane gets a worktree, but the plan has none")`
  cannot fire: `plan_onboard` gives `Some(WorktreeStep)` to every `SeatRole::Lane`. A harmless guard; fine
  to keep.
- `crates/gear-engine/src/onboard.rs:186` — the generation is derived twice from `seat.generation + 1` (once
  for `GEAR_CTX` in the env line, once inside `begin_onboard`). They cannot differ inside one tick (single
  writer, and `begin_onboard` re-reads the seat), but if a future caller ever onboards a seat it has just
  mutated, the agent's `GEAR_CTX` would name a generation the store rejects as stale.
- `crates/gear-cli/src/main.rs:715` — `engine_cfg(&db.to_string_lossy())` looked like it could hand an
  agent a different database than the engine opened. Traced and it cannot: `open_store()` reads the same
  variable with `std::env::var()` (`main.rs:215`), which fails first on a non-UTF-8 `GEAR_DB`, so a lossy
  path never reaches `engine_cfg`. Noted only because the next reader will wonder the same thing.
- The Result repeats the `Files:` and `Verification:` headings four and seven times;
  `ops/CONVENTIONS.md` → "Result format" wants one heading with one line each.
- Progress notes have two entries numbered "2." and none numbered "1."; the second one covers the unit
  tests that the first already attributes to `onboard.rs`. Wording only.

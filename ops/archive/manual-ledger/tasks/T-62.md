- 1. `onboard_queued` is implemented exactly as its doc comment says. Per project it reads the config (`config_toml` → `gear_app::config::parse`) for the repo, the integration branch and every lane's kind, and takes the profile from `cfg.profiles[seat.profile]`. Per **Queued Lane** seat it then: plans (`plan_onboard` with `generation = seat.generation + 1`, `cfg.db_path`, no resume), opens the worktree (`worktree_create` → the root pane), binds the seat (`gear_app::seats::begin_onboard` → a pending binding), exports the context (`pane_run` with the env line) and starts the agent (`agent_start`), and closes with `gear_app::seats::finish_onboard` (the binding and the seat become Active). A step that is not `Ok` parks the seat in NeedsCheck with a reason naming the step; it is never retried automatically. Only lanes are onboarded — the captain and the temps keep their pane. The seats that became Active are returned.
- 2. `tick` calls `onboard_queued` before observing (the module doc comment lists the new step), and `cmd_run` passes `GEAR_DB` as `EngineCfg.db_path`, so an onboarded agent gets the same database as the engine. `engine_cfg` takes the path as an argument (the T-56 unit test is updated).

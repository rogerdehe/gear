## First item of M4 (user, 2026-10-26): a seat follows the work (B02-01)

A trial project had a lane bound to a repo whose work was a dozen lines; the voyage ran 30-40 hours, that lane stood idle 99% of the time and held its slot for good. M4 must fix it:
- a task stores its own repo (and base, gate) when it is created, so rebinding a lane never moves an old task's review or merge target (today a task has no repo column: it is read from its lane's config);
- the lane quota counts active seats, not configured or retired ones;
- a supported rebind: `- rebind <lane> repo=<name> owns=[…]` (or retire + register) that waits for the lane's open tasks to land, previews the change and keeps history;
- the captain's guide: a lane whose repo has no ready work is rebound at once, never left idle.

## Added 2026-10-26 (user, M4 alignment)

- Hand-in retrospective: a lane's or reviewer's hand-in carries an optional short report of friction on the way (a permission it lacked and worked around, a test or build that took far too long, an unclear contract, a missing tool, a step that cost much time). A smooth task reports nothing. The engine adds its own facts to each task (wall time, gate time, attempts, tokens), so a slow task is visible even when the agent says nothing. The captain reads unread reports when it has no other work (an idle doorbell lists them), and the voyage report has a "friction found" section; each one is fixed, logged as a lesson, or judged not worth it.
- Session at hand-in: besides new session / keep / resume on rework, the captain can have a kept session compacted before the next related task (Claude, Codex, pi and OpenCode all have one). The compact command is part of the agent profile as data, sent through Herdr like any prompt; a kind without one gets a new session instead.
- One seat model for lanes and reviewers (user, 2026-10-26): a reviewer seat is a seat like a lane's, not a pane started and closed per review. Every task starts with a session choice from the agent profile: new (`/new`, `/clear`), keep, keep after compact, or resume (rework, re-review). A review always takes new or resume, so it stays independent of the work it judges. Seats stay warm while there is work and are released after an idle spell, so the quota counts active seats (B02-01); a quota fallback or kind change is the in-place kind change. What stays different is only the role: a lane owns a worktree and branch, a reviewer reads the candidate.
  Resume is the CLI's own resume of the task's recorded session, in the same pane: the in-pane command when the CLI takes a session id there, else exit and restart with the profile's `resume_args` (what onboard.rs does today). Never an interactive picker the engine must drive.
  The session choice is a fixed rule the engine applies, never a captain call at dispatch: a review is always new, a re-review or rework resumes, a lane's next task is new unless its plan block says it continues an earlier task (then keep, compacted). The only difference between lanes and reviewers is the idle release time, a config value per role: a reviewer seat is released after a short idle spell, a lane keeps its pane, worktree and build cache.

## M4.1: fixes from real use (user, 2026-10-28)

Problems found after M4's landing and in other projects' first voyages are collected here and fixed together in one short voyage, not one by one.

- **Two projects, two voyages at once (user, 2026-10-28: this will be the normal case).** One engine and one store serve every project, and a tick walks all of them; a step that fails for one project returns from the whole tick (`?` in engine::tick), so one project's bad config or store row stops the other's voyage. Each project's steps must fail alone (its own item, the others go on). Also: an engine upgrade restarts every project's engine at once, and builds of both projects share the machine (machine watch).
- One store per Herdr session is the default since v0.4.5 (a project from another session was registered into orch's store and its lanes started in orch, 2026-10-28). Left for M5: `init` refuses a project whose `herdr_session` is not the session of the store's engine, and the engine never onboards a project of another session (today only the default path prevents it; an explicit `GEAR_DB` still can).
- Without `[temps]` a hand-in waits in Submitted for a captain `pass`, and no code was found that rings the captain for it: the captain must be told a hand-in waits for its verdict.
- Kickoff skeleton: with one model per role, `on_quota = "fallback"` is refused at init ("a quota stop would park for 5h"); the skeleton writes `wait` when a role has a single model.
- Done in v0.4.6 (merged 2026-10-28): the board's colours and the lane column width.
- **A dependency counts when it is merged, not when it passed (M4 friction F-76).** T-215 (deps T-171) was dispatched after T-171 passed but before its merge reached dev, so the code it had to change was only on mast/t171: the lane based its work on that branch and merged twice. Dispatch a task only when each dep is on the integration branch.
- **A lane's next branch starts from its previous, unmerged task (M4 friction F-75).** A home worktree still on the last task's branch cuts the next task branch from that head; the candidate then carries the other task's commits and its merge waits for it, and moving it would need a force push. The packet tells the lane to start the new branch from origin/dev (`git switch -c <lane>/t<n> origin/dev`). (In M4 as T-222.) The same seam leaks uncommitted edits: mast's worktree kept stray edits in five engine files from T-220 into T-222 (friction F-90; the captain stashed them). Before a new task's packet, the engine checks the home worktree is clean and, if not, tells the lane to commit to the old branch or stash with a name, never to carry the edits over.
- **No idle items once a voyage is ready to land (M4 11:40).** After the last task merged, "lane <x> is IDLE" came back for every lane every few minutes, each time it was resolved. While a voyage waits for its landing, idle and run-dry items stay quiet.
- A lane with no task that stays busy blocks its next delivery: the engine delivers only to an idle agent (§10.2), and Flash lanes keep tidying instead of ending their turn (M4 21:12 and 23:53, keel, ~10 min each). After 5 min busy with no task and ready work waiting, the engine interrupts the turn (esc) and delivers.
- Moving a running task to another lane in the plan leaves its open attempt on the old seat (M4 20:27: T-160 keel → hull; the captain abandoned attempt 1 in the store). The plan should abandon it (the old lane told) and the new lane start a new attempt.
- A merge loses a push race to the captain's plan commits on the same branch (M4 03:40, T-187: three retries, then failed until a hand remerge). The captain's plan commits must not fail a merge.
- **Rework budgets are sized for one fix (M4 friction, ~9 reports).** A rework round of 13-25 min is given for a review with three to nine blocking findings; the overrun question then fires on nearly every rework. Size the rework budget from the blocking findings it carries.
- Cut from M4 (station M-2503/M-2572): T-180 admin stop waits for merges (T-121), T-183 names (T-134 F2/F3), T-185 three merge.rs tests over 10 s. T-182 (a push race does not re-run the gate) goes with the push-race item above. Their goals are in gear/voyages/M4.md.
- T-176's rest: the engine reconnects when its Herdr server restarts (following the project's own session is done by v0.4.5's store per session).
- One word for a voyage: "voyage" and "milestone" name the same thing (files in gear/voyages/, headers `# Milestone`). Say voyage everywhere a person reads it; the id stays M1, M2, … (user, 2026-10-28).

## For M5 (user, 2026-10-26; regrouped 2026-10-28)
- **A captain that only relays (user, 2026-10-27, discuss at M5 kickoff).** Lanes think little so the captain must think: design, decide, write exact contracts, judge findings. Seen in another GEAR project: a captain that only splits messages into tasks, passes them on and acknowledges reports, deciding nothing. M5 settles how GEAR prevents and detects this.
- **A light procedure for small tasks (user, 2026-10-27, must).** Small, low-risk work must not go through the full loop (task, hand-in, review, rework, re-review). Example: adding two log lines to see a server error took that whole loop. Size the procedure to the work, decided from M4's per-round token and time data.
- Review per task, not only per project (a captain on another project, 2026-10-28): today `[temps]` switches review on for every hand-in or for none. A task that the compiler and its accept numbers fully check (deletions, a comment cut) needs no reviewer; one that changes test logic does. Part of the light procedure for small tasks: the plan names the tasks that skip review, and the captain settles them on their accept evidence.
- **Machine health watch (user, 2026-10-26 22:21: a long-term feature; "the ship must not break without us knowing").** M4 evidence: load 46 then 159 on 10 cores; two `find /` scans from an aborted lane turn ran 14+ min; four parallel builds plus another project's Go suite; fseventsd at 100% CPU and 3-4 GB for days; the user felt the lag before GEAR did. The engine samples every minute, as facts, not screen text:
  - load average vs cores, memory pressure, swap, free disk on the state and worktree volumes;
  - the processes under each seat's pane (by its shell pid): long-running children of a lane whose turn already ended (orphans, e.g. `find /`), builds and test runs per seat, and the top processes outside GEAR (named, never touched);
  - thresholds (kickoff-configurable): a captain item and a board line when load stays above 2× cores for 5 min, memory pressure is critical, disk is low, or an orphan of a lane runs over 10 min.
  - Actions GEAR may take on its own seats only: end an orphan of a finished lane turn; hold new dispatches while the machine is critical (no build lock: running work goes on). Never touch processes outside GEAR; name them to the captain, who tells the user.
  - Recorded in the voyage report: time spent above the thresholds and what caused it.
  - One shared compile cache for all worktrees (e.g. sccache), so lanes and reviewers do not each rebuild every dependency: M4 had eight `target/` dirs (~80 GB) and six full workspace builds at once (load 74 at two-to-four jobs each). Not a shared target dir: its build lock would serialize the lanes.
- **Concurrent suites can run the machine out of processes (M4 friction F-74, 07:20).** With several full suites at once, each forking git fixtures per test, a reviewer's run hit fork failures (per-user limit 2,666) and left an orphaned fixture wait. The M5 machine watch counts processes against `kern.maxprocperuid` and the engine holds a new suite (lane, reviewer or gate) while the count is high.
- **Builds are the largest friction (M4 friction reports, 05:30: ~35 of 58).** Lane and reviewer builds of 100-800 s under 4 lanes plus up to 4 reviewers, each in its own worktree target; a reviewer's fresh worktree builds cold (9 min). sccache hit 15%: of 4,618 calls, 2,846 were non-cacheable as `incremental` (our own crates), and with no `SCCACHE_BASEDIRS` two worktrees never share an entry. M5 measures the options against the 300 s red line: basedirs for the worktree root, incremental off for reviewer and merge builds only, a warm reviewer target reused across reviews, fewer concurrent full suites.
- Release lanes during a long wait (user, 2026-10-26 20:06; not urgent, saves resources): a kickoff option, asked once (`on_wait = "keep" | "release"`). With `release`, a lane parked on a quota stop (or another long declared wait) is released (agent exits, pane closed, worktree and session kept) and brought back at the reset: same worktree, its session resumed. Default `keep`.
- Stages of a long voyage on the board: a long voyage is cut into stations, each a release that runs end to end (M4 does this by hand as v0.4.0 … v0.4.4); the board shows the stations, which is reached, and what the next one needs. Design it from what M4's stages taught, not before.
- OpenCode and Codex daemon identity proof (T-123), moved from M4 by the user.
- Cut from M4: T-181 acknowledged instructions and the config drift warning (goal in gear/voyages/M4.md).
- A view across Herdr sessions (several stores) and shared quota scheduling, only when it is needed.

- Done in M4: a hand-in window for a moving dev (T-221) and the next branch from origin/dev (T-222).

# T-438 — a reviewer's branch must be on the project's remote before its verdict counts

A reviewer of another project pushed `review/t<n>` to the second remote its
worktree also has, checked that one, handed in, and the merge then could not
find `origin/<review branch>` (T-265 earlier, T-375 at 04:09Z); the captain
pushed and remerged by hand. Now the packet names the exact push, and the
verdict is refused before it is stored when the branch is not on the project's
remote.

## What changed

- **`crates/gear-model/src/branch.rs`** — `review_branch(template, project,
  lane, task)`: the one expansion of `[conventions].review_branch` that the
  engine's packet and the app's check both read (it was a private copy in
  `review.rs`), with its unit test.
- **`crates/gear-engine/src/review.rs`** — the review packet's last instruction
  is now "… and push it with exactly `git push {remote} HEAD:refs/heads/{branch}`
  (the candidate stays untouched; GEAR refuses the verdict until
  `{remote}/{branch}` holds your commit)", and the module's private
  `review_branch` moved to `gear_model::branch`. New test
  `the_review_packet_names_the_exact_push_of_the_review_branch`: the default
  remote and review branch, and a project's own `remote` and
  `review_branch = "b/review/t{n}"`.
- **`crates/gear-app/src/mail.rs`** — before the transaction, a `gear send
  --kind review` that carries a `--verdict` from a Temp seat, is not a
  direction check and brought the hand-in gate is checked with
  `crate::base::require_pushed`: the current directory as the worktree, the
  project's `[conventions].remote`, the review branch from the project's
  template for the task's project, lane and task, and the worktree's
  `git rev-parse HEAD` as the candidate. The refusal is `base.rs`'s, naming
  `` `git push {remote} {branch}` ``. Nothing is stored on a refusal. A HEAD
  git cannot read is a refusal, never an unchecked pass.
- **`crates/gear-cli/src/main.rs`** — `cmd_send` builds the hand-in gate for a
  review that carries a verdict too (one line, moved into `hand_in_gate`), so
  the app's check sees a gate in normal use. The gate's presence is what marks
  a real hand-in, exactly as it does for a result: a review send in the tests
  keeps `base: None` and is not gated.

## Gate signal (captain's decision M-6368)

The contract's "as the result path does for a lane" left open what marks a real
hand-in for a review: the result path's `require_pushed` sits inside
`if let Some(gate) = &args.base`, and a review send carried no gate at all, so
an unconditional check would rewrite the fixtures of about ten existing
review-send tests across gear-app, gear-cli and gear-engine. I asked (question
`r-1793333744156-91462`, M-6367); the captain chose the gate, and allowed the
one line in `cmd_send`. A direction check (M-6371) proposed dropping the CLI
change and gating on `!direction` only — that leaves the check dead in normal
use, which is the failure this task fixes; answered in M-6374.

## Tests

- `crates/gear-app/tests/it/base_gate.rs`, against a real temporary repository
  and a bare origin:
  - `a_review_pushed_to_another_remote_is_refused` — the review branch is
    pushed to a second bare remote the worktree also has: refused with
    `cannot fetch origin/review/t1` and `` `git push origin review/t1` ``,
    no verdict record, nothing in the captain's inbox;
  - `a_review_pushed_to_the_projects_remote_is_taken` — the same verdict after
    `git push origin HEAD:refs/heads/review/t1` is stored;
  - `a_review_branch_behind_the_reviewers_head_is_refused` — the check is the
    reviewer's own commit, not an older tip of its branch;
  - `a_direction_check_is_not_checked_against_a_review_branch` — a direction
    result from an unpushed worktree still goes through.
- `crates/gear-cli/src/main.rs`,
  `a_review_verdict_builds_the_hand_in_gate` — `cmd_send`'s gate for Result
  and Review, and none for a direction check or a progress answer.

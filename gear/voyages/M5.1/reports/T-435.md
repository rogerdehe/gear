# T-435 — report

The overlap check no longer re-diffs a pair of commits it has already diffed.
`fn changed` keeps its results in a process-wide cache keyed by the repo path
and the two full commit ids; the scan reads each pair once, however often it
runs, and a new commit on a task branch is the only pair read again.

## What changed

`crates/gear-engine/src/parallel.rs` only:

- `static DIFFS: LazyLock<Mutex<HashMap<(PathBuf, String, String), BTreeSet<String>>>>`
  (std only) — the diff of each `(repo, from, to)` pair, for the life of the
  process. The scan's callers pass the full commit ids `fn revision` returns,
  which never change for a key, so a cached result is always right.
- `const DIFFS_MAX: usize = 4096;` — the map is cleared when it holds that
  many entries, so a long-running engine does not grow without bound.
- `#[cfg(test)] static DIFF_MISSES: AtomicUsize` — incremented on a miss (a
  real `git diff`), so the test counts git reads.
- `fn changed` asks the cache first and returns the cached set on a hit;
  otherwise it runs the same `git diff` it always ran, records the result, and
  returns it. An error from git returns before the insert: nothing is cached
  for a failed read.
- A poisoned or unavailable lock is a miss, never a failure: the diff still
  runs and the result is still right, so the cache cannot break the scan.

Nothing else changed: `fn scan`, the pair/integration findings, the store
writes and the module's other callers are untouched.

## Tests

`parallel::tests` (the crate keeps its unit tests in `src`, T-412 scratch
directories):

- `a_pair_of_commits_is_diffed_once_and_a_new_commit_is_diffed_again` (new) —
  a real temporary git repository (`dev` plus `heat/t1` changing `src/lib.rs`
  and `steady/t2` changing `other.rs`) and a project with one task per lane.
  The first scan reads 4 diffs (two task branches, each against the
  integration branch and back for the overlap line); a scan at the next
  ten-minute period reads none; a new commit on `heat/t1` reads exactly that
  branch's two pairs again; the scan after that reads none, and `DIFFS` holds
  the old pair and both directions of the new one.

Every existing `parallel_contract` test is unchanged and passes. The deliverable
bar: a cache hit or miss is invisible to the scan's result — a repeated scan
finds the same findings, and `git_read_failure_does_not_claim_that_existing_overlap_went_away`
still exercises the error path (an error is not cached, so it is not counted).

## Out of scope (noticed, not changed)

- `fn revision` and `fn ancestor` run per task, per scan, unchanged: the packet
  names `fn changed` only, and the report's 41.7 s was the diff.
- The cache survives a failed scan and a repo that is renamed or removed: the
  keys are the repo paths and commit ids the scan is given, which is what the
  packet specifies; entries for a gone repo age out only at the 4096 clear.
- `parallel_contract::a_landed_task_is_not_an_open_change_and_open_tasks_still_pair`
  is reported `LEAK` by nextest in this run. It is an integration test this
  task does not touch, and this change opens no file, directory or process of
  its own (the cache and the counter are memory); I did not run the base to
  show the same line, so it is logged, not claimed as fixed.

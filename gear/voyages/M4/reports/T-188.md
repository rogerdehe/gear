# T-188 — Overlap notices stop ringing the captain for nothing

Scope: T-188 — an overlap between a task and the integration branch is an
information line (the board and `gear queue` read it), never a captain item;
an overlap between two open tasks rings once per pair and only when the two
tasks share a file that is not a test file.

Branch: keel/t188 (code @ the hand-in commit; origin/dev merged before the
final verification)

## What was built

`crates/gear-engine/src/parallel.rs` (the overlap scan, T-51):

- **A task against the integration branch is no longer a captain item.** The
  scan still finds the overlap, but it writes it as an information line in
  the project's meta — `parallel:<project>[:<repo>]:integration:<task>` with
  `{"task":…,"integration":…,"files":[…]}` — and opens no message. The lane
  merges dev in and the merge gate catches a conflict, so the captain has
  nothing to answer (M4: six `parallel:` items in the first hour, each
  answered "known").
  - The board and `gear queue` read that meta key. The lines of a child repo
    live under their own prefix (`parallel:<project>:<repo>`), like the rest
    of that repo's scan state.
  - An information line that is gone (the overlap ended) is cleared, so the
    board shows nothing for it.
  - The items an older engine opened for such an overlap close with their
    own reason ("an overlap with the integration branch is an information
    line now"), and the legacy list of overlaps is read as it was.
- **A test file is not a conflict.** A shared path under `tests/` or ending
  `_test.rs`/`_contract.rs` does not count: two tasks that touch only tests
  do not ring the captain, and an overlap with the integration branch lists
  only the files that count. The file set the scan remembers is the filtered
  one, so a change in the test files alone does not ring again.
- **A pair of tasks rings once.** Unchanged: the scan remembers the pair and
  its file set, opens one item per pair, and closes it when the overlap is
  gone.

## The tests

`crates/gear-engine/tests/it/parallel_contract.rs`:

- `a_task_that_overlaps_the_integration_branch_makes_no_captain_item` — the
  overlap with the integration branch opens no item and nothing at all lands
  in the captain's inbox; the information line is there, and it is cleared
  when the overlap ends.
- `two_tasks_that_share_only_test_files_make_no_item` — a shared
  `tests/lib_test.rs` and a shared `src/thing_contract.rs` make no item.
- `two_tasks_that_share_a_source_file_make_one_item_once` — a shared
  `src/lib.rs` makes one item, and the next scan opens none.
- The two tests that expected an item for an overlap with the integration
  branch (`integration_changes_since_the_branch_base_count_too` and
  `the_scan_of_a_child_repo_reads_its_own_integration_branch`) now expect the
  information line: the child's own integration branch is read as before, and
  the line names the repo.

## F2 — a pair of tasks rings once, for its lifetime

`crates/gear-engine/src/parallel.rs`: the scan deduplicated on the serialized
shared file set, so a pair that shared one more file rang the captain again —
after the captain had already answered "known". The scan now deduplicates on a
**persistent pair-notified marker** (`<prefix>:pair:<pair>:notified`):

- the marker is written when the pair's item is opened, and it survives the
  overlap clearing, so a pair that comes back does not ring again;
- an older engine kept the item's id instead of a marker: a pair that already
  has an item counts as notified too (the upgrade does not duplicate an
  alert);
- the stored file set is kept current on every scan, and the open item's text
  follows it, so the captain's item stays true without a second notification;
- another pair rings once of its own.

## F3 — the test-only-overlap regression is split

`two_tasks_that_share_only_test_files_make_no_item` became two tests —
`two_tasks_that_share_only_a_test_file_make_no_item` and
`two_tasks_that_share_only_a_contract_file_make_no_item` — so nextest
schedules them independently and neither pays for the other's fixture.

## The tests that changed with the rule

- `overlapping_branches_name_both_tasks_and_the_shared_file_once` — one item
  for the pair's lifetime: another shared file does not ring again, the
  overlap may clear and come back without a second item, and another pair
  rings once of its own.
- `cleared_overlaps_resolve_and_the_pair_does_not_ring_again` (was
  `cleared_overlaps_resolve_and_can_report_a_later_recurrence`) — the pair
  does not ring again when the overlap comes back.
- `a_pair_rings_once_through_the_engine` (was
  `fresh_file_sets_get_fresh_ids_and_ring_through_the_engine`) — the captain
  is prompted once for the pair, and the engine's ticks report nothing more.

# T-221 — A hand-in is not refused for a dev that moved during its suite (contract v2)

Scope: T-221 — in `crates/gear-app/src/base.rs` the hand-in gate accepts a
candidate that is only just behind the current `origin/<integration>` tip, and
`crates/gear-app/src/config.rs` holds the new setting
`timing.handin_base_window_min` (default 30). The call site in
`crates/gear-app/src/mail.rs` carries the setting to the gate.

Branch: keel/t221 (code @ the hand-in commit; origin/dev merged before the
final verification)

## The bug

The hand-in gate refused a candidate that did not contain the current
`origin/<integration>` tip. A lane that merges and runs its suite raced a
`dev` that lands a merge every ten minutes: hull's T-175 was refused twice
(M4 08:40) because `dev` advanced during its 12-minute merge and suite, and a
lane could race `dev` forever (friction ~12 reports).

The rule was written for a candidate that was *stale*: it was based on a base
that had moved on long before the lane started. The rule could not tell that
case from the case the friction reports are about: a base that moved *while the
lane worked*.

## The fix

- `crates/gear-app/src/base.rs` — `require_current_base` takes the window in
  minutes. When the tip is not an ancestor of the candidate, the candidate is
  accepted if
  - (a) a commit of `origin/<integration>` that is at most
    `handin_base_window_min` minutes old (committer time) is an ancestor of
    the candidate — `based_on_recent_base` asks git for the commits of the
    branch in the window (`git log --format=%H %ct --since=@<epoch>`) and
    checks each of them with `git merge-base --is-ancestor`; and
  - (b) the tip merges into the candidate without a conflict —
    `merges_clean` runs `git merge-tree --write-tree origin/<integration>
    <candidate>`, whose exit code is 0 for a clean merge and 1 for a conflict.

  Otherwise the hand-in is refused as before, with the same message. A window
  of `0` is the old rule: only a candidate that contains the current tip is
  accepted. `git merge-tree --write-tree` needs git 2.38 or later; a git that
  cannot answer is an error, never a pass.
- `crates/gear-app/src/config.rs` — `timing.handin_base_window_min` (default
  30) in the `Timing` section. `0` is a valid setting: the strict rule.
- `crates/gear-app/src/mail.rs` — the hand-in call site passes the window the
  gate carries (`BaseGate.window_min`, filled by `gate_for` from the project's
  config).
- Nothing else changes: the gate still refuses a candidate that is behind and
  old, a candidate that conflicts with the tip, a candidate that is not pushed
  and a candidate that a rework does not build on. The merge gate is not
  touched: it merges the approved candidate onto the current tip with
  `--no-ff` and runs the project's gate (the full suite) on the merged result,
  so a candidate that was accepted for a recent base is still tested on the
  merged tree.

## The tests

`crates/gear-app/tests/it/base_gate.rs` (the gate's own contract):

- `a_candidate_behind_a_recent_base_that_merges_clean_is_accepted` — `dev`
  has a commit that is ten minutes old and a tip that landed meanwhile; the
  candidate is based on the ten-minute-old commit and merges cleanly into the
  tip: accepted. The test also asserts that the tip is *not* in the candidate
  (`git merge-base --is-ancestor`), so the window is what accepts it.
- `a_candidate_behind_the_integration_branch_is_refused` — the candidate is
  based on a forty-minute-old commit of `dev` only: refused, with the old
  message.
- `a_recent_base_with_a_conflicting_change_is_refused` — the candidate is
  based on the ten-minute-old commit and changes the same file as the tip:
  refused (the test asserts that the candidate does carry the ten-minute-old
  commit, so the refusal is the conflict and not an old base).
- `a_candidate_that_contains_the_integration_branch_is_accepted` — a current
  candidate is accepted, as before.
- `a_candidate_behind_the_integration_branch_is_refused_without_a_window` —
  the window is a setting: with `0` a candidate that is behind the tip is
  refused.

The fixtures place commits in the past with `GIT_COMMITTER_DATE`, so the
window is read from real commit times.

## Verification

- `cargo test -p gear-app --test it base_gate` → 19 passed, 0 failed.
- `scripts/test.sh` → the whole workspace passes (1372 tests, 0 failed), on
  origin/dev + this branch. The wall time of the run (396 s) was over the red
  line because a `cargo clippy` run was sharing the machine; the suite itself
  took 141 s.
- `cargo build --workspace --all-targets` → no warning.
- `cargo clippy -p gear-app --all-targets` → no new warning (the warnings in
  `config.rs` and `mail.rs` are older than this task; `base.rs` and
  `base_gate.rs` are clean).

## Friction

- The allowed edits of contract v1 were `base.rs` and `config.rs`; the
  hand-in call site in `mail.rs` is where the configured window has to reach
  the gate, so the contract had to be widened (v2, captain 08:55) before the
  setting could be effective. The first hand-in attempt cost the time of that
  round trip.
- The first `gear` run reported the task on `keel/t217` (a branch that is
  already handed in); the work was moved to `keel/t221` on top of `origin/dev`
  (M-3689), which cost the rebase and a full second run of the suite.
- The first hand-in attempt was refused by the *installed* `gear` (v0.4.0),
  which still runs the old strict rule: the new rule only lives in the
  candidate, not in the released binary. The candidate's base was three
  minutes old at that moment — the new rule would have accepted it — so the
  branch was merged with `origin/dev` and handed in again.

## Out of scope

- The merge gate (`crates/gear-engine/src/merge.rs`) is not changed: it
  already merges the approved candidate onto the current tip and runs the
  project's suite on the merged result.
- A candidate that is behind *and* conflicts with the tip is still refused —
  the window forgives a base that moved, not a work that does not fit.

# T-178 — the engine side of PR landing (design §11.2, §11.3)

Scope: T-178 — in `merge.rs`, a repo in pull-request mode (`merge = "pr"`)
lands a task through its pull request: the gate runs as today, the review's
commits go onto the pull request's head, the merge op goes `Submitted` with
its result JSON and the land forge op is inserted, nothing is deleted; the
merge op is confirmed when the land op is; the failures of §11.3's first two
rows fail as they are written.

Branch: keel/t178 (code @ the hand-in commit; origin/dev merged before the
final verification)

## What was built

`crates/gear-engine/src/merge.rs`:

- **The mode** (`pr_claim`, `claim_pr`): a repo whose `[github] merge = "pr"`
  lands through its pull request. The pull request is the one the claim op
  opened (`{task}:claim`, confirmed): its number is the target, and its head
  is the task's own branch.
- **§11.2 step 1** — steps 1-8 of today's `merge_one_locked` are unchanged:
  the fetch, the reset to `origin/<integration>`, the merges of the candidate
  and the review branch, the conflict checks and the gate. A failure there
  fails the op exactly as today.
- **§11.2 step 2** (`pr_head`) — instead of pushing the integration branch,
  the candidate is reset to and the review branch is merged into it (only
  when the review branch holds commits the candidate does not have), and the
  head is pushed to the task's branch: a fast-forward of the pull request's
  head. The head is recorded.
- **§11.2 step 3** — the merge op goes `Submitted` with the result
  `{"mode":"pr","pr":<n>,"head":"<sha>"}`, and the forge op
  `{task}:{n}:land` is inserted with the payload
  `{"forge":"land","pr":<n>,"head":"<sha>","method":"squash|merge"}` (the
  repo's `merge_method`). Nothing is deleted: the task's branch and the
  review's branch stay until the pull request is merged.
- **§11.2 step 5** (`confirm_pr_merges`) — the next tick sees the merge op
  `Submitted`: when its land op is confirmed, the merge op is confirmed with
  `merged {task} into {integration} by PR #{n}: {merge commit}`, the task's
  merged time is set, the branches the merge consumed are closed, and the
  task's waits and failures are settled.
- **§11.3, row 1** — a task whose claim pull request was never opened fails
  the merge with `no pull request for T-n: the claim PR was never opened`,
  and the captain hears about it as a merge failure today.
- **§11.3, row 2** — a land op the forge refused fails the merge op with the
  forge's own message, and the captain's item names `- remerge T-n`.

## The choices (and why)

- **The claim op is the pull request's name.** The engine reads the store,
  not the forge: the confirmed claim op of the task holds the pull request's
  number. A claim that is there but not confirmed yet is a *wait*, not a
  failure (the claim may still land); a claim that failed or never existed
  is the failure §11.3 names. The refinement matters: a claim that is two
  seconds late must not kill the merge.
- **The head is built in the merge worktree.** The gate has already run on
  the merged tree; the head the pull request gets is the candidate with the
  review's commits on it, which is what the push is a fast-forward of. A
  separate scratch checkout would only cost more git processes for the same
  tree.
- **The branches are closed when the pull request is merged**, not before:
  the pull request's head is the task's branch, and a branch that is deleted
  before the merge would leave the pull request without a head.

# T-178, attempt 2 (the rework: F1-F3 of ops/reviews/T-178.md)

Branch: keel/t178 (one commit for the three fixes; origin/dev merged before
the final verification)

## F1 — a refused land can be retried by `- remerge T-n`

`insert_land_op` now skips only a **live** (Intended, Executing, Submitted,
Unknown) or **Confirmed** land op. A land op that failed or was voided is
followed by a new Intended one with the current head and the current method,
under the same `{task}:{attempt}:land` key. Before, the failed op was enough
to make the function return, so the new merge op of a remerge inserted no land
op and failed again with the old message — the advertised retry could never
work.

## F2 — a recovered merge op becomes Submitted

The launch path moves both `Intended` **and** `Unknown` merge ops to
`Executing` before the worker runs. A restart leaves an `Executing` op as
`Unknown`; the completion handler writes the `Submitted` result only for an
`Executing` op, so a recovered op never got its result JSON and its land op
was inserted without it — and `confirm_pr_merges` (which reads `Submitted`)
never confirmed it.

## F3 — a head that was pushed and not confirmed is reused

`pr_head` builds the head (the candidate with the review's commits on it) and
then looks at the head the branch already holds (`origin/<branch>`). When
that head is the engine's own merge — the same parents and the same tree, but
another sha, because the commit's timestamp is the clock — it is reused and
nothing is pushed. Any other head is not the engine's: the push stays the
ordinary fast-forward, and nothing is ever force-pushed.

## The regressions (each fails without its fix)

- `a_refused_land_is_retried_by_a_remerge` — the forge refuses the landing,
  the captain remerges, a new land op is inserted, the forge is called again
  and merges, and the merge op is confirmed with the pull request's number
  and the task's merged time.
- `a_recovered_merge_op_becomes_submitted_and_confirms` — a merge op that is
  `Unknown` (what a restart leaves) runs again, carries the result JSON
  (`{"mode":"pr","pr":7,"head":…}`), inserts one land op, and is confirmed
  with the merged time after the forge merges.
- `a_pushed_head_is_reused_after_a_restart` — the branch holds the head the
  engine would build, with another timestamp (another sha); the merge reuses
  it: no non-fast-forward, nothing pushed, and the op's result names the head
  that is on the branch.

## The doubt (asked of the captain)

The new `a_refused_land_is_retried_by_a_remerge` drives five real merge
steps (two runs of the merge worker, the forge calls and the confirmation),
so it takes 5-6 s on a quiet machine and 13 s when the fleet is building —
the same band as the merge tests the review set aside (12-13 s). The default
is to keep the test as it is: a shorter one would not show the second forge
call, which is what the review asks for.

# T-159 — progress answers and declared waits in the CLI and app

Scope: T-159 — design §5.2 (`gear send --kind progress` takes `--left <min>`
and `--blocker <text>`, and the answer's fields go into the message's meta) and
§5.3 (`gear send --kind blocked --task --attempt --contract --on T-<m>`
declares a wait: accepted only when the task it waits for exists and is not
Done, `tasks.wait_on`/`wait_cond` are set, the attempt stays Started, and the
captain gets one info item). Attempt 2 fixes the review's F1 and F2.

Branch: mast/t159 (code @ the hand-in commit; origin/dev merged before final
verification)

## Rework (attempt 2: F1, F2)

- **F1 (P1, blocking) — the contract of a blocked message is checked.** The
  message names a contract, and the wait was declared without looking at it: a
  captain who changed the task's contract (and ended the wait with it) could
  have the lane's old command park the revised task on an obsolete
  dependency. The wait is now declared only when the named contract is the
  one the attempt works to **and** the one the task carries now — the same
  two checks a hand-in makes — and nothing is written when the check refuses
  (no wait, no message).
- **F2 (P2, logged) — the request fingerprint carries the new fields.**
  `left`, `blocker` and `on` are part of the request key, so a request id
  reused with a changed field is a `REQUEST_CONFLICT` instead of a replay of
  the old answer; an identical retry still replays.

Files:
- `crates/gear-app/src/mail.rs` — the send takes the new fields: `left` and
  `blocker` (a progress answer, design §5.2) and `on` (a declared wait, §5.3).
  The answer's fields go into the message's meta as
  `{"left": <min>, "blocker": "<text>"}`; the `blocked` kind needs `--task`,
  `--attempt`, `--contract` and `--on`, and a field that belongs to the other
  kind is refused with the reason. The wait itself: the attempt must be the
  sender's and Started, the contract must be the attempt's and the task's
  current one, the task it waits for must exist and must not be Done
  (`T-2 is done: there is nothing to wait for`), and the wait is written on
  the task (`wait_on`, `wait_cond`); the attempt keeps its state and the
  blocked message is the captain's info item (state Info — a wait is a fact,
  not an action). The request key carries `left`, `blocker` and `on`.
- `crates/gear-cli/src/main.rs` — `gear send` takes `--left <min>`,
  `--blocker <text>` and `--on T-<n>`; `blocked` is a `gear send` kind again
  (the help lists it), and the CLI tests: a progress answer with both flags
  stores the meta, a blocked message on an open task sets the wait, the item
  and leaves the attempt Started, a blocked message on a Done task is
  refused, a blocked message with a stale contract is refused (the reviewer's
  case: the task is on v2, the message names v1 — no wait, no message), and a
  request id reused with a changed field is a conflict while an identical
  retry still replays.
- the `SendArgs` constructions in the tests (this lane's and the engine's)
  carry the three new fields.

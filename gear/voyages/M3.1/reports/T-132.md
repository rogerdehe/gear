# T-132 — builds and test runs as fast as they can be, every lane in parallel

Scope: T-132 — (1) `[profile.dev]` and `[profile.test]` debug at
`line-tables-only`, measured before and after; (2) `cargo nextest` against
`cargo test` from a warm cache, and `scripts/test.sh` on the faster one, keeping
each test's time and the over-10 s warning. No machine-wide lock and no cap:
lanes build and test in parallel, that is the point.

Branch: `deck/t132`; the candidate named in the hand-in carries this report.
Base: `origin/dev` merged into the branch before the hand-in (never rebased).

## (1) The profile

`Cargo.toml`: `[profile.dev]` and `[profile.test]` now carry
`debug = "line-tables-only"` instead of the default `debug = 2`. (`test`
inherits `dev` — checked: with `[profile.dev]` set and `[profile.test]` absent,
`cargo build -v` still passes `-C debuginfo=line`. Both are named so the two
profiles a lane builds with state it.)

Measured, each number from a build of the same tree with only this setting
changed:

| | before (`debug = 2`) | after (`line-tables-only`) |
|---|---|---|
| workspace rebuild — CPU (2 runs, `cargo clean -p` the 8 crates, then build) | 162 s, 177 s | 151 s, 142 s |
| workspace rebuild — wall (same runs) | 71.3 s, 106.1 s | 90.9 s, 34.7 s |
| full build from clean — CPU (all dependencies included) | 301 s, 243 s | 271 s, 261 s |
| full build from clean — wall | 129.3 s, 141.8 s | 129.7 s, 53.9 s |
| `target/` after a build from clean | 912 MB | 779 MB |
| the 19 test binaries together | 154 MB | 150 MB |

What this says, honestly: **the artifacts are 15 % smaller and a rebuild of the
workspace costs ~14 % less CPU; the wall time on this machine is not
measurable** — other lanes were building beside this one throughout, load
average ran from 17 to 66, and the same build took 34.7 s and 90.9 s minutes
apart. Nothing here says the build got slower; the CPU numbers, which the load
does not move as much, say it got a little faster.

The executables themselves barely shrink (154 → 150 MB, -3 %) because macOS
keeps debug info out of the binary: cargo's default there is
`split-debuginfo=unpacked`, so it lands in `<binary>.dSYM` and in the object
files of `target/`. That is where the 133 MB of `target/` went, and where the
linker's work goes.

## (2) nextest against cargo test

Both on the same warm cache (test binaries already built), 904 tests, 22 test
binaries, six interleaved pairs — one run of each, then the other, so the
machine's load hits both:

| runner | wall (six runs) | median | CPU |
|---|---|---|---|
| `cargo nextest run --workspace` (a process per test) | 76.9, 60.9, 61.0, 66.2, 90.2, 98.9 | **71.6 s** | ~320 s |
| `cargo test --workspace` (a process per binary) | 71.6, 91.3, 78.4, 124.5, 110.2, 109.9 | **100.6 s** | ~303 s |

Earlier pairs, before the profile change, say the same: nextest 75.2 s and
105.0 s against `cargo test` 131.4 s and 134.6 s.

So `cargo nextest` **stays** in `scripts/test.sh`: about 30 % less wall time for
about 6 % more CPU, which is exactly the trade this task asks for — every test
in its own process, all of them side by side, instead of one binary waiting for
the one before it.

It is also the only one of the two that can print each test's time on a stable
compiler: `cargo test -- --report-time` answers *"The "report-time" flag is only
accepted on the nightly compiler with -Z unstable-options"*, and
`--format json` needs `-Z unstable-options` too. Under `cargo test` the over-10 s
warning would have nothing to read.

`scripts/test.sh` now says so where it can be read: the header records the
measurement and why the tool was chosen ("re-measure before switching: the
numbers above are the reason, not the tool's reputation"), and the summary line
names the runner — `suite: 105 s to run under cargo nextest: below the pass
mark (60 s)`. The build line, each test's time, and the `STUPID TEST, MUST FIX`
warning for anything over 10 s are unchanged.

## Noise, and why the seconds are approximate

This machine was shared the whole time: four other worktrees were building and
running the `gear-engine` suite, and load average went from 17 to 66 during the
hour. Two runs of the same command differ by a factor of two or three. The
numbers above are the ones that survive that: medians over interleaved runs, CPU
seconds, and bytes on disk. A quiet machine would show the same ordering and
smaller absolute numbers.

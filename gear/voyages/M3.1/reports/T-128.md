# T-128 — every crate but gear-engine fits the test-time red line

Scope: T-128 — time the test binaries of `gear-app`, `gear-cli`, `gear-store`,
`gear-herdr`, `gear-board`, `gear-forge`, `gear-model`, find what makes them
slow, and take it out: a git or process fixture built once per file, no
wall-clock sleep, no network. No assertion is weakened or deleted.

Branch: `deck/t128`; the candidate named in the hand-in carries this report.
Base: `origin/dev` merged into the branch before the hand-in (never rebased).

## What the time was

Not one slow loop — **git processes**. On this machine `git <anything>` costs
40–150 ms before it does any work, so a test that materialises a repository with
twenty git calls pays two or three seconds for a fixture it then reads once.
Measured, not guessed: `GIT_TRACE`-free runs with a logging `git` on `PATH`
count every process (the counts below are exact; the seconds are not — see
"Noise").

## What changed

**`crates/gear-app/tests/it/base_gate.rs` — one fixture per file, copied per
test.** The file built a bare origin, two commits, a fetch and two clones for
every one of its 14 tests. Now the repositories are built **once** in a
`OnceLock` and a test copies the trees (`main.rs: copy_tree`) and rewrites the
one absolute path a clone carries — the `url` in `.git/config`
(`main.rs: point_at`). A copy is a walk of a few dozen small files; a clone is a
process and a hundred milliseconds. `publish` also stopped spending two extra
processes (`rev-parse` + `update-ref`) on a ref: `git fetch` writes the ref
itself with a refspec. The file went from **317 git processes to 131** for the
whole binary (22.6 → 9.4 per test), measured with a logging `git` on `PATH`.

**`crates/gear-app/tests/it/cancel_contract.rs` — the same.** Its two slow
tests built the same origin and work repository (21 processes) each; the fixture
is now built once per file, in both its variants (before and after the merge),
and copied.

**`crates/gear-app/tests/it/kickoff_contract.rs` — a repository in two git
processes, not four.** The fixture only needs a branch with a name, so it is
`git init` plus `git commit --allow-empty` instead of init, write a file, add,
commit, switch.

**`scripts/fixtures/make.sh` — the two fixture projects are built side by
side.** `multi` and `running` share nothing, the parent's two children only
need the parent's directory, and the parent's own commit waits on nothing the
children need: the script now runs them as background jobs and waits.
`sh scripts/fixtures/make.sh <dir>` went from 3.0 s to ~1.3 s, and its test — the
only one over 10 s when this task started — from 7.9 s to 4.6–5.2 s. Nothing
about what it builds changed; `fixtures_contract` still asserts every path,
branch, remote and gate.

**`crates/gear-forge/tests/it/github_contract.rs` — one fake `gh` per file.**
Every test wrote its own copy of the same script; the tests now link to one
file, which reads its directory from `$0`. The answers stay per test, in that
test's own directory. (The file was already 73 ms per test, so this is the
smallest of the three; one small file per run is left in the temp dir.)

**`scripts/test.sh` — the run's own `Summary [ 12.3s]` line was counted as a
test over the limit**, so every green run ended with a "STUPID TEST, MUST FIX"
warning naming a test that does not exist. Only a line that starts with a test
status (`PASS`, `FAIL`, `LEAK`, `SIGSEGV`, `TIMEOUT`, `ABORT`, `TRY`) is timed
now.

## Noise, and why the seconds are approximate

This machine was shared while the numbers were taken — other lanes were
building and running the `gear-engine` suite beside this one — and load average
went from 10 to 22 during the hour. A git process cost 40 ms at one moment and
150 ms at another, so **the process counts are the honest measurement and the
seconds are indicative**. Both columns of the table above come from full-suite
runs under the same conditions (16.2 s and 12.5 s wall).

That load is also why the full workspace run is not stable: 893 tests, all
passing, took **59 s at load 16** and **102 s at load 22**, and the number of
tests over 10 s went from 11 to 39 with nothing changed in between. In the 59 s
run, 10 of the 11 are `gear-engine`'s `merge::tests` (10–22 s each, the crate
this task excludes) and one is `fixtures_contract` at 11.8 s — a 4.8 s test
paying the contention of a machine running twenty-second merges beside it. In
the 102 s run, 36 of the 39 are `gear-engine`. On a quiet machine the file is
4.6 s; nothing here is over 10 s on its own work.

The last run, after merging `origin/dev` and with load average 26: 904 tests,
56 s to run, **7 tests over 10 s — all of them `gear-engine merge::tests`**, and
none from `gear-app`, `gear-cli`, `gear-store`, `gear-herdr`, `gear-board`,
`gear-forge` or `gear-model`.

## Left alone, and why

- `gear-board/tests/it/board_contract.rs` reads a pty with a deadline and a
  10 ms sleep while waiting for the board's frame. That is a wait on a child
  process's output, the test file is 1.4 s of test time in total and no single
  test is near a second: rewriting the poll into `poll(2)` would change how the
  read is done for no measurable gain in the crate this task is about.
- `gear-cli/tests/it/fixtures_contract.rs` still asserts its fixture with
  twenty small `git` calls after the build (branch, remote, status per
  repository). Those are the assertions; they are not a fixture, and folding
  them into one shell call would make the failure messages worse.
- `gear-cli/tests/it/offline_contract.rs` clones `https://example.com/…` on
  purpose: `.cargo/config.toml` allows the file transport only, so git refuses
  it before a packet is sent. No network, by test.

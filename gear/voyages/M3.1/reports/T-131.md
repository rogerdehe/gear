# T-131 — no external program to learn GEAR's own ancestry (attempt 1)

Scope: T-131 — `parent_of` reads the parent pid in process on macOS
(`proc_pidinfo`, `PROC_PIDTBSDINFO`) and on Linux (`/proc/<pid>/stat`); the
identity path starts no program at all, so no `/bin/ps` can pile up stuck behind
a `gear` call.

Branch: mast/t131 (code @ the hand-in commit; origin/dev merged before
verification)

Files:
- `crates/gear-app/src/identity.rs` — `parent_of` is now a pure in-process read:
  Linux off `/proc/<pid>/stat` as before, macOS off
  `libc::proc_pidinfo(pid, PROC_PIDTBSDINFO, 0, &mut proc_bsdinfo, size)` →
  `pbi_ppid`; the two absolute-path `ps` spawns and their loop are gone. The
  macOS read checks the returned size and that `pbi_pid` is the pid asked for (a
  recycled pid is not this pid's answer). Any other platform answers `None`
  instead of falling back to a program. `process_ancestors` itself is unchanged:
  own pid first, then parents, bounded at 64, stopping at pid 1.
- `crates/gear-app/Cargo.toml` — `libc` (already a workspace dependency, used by
  `gear-board`/`gear-cli`/`gear-engine`) is now a dependency of `gear-app` too.
- `crates/gear-app/tests/it/app_identity.rs` — new test
  `this_process_ancestry_comes_from_the_os_in_process`: the chain's first entry
  is `std::process::id()`, its second is
  `std::os::unix::process::parent_id()`; the existing
  `a_path_provided_ps_cannot_fabricate_ancestry` probe keeps a fake `ps` in
  `$PATH` from adding a pid.
- `ops/reports/T-131.md` — this report.

Every external program a plain `gear` call (`gear`, no arguments: home page)
still starts — expected: none. What the code has:
- **None from the identity path.** `grep -n "Command::new"
  crates/gear-app/src/identity.rs` finds nothing (both before and after the
  call: `process_ancestors` is the only thing on it).
- **Its own binary, only when no engine is running.** `gear` calls
  `ensure_engine` (`crates/gear-cli/src/main.rs`), which — after taking the
  engine lock and finding it free — re-executes `std::env::current_exe()` with
  argument `run`, detached (`setsid`, output to `engine.log`) and never waited
  on. That is GEAR starting its engine, not an external program: no `$PATH`
  lookup, no name to resolve, nothing to wait for, and it is skipped whenever an
  engine already holds the lock (the case for a lane's own `gear` calls).
- Everything else in `gear-app` and `gear-cli` that starts a program is
  per-command, never on a plain call: `git` in `base.rs` (hand-in checks) and
  `plan.rs` (plan apply, import issues), `opencode models` / `pi --list-models`
  in `kickoff.rs` (kickoff only), `opencode api` in `gear-herdr/src/opencode.rs`
  (kickoff/agent calls), `sh`/`git` in `gear-engine` (merge, review, onboard),
  and `gear-forge`'s `gh`. Herdr is reached over its unix socket, not by
  starting it.

Verification:
- `cargo build -p gear-app` → clean, zero warnings (the macOS branch is the one
  compiled here, Darwin 25.6.0 arm64).
- `cargo nextest run -p gear-app --test it app_identity` → 30 passed, 0 failed,
  including the new `this_process_ancestry_comes_from_the_os_in_process`.
- Real environment: `cargo run -- gear` printed the home page for
  `seat gear:mast` with no engine start line — the same process walked its real
  ancestry in process (`GEAR_ANCESTRY_PROBE=… ancestry_probe --nocapture`
  printed `ANCESTRY=[24213, 10027, 10023, 92103, 87335, 70514, 70512, 70498,
  70495]`, nine pids up to launchd, matching `ps -o ppid=` at every step).
- `grep -n "Command::new" crates/gear-app/src/identity.rs` → no match.
- `scripts/test.sh` → 905 tests run, 905 passed, 0 failed (build 51 s, run
  113 s).

Open questions: none.

Out of scope: the per-command `git`/`sh` spawns above (hand-in checks, plan
apply, merge, review) — they are not on every call and the packet asks only for
those; `proc_pidinfo`'s sibling queries (a `proc_pidpath`-based exe check) —
not needed here; a macOS-only fallback for the other unix platforms — none of
GEAR's supported targets need it.

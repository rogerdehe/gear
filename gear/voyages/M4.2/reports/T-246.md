# T-246 — The board and the captain's home page show the current voyage only

Scope: T-246 — the board (`project_with_agents`) shows only the voyage it
measures plus every task that still waits for work, so the totals, the lane
lines, the graph and the Time & tokens rows no longer carry landed voyages;
the captain's snapshot lists only the voyages with open work (else the one the
board measures) and lost its "+N more voyages" line.

Branch: mast/t246 @ origin/dev (c3ec632b) — the code and this brief.

Files:
- `crates/gear-board/src/lib.rs` — `project_with_agents` computes
  `let workload = workload_voyage(tx, project, now)?;` right after
  `tx.tasks_of_project(project)?` and keeps in `tasks` a task whose milestone is
  the workload voyage's or whose state is not terminal (`!task.state.is_terminal()`);
  with no workload voyage every task is kept. The later `workload_voyage` call is
  gone (the one value is reused for `decisions_of` and `ProjectBoard::workload`).
  The graph is re-read by `graph::tasks(tx, …)`, so it does not follow `tasks` on
  its own (see "Asked"); its rows are now filtered to the ids of the kept tasks.
- `crates/gear-app/src/home.rs` — `snapshot` lists the voyages whose milestone is
  in `open`; when `open` is empty, the voyage named by `plan.workload`. No
  "+N more voyages" line; `SNAPSHOT_VOYAGES` is gone. The list is sorted by
  milestone id (every shown voyage has open work, so the old "open first" sort
  had nothing left to order).
- `crates/gear-board/tests/it/voyage_scope_contract.rs` (new, wired in
  `tests/it/main.rs`) — `the_board_counts_and_works_the_current_voyage_only`:
  M1 (earlier, done) and M2 (later, one done one ready) give
  `totals.tasks == 2`, no M1 task in `frame::token_tasks` or in the lane line or
  the graph, and M2's measured task still listed;
  `a_task_left_open_on_a_landed_voyage_is_still_shown`: an M1 task left Ready is
  still on its lane.
- `crates/gear-app/tests/it/voyage_contract.rs` — new
  `the_snapshot_shows_only_the_current_voyage` (M1 landed, M2 with one done and
  one ready: only the M2 voyage line, no M1 line, no "more voyages", and
  `SNAPSHOT 2 tasks · 1 done`); the T-22 R3 test
  `the_snapshot_shows_the_voyage_that_has_work` now asserts the "+1 more
  voyages" line is gone and M3 is not named.
- `ops/reports/T-246.md` — this brief.

## How it reads

```
# M1 departed earlier, all its tasks done; M2 departed later, T-2 done, T-3 ready
project_with_agents → workload = M2
totals: 2 tasks · 1 done          (T-1 of M1 is no longer counted)
lane hull: T-2 done, T-3 queued   (T-1 is not on the lane line, the graph or Time & tokens)
home SNAPSHOT: Voyage M2 …        M1 is not listed, no "+N more voyages"

# the same store with T-1 of M1 left Ready
lane hull: T-1 ready, T-2 done, T-3 queued   (an open task is never hidden)
```

## Asked (M-4126, question)

The packet says "Every count, lane line, graph and the token rows then follow
from the filtered list", but `graph::tasks(tx, project, now)` re-reads every
task of the project, so filtering the local `tasks` list does not reach the
graph. I asked the captain (M-4126) and went on with the default, which the captain
confirmed as (a) in M-4128: the graph rows are filtered to the ids of the kept
tasks (no API change, `graph::lanes` already comes from the seats). If the
answer had been "leave the graph alone", the two lines in
`project_with_agents` (`shown` + the filter) and the graph assertion in
`the_board_counts_and_works_the_current_voyage_only` are what to revert.

Open questions: the graph, above.

Out of scope: `project_with_agents` reads the whole task table three times
(`tasks_of_project` here, in `graph::tasks`, and in `home::snapshot` for the
`open` set); a voyage with an open task of its own outranks a later voyage
because `workload_voyage` takes the first active report in milestone order —
that is the packet's rule, left as it is. `ops/reports/T-239.md` was not
touched.

# T-240 — An op stuck in Executing no longer holds a lane's delivery slot for ever

Scope: `crates/gear-engine/src/ops.rs` (the fix in `fn confirm_pending_with`
and four tests) and this report.

Candidate: the tip of `hull/t240` — the fix `eaaa37a8`, merged with
`origin/dev` (`f49f6f32`) as `4fee353d`, and this report on top.

## The bug

`fn deliver_doorbell_now` (the `gear send` path) sets its doorbell op to
`Executing`, calls Herdr and records the outcome in a second `store.write`. When
that second write failed ("database is locked") the op stayed `Executing`. Only
`fn recover_on_start` (engine start) moved `Executing` ops on, and the doorbell
expiry and the delivery rules in `fn confirm_pending_with` looked at
`Submitted` and `Unknown` ops only — so the stuck doorbell held the seat's
delivery slot for ever and no doorbell rang again (M4.2: hull sat idle 20 min
with T-236 ready).

## The fix

`crates/gear-engine/src/ops.rs`, `fn confirm_pending_with`, just before its
`for state in [OpState::Submitted, OpState::Unknown]` loop: for every op in
`tx.ops_in_state(project, OpState::Executing)?` whose kind is `Doorbell` or
`Deliver` and whose `now - op.created >= DOORBELL_EXPIRY_S`, the op is set to
`Unknown` with the reason `"stale executing: its sender never recorded the
outcome"` (a transition `recover_on_start` already makes). The loop below then
treats it like any other `Unknown` op: a doorbell expires, a delivery is never
re-sent. `Merge` — and every other kind — is untouched: a merge legitimately
runs longer.

## The tests

`crates/gear-engine/src/ops.rs` (module tests, the `recover_on_start` fixtures:
`testing::seed_project` + `testing::seed_active_seat`, plus a new
`executing_op` helper that inserts an op directly in `Executing`):

- `a_doorbell_stuck_in_executing_does_not_hold_the_slot`: a `Doorbell` in
  `Executing` created `DOORBELL_EXPIRY_S` ago is settled by one
  `confirm_pending` call and ends `Confirmed` with the expiry reason — it is no
  longer `Executing` and the slot is free.
- `a_doorbell_executing_for_ten_seconds_is_left_alone`: created 10 s ago, still
  `Executing` after the call.
- `a_merge_executing_for_an_hour_is_untouched`: still `Executing`.
- `a_delivery_executing_for_five_minutes_becomes_unknown`: a `Deliver` in
  `Executing` for 300 s is `Unknown` after one `confirm_pending_with` call (a
  grace window longer than 300 s, so the delivery rules below do not fail it in
  the same call); it is not re-sent.

Deviation from the packet's wording, asked as M-4060 (question r-1793171846792-27781)
and defaulted: the acceptance says a stale `Executing` doorbell "is Unknown
after one `confirm_pending_with` call and then expires to Confirmed as today".
With the prescribed fix both steps happen in that one transaction, with the same
`now` and `created`, so the call settles it straight to `Confirmed`. The test
above therefore asserts the observable outcome of that one call (`Confirmed`
with the expiry reason, op no longer `Executing`), and the `Unknown` step is
covered on its own by the `Deliver` case, which the delivery rules leave
`Unknown` in the same call.

## Out of scope

- The failing second write in `fn deliver_doorbell_now` is still noisy about
  nothing: the op is now recovered by the tick, but the write itself is not
  retried. Nothing in this packet asked for that.
- A `Forge` op stuck in `Executing` is not covered (only `Doorbell` and
  `Deliver` are, per the packet). A forge call that fails its second write has
  the same shape of problem.

# T-242 — init refuses a gate whose pipe hides a failure

Branch: mast/t242 (code @ the hand-in commit; `origin/dev` merged before
verification, `make check CRATE=gear-app` green on the merged result)

What changed (`crates/gear-app/src/config.rs`, plus one config contract test):
- `validate` now reports a gate that pipes into another command without
  `pipefail`: a pipeline's exit status is its last command's, so
  `go build ./... && go vet ./internal/... 2>&1 | head -20` passed while vet
  had failed and could merge.
- New helper `gate_pipes_without_pipefail` and const `GATE_PIPE`:
  - a `|` that is part of `||` is not a pipe (the scan skips both bytes, so
    `|||` still counts as a pipe);
  - any `pipefail` in the command suppresses the finding (`set -o pipefail; a | b`);
  - no `|` at all → no finding (`make gate`, `a && b`).
- The finding is pushed on `conventions.gate` for `cfg.conventions.gate`, and on
  `repos.<name>.gate` for a `[[repos]]` entry's own gate — only when the entry
  sets one (a repo without a gate inherits the project's, already checked).
- The message is the packet's, verbatim: "the gate pipes into another command,
  so its exit status is the last command's and a failure can pass: drop the pipe
  or start with `set -o pipefail;`".
- The rule is listed in `validate`'s doc comment, next to the other gate rules.

Tests (`crates/gear-app/tests/it/config_contract.rs`,
`a_gate_may_not_pipe_away_a_failure`):
- the packet's `go build ... | head -20` gate → `["conventions.gate"]`;
- `make gate`, `a && b`, `a || b`, `set -o pipefail; a | b` → no issues;
- a repo gate with a pipe → `["repos.api.gate"]`; the same gate behind
  `set -o pipefail;` → no issues.

Verification:
- `make check CRATE=gear-app` — 436 passed, 0 skipped, zero warnings.
- `cargo build --workspace --all-targets` — clean, zero warnings.
- `origin/dev` merged in before the run above (`01e5784c`).

Out of scope (noticed, not changed):
- Existing repo-gate findings use the indexed field `repos[{index}].gate`
  (empty / TODO, integration, release); the packet fixes the new pipe finding's
  field as `repos.<name>.gate`, so the two spellings now coexist for the same
  entry. Worth one naming pass across the repo findings if that matters.
- The pipe scan is textual: a `|` inside a quoted string (`sh -c 'a | b'`) would
  also be reported, and a `|&` pipe is reported like `|` (which is correct for
  `|&`, but the quoted case is a false positive). Edge case outside normal use,
  so not handled here.

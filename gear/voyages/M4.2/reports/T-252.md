# T-252 — Task and review branch names come from the project's config

Attempt 1, contract v4.

Branch: `mast/t252`; the candidate named in the hand-in includes this report.
Base: `origin/dev` merged into the branch before the hand-in.

## What shipped

**A pure template module (`crates/gear-model/src/branch.rs`, `pub mod branch;`).**
`TASK_BRANCH = "{lane}/t{n}"`, `REVIEW_BRANCH = "review/t{n}"`, and
`expand(template, project, lane, task)` filling in `{project}`, `{lane}` and
`{n}`. `{n}` is the task id's number (`T-40` → `40`, from the id's trailing
digits; an id without digits falls back to the old lowercased, dash-free shape
so `{n}` is never empty). No I/O, so the app, the engine and the forge expand a
template the same way.

**The config (`crates/gear-app/src/config.rs`).** `Conventions` gains
`pub task_branch: String` and `pub review_branch: String` (`[conventions]
task_branch` / `review_branch`), defaulting to the two constants. `validate`
checks both templates on a sample (`project "p"`, lane `l`, task `T-1`) and
pushes `conventions.task_branch` / `conventions.review_branch` when a template

- has no `{n}` (every task would share one branch),
- names a placeholder other than `{project}`, `{lane}`, `{n}` (e.g. `{team}`),
- expands to something git refuses: only letters, digits, `.`, `_`, `-` and
  `/`; no leading `/`, `-` or `.`; no `..` or `//`; no trailing `/` or `.lock`,
- or when the two templates give the same name for that sample.

**The users of the name.** `base::task_branch` takes the project's conventions,
the project id, the lane and the task and calls `branch::expand`; its callers
are updated (`mail.rs`'s push check for a hand-in, the CLI's hand-in reply).
`tasks.rs` (the branch hint on the merge op a passing review queues) and
`plan.rs` (`- remerge T-<n>`) expand the project's template too, reading
`[conventions]` from the store inside the transaction they already hold.
`config::conventions_or_default` is the reader those two paths share: the
defaults when a project has no config text at all (a store seeded without one)
or a config that does not parse — a branch name is a hint for the merge, never a
gate on the candidate.

**The forge (`crates/gear-forge/src/sync.rs`).** Its own `Conventions` gains
`#[serde(default)] task_branch: Option<String>`; `branch_of` expands it
(`TASK_BRANCH` when absent) with the project id it has, and the claim and the
adoption of an interrupted claim use it, so a pull request is opened on the
branch the project names.

**The docs.** `skills/gear/references/conventions.md` §8 says, in the
overridable `[conventions]` block, that `task_branch` and `review_branch` name
the branches, which placeholders are filled in, and gives
`task_branch = "{project}/{lane}/t{n}"` as the example.

## v4: seat branches

`gear-model::branch` gains `SEAT_BRANCH = "{project}/{seat}"` and
`expand_seat(template, project, seat)` (placeholders `{project}` and `{seat}`) —
the branch of each seat's own worktree, and of the merge worktree as seat
`merge`, so Herdr names the worktree `<project>-<seat>`.

`Conventions` gains `pub seat_branch: String` (`[conventions] seat_branch`,
default `SEAT_BRANCH`). `validate` checks it like the other two — on the sample
project `p`, seat `s` — and pushes `conventions.seat_branch` when the template
does not name `{seat}`, names `{lane}` or `{n}` (or any other placeholder), or
expands to a name git refuses. The conventions.md line names `seat_branch`,
its default and the worktree name it gives too.

Nothing reads `seat_branch` yet (the packet names no caller): the constant, the
expansion, the config field and its validation are here for the worktree work
to use.

- `cargo build --workspace --all-targets` → exit 0, no warnings.
- `make check CRATE=gear-model` → 13 passed, 0 failed.
- `make check CRATE=gear-app` → 444 passed, 0 failed.
- `make check CRATE=gear-forge` → 42 passed, 0 failed.
- New tests: `gear-model` `branch::tests` (the defaults, `{project}`/`{lane}`,
  `{seat}`, the number of an id); `gear-app` `config_contract` (the defaults and
  a `{project}/{lane}/t{n}` template are valid; `{lane}/fix`, `{team}/t{n}`,
  `/x/t{n}`, `a..b/t{n}`, `{lane}//t{n}`, a trailing `/`, a trailing `.lock` and
  a review branch equal to the task branch each give an issue; a seat branch
  without `{seat}`, one naming `{lane}`, `{n}` or an unknown placeholder, and
  one git refuses each give an issue, while `{project}-{seat}` is valid).

## Out of scope (noticed, not touched)

- `gear_engine::dispatch::task_branch` (`crates/gear-engine/src/dispatch.rs`)
  still hardcodes `<lane>/t<n>`, and `review.rs`'s review branch
  `format!("review/{...}")` with it: the engine is not in this packet's list, so
  a project whose template differs gets the engine's own names there.
- `plan.rs`'s `- remerge` payload still names the review branch as
  `review/{slug}` while the task branch now expands the template; the packet
  named only the task-branch line there.
- `conventions.md` §7 still describes the review branch as `review/t<n>` when
  describing what the engine does; the packet asked for one line (§8).
- A `seat_branch` that names the same branch as `task_branch` for the same
  sample is not a finding: the two samples name a seat and a task, so the names
  can only meet by coincidence, and each template is checked on its own.

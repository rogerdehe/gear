# T-239 — A milestone emptied of its tasks loses its departure

Scope: T-239 — a voyage whose milestone has no task left keeps no departure, so a
reused milestone id starts its clock when its new tasks come; `departure_from_history`
does not take the emptied voyage's drafts as the new voyage's history. A milestone
that still has tasks never changes.

Branch: hull/t239 @ origin/dev (2911a01) — the code and this brief.

Files:
- `crates/gear-store/src/lib.rs` — new `clear_voyage_departure(project, milestone)`
  sets `departure`, `departure_tasks` and `departure_estimate_min` to NULL for that
  voyage (`upsert_voyage` cannot: it COALESCEs those columns, by design).
- `crates/gear-app/src/plan.rs` — `fix_departures`, right after `counts` is built,
  walks `tx.voyages_of_project(project)?`: a voyage with `departure.is_some()` whose
  milestone is absent from `counts` is cleared and the meta
  `departure-reset:<project>:<milestone>` is set to `tx.plan_version(project)?` (the
  version this apply stored). `departure_from_history` reads that meta and starts its
  scan at `reset + 1` instead of 1, so the drafts that carried the trial's tasks are
  not taken as this voyage's history; without the meta it still starts at 1. New
  helper `departure_reset_key(project, milestone)` names the key in one place. The
  doc comments of both functions state the reset.
- `crates/gear-app/tests/it/voyage_contract.rs` — new
  `an_emptied_milestone_loses_its_departure_and_a_reused_id_starts_again`.
- `ops/reports/T-239.md` — this brief.

No other design: the store keeps its "a departure is fixed once" rule (`upsert_voyage`
and `set_voyage_departure` are untouched), the milestone words (`title`/`done`/`bar`/
`eta`) survive the reset because only the three departure columns are cleared, and
`record_voyages` (which runs after `fix_departures`) re-upserts the block with
`departure: None`, which COALESCE keeps NULL.

## How it reads

```
# M1 departs at NOW with 2 tasks of 30m
voyage M1: departure=NOW, departure_tasks=2, departure_estimate_min=60

# the trial is moved to M0 (T-1 and T-2 now on M0), apply at NOW+100
voyage M1: departure=NULL, departure_tasks=NULL, departure_estimate_min=NULL
meta departure-reset:p:M1 = 2
voyage M0: departure=NOW+100, departure_tasks=2

# the real voyage reuses M1 with one new 45m task, apply at NOW+200
voyage M1: departure=NOW+200, departure_tasks=1, departure_estimate_min=45
```

## Verification

- `cargo test -p gear-app -p gear-store` → 28 + 405 + 10 + 53 passed, 0 failed.
  `cargo build --workspace --all-targets` → clean, no warnings.
- `voyage_contract::an_emptied_milestone_loses_its_departure_and_a_reused_id_starts_again`
  — the M1 voyage departs at NOW with 2 tasks and a 60m scope; after the move to M0
  every departure column of M1 is NULL while M0 departs at NOW+100 with 2 tasks; after
  the reuse, M1 departs at NOW+200 with 1 task and a 45m scope (the new task's estimate,
  not the trial's 60m) and its block words are the new ones.
- The existing departure tests are unchanged and pass: a milestone that keeps its tasks
  keeps its departure (a later apply, a grandfathered edit, the migration that recovers
  the estimate from the departure plan).

Open questions: none.

Out of scope: the `departure-reset:<project>:<milestone>` metas stay in the store
after the reused voyage has departed — harmless, and a later emptying overwrites the
value with the newer version. A voyage cleared while its milestone block still exists
keeps its words (`title`/`done`/`bar`/`eta`), as T-239 asks (only the departure goes).

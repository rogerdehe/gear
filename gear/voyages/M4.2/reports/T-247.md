# T-247 — A config re-apply does not bring retired lanes back; a task does

Branch: `mast/t247`, started from `origin/dev`.

## What changed

1. `crates/gear-app/src/admin.rs`, `fn re_register`: the `Retired -> Queued`
   step ("registered again") is gone. A registered lane keeps its profile from
   the config, and its state — a retired lane stays retired through any
   re-apply, whether the new config still names it or not. The doc comment of
   `re_register` says so.
2. `crates/gear-app/src/plan.rs`, `fn apply_queue`, right after
   `end_parked_lanes(...)`: for every Lane seat of the project in `Retired`
   whose name is still in the project's current config (`project_config`, the
   same reader the rest of the apply uses) and which some task of the project
   with `lane == seat.name` holds in state `Ready`, the seat is set to `Queued`
   with the reason `a task names it again`, and `start <lane>` is pushed to
   `staffed`. A retired lane that is not in the config stays retired whatever
   its tasks.

## Tests (`crates/gear-app/tests/it/config_change_contract.rs`)

- `a_retired_lane_stays_retired_until_a_task_names_it` replaces the T-54 test
  that asserted the old behaviour: a lane retired at generation 1 is still
  `Retired` (reason `reclaimed`, generation 1) after `gear admin init` re-applies
  a config that still names it; a plan apply with a **NEW** task on that lane
  then sets it `Queued` (reason `a task names it again`) and `staffed` contains
  `start heat`.
- `a_retired_lane_out_of_the_config_stays_retired`: the retired lane is dropped
  from the config (allowed for a retired lane), a NEW task still names it, and
  the apply leaves it `Retired` — `staffed` carries no `start heat`.

## Out of scope (noticed, not changed)

  and registered again" (T-125 home-worktree reuse); the behaviour stays valid

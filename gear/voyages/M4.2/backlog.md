# M4.2 backlog

The list M4.2 drew from at its departure; what it took is in gear/voyages/M4.2/plan.md.

## Fixes from real use (user, 2026-10-28; collected after M4 landed and during M4.1, which took only T-226 and T-227)

Problems found after M4's landing and in other projects' first voyages are collected here and fixed together in one short voyage, not one by one.

- **Two projects, two voyages at once (user, 2026-10-28: this will be the normal case).** One engine and one store serve every project, and a tick walks all of them; a step that fails for one project returns from the whole tick (`?` in engine::tick), so one project's bad config or store row stops the other's voyage. Each project's steps must fail alone (its own item, the others go on). Also: an engine upgrade restarts every project's engine at once, and builds of both projects share the machine (machine watch).
- One store per Herdr session is the default since v0.4.5 (a project from another session was registered into orch's store and its lanes started in orch, 2026-10-28). Left for M5: `init` refuses a project whose `herdr_session` is not the session of the store's engine, and the engine never onboards a project of another session (today only the default path prevents it; an explicit `GEAR_DB` still can).
- Without `[temps]` a hand-in waits in Submitted for a captain `pass`, and no code was found that rings the captain for it: the captain must be told a hand-in waits for its verdict.
- Kickoff skeleton: with one model per role, `on_quota = "fallback"` is refused at init ("a quota stop would park for 5h"); the skeleton writes `wait` when a role has a single model.
- Done in v0.4.6 (merged 2026-10-28): the board's colours and the lane column width.
- **A dependency counts when it is merged, not when it passed (M4 friction F-76).** T-215 (deps T-171) was dispatched after T-171 passed but before its merge reached dev, so the code it had to change was only on mast/t171: the lane based its work on that branch and merged twice. Dispatch a task only when each dep is on the integration branch.
- **A lane's next branch starts from its previous, unmerged task (M4 friction F-75).** A home worktree still on the last task's branch cuts the next task branch from that head; the candidate then carries the other task's commits and its merge waits for it, and moving it would need a force push. The packet tells the lane to start the new branch from origin/dev (`git switch -c <lane>/t<n> origin/dev`). (In M4 as T-222.) The same seam leaks uncommitted edits: mast's worktree kept stray edits in five engine files from T-220 into T-222 (friction F-90; the captain stashed them). Before a new task's packet, the engine checks the home worktree is clean and, if not, tells the lane to commit to the old branch or stash with a name, never to carry the edits over.
- **No idle items once a voyage is ready to land (M4 11:40).** After the last task merged, "lane <x> is IDLE" came back for every lane every few minutes, each time it was resolved. While a voyage waits for its landing, idle and run-dry items stay quiet.
- A lane with no task that stays busy blocks its next delivery: the engine delivers only to an idle agent (§10.2), and Flash lanes keep tidying instead of ending their turn (M4 21:12 and 23:53, keel, ~10 min each). After 5 min busy with no task and ready work waiting, the engine interrupts the turn (esc) and delivers.
- Moving a running task to another lane in the plan leaves its open attempt on the old seat (M4 20:27: T-160 keel → hull; the captain abandoned attempt 1 in the store). The plan should abandon it (the old lane told) and the new lane start a new attempt.
- A merge loses a push race to the captain's plan commits on the same branch (M4 03:40, T-187: three retries, then failed until a hand remerge). The captain's plan commits must not fail a merge.
- **Rework budgets are sized for one fix (M4 friction, ~9 reports).** A rework round of 13-25 min is given for a review with three to nine blocking findings; the overrun question then fires on nearly every rework. Size the rework budget from the blocking findings it carries.
- Cut from M4 (station M-2503/M-2572): T-180 admin stop waits for merges (T-121), T-183 names (T-134 F2/F3), T-185 three merge.rs tests over 10 s. T-182 (a push race does not re-run the gate) goes with the push-race item above. Their goals are in gear/voyages/M4/plan.md.
- T-176's rest: the engine reconnects when its Herdr server restarts (following the project's own session is done by v0.4.5's store per session).
- One word for a voyage: "voyage" and "milestone" name the same thing (files in gear/voyages/, headers `# Milestone`). Say voyage everywhere a person reads it; the id stays M1, M2, … (user, 2026-10-28).
- Task branch name from a template (a captain on another project, 2026-10-28; wanted before that project's M2): `[conventions] task_branch = "{project}/{lane}/t{n}"`, default `"{lane}/t{n}"` so nothing changes for existing projects. init requires `{lane}` and `{n}`, refuses a template that does not expand to a valid ref, and refuses one whose refs would clash as git directories with an existing branch (`<project>/<lane>/t1` against a branch `<project>`). Today the name is built in at least five places (gear-app base::task_branch and tasks.rs:981, gear-engine dispatch::task_branch and merge branch_of, gear-forge sync branch_of; home branches in onboard.rs and review.rs): one function first, every caller through it.
- A wrong model id pins a review round for good (a captain on another project, 2026-10-28; the user watched it and called the design bad). `review = ["anthropic/claude-sonnet-5-5"]` passed four `gear admin init`s; the claude CLI refused it on the first turn and the reviewer sat idle while the home page said "temps 1 running". The captain fixed the config (v4) and, as the stall item says, killed the agent and started it with the right `--model`; on the next tick the engine's restart (T-209, `engine.restart_config.<seat>`) put it back with the args recorded when the round began (`--model anthropic/claude-sonnet-5-5 --resume …`), every time. `- release` is refused while it holds a review, so the only way out was the captain settling the task without its review. The lane kind is pinned the same way: after a re-init from opencode to pi (config v5) the running opencode lanes stayed until the captain stopped them by hand. Fix, in order: (1) a restart or resume takes the kind, model and start args from the project's current config version, not the round's snapshot (a re-init is a config change; a changed kind switches at the lane's next safe point, as the in-place kind change of v0.4.3 already does for a declared switch); (2) init refuses a provider/ prefix for a `claude` kind, and checks ids against the CLI's model list where the kind has one; (3) a seat whose first turn ends on a model error with no tool call is a captain alert, not a running seat; (4) the stall item's text says what to do when a restart comes back unchanged.
- One identity refusal of a pi lane's write (a captain on another project, 2026-10-28, M-42): "seat <project>:<lane> was claimed with the pane <pane>, but … no pane of this session runs this process (its tools run outside every pane …)". It happened once; the same lane handed in fine minutes later. pi runs its tools as its own children (checked: git under pi under the pane's shell), so the ancestry proof should hold; the likely cause is a call while the lane was still the old opencode agent (its tools run in `opencode serve`, started from another session) or a Herdr read that failed for a moment. Find the call in that project's store and engine log before changing the rule; the refusal text should name the socket it asked and the ancestry it saw.
- A config re-init brings retired lanes back (2026-10-28): after M4's lanes were retired, a re-init that only dropped a pi flag re-registered deck, hull, keel and mast and the engine started all four agents again (hull on Codex). A retired lane stays retired until a staff line or the user brings it back; init prints which lanes it would start.
- Verification commands that build the whole repo, run by every lane, reviewer and gate at once, took the machine to load 175 (another project's Go voyage, 2026-10-28; `go test -list ./...` on a baseline checkout too). Accept commands are scoped to the packages a task touches; with the machine watch, the engine holds new suites while load is high.
- An urgent instruction cannot reach a lane inside a long tool call (a captain on another project, 2026-10-28): the message waits in the agent's queue (pi "Steering") until a 3-minute `go test ./...` returns, and `gear send --urgent` does not interrupt. An urgent instruction interrupts the working turn first (the profile's interrupt key, as quiet.rs does for a stuck turn), then delivers, and says so to the captain.
- The home page's `next: gear reply M-n --resolve` cannot be run as printed: `gear reply` requires `-m` (trial project feedback B04-02, v0.3.4; still so in v0.4.6, home.rs). Print `gear reply M-n --resolve -m "<what was done>"`.
- "deliveries not confirmed: N" on the home page counts old operations: with no lane working it showed 3 on this project (v0.4.6), and a trial captain read it as lost messages (B04-01). Count only deliveries still waiting for their check-in, and name them.
- Run-dry and idle notices only when work can move (user, 2026-10-28, M4.1): "lane X has nothing to start after T-n", "runs dry in ~28 min" and "lane X is IDLE" rang for every lane of a voyage whose plan had nothing left to start anywhere, and again after each plan apply. They are worth a captain's look only when another lane still has queued work that could be moved (an imbalance); when no lane has queued work, the voyage is in its tail and they stay quiet. Each fact rings once, not again per apply. Same family as "no idle items once a voyage is ready to land".

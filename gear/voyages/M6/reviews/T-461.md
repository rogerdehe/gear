- F2 [P2, logged] a goal check written in the same apply as a landing is stored under `voyage_of` (the draft's last milestone block, else the current voyage), while the land guard reads the milestone from the station item's own thread — `crates/gear-app/src/plan.rs:193` and `:4008` — so landing a *non-current* voyage with `done (n): met …` lines in the same apply stores the check under the wrong `goal-check:<project>:<milestone>` key and the landing is still refused for the open clauses the captain just checked. Landing the current voyage (the normal flow) is correct. Fix if desired: derive the goal-check milestone from the station item(s) being landed (or require a milestone block) and pass it into `record_goal_check`.
- F3 [P3, logged] when a draft moves several tasks without `--confirmed`, the refusal names only the first move — `crates/gear-app/src/plan.rs:3661` (`&moved[0]`) — the captain is told one task and may miss the rest; the line and the summary still fail the whole apply. Fix if desired: list all `moved` ids in the message.

## Set aside
- Moving a task from a milestone to no milestone (`milestone=` absent) is not guarded as "between milestones": the contract says "between milestones", so this is outside it (and pre-existing behaviour).
- A confirmed line naming only the cut but not the open clauses (or vice versa) when both hold is refused: both conditions independently refuse a landing, so requiring both named is the safe reading, not flagged.
- A task moved out and back is counted once as a cut (`cut_tasks` dedups and suppresses when the task is currently in the voyage); a cancelled task moved between milestones can contribute to two voyages' cut counts — both outside normal use.
- `land` followed by a tab instead of a space would pass the action validation but skip the new land guard (`response.starts_with("land ")`); a captain writes `land `, and this is an edge case.
- The `record_goal_check` milestone inference and the unused-arrow validation are the writer's own "out of scope" notes; they are logged as F1/F2 above, not treated as blocking.

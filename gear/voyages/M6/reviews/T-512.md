## Set aside
- The op's `candidate` payload is the audit's checked candidate (the integration tip), not a pinned review-branch head; the review record is merged by the review branch's current tip. This matches how the merge gate always merges review branches (by name, current tip), and `still_current` requires `candidate` to equal the attempt's candidate, so pinning the review head there would void the op. Nothing moves `review/t<n>` between the captain's rule and the merge in normal use, so not flagged.
- If the reviewer never pushes `review/t<n>` (e.g. a text-only review hand-in with no branch), the audit's merge op would confirm as "already merged" without landing any record, because the audit's candidate is always already on `dev` and the missing-review failure branch is gated on `!already`. In the normal audit flow the review branch exists before the captain rules (the reviewer pushes it as part of the hand-in), so this is an edge case outside normal use — logged, not blocking.

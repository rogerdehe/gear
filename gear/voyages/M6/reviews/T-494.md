## Findings
- F1 [P2, logged] the deps column is hard-capped at four columns regardless of frame width — `crates/gear-board/src/frame.rs:1349` (`let cap = 4.min(width.saturating_sub(deps_x + 40));`) — so a task waiting for five or more unmerged tasks draws only three lines plus `+N` even on a wide frame where all five would fit, against goal (1) "a line from the task to each task it waits for". The acceptance only exercises up to four deps, so this is outside normal use. Fix (~1 line): drop the `.min(4)` and let the width set the cap (the `40` reserve already bounds it), or raise the bound and keep the reserve.
- F2 [P3, logged] the header's title column no longer lines up with the rows — `crates/gear-board/src/frame.rs:1360` computes `tw` from the new `info_x = deps_x + deps_width + 1`, while `crates/gear-board/src/graph.rs:358` truncates each row's title to `tw` computed from the old `info_x = 9 + 6*last + 6`. With a deps column of 2-4 lines (or none) the two widths differ by 1-3 columns, so the header's `what`/`stage`/`time` drift relative to the task rows. Cosmetic, but it is a visible change to a part the contract says stays as it is; the golden test's right-side pending hides it. Fix (~2 lines): pass view_tasks' `info_x` (or `tw`) into `git_rows` so rows and header share one width.
- F3 [P3, logged] a `+N` of 10 or more overruns the task text — `crates/gear-board/src/frame.rs:1408` reserves one column for the count (`plus_x = deps_x + drawn`, text at `plus_x + 2`) but `+10` is three characters, so the `0` lands on the first character of the task text. Only reachable with 11+ omitted lines; edge case.

## Findings
- F1 [P2, logged] The direction-branch close falls back to the seat's recorded checkout for jobs whose meta predates the `branch` field — `crates/gear-engine/src/review.rs:811-816`. `branch_key`/`repo_path_key` are keyed by seat, not job, so a direction job that stays `running` while its seat is parked/reset and then reused (a checkout failure or a captain reset mid-check) will, when that old attempt finally ends, read the *new* job's branch and worktree and detach/delete those instead. Smallest fix: when `job["branch"]` is absent, skip the deletion (do not fall back), or write the fallback branch into the job meta before deleting, so only a branch the job itself names is deleted. This is a recovery path, not normal use, so it is logged, not blocking.

## Set aside
- A direction branch left by a job that already closed before this change (meta already `{"checked_sha":…}`, e.g. the cited `origin/direction/t-328`) is not deleted: `finish_direction_results` only deletes for jobs still in `running` state. The contract's rule is "deleted when its job closes" — forward-looking — and the active reviewer still on `direction/t-400` is handled by F1's fallback, so pre-existing stale branches are outside the requirement and not flagged.
- A done task's branch holding only report commits is listed to the captain (not deleted): the contract says "listed to the captain otherwise" for anything not an ancestor of dev, and the merge path already silently closes report-only branches (T-402), so this is correct and not flagged.
- `Coverage.integration` is reported from the root `[conventions].integration`, while a task with a `base` snapshot is actually checked against its own base; the check itself is right and the label is cosmetic.
- A candidate that was squash-merged or cherry-picked is listed as off (its commit is not literally an ancestor of dev); this is the report's documented, safe-fail behaviour ("a merge that took a different commit") and not flagged.

# T-472 — report

The fleet and machine health watch. Once a minute the engine samples the
machine's load, free memory and the free space of the volumes it needs, and
each lane's and reviewer's own processes (the pane's shell and foreground
processes, children included). A machine that stays short is relieved by
stopping a seat whose processes are over the safe line; a machine that is
short for another reason gets one urgent captain item naming the top
processes, which are never touched.

## What changed

`crates/gear-engine/src/health.rs` (new):

- `Read` (the machine and process reader) with `SystemRead` as production: one
  `ps -axo` per sample builds the process table; `sysctl`/`vm_stat` give the
  load and free memory, `df -k` the free space of the state directory and the
  project's repos. A seat's own processes are its pane's shell and foreground
  processes and every child of them, plus the foreground process group (a
  build that left the shell's tree in its own session). The top processes
  outside the fleet are named by the CPU they used since the last sample.
- `check` (one tick step): once per `[health].sample_min` minutes (one by
  default); between samples it is one meta read. Each seat's cumulative CPU
  seconds are kept, so the next sample gives its real use over the interval
  (a `ps` %cpu average would hide a process that just started burning a
  core). A machine that stays short for `machine_over_min` minutes (load over
  `load_x_cores` × the cores, free memory under `mem_free_pct` %, or a
  watched volume under `disk_free_gb` GB) is either:
  - internal: a seat's processes are over the safe line (`seat_cpu_pct` % of
    one core or `seat_mem_mb` MB for `seat_over_min` minutes). Its turn is
    interrupted (`esc`), its agent stopped with the profile's exit, the seat
    parked in NeedsCheck, and the captain gets one urgent item with what was
    measured and how to start it again (`- retry <lane>`);
  - external: no seat is over the line. The captain gets one urgent item
    naming the top processes and the machine's facts; nothing outside the
    fleet is touched.
  The machine item is resolved when the machine is back; a seat's item is
  resolved when the seat works again under the safe line; a later spell is a
  new item.
- `Silent` (a reader that reads nothing): the engine's own tests keep it, so
  a test never reads the machine it runs on.

`crates/gear-app/src/config.rs`: the kickoff-configurable `[health]` section
(`sample_min`, `load_x_cores`, `machine_over_min`, `mem_free_pct`,
`disk_free_gb`, `seat_cpu_pct`, `seat_mem_mb`, `seat_over_min`) with the
defaults above, and `validate` refuses zero lines.

`crates/gear-engine/src/lib.rs`: the module, `EngineCfg.health` (the reader),
the tick step (after the dialog step, before the blocked watch) and
`TickReport.health`.

`crates/gear-cli/src/main.rs`: the running engine uses `SystemRead`; a test's
`EngineCfg` keeps the silent reader.

## Cost

The watch's own cost is one sample a minute. Measured on this machine: five
samples (the same commands `SystemRead` runs: `ps`, three `sysctl`, `vm_stat`,
two `df`) took 0.17 s user + 0.41 s system CPU, i.e. **116 ms of CPU per
sample**. At one sample per 60 s that is **0.19 % of one core**, far below the
1 % line. The test `the_watch_costs_under_one_percent_of_one_core` measures
the real reader's CPU with `getrusage` and fails above 600 ms (1 % of a
minute); it passes. Between samples the tick only reads one meta key.

## Tests

`crates/gear-engine/tests/it/health_contract.rs` (new module), with injected
readings:

- `a_seat_over_the_safe_line_is_stopped_and_the_captain_told` — a lane whose
  own processes hold 3 GB for five minutes while the machine is short: its
  turn is interrupted (`esc`), the agent gets the profile's exit, the seat is
  NeedsCheck with the reason, one urgent item in `health:p:heat` names the
  numbers and `- retry heat`; the reviewer under the line is untouched, and no
  machine item is opened for an internal cause.
- `a_machine_short_for_another_reason_names_the_top_processes` — no seat over
  the line: one urgent item in `health:machine:p` names `fseventsd` (pid 4242)
  and the other build; no seat stopped, no key sent.
- `a_fine_machine_stops_nothing_even_when_a_seat_is_over_the_line` — a fine
  machine leaves a heavy seat alone.
- `the_watch_samples_once_a_minute` — two ticks inside the minute make one
  sample; the next minute makes the second.
- `the_machine_item_is_resolved_when_the_machine_is_back` — the item is
  resolved when the machine recovers, and a later short spell is a new item.
- `the_watch_costs_under_one_percent_of_one_core` — the measured cost above.

Unit tests in `health.rs` cover the parsers (`ps` lines and both platforms'
CPU time formats, `vm_stat`, `df`), the seat tree walk, and the short-machine
lines.

`crates/gear-app/tests/it/config_contract.rs`:
`a_health_section_keeps_its_thresholds` (the section parses, a partial section
keeps the other defaults) and `health_thresholds_are_validated` (a zero line
is refused).

## Out of scope

- The captain's own seat is not watched: the backlog's watch is the fleet's
  lanes and reviewers ("the fleet's own lanes and reviewers"). A runaway
  captain agent is the user's agent and is named in the external item if it
  is outside the fleet.
- No orphan rule: the M5 item also wanted a lane's child over 10 minutes
  ended; this goal is CPU and memory, so a long single-core orphan is only
  caught when the machine is short. Logged for the captain.
- No board line: the M5 item mentions one, the M6 goal asks only for the
  captain's items.
- With several projects on one machine, the top list of one project's item
  names another project's seats as external (it is "outside this fleet"). One
  project per machine today; logged.
- The thresholds are read from the project config; a config that does not
  parse falls back to the defaults instead of failing the watch.

# T-523 — report (attempt 1)

A tick reads only the ops it needs: the filters the merge step and the lane's
nudge made in Rust are now in SQL, and schema v9 carries the indexes for them.

## Store (`crates/gear-store`)

New reads, next to `ops_of_seat_kind` in `src/lib.rs`:

| read | SQL | serves |
| --- | --- | --- |
| `ops_of_kind_in_states(project, kind, states)` | `WHERE project=? AND kind=? [AND state IN (…)] ORDER BY created, id` | the merge step's queue and lookup, a review's confirmed deliveries |
| `op_keys_of_kind(project, kind)` | `SELECT task, attempt … WHERE project=? AND kind=?` | `merge_keys` — the columns only, never the payload |
| `ops_of_seat_kind_task(seat, kind, task, attempt)` | `WHERE seat=? AND kind=? AND task=? AND attempt=?` (same order as `ops_of_seat_kind`) | the lane's deliveries of one attempt |

Schema v9: `operations_kind (project, kind, state)` and
`operations_attempt (seat, kind, task, attempt)` in `schema.sql` for a fresh
store, and `step_8_to_9` in `migrate.rs` (`SCHEMA_VERSION` 9, in `STEPS` after
`from: 8`) for a store already in use — create-only, no row touched, run on the
first open of the upgraded binary. The module doc lists v8 and v9.

## Engine callers routed (`crates/gear-engine`)

- `merge.rs` — `merge_keys` reads the merge keys in SQL without the payload (it
  used to walk every op of the project in seven states and parse each delivery
  and doorbell); `merge_op_of` and `ready_merges` ask for `kind=merge` with the
  states they need instead of every op of those states.
- `lane_nudge.rs` — the redelivery, `nudges_used`, `retry_failed` and
  `nudges_of` ask for their attempt's deliveries; they used to read every
  delivery the seat ever had and filter in Rust.
- `quota.rs` — `retire_unconfirmed_deliveries` asks for the project's
  deliveries in Submitted/Unknown (it kept the seat's own and its generation).
- `review.rs` — the "the hand-in reached a reviewer" check asks for the
  project's confirmed deliveries instead of every confirmed op.

Same results as before: each caller keeps exactly the filter it had, now that
SQL already returns only the rows of that kind (and, for the lane, of that
attempt). No other change.

## Tests

New `crates/gear-store/tests/it/ops_by_kind_contract.rs` (registered in
`tests/it/main.rs`), plus the version pin in `v7_contract.rs` moved 8 → 9:

1. `the_kind_queries_return_what_the_rust_filter_returned` — a store of merge
   ops in all seven states (two tasks, two seats), 12 deliveries of two seats
   and three attempts, 10 doorbells and 10 forges. Each new query's rows are
   exactly the ones the old Rust filter kept: `merge_keys` against the
   seven-state walk for every state list that the engine passes (all, two, one,
   empty), and `ops_of_seat_kind_task` against `ops_of_seat_kind` filtered by
   task and attempt — including the attempt nobody delivered (no rows).
2. `the_kind_queries_use_the_new_indexes` — `EXPLAIN QUERY PLAN` of the four
   statements: `SEARCH operations USING operations_kind` /
   `operations_attempt`, no `SCAN operations`.
3. `a_version_8_store_gains_the_kind_indexes_when_it_is_opened` — the fixture
   drops both indexes and stamps the store 8; the plan before has no
   `operations_kind`, opening stamps 9, the rows are unchanged (the seven merge
   keys still read) and both plans use the new indexes.

No wall-clock assertion anywhere: the plan is the check (T-520's rule).

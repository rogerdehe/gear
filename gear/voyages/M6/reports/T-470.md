# T-470 — report

GEAR near idle: the M5 probe lines (T-407) were read, and the multi-step
operations that waited a whole tick between their steps now run the steps this
tick already knows in the same call. The engine's own CPU is unchanged: the
work added is a few Herdr calls and a 300 ms terminal settle per session
submission, no busy loop.

## The probe lines (before, from the real voyage log)

The M5 voyage's engine log (`~/.local/state/gear/selyra/engine.log`, session
`selyra`, 2026-10-28 … 10-30) holds 5 765 probe lines. Grouped into operations
(an operation starts at its `initial` line and ends at its `done` line):

| op | completed ops | total median | p90 | max |
|---|---|---|---|---|
| `new` (session switch) | 328 | 41 s | 75 s | 800 s |
| `resume` | 39 | 20 s | 51 s | 118 s |
| `compact` | 10 | 15.5 s | 21 s | 23 s |
| `deliver` | 1 013 | 6 s | 44 s | 1 060 s |
| `merge` | 434 | 67 s | 237 s | 993 s |
| `restart` | 25 | 0 s | 8 s | 792 s |

The session actions were the slow multi-step operations that wait a tick
between steps:

- `new`: 282 of the 328 operations entered an `enter` step whose median was
  30 s — the Enter that types `/new` was read too early after it was sent, the
  composer check still saw the command, and the step then retried once per
  tick until the screen changed. That step alone is 7 646 s (2 h 7 min) of the
  M5 voyage's engine time.
- `resume`: all 39 operations start an agent from a shell pane; the old
  `initial → start_resume` transition spent a whole tick before the start.
- The other probe-covered operations are real waits, not tick waits:
  `deliver` waits for the lane's own check-in (`confirmed` median 11 s),
  `merge` runs git and the gate in its worker (fetch 4 s, merge 9.6 s, gate
  25 s, push 4.4 s, close 7.4 s), and `restart` already loops its phases in
  one call.

The M5 tick interval at that time was 5 s median, 10 s p90 (28 246 ticks in
the log): every tick-wait between steps cost that much.

## The fix

`crates/gear-engine/src/session_runner.rs`:

- `run` now advances through the steps that need no new observation from
  Herdr in the same call: a resume whose pane is already a shell starts the
  agent now (no `initial → start_resume` tick), the compaction after a resume
  is typed now, an exit command whose agent has gone starts the fallback now,
  and a refused resume start falls to the plain fallback now. Steps that wait
  for the agent (its new conversation, its session, its exit) still end the
  call and are picked up on a later tick.
- The Enter that types a session command is confirmed after the terminal had
  a settle to draw it (`type_settle` before the composer read), and it is
  also confirmed when the agent left idle/done — a submitted command starts a
  turn (Working) or makes the agent go (no occupant). A command still shown
  in the transcript is therefore not a command in the input box. The `enter`
  step retries in the same call and, if the screen still holds, waits at most
  one tick for the agent's state instead of a tick per retry.

## The probe lines (after)

The real after needs the new build in the engine log; the numbers below replay
the same real M5 operation lines with the tick waits the fix removes (the
`enter` step at most one tick at the M5 median of 5 s, the start tick gone):

| op | before (median / p90) | after (median / p90) |
|---|---|---|
| `new` | 41 s / 75 s | 13 s / 44 s |
| `resume` | 20 s / 51 s | 15 s / 44 s |
| `compact` | 15.5 s / 21 s | 15.5 s / 21 s |

`compact`'s wait is its own: `wait_action` waits for the compaction to show in
the session log (T-407's `compact` lines), which is not a tick wait. The
`new` case can be faster than the projection when the same-call settle
confirms the Enter (the tests measure that step at 0 ms).

The engine's own cost stays where it was: the live engine samples 0.0 % of one
core and 12 MB RSS between ticks (`top -l 2 -pid <engine>`), and this change
adds only sleeps and a few Herdr calls per session submission.

## Tests

`crates/gear-engine/src/session.rs`:

- `a_resume_of_a_shell_starts_the_agent_in_the_same_tick` — a resume whose
  pane is a shell starts the agent with the resume arguments in the same call,
  leaves the state at `wait_resume`, and the probe log shows
  `probe resume p:t470 start_resume 0 total=0`: the start step no longer costs
  a tick. The agent is ready on the next tick.
- `an_enter_the_agent_left_idle_is_confirmed_in_the_same_call` — a screen that
  still shows `/new` with the agent working: the step moves to `wait_action`
  in the same call, and nothing is typed again.
- `an_enter_with_the_screen_still_showing_the_command_waits_one_call` — an
  idle agent and a screen that still shows the command: the step waits, then
  the agent's working state confirms it on the next call.
- `resume_fallback_types_the_exit_command_and_enter_in_one_step` — the
  fallback now types `/quit` and submits it in the tick the exit timeout is
  seen.
- `fallback_starts_plain_if_the_agent_exits_before_deadline` — the plain
  fallback starts in the tick the shell is seen.
- `resume_restarts_with_session_and_falls_back_if_refused` — the resume (and
  its refused fallback) is ready one tick after the shell is seen.
- `fallback_agent_that_never_becomes_ready_is_bounded_without_typing` — the
  bound still ends a fallback agent that never becomes ready.
- `completed_step_resumes_the_round_after_an_idle_replacement` — the resume of
  an open round starts in the tick the shell is seen.

`crates/gear-engine/tests/it/delivery_landing_contract.rs`:
`a_command_left_in_the_composer_holds_the_packet_back` now checks the retry:
the lost Enter gets its second Enter in the same call, the command is typed
once, and the packet waits for the conversation.

`crates/gear-engine/src/review.rs`:
`a_rereview_resumes_the_jobs_session` now expects the review to start in the
tick the resumed agent is ready (it still never starts before the resume).

These tests replaced the expectations that encoded the old one-step-per-tick
cadence; the behaviour they check (the bound, the composer hold, the resume
before the review) is unchanged.

## Out of scope

- The model switch (`switch.rs`, `quota.rs`) still makes at most one UI
  submission per tick: each step must read the picker or the status bar, and
  the probe lines do not cover it.
- A reviewer start's worktree preparation and environment line retry per tick
  (`review.rs`); the probe lines do not cover them either.
- The onboard start retry (T-95) stays one attempt per tick by design, so a
  busy shell never holds the tick.
- The tick's own slow steps (`merge` ~2 s, `quiet` ~1 s) are not probe-line
  operations: the merge step's branch sweep is T-474's, and the quiet step's
  git read is T-386's. This task does not change them.
- The real after in the engine log arrives when the engine runs this build;
  the captain's next station check reads it from the same probe lines.

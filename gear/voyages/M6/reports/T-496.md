# T-496 — report

omp's session log reads through GEAR's pi-jsonl reader, so an omp seat's
tokens, model and cost are known once its session file is known.

## What I checked

The captain put a real omp 18.12.6 session (the T-495 probe, redacted) at
`target/tmp/omp-session-sample.jsonl`. Its records are pi's: `{"type":
"message", "message": {"role": "assistant", "model": …, "provider": …,
"usage": {"input", "output", "cacheRead", "cacheWrite", "cost": {"total"}}}}`
with the record time in the ISO `timestamp` and the completion time in
`message.timestamp` (ms). That is exactly what `pi_jsonl` and
`usage_records_in` read, so I reused the reader — no new log kind and no new
parser.

The built-in omp profile already names `usage_log: Some("pi-jsonl")` (T-495);
I added a comment above that field recording that a real omp log was checked
(T-496) and where its fixture lives. No other field changed.

## Fixture and tests

`crates/gear-usage/tests/it/fixtures/omp-session.jsonl` is the real probe's 11
records, redacted, with the session id `01a1917f-fad9-7369-ac78-80c212a8a31f`,
the model `minimax/MiniMax-M2` and the times kept. The probe's calls failed
with `invalid api key`, so every usage number in the real log is 0; **the
three assistant records' usage numbers are set by hand** in the fixture
(1200/300/4000/500/0.0123, 800/150/6000/0/0.0089 and
900/200/7000/250/0.0102) so the sums are meaningful.

`crates/gear-usage/tests/it/omp_jsonl_contract.rs` (5 tests):

- the session reads 3 records, input 2900, output 650, cache_read 17000,
  cache_write 750, reasoning 0, cost 0.0314;
- each record's model is `minimax/MiniMax-M2` and its times are the log's;
- a window inside the session counts only its records;
- the last context is 8150;
- a session file that was never written is unknown.

The pi fixture and its contract are untouched; the pi tests pass as before.

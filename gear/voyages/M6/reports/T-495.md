# T-495 — report

omp (oh-my-pi 18.12.6) now starts as a lane or a reviewer like the five CLIs
GEAR knows: it has a built-in profile, `gear admin install-skill --agent omp`
writes the skill under omp's agent directory, and kickoff lists omp with its
models.

## What changed

`crates/gear-herdr/src/profile.rs`:

- `builtin("omp")` and `builtins()`: unattended `--auto-approve` (omp's own
  flag; `--approval-mode yolo` is its other spelling and is not passed),
  rules through `--append-system-prompt {rules_file}` (omp's help: text or
  an existing file, like pi), exit by the `/quit` command (no keys), new
  session `/new`, compact `/compact`, `pi-jsonl` usage (omp writes pi's
  session files), session_ref **false** (Herdr 0.9.1 reports no
  `agent_session` for an omp pane), resume `--resume {session}` (omp has no
  `--session`), and the quota/rate-limit/auth/back-off/error markers omp's
  own screens carry (below). `blocked_markers` and `dialogs` stay empty:
  omp has no pi-guardrails strings and `--auto-approve` keeps approval
  dialogs away.

`crates/gear-app/src/skill.rs`: `SkillAgent::Omp`, `as_str`/`parse`/`ALL`,
and `skills_root` = `~/.omp/agent/skills` (`omp config path` names the agent
directory `~/.omp/agent`; user skills live in `<agent-dir>/skills` like pi).

`crates/gear-app/src/kickoff.rs`: `models_of("omp")` runs `omp models
--json` and `parse_omp_models` takes each entry's `selector` (the id
`--model` takes); no list is reported as `no model listed by omp models`.

`skills/gear/SKILL.md`, the CLI help and `skill_contract`: the installer's
kind list now names omp.

Tests: `the_omp_profile_starts_unattended_with_the_rules` (profile args,
exit, resume, signs), `omp_models_are_the_selectors`, `a_lane_of_kind_omp_is
_accepted`, `install_skill_contract` writes and reads the skill for omp.
`builtin_contract` and `profiles_contract` used omp as their example of a
kind without a built-in profile; they now use `gemini` and a profile named
`plain`.

## Real Herdr start (Herdr 0.9.1)

Test worktree `/Volumes/Data/tmp/pi/omp-probe` (a git repo), pane created with
`herdr workspace create --cwd … --label omp-probe2 --env MINIMAX_API_KEY=…`,
then, with the profile's arguments:

```
herdr agent start omp-probe2 --kind omp --pane w1JP:p1 -- \
  --auto-approve --append-system-prompt /Volumes/Data/tmp/pi/omp-probe/rules.txt \
  --model minimax/MiniMax-M2 --thinking low
```

`["omp","--auto-approve","--append-system-prompt",…,"--model","minimax/MiniMax-M2","--thinking","low"]`,

## Friction

Past the 50-minute budget, and the machine has no omp provider authenticated
(`omp auth export` is empty), so the live start was made with
`MINIMAX_API_KEY` taken from pi's own `auth.json` and the one-time setup
wizard had to be skipped with ctrl+c before the composer appeared. Both are
recorded above.

## Out of scope (noticed, not changed)

- omp's SOP is still `gear --skill agent:pi` (omp is a pi fork); the packet
  asked for the profile and the skill target, not a new SOP file, so
  `agent:omp` is not a topic yet.
- `session_ref` is false because Herdr 0.9.1 reports no session for omp; if
  Herdr starts reporting one, omp's `pi-jsonl` usage becomes readable without
  a code change beyond flipping the flag.
- `omp models --json` lists only models of authenticated providers; an
  unauthenticated machine shows omp with a "not checked" note, which is the
  honest answer.

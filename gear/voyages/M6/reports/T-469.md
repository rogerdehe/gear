# T-469 — Role charters fit the models the user chose

Lane mast · contract v2 · branch `mast/t469`

## What changed

**gear-app**

- `crates/gear-app/src/charter.rs` (new): role charters from the config the
  user confirmed at kickoff. `text(config, role, seat, done, bar)` renders a
  lane's or the reviewers' rules file: the config's `charter` replaces the
  role's stance in the fixed rules file; the GEAR working rules that follow the
  stance marker are always rendered; a role that names no charter renders as
  the fixed file does today. `arguments(...)` writes the rules file
  (`rules/lanes/<lane>.md`, `rules/review.md`) with the voyage's `done:` and
  `bar:` and returns the profile's instructions args — empty for a captain
  (whose guide is the skill topic), for a profile that takes no instructions
  argument, and for a resumed conversation (`resumed = true`): a resumed
  session already holds the charter it started with.
- `crates/gear-app/src/config.rs`: `charter` on `[[lanes]]` and on `[temps]`;
  a blank charter is a config finding (`lanes[i].charter`, `temps.charter`).
- `crates/gear-app/src/kickoff.rs`: the skeleton names the optional charter
  for a lane and for the reviewers.

**gear-engine**

- `crates/gear-engine/src/rules.rs`: the rendering lives in
  `gear_app::charter`; the engine passes the seat's name and whether the start
  resumes a conversation.
- `crates/gear-engine/src/restart.rs`, `session_runner.rs`: a restart or a
  session step that resumes the seat's session gets no charter again; the
  fallback (new) start and the onboarding/review starts do.
- `crates/gear-engine/src/onboard.rs`, `review.rs`: pass the seat's name.

**Skill texts**

- `skills/gear/references/conventions.md`: new §10 "Role charters".
- `skills/gear/references/captain.md`: the kickoff sheet asks for one charter
  per role, and the config example carries it per lane and for the reviewers;
  the captain's hand-fix/urgent-fix paragraph is untouched.
- `skills/gear/references/rules/lane.md`, `rules/review.md`: a stance marker
  separates the role's stance (replaced by a charter) from the working rules
  every seat keeps. The marker line is never rendered, so a role without a
  charter renders exactly today's text.

## Tests

- `crates/gear-app/src/charter.rs`: two charters render two rules files (one
  per lane) with the working rules and the voyage line; the reviewers'
  charter renders `rules/review.md`; a resumed session gets no charter again
  and a new one does; a role without a charter renders as today; a profile
  without instructions args still gets its rules file; an unchanged file is
  not rewritten; both fixed files hold a stance and working rules.
- `crates/gear-app/tests/it/config_contract.rs`: a charter parses per lane and
  for the reviewers; a blank one is a finding.
- `crates/gear-cli/tests/it/skill_contract.rs`: the conventions and the
  captain reference describe the charter, and the captain's guide still carries
  its hand-fix text.
- `crates/gear-engine`: `session.rs` — a resumed pi session starts without the
  rules and a new (fallback) one with them; `pi_lane_contract.rs` and the
  quota restart fixture now name `rules/lanes/<lane>.md` and assert the fixed
  rules are rendered without a charter.

## Out of scope

- `docs/design/17-conventions.md` is unchanged: the shared text every project
  reads is `skills/gear/references/conventions.md` (§10 added there).
- The captain has no configurable charter (captain's answer M-6665): it keeps
  `skills/gear/references/captain.md` as it is.
- A lane's charter is text only: the engine does not check that a strong-model
  lane actually designs; the charter is what the captain writes for that
  model.
- Rules files of an older engine (`rules/lane.md`, `rules/review.md` at the
  top level) are left behind; a seat's next start writes the new paths and
  nothing removes the old ones.

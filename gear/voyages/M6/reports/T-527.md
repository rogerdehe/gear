# T-527 — report (attempt 1)

The overlap scan starts a few git processes per pass instead of one per ref.

## `crates/gear-engine/src/parallel.rs`

**One read of the refs, one of the candidates.** The scan used to call
`revision` — one `git rev-parse --verify <ref>^{commit}` process — for the
integration branch, the remote integration branch, and per open task its
candidate, its local branch and its remote branch. Now a pass reads:

- **one** `git for-each-ref --format='%(objectname) %(refname)' refs/heads refs/remotes`
  into `Tips.refs` (refname → commit id), and
- **one** `git cat-file --batch-check` (stdin: the tasks' candidates) into
  `Tips.commits`, accepting only `<id> commit <size>` — the commit check
  `rev-parse --verify` did, so a candidate that names a tree, a blob or nothing
  git knows is still no candidate (T-431). No candidates, no process.

`revision` is now `Tips::revision`, answering from those maps: a ref the pass
read, or a candidate git resolved to a commit. The `rev-parse --git-dir` check
that opens the pass stays.

**The ancestry answer is kept.** `ancestor(repo, from, to)` checks a
process-wide `ANCESTORS` map first (key: repo plus the two full commit ids,
which never change), followed by a `git merge-base --is-ancestor` only on a
miss, and inserts the answer. Bounded like the diff cache of T-435
(`ANCESTORS_MAX = 4096`, cleared when full); an error from git is no answer and
is not kept.

Same findings as today: the scan's logic is untouched — only where the commit
ids and the ancestry answers come from. The branch-tip map and the candidate
map are local to the pass, so a new push on the next period is read again; only
the ancestry of a fixed pair is remembered, which no push can change.

## Tests (`parallel.rs` test module)

- `a_scan_reads_the_refs_and_the_candidates_in_one_process_each` — a real repo
  whose `dev` and two task branches diverge (so the pass has both a pair and
  two integration lines to find) with an attempt per task carrying its branch
  tip as candidate, against the same store without candidates:
  - `for-each-ref` ran **once** for the pass and `cat-file --batch-check`
    **once** (counters `REF_READS` / `CAT_FILE_READS`, the way `DIFF_MISSES`
    counts git reads for T-435);
  - the findings are identical to the store without candidates — the pair
    `tasks:T-1:T-2` and both `integration:T-1` / `integration:T-2` lines, same
    files;
  - the next pass runs one more of each and **no** ancestry read: the pairs of
    the first pass are the cache's.
- `a_second_ancestry_answer_for_a_pair_runs_no_git` — `ancestor` twice for the
  same pair: one `merge-base` process, and the second answer is the cache's; a
  different pair is a new read; the map holds both answers.

No wall-clock assertion: every count is a process count.

## Noted

- `git cat-file --batch-check` echoes the expression it was given, so a
  candidate stored as a branch name (before T-421) is passed on by name, exactly
  as the old code's shorthand resolution did; the commit type check is what
  decides whether it is a candidate.
- The ancestry cache is process-wide like the diff cache: an engine holds it for

# T-471 — report

The board no longer renders a frame it does not need, and a rebuild reads the
shown voyage's rows instead of every row of the project. Measured on the real
`gear` store: a rebuild fell from 0.19 s to 0.10 s of CPU, and a board with a
commit from another connection every 2 s fell from 6.5 % to 4.2 % of one core;
with the engine's own writes it is 2.9 %. Both are under the 10 % / 50 MB line
(RSS 13.9 MB).

## What changed

`crates/gear-board/src/lib.rs`:

- `run_with` keeps the frame text it rendered last together with a
  `RenderKey`: the board generation (a counter that moves on every rebuild and
  every project rotation), the tab, the selection, the header details, the
  opened lanes, the size and the panel. The frame is rendered again only when
  one of those moved; every other refresh reuses the text. The key includes
  `Screen::opened` because the Cost view's `Enter` changes it without a panel
  (the `decisions_contract::enter_opens_a_lane_and_closes_it` test caught that
  on the first run).
- `hook` gained `rendered()`/`renders()` next to the build counter, so a test
  can prove that a refresh renders no frame.
- `project_for` builds the graph with `graph::tasks_shown` for the shown tasks,
  measures one voyage with `voyage::report_for`, and reads the deliveries in
  flight with `Tx::unsettled_deliveries` instead of every op of the project in
  the four open states.

`crates/gear-board/src/graph.rs`: `tasks()` now delegates to a private
`tasks_of` that takes a row filter; the new public `tasks_shown` filters the
project's task rows before their history is read. The result is the same as
`tasks()` filtered by the shown set, in the same order.

`crates/gear-board/src/voyage.rs`: the new `report_for` measures one voyage;
`build_reports` gained an `only` filter. The report is the one
`reports_including_finished` gives for the same milestone.

`crates/gear-store/src/lib.rs`: the new `Tx::unsettled_deliveries(project)` —
the Deliver ops in `intended/executing/submitted/unknown`, ordered by
`created, id`. The board's list is sorted by age afterwards, so the rows and
the order are the ones the old scan gave; the scan of every op in those states
is gone.

The frame's text and the terminal writes are unchanged (T-403): a frame that
says what the last one said is still not written.

## Measurements

A release `gear` built from `origin/dev` before the change, and the same binary
rebuilt from this branch, both run on the real store
(`GEAR_DB=/Users/roger/.local/state/gear/gear.db`, project `gear`, 494 tasks,
5448 ops), in a pty, sampled with `ps -o time=,rss=` at the start and the end of
60 s.

| run | before | after |
|---|---|---|
| one rebuild (`gear board --json --project gear`), CPU | 0.19 s (user 0.13 + sys 0.06) | 0.10 s (user 0.08 + sys 0.02) |
| rebuild sections | graph 38 ms, shown-task loop 18 ms, workload 5 ms | graph 13 ms, unsettled deliveries 14 ms, rest 21 ms |
| 60 s, a write from another connection every 2 s | 3.89 s = 6.5 % of one core, RSS 15.4 MB | 2.51 s = 4.2 %, RSS 13.9 MB |
| 60 s, no synthetic writes (engine writing on its own) | 0.31 s = 0.5 %, RSS 15.6 MB | 1.7 s = 2.9 %, RSS 14.8 MB |

The last row is not a like-for-like pair: the "before" idle run found
`data_version` still, while the "after" runs saw the engine commit four times a
minute, so they rebuilt four times. The synthetic-write row is the like-for-like
comparison, and it is also the pessimistic one (a commit every 2 s instead of
the engine's tick).

## Question and the captain's answer

The wording "redraws only what changed and reads the store incrementally" had
two readings, so I asked (`M-6800`, `r-1793425891142-21171`) with the default I
took: render the frame only when its inputs moved, and read only the shown
voyage's rows; a real row-delta terminal write as the other option. The captain
answered (`M-6803`): take the first, and do the row-delta only if the board is
still over 3 % of one core. With the engine's own writes the board is 2.9 %, so
the row-delta was not taken; the synthetic worst case is 4.2 %, still under the
10 % acceptance line.

## Out of scope

- The row-delta terminal write (option 2 of the question) was not taken: the
  frame is still written whole when its text changed (T-403), and a frame that
  did not change is not written.
- The remaining rebuild cost is in the graph history, the one remaining table
  scan in `unsettled_deliveries` (the operations table has no
  `(project, kind, state)` index), and the waiting/quota/decision reads. An
  index or a cheap change fingerprint would cut it further; neither is in this
  task.
- `gear_board::run` (JSON and the one-frame path) is unchanged; it builds one
  board and renders once.

# T-516 — report (attempt 1)

The merge step no longer reads every done task of a project on every tick.

## The change

`crates/gear-engine/src/merge.rs`:

- `tell_captain_lost` (step 1b) is now gated in `merge_passed` itself, and the
  scan itself is untouched:
  - `LOST_SCAN_EVERY_S = 300` and the meta key `engine.lost_scan.<project>`,
    written when the scan runs, exactly as `branch_sweep_key` does for the
    branch sweep.
  - The scan runs when `now - last >= LOST_SCAN_EVERY_S`, and **at once in the
    tick after a merge op of the project reached a final state**: `Confirmed`
    or `Failed`. That is `merge_settled_at`, one read of the newest settled
    merge op (`updated`) per tick; a settled merge can leave an attempt lost, so
    the captain still hears about it in the very next tick (300 s would be too
    late for that case).
  - Before `merge_settled_at` existed there was no record of "a merge settled
    since the scan"; the timestamp comparison against the stored scan time is
    that record, and it costs one extra indexed query per state — the step
    already does seven of them for `merge_keys`.

Two existing unit tests in `merge.rs` (`an_open_lost_item_of_a_skipped_task_is_resolved`,
`an_open_lost_item_closes_while_a_merge_is_in_flight`) expected a second tick
1 s after the first to resolve an item. Under the new cadence they tick at
`+LOST_SCAN_EVERY_S`, where the scan is due again; a comment says why. Nothing
else about them changed.

## Measurement

`crates/gear-engine/tests/it/merge_scan_contract.rs`:

- `the_lost_scan_runs_once_every_five_minutes`: the first tick names a lost
  task; a lost task added after it is not named by the tick 10 s on, and is
  named by the tick 300 s on.
- `a_settled_merge_op_brings_the_next_scan_at_once`: for both `Confirmed` and
  `Failed`, a merge op settling at T0+5 makes the tick at T0+10 (still 290 s
  before the scan is due) scan and name a lost task.
- `an_idle_merge_step_on_five_hundred_done_tasks_is_under_a_hundred_milliseconds`:
  500 done tasks with merge times, the scan run once, then an idle tick.

Numbers, in-memory store, 500 done tasks, idle tick after the scan:

| step | idle `merge_passed` |
|---|---|
| scan on every tick (before) | **110 ms** (the test fails) |
| scan every 300 s (after) | **42 ms** |

The remaining 42 ms is the rest of the step on 500 tasks (the passed-task scan
and the merge-keys read), not the lost scan: on a real on-disk store of the
fleet's size the old path measured 2100–3300 ms a tick, which is the cost this
task removes. The acceptance bar — under 100 ms with no merge op and no change —
holds.

## Noted

- An open `merge-lost` item can now take up to 5 minutes (or the next settled
  merge) to be resolved or opened; that is the cadence the contract names, and
  every path that reads the item is unchanged.
- The trigger is the newest settled merge op of the project, so a project whose
  last merge settled before the last scan waits for the 300 s window; this is
  the intended behaviour ("at once in the tick after a merge op … reached a
  final state").

# T-516 — rework (attempt 2)

- **F1** (the failed gate): the idle-step test no longer gates the acceptance run
  on one wall-clock reading. It now pins the deterministic fact first — the idle
  tick does not move `engine.lost_scan.p`, so the scan did not run — and then
  takes the **best of three** idle ticks for the under-100 ms bar, so a single
  scheduling spike on a shared machine cannot fail it. `passed_tasks` was left
  alone: the best-of-three figure leaves the scan's cost out, and the remaining
  idle cost is the merge step's own reads, which the contract keeps.
- **F2**: the settled-merge trigger is now a word, not a scan. Where a merge op
  reaches a final state the step writes `engine.last_settled.<project>` — the
  worker collect (`Confirmed`), the PR land (`Confirmed`), `fail_merge`
  (`Failed`), and the two void/deny paths that take `Unknown` to `Failed` — and
  step 1b compares that against the scan's time. `merge_settled_at` and its two
  extra `ops_in_state` scans per tick are gone.
- **F4**: `an_attempt_with_a_queued_merge_is_not_named_lost` now seeds
  `engine.lost_scan.p` so the tick really runs the scan, and asserts the scan
  ran (the stored time moved to the tick's `now`): the empty inbox now means the
  queued-merge filter held, not that nothing was read.
- The `lost_task` fixture seeds the settle word along with its `Failed` op, the
  way production writes it; without it those T-397/T-408 unit tests would tick
  while the scan was not due. `an_open_lost_item_of_a_skipped_task_is_resolved`
  and `an_open_lost_item_closes_while_a_merge_is_in_flight` keep their
  `+LOST_SCAN_EVERY_S` ticks from attempt 1.
- **F3** stays logged, as the rework says: a merge that settles just before a
  tick whose scan is due can be seen on the following tick, so a newly-lost
  attempt may wait up to 300 s instead of one tick. The item is delayed, never
  dropped.

# T-454 — a notice to a working agent waits for its idle moment

## What changed

The M5 case (M-6183, T-407 rework): the overrun and quiet-lane notices were
typed into a lane running a 9-minute `make check`; pi stopped the command to
read them, twice, so the acceptance never finished. Two engine paths caused it,
both fixed:

- `crates/gear-engine/src/doorbell.rs`: `is_notice` names the engine's own
  sender (`NOTICE_SENDER` = `engine`), and `reaches_while_working` answers
  `false` for an engine message. The tick (`doorbell_inputs`) and `gear send`
  both read that one rule, so an engine notice — the overrun question, the
  no-push question, the think ask, every item the engine writes — is not typed
  into a working agent. It is stored as before and the doorbell rings it at the
  seat's next idle moment. `at_once` is unchanged for a seat's word: an urgent
  message, and every captain instruction to a lane whose agent queues input,
  still goes at once.
- `crates/gear-engine/src/ops.rs`, `check_op`: the T-241 escape that cuts a
  working lane's or reviewer's turn is now set only when a covered message is
  urgent **and** is not an engine notice. So an urgent engine notice no longer
  sends `esc` before the text either; an urgent captain instruction keeps its
  path (cut, then typed).

`docs/design/07-mail.md` §Doorbell states the T-454 exception next to the T-130
rule it narrows.

## Tests

`crates/gear-engine/tests/it/doorbell_while_working.rs` (real tick, FakeHerdr):

- `a_notice_to_a_working_lane_waits_for_its_idle_moment`: an urgent engine
  notice to a working `pi` lane produces no prompt and no `esc` and no doorbell
  op while the agent works; after the pane reports Idle the same tick types one
  doorbell naming the message and the op is Submitted.
- `an_urgent_captain_instruction_is_not_held`: with two working lanes, the
  captain's urgent instruction reaches the codex lane in the same tick while
  the engine notice to the other lane is held; the notice arrives once that
  lane is idle.

The existing T-130 tests (working pi lane gets a captain instruction, working
codex lane gets an urgent message at once, normal message waits for idle) pass
unchanged.

## Out of scope, for the captain

- A reviewer's overrun question is an engine notice too, so it now waits for
  the reviewer's idle moment instead of cutting a running review command. The
  review-slot exception in `doorbell_inputs` still lets it ring as soon as the
  reviewer is idle. During a long review turn it arrives only when the reviewer
  stops; the round's own "no answer" item still reaches the captain after 10
  active minutes. Asked the captain; default taken: it waits like any notice.
- `gear send`'s immediate path (`ring_recipient_now`, `deliver_doorbell_now`)
  is unchanged: only seats send there, and a seat's word keeps its path.
- The loop guard's own `esc` (`quiet::loops`, T-288's busy interrupt) is a
  separate mechanism and is not touched.

## Friction

The packet's "notice" boundary needed one reading: whether the reviewer's
overrun question is a notice like the rest. The contract says "a notice to a
busy seat"; I took that to include it and asked the captain (default: held).

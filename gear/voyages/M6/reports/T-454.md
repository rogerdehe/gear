# T-454 — a notice to a working agent waits for its idle moment

## What changed

The M5 case (M-6183, T-407 rework): the overrun and quiet-lane notices were
typed into a lane running a 9-minute `make check`; pi stopped the command to
read them, twice, so the acceptance never finished. Two engine paths caused it,
both fixed:

- `crates/gear-engine/src/doorbell.rs`: `is_notice` names the engine's own
  sender (`NOTICE_SENDER` = `engine`), and `reaches_while_working` answers
  `false` for an engine message, so the tick (`doorbell_inputs`) and `gear send`
  never type a notice into a working agent. The notice is stored as before and
  the doorbell rings it at the seat's next idle moment. `at_once` is unchanged
  for a seat's word: an urgent message, and every captain instruction to a lane
  whose agent queues input, still goes at once.
- `crates/gear-engine/src/ops.rs`, `check_op`: the T-241 escape that cuts a
  working lane's or reviewer's turn is set only for a seat's own urgent message.
  An urgent engine notice no longer sends `esc` before its text; an urgent
  captain instruction keeps its path (cut, then typed).

Contract v2 adds the one exception, implemented: the notice that closes a
direction check under its reviewer (T-444,
`The direction check of … is closed …`) is not held. `ends_direction_check`
recognises it, so `reaches_while_working` lets it into a working reviewer, and
`check_op` cuts that turn first (the profile's interrupt key, the same escape
an urgent doorbell uses) and then delivers the notice, so the reviewer ends its
turn at once. Every other engine notice — the quiet, no-push, think and overrun
ones — waits.

`docs/design/07-mail.md` §Doorbell states the T-454 rule and the T-444
exception next to the T-130 rule they narrow.

## Tests

`crates/gear-engine/tests/it/doorbell_while_working.rs` (real tick, FakeHerdr):

- `a_notice_to_a_working_lane_waits_for_its_idle_moment`: an urgent engine
  notice to a working `pi` lane produces no prompt, no `esc` and no doorbell op
  while the agent works; after the pane reports Idle the same tick types one
  doorbell naming the message and the op is Submitted.
- `an_urgent_captain_instruction_is_not_held`: with two working lanes, the
  captain's urgent instruction reaches the codex lane in the same tick while
  the engine notice to the other lane is held; the notice arrives once that
  lane is idle.

`crates/gear-engine/src/ops.rs` (execute_intended):

- `the_direction_closed_notice_cuts_a_working_reviewers_turn_first`: a working
  reviewer is sent the escape before the notice, and the notice is typed.
- `an_ordinary_notice_to_a_working_reviewer_waits`: no escape, no text; the op
  covers nothing, so the message waits for the next idle moment.

`crates/gear-engine/tests/it/doorbell_contract.rs`
`a_notice_waits_for_idle_except_the_direction_closed_one`: the rule at the
decision point — an urgent engine notice waits for a lane and for a reviewer,
the direction-closed notice reaches the reviewer, and a captain's urgent
message and captain instruction still reach a working `pi` lane.

The existing T-130 tests (working pi lane gets a captain instruction, working
codex lane gets an urgent message at once, normal message waits for idle) and
the T-444 direction tests pass unchanged.

## Out of scope, for the captain

- A reviewer's overrun question is an engine notice too, so it now waits for
  the reviewer's idle moment (the captain's answer, M-6567: that is right; the
  direction-closed notice is the only exception). The review-slot exception in
  `doorbell_inputs` still lets it ring as soon as the reviewer is idle; the
  round's own "no answer" item still reaches the captain after 10 active
  minutes.
- `gear send`'s immediate path (`ring_recipient_now`, `deliver_doorbell_now`)
  is unchanged: only seats send there, and a seat's word keeps its path.
- The loop guard's own `esc` (`quiet::loops`, T-288's busy interrupt) is a
  separate mechanism and is not touched.

## Friction

The contract moved to v2 while the v1 work was in hand: the direction-closed
notice had to keep the at-once path after the first full check had already run,
so the acceptance suite ran twice (132 s and 66 s of test time). The reviewer
overrun question was asked and answered (M-6567) in time.

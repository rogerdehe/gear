# T-457 — Codex 0.165's startup screens

Lane mast · contract v1 · branch `mast/t457` · candidate `6c45521e`

## What changed

**gear-herdr (`crates/gear-herdr/src/profile.rs`, `src/lib.rs`)**

- `Profile` gains `dialogs: Vec<Dialog>`: a dialog is a screen a CLI opens
  that must be answered before its composer takes text, with the lines that
  identify it and the keys that answer it.
- `classify_screen` reads a dialog screen as `ScreenFlag::Blocked`, although
  Herdr reports the agent done/idle while the dialog waits.
- `Profile::dialog(screen)` returns the open dialog (tail window only, like
  every other marker).
- `gear_herdr::answer_dialog(herdr, pane, profile)` reads the pane's tail and
  sends the answer keys; `None` when no dialog is open or the screen cannot
  be read (nothing is sent).
- codex profile:
  - dialogs: `Where should the new conversation run?` (and the fork form
    `Where should the forked conversation run?`) → `enter`, the preselected
    `Use current Git worktree`, so the seat keeps working in its own
    worktree.
  - dialogs: `Choose which working directory to use` /
    `Current = your current working directory` → `enter`, the preselected
    current directory (the seat's own).
  - start args gain `-c tui.resume_cwd="current"` (Codex 0.165's own
    setting, read from the installed binary's strings): a resume uses the
    directory Codex was started in — the seat's own worktree — and the
    resume dialog never shows. The dialog answer stays as the fallback.
- The session command stays one `pane.send_text` call (one go), tested.

**gear-engine (`crates/gear-engine/src/session_runner.rs`, `session.rs`)**

- A `new` or `resume` session step answers an open startup dialog with the
  profile's keys and waits one tick before it records the session, so the
  next delivery's text no longer lands in the dialog.
- `guardrails.rs`: the captain notice for a Blocked screen now names both
  causes — a guardrails refusal or a startup dialog waiting for an answer.

**Tests**

- `crates/gear-herdr/tests/it/codex_dialogs_contract.rs` (new, registered in
  `tests/it/main.rs`): the two M5 screens as fixtures — the `/new` screen
  and the resume directory screen — are read as Blocked, are recognised as
  the codex dialogs, are answered with `enter`, the resume start args carry
  `tui.resume_cwd="current"`, a plain composer is no dialog and gets no key,
  and a slash command is typed in one call.
- `crates/gear-engine/src/session.rs`: a codex `/new` whose screen shows the
  worktree dialog is answered before the session is recorded; once the
  dialog is gone the step records `new-unconfirmed` on the usual timing.
- `builtin_contract.rs` / `profile.rs` unit test: the pinned codex start-arg
  lists carry the new `tui.resume_cwd` pair.
- The `Profile` literals in engine tests carry the new empty `dialogs` field.

## Facts checked against the installed codex-cli 0.165.0

The dialog texts and the config key were taken from the installed binary
(`@openai/codex` 0.165.0, the native binary's strings), not guessed:

- `Where should the new conversation run?` / `Where should the forked
  conversation run?`, `Use current Git worktree` — `Keep using the current
  working directory`, `Create new Git worktree` — `Create a separate checkout
  of this repository in another directory`.
- `Current = your current working directory`, `Use session directory (`,
  `Choose which working directory to use when the current directory and
  saved session differ`.
- `tui.resume_cwd` with `ask` / `current` / `session`; the binary's own error
  text names `tui.resume_cwd = "current"` (needs `--cd` only for a remote
  workspace, which GEAR does not use).

The resume screen fixture orders `Current = your current working directory`
first; the binary's string order suggests it, and with `tui.resume_cwd`
the dialog does not show, so the order does not decide the seat's directory.

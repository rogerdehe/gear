# T-517 — report (attempt 1)

The engine's tick reads only the rows it needs: schema v8.

## The change

`crates/gear-store/src/schema.sql` and `migrate.rs` (v8, `step_7_to_8`):

| index | serves | what it replaces |
|---|---|---|
| `operations_state (project, state, created, id)` | `ops_in_state` | a scan of the whole `operations` table on every call |
| `messages_thread (project, thread, created, id)` | `thread_messages` | a scan of the whole `messages` table on every call |
| `attempts_seat (seat, state, task, n)` | `open_attempts_of_seat`, the seat's attempts | `SCAN attempts` |
| `rounds_seat (seat, start_at)` | `open_round_of_seat`, the seat's last round | `SCAN rounds` |

The first two are the contract's own; the last two are the other full-table
scans of the tick's tables that `EXPLAIN QUERY PLAN` found. Everything else the
engine calls each tick was already answered by an existing index — I checked
each (`messages_to_since`/`messages_from_since`/`messages_open_to`,
`rounds_of_project`, `rounds_to_process`, `rounds_of_task`, `review_budget_min`,
`attempts_of_task`, `attempt_times_of_task`, `ops_of_project_kind`,
`ops_of_seat_kind`, `ops of a seat`, the message reads by task and attempt): a
`SEARCH … USING INDEX` with at most a temp B-tree for the `ORDER BY`, no
`SCAN`.

No row changes: the migration only creates the indexes, so an existing store
gains them when it is opened — that is why this is a schema step rather than
only a `schema.sql` edit (a store already stamped at the current version never
re-reads `schema.sql`).

## Tests

`crates/gear-store/tests/it/read_indexes_contract.rs`:

- `a_fresh_store_has_the_indexes_the_tick_reads_by`: for each of the four reads
  the plan is a `SEARCH` on the named index, with no `SCAN operations`,
  `SCAN messages`, `SCAN attempts` or `SCAN rounds`.
- `an_older_store_gains_the_indexes_when_it_is_opened`: the same store taken
  back to v7 (indexes dropped, stamp set to 7) is answered by the autoindex
  alone; opening it carries it to `SCHEMA_VERSION` and the plans hold.
- `a_hundred_reads_on_five_thousand_rows_stay_under_two_hundred_milliseconds`:
  5000 operations and 5000 messages, of which the state the engine asks for and
  the thread it reads hold 50 rows each; 100 `ops_in_state` calls and 100
  `thread_messages` calls each stay under 200 ms on the store file, and the
  plans still hold on the big store.

`v7_contract`'s pin `assert_eq!(SCHEMA_VERSION, 7)` becomes 8 (that test reads
what the binary writes; the v6 fixture is still carried all the way up and the
v7 column is still there).

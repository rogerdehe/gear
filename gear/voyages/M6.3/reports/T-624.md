# T-624 — report

A feature's spread deps are kept apart from a member's own (Lawrence M2: T-86's
block said `deps: -` and the apply kept T-63, T-79 and T-80; they were F-4's
outside wait, written into every member's stored deps, so every later apply read
them back as the member's own).

## What changed

- `crates/gear-app/src/plan.rs`, rule (3) of the feature deps: the spread is
  recorded per feature in meta `feature_wait:{project}:{feature}` as a JSON
  object of outside dep → the member that declares it.
- At the start of each apply, the previously recorded spread is stripped from
  every member's stored deps before the graph is read; the spread is computed
  again from the members' own deps (the stripped stored deps plus the draft's
  deps) and stored again. An unmentioned member's stored deps are set to the
  graph's deps, so a spread that changed reaches it too.
- The apply prints one line per member that waits on work it did not name:
  `T-86 waits on T-63 (F-4: T-89 needs it)`.
- `gear plan show T-n` prints the spread on its own line
  (`waits (feature F-4): T-63, T-79, T-80`), not in `deps:`; the `deps:` line
  is the member's own deps.
- New `feature_wait_key` and `feature_wait` helpers.

## Out of scope

- A feature whose members are all terminal keeps its `feature_wait` meta; the
  strip reads it but the terminal members are not rewritten.
- The spread meta is a JSON object; a malformed value is read as empty.

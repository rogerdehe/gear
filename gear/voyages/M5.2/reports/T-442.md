# T-442 — report

Plan apply now refuses a task whose milestone no plan describes, before
anything is written: a `NEW` block, or an existing task's block that changes
its milestone, whose `milestone=` names a milestone with neither a
`# Milestone <id>` block in this plan file nor a stored voyage with a non-empty
done sentence. A made-up id or a typo therefore never becomes a voyage row
with a departure and no words (the other project's `M1.1-cancelled`, whose
departure later won the board).

## What changed

`crates/gear-app/src/plan.rs` only:

- `fn milestone_described(tx, project, draft, milestone) -> GearResult<bool>` —
  the two things T-442 accepts as a description: a `# Milestone <id>` block in
  the draft's own file (`draft.milestones`, read with `milestone_parts`), or a
  stored voyage whose `done` is set and not blank (the words an earlier apply
  recorded, the same test `crate::goal::missing_blocks` makes).
- In the step-5 validation loop of `fn apply_queue` (after the existing
  state/field checks of a block, before the estimate cap and before any queue
  write): for a block whose `milestone=` is set and that **moves** the task —
  a `NEW` block always, an existing task's block when its `milestone` differs
  from the stored one — an undescribed milestone is refused with
  `bad(item.line, "<task>: milestone <id> is not described: add a `# Milestone
  <id>` block with its done, bar and eta, or use a milestone the plan
  describes")`. The task is `T-<n>`, or `NEW` for a new block, the wording the
  neighbouring checks use for one. A task already in such a milestone that the
  plan does not move is history: nothing is refused, and cancelling keeps its
  milestone — a cancelled block that *moves* a task is checked like any other.
- The step-5 bullet of the `apply` doc comment lists the new rule.

## Tests

`crates/gear-app/tests/it/voyage_contract.rs`:

- `a_new_task_on_a_milestone_no_plan_describes_is_refused` (new) — a `NEW`
  block on `M1.1-cancelled`: `BadFormat` with the text, and nothing written
  (plan version 0, no task, no voyage row).
- `a_task_moved_to_a_milestone_no_plan_describes_is_refused` (new) — a block
  moving `T-1` to `M1.1-cancelled` is refused with the text; the same line
  with `state: cancelled` (a move, since the milestone changes) is refused too;
  after both, plan version, milestone, state and the absence of a voyage row
  are unchanged.
- `a_task_moved_to_a_milestone_the_store_describes_is_applied` (new) — two
  applied voyages, then a queue-only plan that moves `T-1` into `M2`: it
  applies, and the `# Milestone M2` block comes back into the file (T-333).
- `a_task_already_in_an_undescribed_milestone_is_left_alone` (new) — `T-1` is
  stored on `M0` with no block and no voyage (history); a `state: cancelled`
  line naming the same `M0` is not a move: it applies, asks for no block the
  milestone cannot give, and the task keeps `milestone=M0` (see the question
  sent to the captain about the acceptance's wording of this case).
- `the_departure_is_the_first_task_creation_even_without_the_block` (T-333,
  one assertion changed) — its first apply refuses a `NEW` block on an
  undescribed `M1` with the new text instead of T-333's, which the new check
  now reaches first.

Every other `voyage_contract::` and `plan_apply_contract::` test is unchanged
and passes.

## Friction

- The acceptance says `make check CRATE=gear-app TESTS='<nextest filter>'`, but
  the `check` target does not read `TESTS`: the variable is silently dropped
  and the whole crate runs in about 20 s. Not a blocker here, but the packet's
  narrower command cannot be run as written.
- The acceptance's "an existing task already in an undescribed milestone and
  not moved applies untouched" cannot hold for a block that restates
  `milestone=<M>`: `crate::goal::missing_blocks` (T-333, outside this contract)
  refuses such a non-cancelled block first. Asked the captain, went on with the
  cancelled-line form (question, thread `hull:276`).

## Out of scope (noticed, not changed)

- `fn fix_departures` still writes a departure-only voyage row for the
  milestone of a task the queue does not mention at all, so an old wordless
  milestone in the store keeps getting a departure from any apply; T-441's
  board now ignores those for the fallback, and T-442's contract names only the
  blocks that move a task.
- `crate::goal::missing_blocks` keeps its own T-333 refusal for a non-cancelled
  block naming an undescribed milestone; for the cases T-442 covers, the new
  check now answers first with the milestone-focused text.

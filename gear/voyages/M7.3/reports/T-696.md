# T-696 — the merged checks accept a squash

## What changed

Replaced ancestry tests with `gear_app::base::landed_in(dir, reference, commit)`
in `crates/gear-engine`:

- `merge.rs` `prepare_merge`: the `already` answer (the candidate is on
  `base_ref`). It is now computed before step 3, and step 3's "on no pushed ref"
  failure is skipped when `already` is true: a squash closes the task's branch,
  so a restart after a squash must still answer "already merged".
- `merge.rs` `on_a_stable_branch` (the lost scan's finished-voyage check).
- `merge.rs` `land_carried` (the carried-task check).
- `merge.rs` the lost scan's two remaining "is this candidate merged" checks
  (the `told` branch and the open-voyage branch) — both are the same question
  and the acceptance's lost-merge case reaches the second one.
- `parallel.rs` the "candidate already in its base" test
  (`ancestor(&input.repo, &candidate, &base_tip)`).

Every site keeps its previous behaviour on a git error: `landed_in`'s `Err` is
`unwrap_or(false)`, so a check that cannot answer does not pass.

## Tests (acceptance)

- `merge::tests::a_restart_after_a_squash_merge_says_it_was_already_merged`:
  a squash commit on dev names the candidate in `Gear-Candidate:`, the task's
  branches are gone; the same merge op restarts, says "already merged" and
  pushes nothing.
- `merge::tests::a_squashed_candidate_is_not_named_lost`: the lost-merge scan
  does not open a merge-lost item for a candidate named by a squashed commit,
  and keeps the landed answer.
- `parallel::tests::a_task_squashed_onto_the_integration_branch_is_not_an_open_change`:
  a task squashed onto dev is not an open change: no overlap and no pair.

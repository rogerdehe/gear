## Findings
- F1 [P0, blocking] `branch_on_release` (finished.rs:1199) builds the integration ref from `config.conventions.integration` instead of the repo's own `repo.integration`. The reclaim loops every repo in `config.repos()` (finished.rs:309), and a `[[repos]]` entry can override `integration` (`config.rs` `repo_of_section`, line 161). For a child repo whose integration is `p/feature` while the project default stays `dev`, the deletion guard (finished.rs:476) checks `origin/dev` against release; when `dev` is on release it returns true and deletes `p/feature` even though it holds unreleased work — lost work, a broken safety rule. The `else` branch right below it uses `repo.integration` correctly (finished.rs:488), which makes the inconsistency plain. Fix: pass the repo's integration into the function — change `branch_on_release(repo, config, release)` to take an `integration: &str` (or pass `&repo.integration`), call it at finished.rs:476 with `&repo.integration`, and use that value in the `adds_nothing` ref at finished.rs:1199. ~3 lines.

- F2 [P3, logged] The records-only item is written Open on thread `records:<milestone>` (finished.rs:514). On the next scan `merge_records` sees the captain's branch is gone (`Recorded::Missing`) and `resolve_records` (finished.rs:1060) resolves the first Open message on that thread — this item — with the reason "there is no branch p/captain/M1 on the remote". The line and the once-only meta key still hold (so the acceptance "a second scan writes nothing" passes), but the notice is auto-closed with a reason that is about the captain's branch, not the notice. Not blocking: no data is lost and the text remains. A minimal guard would resolve only the records-merge items (match their body) or give this notice its own thread.

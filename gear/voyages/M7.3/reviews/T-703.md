Correctly treated as out of scope, not hidden.

## Findings
- F1 [P2, logged] A confirmed apply on a departed voyage names `current_voyage`, not the departed voyage the draft is confirming — crates/gear-app/src/plan.rs:3922. The `None if draft.confirmed` arm is never exercised by the tests (`a_departing_apply_names_the_eta_against_the_measured_speed` carries `depart: now`, so it hits the `departing` arm), and `current_voyage` picks "the last departed voyage that is still open", so a confirmed change to a non-current departed voyage prints the wrong voyage's eta and open-task sum. Fix: derive the milestone from the draft's milestone blocks whose stored voyage has a departure (the first `draft.milestones` id for which `tx.get_voyage` reports `departure.is_some()` and an eta), instead of `current_voyage`, and add one test that confirms a departed voyage without a `depart: now` line — about 6 lines.
- F2 [P3, logged] The eta line reads `task.estimate_min.unwrap_or(0)` directly — crates/gear-app/src/plan.rs:3941 — so a legacy task with no stored `estimate_min` but a goal that says "Estimate: …" is counted as 0, unlike `gear_board::voyage::estimate_of` (used by `record_voyages` for `departure_estimate_min`). It only undercounts the advisory number. Fix: use `gear_board::voyage::estimate_of(tx, project, &task)?.unwrap_or(0)` as the estimate; about 2 lines.
- F3 [P3, logged] `estimate_warning`'s doc comment says "more than twice the calibrated minutes, or less than half of them" — crates/gear-app/src/plan.rs:3873 — but the code compares the estimate with `speed.median_work_min` (plan.rs:3898). The comment misleads the next reader. Fix: reword to "more than twice the measured median work time, or less than half of it"; 1 line.

## Set aside
- A voyage with no open tasks prints no eta line (there is no lane sum to name); a task without an estimate contributes 0 to its lane. Both are the only sensible reading of "open tasks at about <h>" and are disclosed in the report.
- The per-lane sum accumulates into `u32` (`*per_lane.entry(lane).or_default() += minutes`); overflow needs absurd totals (hundreds of tasks at the u32 estimate ceiling) — outside normal use.
- A model with ≥5 measured work-time samples but fewer estimates still yields a `calibrated` value: this is T-702's accepted `samples` semantics (`ModelSpeed` cannot distinguish ratio samples), inherited here, not introduced by this task.
- The "less than half" direction (ratio > 2, estimate under the median by more than half) is implemented correctly but untested; the acceptance only names the 0.2 direction, so it is not a gap against the contract's tests.

# T-78 — the forge layer: `crates/gear-forge`, GitHub through `gh` (attempt 2)

Scope: T-78 rework of review finding F1 — a claim is opened as a draft, and
GitHub refuses to merge a draft, so the ordinary claim → hand-in → verdict →
merge path had to be completed inside the crate: the merge now turns the claim
ready first, with no hand. F2 and F3 stay logged, per the review.

Branch: base/t78 (code @ the hand-in commit; origin/dev merged before
verification, gate green on the merged result)

What changed in this rework:
- `crates/gear-forge/src/github.rs` — `GitHub::merge` now calls `make_ready`
  first: it reads `gh pr view <n> --repo … --json isDraft` (typed
  `Unreadable` on nonsense) and, only when the pull request is a draft, calls
  the bounded `gh pr ready <n> --repo …`. A pull request that is already ready
  — a retry after a failed merge, or one opened by hand — is left alone, so
  the step is idempotent and no call is repeated. A failed readiness is the
  `Failed`/`Timeout`/`Tool` error of that call, and nothing is merged after it.
- `crates/gear-forge/tests/it/github_contract.rs` — the fake `gh` now answers
  per call (`out-<cmd>-<sub>`, `err-…`, `code-…`, falling back to the generic
  answer) and records the sequence of calls, so the draft path can be driven
  through claim → view → ready → merge. Three new tests: a draft claim is made
  ready before it merges (the exact call sequence, and the merge command line),
  an already-ready pull request is not made ready again (no `pr ready` call),
  and a failed readiness is a typed `Failed` with no merge after it. The
  existing merge, unreadable-answer and no-call tests were updated to the new
  sequence.
- `ops/reports/T-78.md` — this brief.

Everything from attempt 1 stands: the `Forge` trait and its types, `GitHub`
over `gh` (explicit repo, JSON, no prompts, 30 s bound, typed errors),
`Local` as the no-op forge, and the ORCHESTRATE `CLAIM`/`COMPLETION` markers.
The crate remains a workspace member and a `[workspace.dependencies]` entry.

Logged, not reworked (the review's F2 and F3, both P2 and explicitly not part
of this rework):
- F2 — `gh pr merge` exits 0 for a queued PR, and this crate reports
  `merged: true`. A merge-queue state read (`gh pr view --json state`) is the
  follow-up; this voyage has no queue requirement.
- F3 — after the child exits, the output reader waits for pipe EOF without the
  deadline, so a descendant holding the pipe delays the answer past the bound.
  A `recv_timeout` against the deadline, and draining stdout and stderr
  concurrently, are the follow-up.

# T-62 — A task whose commits carry another task's work waits for that task

Attempt 2, contract v1 — the rework of the two blocking findings of attempt 1
(F1: only the latest attempt's candidate was checked, so a task built on an
earlier, rejected attempt of another task did not wait; F2: waiting merges
could starve each other, and a wait's reason did not refresh).

A merge whose candidate carries the work of another task does not go through
before that task has landed on the integration branch. The wait is not a
failure: the merge goes back to the queue, and the captain is told once which
task it waits for.

**What this branch carries.** T-61 (the merge of the approved candidate, with
its F1/F2 rework) is on `dev` now, and this branch is cut from the same line,
so it adds only the T-62 work below to T-61's code.

## What changed

`crates/gear-engine/src/merge.rs`:

- **The merge asks what its candidate carries.** Before it merges, the worker
  looks at the other tasks of the project — **every attempt's candidate**, not
  only the latest (F1): a task that reworked handed in a new candidate, and
  the task built on the older branch carries the older, now rejected work. It
  asks git, in the merge worktree and after its fetch: is that candidate an
  ancestor of this candidate, and is it on the integration branch yet? A
  candidate that is an ancestor, is not on the integration branch and is not
  the same commit is **carried work**: the task it belongs to has not landed
  yet. A task that handed in several attempts is one task to wait for (the
  first carried one wins), not three.
- **A merge that carries work waits.** It returns `Waiting` with the tasks it
  waits for; the engine puts the op back in the queue (`Unknown`, with the
  reason `waits for T-<n>`) instead of failing it. Nothing is pushed, and the
  integration branch stays where it was.
- **The captain is told once.** One open item per waiting merge (the thread
  `merge-wait:<task>`), naming the task it waits for and saying whether that
  task has passed its review. A tick that finds the item already open updates
  its text instead of adding a second one. The item closes when the merge goes
  through (or when the merge is voided).
- **A waiting merge goes last in the queue, and the waiting ones take turns
  (F2).** The merge of the task a waiting merge waits for must be able to land
  first; among the waiting merges the one that has waited longest runs first
  (sorted by the op's `updated`, which every retry refreshes), so no waiting
  task starves behind another. This matters after a restart, when every op is
  `Unknown`: without the turn-taking the oldest-waiting op would take the
  worker every tick and the others would never run.
- **The same commit is not carried work.** Two tasks may hand in the same
  commit; neither of them waits for the other.

## Acceptance evidence (tests with real git, in `crates/gear-engine/src/merge.rs`)

- `a_merge_waits_for_the_task_its_commits_carry` — the whole path with no
  hand edit in the store: T-2 is built on T-1's branch and passes first. The
  engine queues T-2's merge itself and runs it: the merge waits (the op is
  `Unknown` with `waits for T-1`, not `Failed`), the integration branch is
  untouched, and the captain's inbox holds exactly one item naming T-1 and
  saying it has not passed its review. Later ticks do not add a second item.
  T-1 passes: T-1's merge lands first, then T-2's, and the captain's item
  closes.
- `a_merge_that_carries_no_other_task_is_not_held` — T-2 is cut from `dev`,
  not from T-1's branch: T-2's merge goes through while T-1 has not passed,
  and the captain is not told about a wait that did not happen.
- `a_waiting_merge_goes_last_in_the_queue` — the ordering rule itself: a
  merge that waits goes after the one that can run.
- `a_merge_waits_for_an_earlier_attempt_of_the_task_it_carries` (F1) — T-1
  handed in attempt 1, was sent back and handed in attempt 2; T-2 was built on
  attempt 1 (the rework is outside T-2's history). T-2's merge waits for T-1;
  when the rework passes, T-1 lands first, then T-2.
- `waiting_merges_take_turns_and_a_chain_lands_in_order` (F2) — T-3 is built on
  T-2 on T-1; the three verdicts arrive deepest first, each merge finds its
  wait, the engine restarts (every waiting op is `Unknown`), and the chain
  still lands in order: T-1, then T-2, then T-3.

## Validation

- `cargo test --workspace` → **684 passed, 0 failed** (the merge module: 36).
- `cargo build --workspace --all-targets` → exit 0, no warnings.
- `git diff --check` → clean.
- The tests fail when the engine does the wrong thing (each mutation reverted
  afterwards):
  - the carried check removed → `a_merge_waits_for_the_task_its_commits_carry`
    fails (T-2 lands before T-1 passed);
  - the queue order rule removed → `a_waiting_merge_goes_last_in_the_queue`
    fails;
  - the one-item rule removed → `a_merge_waits_for_the_task_its_commits_carry`
    fails (four items in the captain's inbox instead of one);
  - only the latest attempt's candidate checked (F1) →
    `a_merge_waits_for_an_earlier_attempt_of_the_task_it_carries` fails;
  - the turn-taking removed (F2) →
    `waiting_merges_take_turns_and_a_chain_lands_in_order` fails;
  - the wait's reason/time not refreshed on an `Unknown` op (F2) → the same
    test fails.

They were fixed on `steady/t61` and land with T-61's merge; this branch

- F3 (a pushed tag is not a pushed ref) is logged, not reworked.

## Out of scope

- A task that is cancelled never passes, so a merge that carries its work
  waits until the captain acts (the line says which task it waits for). The
  engine does not decide that a cancelled task's work may ride in with the
  task built on it.
- A merge whose carried task was merged by hand with a squash waits: its
  candidate is not an ancestor of the integration branch. GEAR merges with
  `--no-ff`, so its own merges never do that.
- The captain's item about a wait is closed by this task's engine when the
  merge goes through; T-70's alert life cycle (one item per fact, resolved by
  the engine when the cause clears) still owns the other kinds.

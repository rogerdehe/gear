# T-89 — Onboarding waits for the shell before starting the agent

Attempt 1, contract v1.

Branch: `course/t89`; the candidate named in the hand-in includes this
report. Base: `origin/dev` at 6379d19, merged into the branch before the
hand-in.

## What shipped

After the environment line is typed into a fresh worktree's pane, the start
waits for the shell instead of failing on the first refusal: Herdr answers
`agent_pane_busy` while the shell still runs the environment line (a slow
`nvm`/plugin init is the normal case), and that answer is **not yet**, not a
failure.

- the wait is bounded — `EngineCfg.pane_busy_limit_s`, default **20 s** —
  and between two attempts it waits `pane_busy_wait_ms` (default 250 ms), so
  a fast shell starts almost at once;
- the first refusal never parks a lane: it is retried until the shell is
  free, and the lane goes Active;
- only when the wait runs out does the seat park in NeedsCheck, with a
  reason that says what happened:
  `agent_start: refused (agent_pane_busy): the shell was still busy after 20s (the environment line has not finished)`.

The two settings are on `EngineCfg` so the tests do not sleep 20 s; the
production defaults are the goal's numbers. The fake Herdr's single refusal
(`refuse_next_start`) became a counted one (`refuse_starts: Option<(String,
u32)>`), so a shell busy for several attempts can be modelled.

## Acceptance evidence

- `onboard::tests::a_busy_shell_at_start_is_retried`: one `agent_pane_busy`,
  then the start succeeds → the lane is **Active**, not NeedsCheck.

## One deviation, stated

The goal suggests retrying "on the next tick". The wait here is **in place**
(bounded to 20 s), because the onboarding creates the seat's generation and
binding *before* the start: a retry on a later tick would have to resume
that half-done onboarding, and `SeatState` deliberately has no
`Starting → Starting` transition. A cross-tick retry is a resume path of its
own (like the model-switch one) and is logged, not built here. The
acceptance's two facts hold either way: a first `agent_pane_busy` never
parks, and a shell busy past the limit does — with the reason.

The in-place wait costs the tick up to 20 s, once per lane at onboarding
(three lanes = at most a minute at a cold start), and only when a shell is
actually slow. Every later tick is unaffected.

## A test race found on the way (fixed)

`onboard_run_contract::grok_is_trusted_and_started…` flaked: grok's trust
file is written under `HOME`, two tests in the same binary set `HOME`
process-wide, and one could write into the other's temp home (the failure
showed a `/fake-worktrees/home-heat` entry in the other test's file). Both
grok-onboarding tests now take a shared `HOME_LOCK` and one of them sets a
temp `HOME` (before, it wrote into the real `~/.grok`). Four consecutive runs
of the suite are clean.

The traces earlier runs already left in the developer's
`~/.grok/trusted_folders.toml` (`/fake-worktrees/*` entries) are not removed
by this task: that file is the user's.

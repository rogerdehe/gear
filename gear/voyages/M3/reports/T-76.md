# T-76 — Codex's first-run "Trust this folder?" dialog never stops a seat

Attempt 1, contract v1.

Branch: `course/t76`; the candidate named in the hand-in includes this
report. Base: `origin/dev` merged into the branch before the hand-in.

## What shipped

The codex profile's start args now trust the folder the agent runs in
(trial G08), and the engine fills the folder in per worktree:

```
--dangerously-bypass-approvals-and-sandbox
-c check_for_update_on_startup=false
-c projects={"/<canonical worktree>"={trust_level="trusted"}}
```

- `crates/gear-herdr/src/profile.rs`: the codex profile's `unattended_args`
  carry `projects={"{repo_root}"={trust_level="trusted"}}`, and
  `render_args(args, folder)` fills `{repo_root}`. It writes the folder **as
  the filesystem resolves it** (`std::fs::canonicalize`): Codex canonicalises
  its working directory and looks the folder up by the canonical path, so a
  symlinked path (a temp dir's `/var`, a linked checkout) does not match. A
  path that does not exist is written as it came.
- `crates/gear-engine`: the three `agent_start` sites render the args —
  onboarding (`created.path`), a reviewer's start (its worktree), and a
  restart (the seat's worktree; a seat from before the worktree was recorded
  falls back to the root of its lane's repo, which Codex trusts the same way).
  Only worktrees the engine made for the project's registered repos are ever
  filled in.

## Two details found live, and the form that works

- **The dotted spelling from the goal is silently ignored by Codex.**
  `-c 'projects."<path>".trust_level="trusted"'` neither trusts the folder nor
  warns about itself (checked with a deliberately bogus value too). Codex's
  own writer uses `projects."<key>".trust_level` in its **config file**, which
  works; on the command line the inline table is the form that takes effect:
  `-c 'projects={"<path>"={trust_level="trusted"}}'`. The profile uses it.
- **The path must be canonical.** With the inline table and the worktree's
  path as `-c` was given it (`/var/folders/…`, a symlink), the dialog still
  appeared; with the resolved path (`/private/var/folders/…`) it did not.

## Live check (stated as the acceptance asks)

A scratch repo with a bare origin, a `dev` checkout and a fresh worktree
`home/heat` cut from it; Codex's TUI (codex-cli 0.164.0) run in a pty in that
worktree, with a fake provider so no quota was used:

- **Without** the trust arg the TUI shows exactly the trial's dialog:
  `Trust this folder? Codex can read, edit, and run files here…  › 1. Trust and
  continue  2. Quit`, with `Note: You're in a subdirectory of a Git project.
  Trusting will apply to the repository root: /…/<repo root>`.
- **With** `-c 'projects={"/private/…/home-heat"={trust_level="trusted"}}'` the
  TUI goes straight to the composer (`› Ask Codex to do anything`), no dialog.

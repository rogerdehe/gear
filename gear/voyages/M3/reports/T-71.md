# T-71 — No seat is rung with an earlier job's or voyage's messages, and a new agent gets its task before any doorbell

Attempt 2, contract v3 — the rework of the two blocking findings of attempt 1
(F1: a temp seat was still rung for an answer about the task of its previous
job when that answer was written after the new job started; F2: the generation
filter also hid the captain's open items after a handover). F3 is logged, not
reworked, as the captain decided.

A seat is only rung for the messages of its **current generation**, and a seat
that is being handed work is not rung in the same tick. The trial saw both go
wrong: a fresh reviewer first read "6 item(s) waiting for you (1 urgent)" and
only then its packet (on T-61 both went into its pane in one second and the
packet was swallowed), and a re-registered lane spent its first turn on the
previous voyage's messages.

## The cause

A warm temp seat keeps its id across jobs (and a lane keeps its name across
voyages), so the seat's id says nothing about which job a message belongs to.
The doorbell counted messages from time 0 (`messages_to_since(.., 0)`) and
matched them against the views of the current generation, so the answers to an
earlier job looked unshown for ever. The tick also decided the doorbells
*before* it created the deliveries of the same tick, so a seat could get both
in one second.

## What changed

- **`crates/gear-app/src/seats.rs`** — `generation_started(tx, seat, generation)`,
  `generation_since(..)` and `message_belongs(seat, message, since)`: the
  generation starts when its binding is opened
  (`begin_onboard` writes the binding in the same transaction that bumps the
  generation), so the binding's `created` is the moment. `generation_since`
  returns one second before it, because the message queries take a strict
  `created > since` and a message written in the same second as the binding is
  this generation's. A seat without a binding of that generation gets `0`:
  nothing is known about its start, so nothing is hidden. `message_belongs` is
  the one rule both the doorbell and the home page use: written after the
  generation started, and — for a **temp seat** — about the task it reviews
  now (`seat.task_id`), so a late answer about the previous job's task never
  reaches the new job (F1 of the review).
- **`crates/gear-engine/src/lib.rs`, the doorbell** — the worker seats' lists
  (open action items and unshown replies/instructions) are filtered by that
  rule. The **captain's** open action items are not: they ring until they are
  answered, whatever generation took the seat over (`attention::should_show`
  governs them), so a handover does not hide the engine's items (F2 of the
  review). An earlier job's answer no longer counts as unshown for the new
  job; an earlier voyage's open question no longer rings a re-registered lane.
- **`crates/gear-app/src/home.rs`** — the `UNSHOWN` block of `gear` uses the
  same rule, so a new reviewer never reads another task's answers as its
  instructions, even when they are written after its job started.
- **`crates/gear-engine/src/lib.rs`, the tick** — the doorbell is decided and
  intended after every delivery of the tick (the lane dispatch, the reviewer's
  start and the releases), just before the execution. A seat that is being
  handed work holds its delivery slot then, so the doorbell waits: the delivery
  goes alone, and the doorbell rings on a later tick once the packet is
  confirmed. This also means the dispatch is no longer skipped because of a
  doorbell op intended earlier in the same tick.

## Acceptance evidence (`crates/gear-engine/tests/it/doorbell_isolation.rs`, real store + fake Herdr)

- `a_warm_reviewer_gets_its_packet_before_any_doorbell` — the reviewer's second
  job (generation 2) with an earlier job's answer and its packet due in the
  same tick: the pane gets the packet and nothing else.
- `an_earlier_jobs_answer_does_not_ring_the_new_job` — the earlier job's reply
  and an open question of that job, no delivery: no doorbell at all.
- `a_reply_to_the_current_job_rings_after_the_packet` — a reply written after
  this job started, with the packet already taken: the doorbell rings.
- `a_reregistered_lane_starts_with_its_task_not_a_doorbell` — a lane on
  generation 2 with an open question from the previous voyage and a ready task:
  the task is delivered, nothing else.
- `an_earlier_voyages_question_does_not_ring_a_reregistered_lane` — the same
  lane with the old question and nothing to deliver: no doorbell at all.
- `a_tick_with_a_doorbell_and_a_delivery_for_one_seat_sends_only_the_delivery`
  — a message of this generation and a task due for the same lane in one tick:
  only the delivery is sent.
- `the_captains_open_items_still_ring` — the captain's own item still rings.
- `a_new_reviewers_gear_shows_no_message_from_an_earlier_job` — the home page
  shows this job's answer and not the earlier job's.
- `a_late_answer_about_the_previous_task_does_not_reach_the_new_job` (F1) — an
  answer about the previous job's task, written *after* this job started: no
  doorbell and not on the home page.
- `an_open_item_from_before_a_new_captain_generation_still_rings` (F2) — the
  captain's item that was open before a handover still rings.

## Validation

- `cargo test --workspace` → **680 passed, 0 failed** (10 of them new).
- `cargo build --workspace --all-targets` → exit 0, no warnings.
- `git diff --check` → clean.
- The tests fail when the engine does the wrong thing (each mutation reverted
  afterwards):
  - the generation check dropped → `an_earlier_voyages_question_does_not_ring_a_reregistered_lane` fails;
  - the home page's generation filter removed →
    `a_new_reviewers_gear_shows_no_message_from_an_earlier_job` fails;
  - the doorbell decided before the dispatch (the old order) →
    `a_tick_with_a_doorbell_and_a_delivery_for_one_seat_sends_only_the_delivery` fails;
  - the temp seat's task check dropped (F1) →
    `a_late_answer_about_the_previous_task_does_not_reach_the_new_job` fails;
  - the generation filter applied to the captain's items again (F2) →
    `an_open_item_from_before_a_new_captain_generation_still_rings` fails.

## Out of scope

- The home page of the `course` lane's crate: the contract names it ("in the
  doorbell and in the seat's `gear` home page alike"), so this branch changes
  `crates/gear-app/src/home.rs` (one line) and adds its helper to
  `crates/gear-app/src/seats.rs`. The rest of gear-app is untouched.
- The captain's inbox batch (`mail::select_batch`) is not generation-filtered,
  and the captain's open action items ring regardless of the generation (F2);
  only the worker seats are isolated per job/generation.
- An earlier job's open items stay in the store (hidden from the seat, still
  visible to the captain): nothing is deleted or resolved by this task.

# T-86 — the captain registers the project itself

Scope: T-86 — `gear admin init` accepts the project's own captain (with
`GEAR_ADMIN=1`) as well as the user's shell, and refuses every other seat; the
README drops the "register in your own shell" step and installs the skill for
every CLI the project runs; the captain guide makes `init` the captain's job at
kickoff (the confirmed sheet is the consent) and after every config change.

Branch: base/t86 (code @ the hand-in commit; origin/dev merged before
verification, gate green on the merged result)

Files:
- `crates/gear-app/src/admin.rs` — the caller check of `init` (the one hunk
  outside this lane's paths, and the reason for it: the guard lives there, not
  in the CLI). `GEAR_ADMIN=1` stays required for everyone; a caller with a
  context must be the project the config names, seat `captain`, and — when the
  seat is registered already — the captain's role at the caller's generation.
  A first registration has no seat, so there the name and the project are what
  can be asked. Every other agent is `Forbidden`, and the module doc says so.
- `crates/gear-cli/src/main.rs` — `cmd_admin_init` keeps the fast
  `GEAR_ADMIN=1` check and drops the "never in an agent" refusal, which is now
  the app layer's decision (it is the only way to keep one rule for both
  callers).
- `crates/gear-cli/tests/it/admin_init_contract.rs` — 7 CLI tests, as a child
  process against a scratch store and no Herdr (so no engine starts):
  the captain registers its own unregistered project at kickoff; the captain
  re-registers after a config change (the seat `init` bound at generation 1 is
  accepted); a lane is refused and nothing is registered; another project's
  captain is refused; a stale captain generation is refused; the user's own
  shell still registers; without `GEAR_ADMIN=1` nobody registers, with or
  without a context.
- `crates/gear-cli/tests/it/main.rs` — the new test module.
- `README.md` — step 1 exports `GEAR_CTX` and `GEAR_ADMIN=1` (with the reason:
  it lets the captain register); step 3 is no longer a user chore — confirming
  the sheet is the consent and the captain registers and re-registers from its
  own pane; the skill section installs the skill for every CLI the project
  uses, not only the captain's (trial G06).
- `skills/gear/references/captain.md` — the captain registers the project at
  kickoff (the confirmed sheet is the consent, and the only reason its pane
  carries `GEAR_ADMIN=1`) and after every config change, with how a refusal
  reads and what a second `init` does (the next config version).
- `ops/reports/T-86.md` — this brief.

No privilege comes with the consent: `admin stop` and `admin install-skill`
still refuse any caller with a context, and every other `admin` subcommand is
the user's. `init` is the one command a captain may run, and only for its own
project.

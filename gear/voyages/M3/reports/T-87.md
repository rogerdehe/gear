# T-87 — the fixture projects of the live acceptance

Scope: T-87 — `scripts/fixtures/make.sh <dir>` builds, from nothing and
offline, the two projects one small voyage each runs on: `multi/` (a parent
repo with two child repos, each with a local bare origin, its own integration
branch and a gate) and `running/` (a project that already has its own ways, for
`gear --skill adopt`). A second run replaces both.

Branch: base/t87 (code @ the hand-in commit; origin/dev merged before
verification, gate green on the merged result)

Files:
- `scripts/fixtures/make.sh` — the builder. `origins/{parent,web,api}.git` are
  bare local repositories created with `git init --bare -b <branch>`, so the
  clones are on the right integration branch from the start: the parent on
  `dev`, the children on `feat`. The parent is a clone of its origin; the
  children are cloned into `web/` and `api/` inside the parent, which ignores
  them (`web/`, `api/` in `.gitignore`) — a project of several repos, exactly
  as T-53/T-59 describe it. Every repo carries `gate.sh` (POSIX `sh`, checks
  its own files and runs its own program, well under a second) and a release
  branch `main`. Git runs with a fixture identity, no signing and
  `core.hooksPath=/dev/null`, so a machine with its own hooks or signing still
  builds a fixture. `running/` is a repository on `main` with
  `.github/workflows/ci.yml`, a `CLAUDE.md` and an `AGENTS.md` that contradict
  each other and GEAR (rebase/force-push/commit to main/no tests vs. a branch
  and a test per change), `.claude/skills/release-check/SKILL.md`, three stale
  docs under `docs/`, and `src/bad.py` (mutable default argument, global state,
  bare except) next to the exemplar `src/good.py`, with `make check` running
  its gate. `<dir>/FIXTURE.md` says what each fixture is and carries the
  config template of the multi-repo project (`[[repos]]` with `path`,
  `integration = "feat"`, `gate`, and the project's own `dev`/`main`/gate).
- `crates/gear-cli/tests/it/fixtures_contract.rs` — the layout test: it runs
  the script twice, checks the three repositories, their branches and that each
  `origin` is an absolute local path (no scheme, no `@`), that the parent
  ignores the children, that every gate passes in seconds, that `running/` has
  every part of its own ways, and that the second run replaced both projects.
- `crates/gear-cli/tests/it/main.rs` — the new test module.
- `ops/reports/T-87.md` — this brief.

Verification:
- `env -u GEAR_DB -u GEAR_CTX cargo test -p gear-cli --test it fixtures` —
  passed (the script runs twice inside it; the whole test is 9 s, most of it
  git).
- The script by hand, twice into the same directory: the second run replaces
  `multi/` and `running/` (a marker written between the runs is gone) and all
  four gates still pass.
- `env -u GEAR_DB -u GEAR_CTX cargo build --workspace --all-targets` — exit 0,
  zero warnings.
- `env -u GEAR_DB -u GEAR_CTX cargo test --workspace` — 756 passed, 0 failed,
  0 ignored, zero warnings.

For the live acceptance (the captain): `sh scripts/fixtures/make.sh <dir>`, then
register `<dir>/multi` with the `[[repos]]` config in `<dir>/FIXTURE.md`; the
gates are `sh gate.sh` in each repo, and `running/` is the adoption voyage
(`gear --skill adopt`).

Open questions: none.

Out of scope: the GitHub sandbox project (a real remote by definition, so not a
fixture); the config of the *running* project (the adoption voyage's captain
writes it); and a fixture for the GitHub mode — T-91's live run uses the
sandbox repo.

# T-64 — the parallel-change check ignores a landed task

Scope: T-64 — a task whose candidate is already in the integration branch is
no longer treated as an open change, so a merged task raises no parallel item
and no open task is paired with work that already landed.

Branch: base/t64 (code @ the hand-in commit; origin/dev merged before
verification, gate green on the merged result)

Files:
- `crates/gear-engine/src/parallel.rs` — the scan now carries, per task, the
  candidate of its latest attempt (the same read that already collects the
  hand-ins for the early-scan trigger, so no extra store query), and skips a
  task whose candidate is an ancestor of the integration branch. Skipping
  happens before the branch is resolved, so such a task neither produces an
  `integration:<task>` conflict nor joins the task-vs-task comparison.
- `crates/gear-engine/tests/it/parallel_contract.rs` — the new test, and the
  `hand_in` helper generalised to any task/seat/attempt number.
- `ops/reports/T-64.md` — this brief.

Why the old check was wrong: the engine merges the **approved candidate**, not
the branch (T-61), and a branch may still point past that candidate at commits
no merge will take. The check compared the branch head only, so it saw the
leftover commits as an open change. When another task had landed on the
integration branch and touched the same file, the two sides intersected and it
opened "parallel changes: T-58 (config) and integration dev share files
[…main.rs]" for a task that had already merged — the M2.1 signal.

The landed test is the candidate, not the task's state: a task in `Done` is
accepted but its merge may still be queued, and that case must keep being
watched (the existing `integration_changes_since_the_branch_base_count_too`
test holds it). A task whose latest attempt is a newer, unmerged rework is
open again and is compared as before.

Verification:
- The new test, red on the old code and green with the fix:
  `cargo test -p gear-engine --test it
  parallel_contract::a_landed_task_is_not_an_open_change_and_open_tasks_still_pair`
  — before: `a merged task raises no parallel item: ["M-1"]`; after: passed.
  It builds a real git repo: T-1 hands in a commit, the integration branch
  merges it, another task lands on the same file, and T-1's branch moves past
  the merged candidate → no item at all. Then a newer T-1 attempt (not merged)
  plus an open T-2 on the same file → exactly one pair item naming
  `T-1 (heat) and T-2 (steady)`.
- `env -u GEAR_DB -u GEAR_CTX cargo test -p gear-engine` — 124 + 159 passed.
- `env -u GEAR_DB -u GEAR_CTX cargo build --workspace --all-targets` — exit 0,
  zero warnings.
- `env -u GEAR_DB -u GEAR_CTX cargo test --workspace` — 725 passed, 0 failed,
  0 ignored, zero warnings; every pre-existing parallel contract still passes
  (the legacy namespace, the back-off, the per-repo scan, the resolution of a
  cleared overlap, and the doorbell path).

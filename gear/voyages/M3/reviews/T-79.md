F1 [P1, blocking] The submitted candidate cannot run workspace acceptance — `crates/gear-engine/src/merge.rs:1539` and `:1817`. The new required TaskRow.issue field was not added to the two fixture constructors brought in with the T-62 merge. Both independently run workspace tests and all-targets build exit 101 with E0063 before the full suite can execute. This is a failed mechanical fact and breaks the explicit `cargo test --workspace` acceptance requirement. Smallest fix: add `issue: None` to both TaskRow initializers in merge.rs (two production-test lines), then rerun workspace tests and the all-targets build on the final merged candidate. No merge behavior change or refactor is needed.
F2 [P1, blocking] A child repo without a GitHub section silently uses the root repo's GitHub identity — `crates/gear-app/src/config.rs:115`, ProjectConfig::repo_of_section. The `.or(self.github.as_ref())` fallback makes a local-only child inherit the entire project section, including its owner/name and PR mode. Independent reproduction: valid config with project `[github] repo = "root/project", merge = "pr"` and `[[repos]] name = "child", path = "child"`, with no repos.github section, resolves the child as `Some(Github { repo: "root/project", ... merge: Pr })`. No valid config can disable GitHub for that child while preserving the root mode. This violates the contract's per-repo "absent = local-only" behavior in ordinary parent/child projects and supplies the wrong repository identity to the GitHub workflow. It breaks the DELIVERABLE bar for normal-use errors and the repo isolation needed by done-sentence (1)/(4). Smallest fix: in repo_of_section, resolve only `section.github.as_ref().and_then(GithubSection::resolved)`; keep root_repo resolving the project section. Update the associated inheritance comments. Add a regression with a GitHub root, one child lacking a section, and one explicitly configured child: root keeps its identity, absent child is None through both repos() and repo_of_lane(), explicit child keeps its own identity (roughly one removed production line, comment adjustments and 20–30 test lines).
F3 [P2, logged, nonblocking] Invalid issue numbers pass validation and oversized values change sign in storage — `crates/gear-app/src/draft.rs:549`, `crates/gear-app/src/plan.rs:292` and `:330`. The parser accepts all u64 values and a leading plus; apply casts to i64 unchecked. The independent apply probe stored `#0` as 0, `#+12` as 12, `#9223372036854775808` as -9223372036854775808, and `#18446744073709551615` as -1. Such links cannot identify a real issue. Suggested small follow-up: require nonempty ASCII digits and a positive value representable as i64 at parsing, and avoid unchecked narrowing in apply; cover zero, plus-prefixed input and overflow. These are invalid-input/range edge cases, not normal GitHub issue numbers, so they are logged under the supplied DELIVERABLE bar and do not add rework.

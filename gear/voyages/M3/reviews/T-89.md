## Findings
F1 [P1, blocking] Busy starts do not yield to the next tick — `crates/gear-engine/src/onboard.rs:337` (and the `Starting` filter at line 184). A first refusal enters a sleep/retry loop in the same invocation. An independent standalone Rust probe linked against the built candidate, using a configured claude lane and `FakeHerdr.refuse_starts = Some(("agent_pane_busy", 1))`, observed first invocation: Active, two AgentStart calls, elapsed 263 ms; the next invocation did nothing. The contract requires the refusal to remain pending and retry on a later tick. With a persistently busy shell, this loop occupies the engine for 20 seconds per lane before its other work can run: `tick` calls `onboard_queued` before observation, dispatch, settlement and dialog handling (`crates/gear-engine/src/lib.rs:132`). Slow shell initialization is the normal-use fault this task targets, so this is required behavior missing under the M3 DELIVERABLE bar, not an optional edge-case improvement. Smallest fix: in `onboard_queued`/`onboard_seat`, keep a bounded pending start in seat metadata after a busy refusal, return `Ok(false)`, and include that pending start in the Starting resume filter. On a subsequent tick, reuse the existing binding/pane and generation to attempt the start once; do not recreate the worktree, repeat the env command or call `begin_onboard` again. Clear pending metadata on success or exhaustion; on exhaustion park with the existing reason. Keep the existing model-gate completion after a successful start. This is localized onboarding plumbing, roughly 60–100 lines plus tests, without a new seat state or transition. Update the fake tests to assert first tick Starting with no NeedsCheck, next tick Active after one refusal; repeated busy ticks must exhaust the bound into NeedsCheck with the reason, and the env command/generation must occur only once. A second queued lane should still be processed while the first waits.

- Zero/negative limit or zero polling interval can be constructed programmatically, but production uses fixed positive defaults. These are edge configurations, not rework under the supplied bar.
- HOME isolation changes address the reported process-wide test race. Manual restoration does not run after a panic; this is a test-failure edge case and does not block this task.

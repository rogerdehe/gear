# T-655 — the landing reclaim deletes the branches of the landed voyage's cancelled tasks, after recording each tip sha

Candidate: bce48c79 (branch hull/t655)

## What changed (crates/gear-engine/src/finished.rs only)

Inside `reclaim`, before the `project_branches` loop, per repo:

- One `store.read` collects the project's cancelled tasks of the landed
  milestone whose lane and repo match this repo, with their branch from
  `gear_app::base::task_branch_of`, and the branches of every non-cancelled
  task (lane Some). A cancelled task whose branch a live task shares (a shared
  feature branch) is skipped and keeps today's rule.
- A branch equal to `repo.integration`, `repo.release` or
  `config.conventions.staging` is skipped.
- For each remaining branch: `remote_branch_tip` — None means already gone.
  Otherwise, in one `store.write`, the line
  `T-<n> cancelled: <branch> at <sha>` is inserted as a Resolved System message
  on thread `landing:<milestone>` for the captain (unless that exact body is
  already there). No captain → nothing deleted, the branch is named in `left`.
  Only after the record is written is `delete_remote_branch` called; an error
  is named in `left`. Handled branch names are remembered in a `BTreeSet`.
- The `project_branches` loop skips the handled names; other branches keep the
  T-618 rule.
- `reclaim`'s doc comment now says a cancelled task's branch is deleted after
  its tip is recorded on `landing:<milestone>`, so its work stays recoverable.

# T-578 — report

Plan apply for features (M6.2, feature integration stage 1, part 2/7). All of it
is in `crates/gear-app/src/plan.rs` plus one new test file.

## What changed

- `crates/gear-app/src/plan.rs`:
  - `FeatureWork` / `Features` and `feature_work(...)`: the members of every
    feature the queue names (the tasks marked `feature: F-<n>` that are not
    cancelled, the existing ones included, by task number), the feature's
    branch (`[conventions].feature_branch` with `{project}` and the lower-case
    `{feature}` filled in), the check a member's merge runs
    (`feature_check`, else the literal `true`), the lane holding most members
    (ties: the first in the draft), the members' milestone, their highest
    priority, their goals (one per line) and the one issue they name.
  - (1) A member's `base`/`gate`: on a NEW block where base/gate are set today,
    and on an existing task whose feature changes (or is cleared with `-`, when
    base/gate go back to the lane's integration branch and full gate). The mark
    itself is stored with `set_task_feature`.
  - (2) The cap: more than `feature_max_tasks` not-cancelled members is
    `BadFormat` naming the feature, the count and the cap.
  - (3) A dep in the draft from a task outside a feature on one of its members
    is `BadFormat`: `<id>: deps on a feature's task <dep> name the feature's
    integration task <carrier>`. Deps between members of one feature stay
    allowed.
  - (4) The feature's integration task, after the queue writes: created in the
    same apply when `feature_carrier` names none — goal
    `Integrate feature F-<n>:` with the members' goals one per line, accept
    `the full gate passes on the feature branch merged into <integration>`,
    lane/base/gate/repo of the chosen lane (a normal task: integration base,
    full gate), milestone and priority of the members, `estimate_min` 10,
    deps = the members, `set_task_branch_override` = the feature's branch,
    `set_feature_carrier`, pushed to `created` last so `record_task_stations`
    still maps the draft's NEW blocks. On a later apply the carrier's deps are
    set to the members that are not cancelled.
  - (5) The members' `issue:`: differing issues among the members are
    `BadFormat`; the carrier gets the one issue and every member keeps none.
  - `priority_order(...)`: `now` … `wont` as 0 … 4, to pick the highest.
  - A project with no `feature:` mark anywhere does none of it: the extra work
    is a meta read per task and no write.
- `crates/gear-app/tests/it/feature_plan_contract.rs` (new, registered in
  `main.rs` as `mod feature_plan_contract;`): six tests —
  - `a_feature_gets_one_integration_task_and_its_members_its_branch`: three
    members (two `heat`, one `wire`, `issue: #12`, deps inside the feature) get
    base `p/feature/f-1` and gate `true`, the mark, no issue; one carrier with
    all three as deps, lane `heat`, priority `must`, issue 12, estimate 10,
    base `dev`, gate `make test`, branch override `p/feature/f-1`, and the
    goal/accept the packet names.
  - `a_configured_feature_check_is_the_members_gate`: `feature_check` from the
    config is the members' gate, the carrier's stays `make test`.
  - `a_member_over_the_cap_is_refused`: an eleventh member under the default
    cap is refused, the message names the feature and the cap of 10, and the
    apply writes nothing.
  - `a_dep_from_outside_on_a_member_is_refused`.
  - `a_re_apply_adds_a_member_to_the_carriers_deps`: the third member joins the
    carrrier's deps and the carrier keeps the issue and stays the same task.
  - `a_plan_without_a_feature_line_is_unchanged`: no carrier, no mark, base
    `dev`, gate `make test`, no branch override.

## Out of scope / noted

- The packet does not say what a finished carrier means: a `feature_carrier`
  that names a Done/Failed/Cancelled task is treated as absent, so a member
  added afterwards gets a new carrier. Not exercised by a test.
- Clearing the field (`feature: -`) on an existing task puts base/gate back to
  its lane's repo values; the packet names only "when their feature changes".
- The carrier is not marked with the feature (it is not a member), so it is
  outside the cap and keeps no `feature:` in `plan show`.
- The carrier's fixed `estimate: 10` is not checked against a project whose
  `max_task_min` is below 10.
- The engine side (a member's merge into the feature branch, `feature_check`
  running there, a member's deps releasing on that merge, the carrier reviewed
  and gated once with the full gate) is the rest of the series, not here.
- One extra meta read per existing task on every apply, to know the marks;
  no index, no cache.

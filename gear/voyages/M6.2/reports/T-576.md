# T-576 — a merge a red batch sends back is queued, not unknown

Prometheus 2026-11-05: O-7384..O-7390, T-716..T-726, sat `unknown` from 19:43
with "its batch failed the gate: it is gated again in a smaller batch"; no later
batch took them, the lost scan said "nothing will merge it", and `- remerge
T-722` was refused as "already unknown, not failed".

## The rule

`unknown` means **a push whose outcome nobody knows**. A merge a batch or a train
sends back knows its outcome (nothing was pushed), so it is **queued again**.

## What changed

1. **`crates/gear-engine/src/merge.rs`** — `Report::Requeue` (what the batch and
   train collections return for a member they send back: lock busy, a conflict in
   a batch, a red gate, a race, "it waits for the next batch") now goes through
   **`requeue_merge`**, which puts the op back to **`Intended`** with the same
   reason. `retry_merge` (→ `Unknown`) still serves `Busy`, `Waiting` and
   `Raced` — the reports whose outcome really is open — and the single-merge
   paths are unchanged.
2. **`crates/gear-model/src/state.rs`** — `Unknown → Intended` is a legal op
   transition (T-576). A merge queued again re-runs from the remote
   (`merge_one` resets and adopts an already-completed push), so nothing is
   retried blindly.
3. **`crates/gear-app/src/plan.rs`** — `- remerge` now accepts an `unknown` op
   **when no worker runs it** (a worker's op is `executing` or `submitted`):
   that op goes back to `intended` with "remerge: queued again by the captain",
   and the remerge op is queued as before. The refusal ("already unknown, not
   failed") is gone for exactly that case; `intended`, `executing` and
   `submitted` are still refused as merges in flight, and `confirmed` as merged.
4. **The lost scan** (`tell_captain_lost`) already reads `unknown` as a merge in
   flight (it scans `Intended, Executing, Submitted, Unknown`) — no change was
   needed; the packet's third point holds.

## Decisions

- **A batch's push race is queued, not unknown.** The packet's rule is "unknown
  only for a push whose outcome is unknown"; a rejected non-fast-forward push
  landed nothing, so its outcome is known. One existing test changed because
  its old expectation was the bug.
- **The single-merge `Raced`/`Busy`/`Waiting` paths keep `Unknown`.** They are
  out of the packet's scope, and `Waiting` carries the T-62/T-553 meaning that a
  merge waiting for another task is landing, not lost.
- **"No worker runs it" is read from the op's own state**: a running merge op is
  `executing` or `submitted`; `unknown` is exactly the state a worker leaves
  behind when it lets go, so remerge may requeue it.

## Out of scope, logged

- Ops already stuck `unknown` in an existing store heal on the next `- remerge`
  (the op becomes intended); no migration writes to them by themselves. A merge
  queued again always re-reads the remote, so a stale unknown op cannot land
  twice.
- The single-merge `Report::Raced` path still sets `Unknown` — harmless (the
  queue reads unknown ops) but inconsistent with the new rule; it is the one
  place the packet did not name, and changing it would move the T-62 waiting
  semantics, so it is left for a task of its own.
- `docs/design/` is untouched.

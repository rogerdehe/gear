# T-579 — report

A hand-in is checked against its task's base, not the lane's (M6.2, feature
integration stage 1, part 3/7).

## What changed

- `crates/gear-app/src/base.rs`:
  - `gate_for`: the integration branch a hand-in must contain now comes from
    the seat's open attempt's task — `tx.open_attempts_of_seat(&ctx.seat_id())`
    first, then its task's `base` when set (and not blank) — and only otherwise
    from today's `config.repo_of_lane(&ctx.seat).integration`. The doc comment
    says why: a member of a feature works on the feature's branch and its work
    contains that branch, not the integration branch the feature has not
    reached yet.
  - `pushed_branch(store, conventions, project, lane, task)`: the branch a
    task's work is pushed to — `task_branch_override` when the task names one
    (the feature's branch, set by plan apply on the integration task), else the
    `[conventions].task_branch` template as before.
- `crates/gear-app/src/mail.rs`: both `require_pushed` call sites take that
  branch instead of the template:
  - the `gear send --kind result` push check (the packet's site);
  - the reviewer's verdict push check (`MsgKind::Review`), which looks for the
    reviewer's commit on the task's branch (T-558: no review branch on the
    remote) — for a member that is the feature's branch too, so leaving it on
    the template would refuse every review of a feature's member. Asked the
    captain (question, default: both), reported here as the one place I went
    past the packet's literal sentence.
- `crates/gear-app/tests/it/base_gate.rs`, a new `T-579` section with a root
  config (`ROOT_CONFIG`, `world_with_config`):
  - `a_task_base_is_the_branch_its_hand_in_is_checked_against`: the feature's
    branch exists on the remote, `dev` moves on, the member's `heat/t1`
    contains the feature's branch — `gate_for` names `p/feature/f-1`,
    `require_current_base(…, "dev", …)` refuses the same candidate, and the
    hand-in through `mail::send` with that gate is accepted and stored
    (attempt `Submitted`).
  - `a_task_without_a_base_keeps_the_lanes_integration_branch`: `gate_for`
    still names `dev`, window 30.
  - `a_task_branch_override_is_the_branch_a_hand_in_is_pushed_to`: a candidate
    pushed on `p/feature/f-1` only is refused while the check reads `heat/t1`,
    and accepted once `set_task_branch_override` names that branch.

## Out of scope / noted

- `gate_for` takes the *first* open attempt in the store's order (a handed-in
  one sorts last, as the engine's own `lane_view` reads it); a lane holding a
  handed-in attempt and a new open one is checked against the one it is working
  on.
- A member's own task branch is still the lane's template: the member merges
  the feature's branch into `heat/t1` like it merges `dev`, which is what
  `base` is for; the override is the integration task's (its candidate is the
  feature's branch). The override is honoured for any task that names one,
  whatever the reason.
- The engine's merge side (a member merging into the feature's branch,
  `feature_check` running there, the feature's integration task gated once) is
  the rest of the series.

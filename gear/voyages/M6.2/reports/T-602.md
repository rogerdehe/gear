# T-602 — report

One place names a task's branch, and it knows the feature override.

## What changed

`gear_app::base::task_branch_of(tx, conventions, project, lane, task)`
(`crates/gear-app/src/base.rs`) is now the one function that names the branch of
a known task: the branch the task itself names — `tx.task_branch_override` — when
it names one, else today's `task_branch(conventions, project, lane, task)`
template. `pushed_branch` (the hand-in's push target) is that function read
inside a store read, so the two cannot drift.

Every caller that names the branch of a known task calls it:

| caller | what it names |
|---|---|
| `gear-engine/src/review.rs` | the review packet's push target (`git push <remote> HEAD:refs/heads/<branch>`), and the branch the direction check reads the tip of |
| `gear-engine/src/dispatch.rs` | the branch the assignment/rework text tells the lane to work on |
| `gear-engine/src/parallel.rs` | the branch whose tip is the open change (`TaskIn.branch`, read once per task in the scan's transaction instead of carrying the template) |
| `gear-engine/src/handover.rs` | the branch a lane's handover names |
| `gear-engine/src/quiet.rs` | the branch the push clock reads |
| `gear-engine/src/merge.rs` | `merge_passed`: the branch a merge op merges (and keeps) |
| `gear-app/src/tasks.rs`, `gear-app/src/plan.rs` | the merge op's branch — the two local overrides v0.6.82 added are gone; the override is still read once for `keep_branch`, and the branch itself comes from `task_branch_of` |
| `gear-cli/src/main.rs` | the branch the hand-in reply says not to push again |
| `gear-forge/src/sync.rs` | the branch a claim/adoption asks the forge for (`Fact.branch`, read once when the facts are collected) |

Two callers keep the template, and say why in a comment:

- `dispatch::task_branch(template, …)` stays the template primitive (a caller
  holding only a config, `config.rs` validation).
- `merge.rs::task_branches` (the T-474 sweep) enumerates the branch a lane cut
  from the template, never the branch the task itself names: the feature's
  branch is not a task branch to close — T-582 keeps it through the integration
  task's merge and the captain deletes it at landing.

`gear-forge` cannot depend on `gear-app` (the dependency runs the other way), so
that one caller reads the override from the store's own accessor and expands the
template exactly as `task_branch_of` does; the comment there says so.
`config.rs` validation is untouched, and so is the empty-value rule of the
accessor. `feature::branch_override` — which duplicated the meta key "until
T-577's accessor lands" — now calls the accessor.

## Tests

- `gear-app` `base::tests::task_branch_of_reads_the_override_then_the_template`
  — both ways: the template with no override (`mast/t9`), the task's own branch
  with one (`p/feature/f-1`), and a second task of the same project still on the
  template.
- `gear-engine` `review::tests::the_review_packet_of_a_feature_task_names_the_feature_branch`
  — the normal task's packet still says `git push origin HEAD:refs/heads/heat/t1`
  and the verdict is refused until `origin/heat/t1` holds the commit; with
  `task_branch_override = p/feature/f-1` the packet names
  `refs/heads/p/feature/f-1` for the push and for the refusal, and no longer
  names `heat/t1`. This is F-2's failure: its reviewer was told `mast/t600`, a
  branch that never existed, and its hand-in was refused until it pushed to the
  feature's branch.

# T-582 — the merge uses the branch override, and a member lands on the feature's branch

## What changed

`crates/gear-engine/src/merge.rs` only.

- **The merge op names the task's own branch** (`merge_passed`): the payload's
  `branch` is `tx.task_branch_override(project, task)` (T-577's accessor) when
  the task has one, else the lane's `[conventions].task_branch` as before. Such
  an op also carries `"keep_branch": true`.
- **The merge's target and gate come from the task** (`repo_of_op`): the repo
  the op works in is still the task's repo snapshot, and now its
  `integration` is the task's `base` when it has one and its `gate` is the
  task's `gate` when it has one. So a member of a feature (`base =
  p/feature/f-1`, `gate = true` or the feature's check) is merged into the
  feature's branch with the feature's own check; the integration task (`base` =
  the integration branch, `gate` = the full gate) merges the feature's branch
  into the integration branch with the full gate; and every task created before
  v6, or by a project with no `feature:` line, is unchanged.
- **The feature's branch survives its landing** (`prepare_merge`,
  `close_branches`, `close_pr_branches`): `Prepared::keep_branch` follows the
  op's payload, so the close after the integration task's merge deletes the
  review branch as usual and leaves the feature's branch on the remote, in the
  local mode and in pull-request mode alike. Nothing else about the close
  changes: a member's own branch is deleted as any task branch is.
- `worker_key` follows the repo, so merges into the feature's branch and merges
  into the integration branch do not batch or train together — they cannot: a
  gate that checked one target says nothing about the other. They share the one
  merge worktree and its lock, so they run one after the other.

## Test

`make check CRATE=gear-engine TESTS='test(merge::)'`: **133/133 passed**, three
of them new (Pair / Scratch fixtures, a real bare origin):

- `an_integration_task_merges_the_feature_branch_and_keeps_it` — `T-5` carries
  the override `p/feature/f-1`; `merge_passed` queues its merge with
  `branch = p/feature/f-1` and `keep_branch = true`; `repo_of_op` says the merge
  targets `dev`; the merge lands the feature branch's work on `dev` and the
  feature's branch is still on the origin at its own tip, not named closed.
- `a_member_merges_into_the_feature_branch_without_the_project_gate` — a member
  task with `base = p/feature/f-1` and `gate = true` in a project whose
  `[conventions] gate = "false"`: `repo_of_op` gives the feature's branch and
  `true`, and the merge lands the member's work on `p/feature/f-1`, leaves `dev`
  alone, and closes the member's own branch. A merge that ran the project's gate
  could not have landed at all.
- `a_conflicting_member_is_refused_and_leaves_the_feature_branch` — the feature
  branch and the task both change the README: the merge is refused
  (`conflict merging …`) and the feature's branch is exactly where it was.

## Decisions and deviations

- **The base is the merge target.** The goal text names only the branch
  override, but its acceptance asks for "a member task with base
  `p/feature/f-1` … merges into the feature branch", and no code merged into
  anything but `repo.integration`. `repo_of_op` is the one place that decides
  which repo/branch/gate a merge op works on, so the change is one function and
  every step (fetch, reset, gate, push, close, train, batch, PR) follows it.
- **Two `branch_of(` calls exist in `merge.rs`, not three** (the packet says
  three): the merge op payload, which is converted, and the branch sweep, which
  is not — see below.
- **The payload carries `keep_branch`, not the store**, so the close needs no
  store read and a batch's close works the same.

## Out of scope, logged

- **The branch sweep (`task_branches`) still names branches from the template.**
  Naming the override there would let T-474's "a done task leaves no branch
  behind" delete the feature's branch the moment the integration task is Done,
  which the packet forbids. A cancelled integration task's feature branch is
  therefore not swept; the captain deletes it by hand.
- **The captain's `- remerge T-x` (`gear-app/src/plan.rs`) builds its own merge
  op** with the template branch and without `keep_branch`. A member remerges
  correctly (its lane branch is the one to merge, and `repo_of_op` gives the
  feature branch as the target); a **remerge of the integration task** would
  look for the lane's branch instead of the feature's and fail as "the task
  branch … is missing on origin". It is an edge (the integration merge
  conflicting with the integration branch) and it is in another file than the
  packet's; a two-line change there (override + keep flag) closes it.
- `sweep_branches` and the branch-age items are untouched.
- Pull-request mode: a member's merge would open its pull request against the
  feature's branch. It follows from `repo_of_op` and is not exercised by a test.

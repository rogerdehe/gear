# T-598 — report

A red full gate on a feature names the member that turned it red (M6.2, feature
integration, stage 3).

## What changed

`crates/gear-engine/src/merge.rs`:

- `Failed` carries `gate: Option<String>`: set **only** where the gate itself
  refused (`Failed::gated`) and only to the integration tip the failed merge was
  built on (read from the merge worktree right after it is reset to that tip).
  A conflict, a missing branch, a candidate on no pushed ref and a gate that
  could not judge keep `gate: None`, so none of them starts a search.
- `settle_report`, on `Report::Failed`, still rungs the captain through
  `fail_merge` and then calls `request_bisect`: for a task with a
  `task_branch_override` (the feature's integration task) it writes the request
  into the candidate's meta key
  `engine.bisect.<project>:<task>:<candidate>`. One key per candidate is the
  whole rule "a second failure of the same candidate starts no second bisect":
  the key outlives the search and reads `started` from then on.
- `start_bisects` (called from `merge_passed`, **after** `collect_finished` and
  before the tick's early return, so a failure is searched on the same tick it is
  collected): opens the worktree `<project>-bisect` through Herdr exactly as the
  merge worktree is opened (seat `bisect`, the project's `seat_branch` template,
  `previous_default` settled first, `check_worktree`, the T-107 hook clean) and
  hands the search to a thread of its own. No lock of the merge worktree, no
  worker of the merge registry, no merge waiting on it.
- `run_bisect` reads the feature branch's first-parent line after its fork from
  the integration branch (`git log --first-parent --reverse`), keeps the merge
  commits, names each by the task its subject gives (`merge(<T-n>): …`, parsed
  from the project's `[conventions].merge_message`), and binary-searches the
  smallest member count whose prefix turns the gate red. Each probe is
  `reset --hard <the tip the failed merge used>` + `merge --no-ff
  <that member merge commit>` + the project's gate (the same `gate_command`, its
  own round name, `GEAR_GATE_TEMPFAIL`/`GEAR_GATE_FAILED` files cleared first).
  At most `ceil(log2(n)) + 1` runs: the search costs `ceil(log2(n))` and one more
  probe confirms the member it landed on. A probe that cannot be judged (exit
  75/126/127, a tempfail file, a conflict, a ref it cannot read) ends the search
  with nothing to say, and the item keeps the gate's own reason.
- `collect_bisects` (also from `merge_passed`) appends the one line to the open
  `merge-failed:<task>` item — and only to an open one, so a merge that landed or
  was retried meanwhile is not reopened.
- `MergeWorkers::bisects` + `BisectWorker`/`BisectDone`, and
  `MergeWorkers::bisect_running` for the tests. One search per repo worktree at a
  time: a request that finds it taken stays pending for a later tick.
- The two lines, word for word:
  `bisect: the gate turns red at merge(<T-n>) <sha>` and
  `bisect: every member is green alone; the red comes from the refresh or the mix`.

## Verification

- `make check CRATE=gear-engine TESTS='test(merge::tests::a_red_feature_gate_names_the_member_that_turned_it_red)'`
  and the same by name for
  `merge::tests::a_normal_tasks_failed_merge_starts_no_bisect` and
  `merge::tests::the_train_merges_another_task_while_the_bisect_runs`:
  3 tests, 3 passed. The fixture is the `Pair` scratch repo with a feature branch
  built the way GEAR builds one (two member merges, `merge(T-1): …` then
  `merge(T-2): …`) and the gate `test ! -f b.txt`, which is red exactly when the
  second member is in the tree:
  - the feature merge fails, the captain's item says so, and the search appends
    `bisect: the gate turns red at merge(T-2) <sha of that merge>`, one meta key
    per candidate, nothing pushed to `dev`;
  - a normal task's failed gate leaves no bisect meta, opens no bisect worktree
    and adds no line to its item over three further ticks;
  - with the search's gate held (`blocked` in the bisect worktree) the ordinary
    task T-3 still lands on `dev` while no bisect line exists, and the line
    appears once the search is let go — the train never waits for a bisect.
- `make check CRATE=gear-engine` → 1084 tests, 1084 passed.
- `make gate` → fmt 1 s, build 15 s, test 50 s: 2571 tests, all passed, gate
  total 66 s (limit 80 s).
- `cargo clippy -p gear-engine --tests`: no warning in the new code.

# T-581 — a feature's integration task hands itself in

## What changed

A new module `crates/gear-engine/src/feature.rs`, its step in the tick, and one
filter in `crates/gear-engine/src/dispatch.rs`.

- **Never delivered to its lane** (`dispatch.rs`, `ready_tasks_of`): a task with
  a `task_branch_override` is not in the lane's ready work, so no packet is
  intended for it — neither its first attempt nor a rework. The filter sits
  next to T-505's audit filter, in the one place every assignment reads.
- **Hands itself in** (`feature::start_features`, called from the tick as step
  `6f`, right after the voyage audit and before the review step): for every
  Ready task of the project with an override whose deps all have a merge time
  (`gear_app::tasks::merged_at`), the step fetches the task repo's remote, reads
  the override branch's tip (the tick's `repo_tips` map, as the audit step
  does), and records the hand-in in one transaction with the same store calls a
  lane's `gear send --kind result` makes: `tasks::start_attempt`,
  `tasks::on_delivery_confirmed`, `tasks::submit_result` — attempt `Submitted`,
  candidate = the tip, report `the feature branch <branch> at <sha>`, task
  `Verifying`. The writer is the task's lane seat, as an audit's writer is.
- **A failed review waits for the captain**: attempt `n` = last + 1, and when a
  Rejected attempt already carries the branch's current tip the step hands
  nothing in (a wait, not a failure) — the captain re-plans the member work,
  the tip moves with the members' merges, and the next tip is handed in.
- **Report**: `TickReport::features` / `feature_failed`, as T-505's
  `audits` / `audit_failed` are reported.

## Test

`make check CRATE=gear-engine TESTS='test(dispatch::) | test(feature)'`:
**23/23 passed**.

- `feature::tests::a_feature_task_with_every_member_merged_hands_itself_in` —
  fixture: a bare `origin` with `dev` and `p/feature/f-1`, the checkout the
  project reads, members `T-1`/`T-2` Done and merged, `T-9` Ready on the
  feature's branch. First the lane's `ready_tasks_of` holds no `T-9` (no
  delivery op is ever intended), then the step hands in `p:T-9/1`: the task is
  `Verifying`, attempt 1 is `Submitted` with `p/feature/f-1`'s tip as the
  candidate and `the feature branch p/feature/f-1 at <sha>` as the report, and
  the remote still holds exactly `dev` and `p/feature/f-1` (nothing was
  pushed).
- `feature::tests::a_member_that_is_not_merged_holds_the_hand_in` — only `T-1`
  merged: nothing handed in, no attempt, `T-9` still Ready.
- `feature::tests::a_failed_review_of_the_same_tip_waits_for_the_captain` — a
  Rejected attempt 1 on the current tip: nothing is handed in, no failure is
  reported, and the attempt is not replaced.
- `dispatch::tests::a_feature_integration_task_is_never_the_lanes_ready_work` —
  a lane with `T-1` (normal) and `T-9` (override): only `T-1` is ready work, so
  a normal task is delivered as before.

## Decisions and deviations

- **`task_branch_override` is read from its meta key.** The packet names T-577's
  store accessor, which is on `mast/t577` and not in dev, so a branch started
  from `origin/dev` cannot call it. `feature::branch_override` reads
  `task_branch_override:{project}:{task}` (empty = none), the key T-577's apply
  writes; the accessor answers the same and the helper's body is the one line to
  change once T-577 lands. Asked the captain; default (a) taken.
- **A new module, not `dispatch.rs`**: the packet allows either, and the step
  reads like `audit.rs` (a task the engine hands in). The acceptance's own
  filter `test(feature)` names it.
- **Attempt `n` = last + 1**, as the audit step does, so the packet's "attempt
  1" holds for an untried task and a re-planned feature gets the next number.
- **The failed-review wait is a skip, not an item**: the line "the captain
  re-plans member work; the task waits" is read as no hand-in while the tip is
  the one that failed.

## Out of scope, logged

- A lane whose seat is not `Active`/`Standby` or already has an attempt in
  progress: `start_attempt` refuses and the refusal is reported as
  `feature_failed` for that tick; the next tick tries again. No captain item —
  the audit step behaves the same.
- The feature's branch is not deleted after the integration task merges (T-582's
  merge work owns the branch).
- `skills/gear/references/captain.md` gains the `feature` field in T-583.

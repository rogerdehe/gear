# T-565 — a changed default seat branch moves the seat branches too

## What changed

**`crates/gear-app/src/seat_branch.rs` (new)** — the seat branch move in one
place, for both callers:

- `PREVIOUS_DEFAULT` = `{project}/{seat}` (the default before v0.6.55) and
  `previous_default(project, seat)` → `p/hull`;
- `settle(dir, old, new, remote)` → `Free` / `Renamed { old, new, remote }` /
  `Err(naming the ref)`. A ref that is a **folder of the new name** (git's D/F
  conflict: `p/hull` blocks `p/hull/home`) is settled first: it is the seat's own
  old branch and is renamed (`git branch -m`, inside the worktree that has it
  checked out when git cannot rename it from here), or it is somebody else's and
  is **named and left alone**;
- `blocking_ref`, `rename`, `move_remote`, `has_branch`, `git`;
- `move_remote` pushes the new name and deletes the old one. When the old name is
  a folder of the new one the remote refuses both at once (that is exactly the
  T-565 failure), so on that error the old ref goes first and the new one
  arrives after it; every outcome is one line for the captain, never a failure.

**`crates/gear-app/src/admin.rs`** — T-559's apply path keeps its messages and
uses the shared `git`/`has_branch` runner from that module (its local copies are
gone), so the apply and the engine move a branch the same way.

**`crates/gear-engine/src/onboard.rs`**

- `settle_project_seat_branches`: every lane's seat branch is settled **once per
  `conventions.seat_branch` template**, remembered in
  `engine.seat_branch_settled.<project>` — a running engine runs no git for it
  after the first tick, and a new GEAR default (or a re-applied config) is
  settled at the next tick. This is the case the user hit: GEAR's own project
  writes no `seat_branch`, so no apply ran the rename. Something that moves is
  reported once, in the seat's `worktree:<seat>` item.
- `settle_seat_branch` is called in `onboard_seat` **before the worktree is
  opened or created**, so a ref that stands in the way fails the start naming it
  (the seat parks with that reason) instead of git refusing
  `worktree_create` with a D/F error.

## Rework (attempt 2)

**F1** — the merge seat's branch is now settled too. The reviewer is right: the
merge seat is not a `SeatRow`, so neither the apply path (T-559) nor the lane
pass touched it, and the goal's own failure (`p/merge` blocking `p/merge/home`)
stayed. `stage_worktree` (`crates/gear-engine/src/merge.rs`) now calls
`gear_app::seat_branch::settle(&repo.path, &previous_default(project, seat),
&branch, &remote)` **before** it opens or creates the worktree, for every stage
the seat already varies over (`merge`, `merge-2`, …). A foreign ref in the way
fails the step with its name — which the merge reports as a wait, never touching
the ref.

**F2** — left as the rework says (outside normal use: a per-template marker
written after a blocked settle; a queued seat recovers on the next tick because
`onboard_seat` settles every tick).

## Decisions and deviations

- **Where the "engine starts" pass lives**: in `onboard_queued`, which every
  tick runs for every active project. It is gated on the template it last
  settled, so it costs nothing after the first tick; an engine restart is the
  same tick path as a start.
- **Failure is named, not fatal**: in the project pass a blocked ref becomes one
  `worktree:<seat>` item and the project goes on; in `onboard_seat` it stops that
  seat with the reason (the existing behaviour for a failed start step).
- **The remote move deletes before pushing** only when the push is refused *and*
  the old name is a folder of the new one; every other case keeps T-559's
  push-then-delete order.

## Out of scope, logged

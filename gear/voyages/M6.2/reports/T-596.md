# T-596 — report

The parallel-change scan reads a task against the branch its work merges into.

## What changed

- `crates/gear-engine/src/parallel.rs`
  - `TaskIn` carries the task's own base (`task.base`, trimmed; an empty value
    is none), read in `inputs` for the scanned project's tasks and for the other
    projects' tasks of the same repo (T-281) through one helper, `task_base`.
  - `scan` resolves one base tip per task: `task.base` when it names one, else
    the repo's integration branch. The integration branch keeps the resolution
    it had (local when it contains the remote, else the remote); any other base
    is the local ref `refs/heads/<base>`, else `refs/remotes/<remote>/<base>`,
    both read through the pass's `Tips` — no new git process, no fetch.
  - Everything that was read against the integration branch is now read against
    that base tip: the landed test (`merge-base --is-ancestor candidate base`,
    T-64) and the file set (`changed(base, head)`).
  - A task whose candidate is already in its base is skipped like a landed task
    (T-64). For a member of a feature that is its work merged into the feature's
    branch, waiting for the feature to reach the integration branch: it neither
    overlaps its base nor pairs with an open task.
  - The information line of an overlap is now `Integration { base, files }`
    instead of a `Conflict` whose `left`/`right` no reader used for these lines,
    and `check` writes its `base` under the same meta key. So a member's line
    reads `overlap: T-590 shares … with p/feature/f-1`, not with `dev`.
- `crates/gear-board/src/lib.rs`, `crates/gear-app/src/queue.rs`: the `Overlap`
  docs now say "the branch the task merges into (the integration branch, or the
  feature's branch a member merges into)". The meta shape is unchanged, so the
  board, `gear queue` and the frame render as before.

## Noted

- A base branch neither the local nor the configured remote's refs name (a
  feature planned but not started — the engine creates the feature branch from
  the integration branch before a member is dispatched, T-580) is treated as the
  integration tip, which is what it will be cut from. That is an edge case
  outside normal use and is logged here rather than failing the repo's scan: a
  parallel scan is evidence, and one odd branch must not blind it.
- The carrier (a feature's integration task) has the integration branch as its
  base, so the scan still names its branch with the lane's `task_branch`
  template rather than its `task_branch_override`. That is pre-existing (T-577
  added the override after this scan's ref read) and outside this contract; a
  carrier with no lane branch on disk is skipped as before, no pair and no item.
- One test field of the old findings, `Conflict` for information lines, was dead
  code (no reader of `left`/`right` for an overlap); replacing it with
  `Integration` is what made the base name available to `check` without reading
  it back out of a formatted string.

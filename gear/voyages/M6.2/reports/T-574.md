# T-574 — report

The captain can put one merge first (2026-11-05: Prometheus's T-738 held the fix
every red round waited for, and its merge was last of eight `now` merges plus
seven recovered ones, an hour away; the GEAR captain moved it by editing the
store).

## What changed

1. **The line** (`crates/gear-app/src/draft.rs`): `# Staff` takes
   `- merge-first T-<n>`, parsed like `- remerge` into
   `StaffItem::MergeFirst { line, task }` (a task id, and nothing else on the
   line).

2. **The apply** (`crates/gear-app/src/plan.rs`): `mark_merge_first` refuses a
   task with **no queued merge** — `T-x has no queued merge: merge-first moves a
   merge that is already waiting in the queue` — and otherwise writes
   `engine.merge_first.<project>` = the task id (`plan::merge_first_key`), with
   the staff decision recorded. The line is **one-shot**: the apply drops the
   staff lines it used from the file, exactly as it does for `remerge`, and the
   engine clears the mark when that merge starts.

3. **The order and the aloneness** (`crates/gear-engine/src/merge.rs`):
   - `now_first` puts the marked task's op first — before the `now` tasks and
     before everything else, so a `now` merge cannot pass it;
   - in the launch loop the marked op is `alone`: it never joins a batch
     (`merge_batch`) and never starts a train (`merge_parallel`), so nothing is
     gated beside it and nothing changes under its gate;
   - the mark is cleared in the same step that moves the op to Executing.

`trio_world`, `batch_of(gate, size)` (`batch_of_two` now delegates).

## Out of scope

- One mark at a time: a second `- merge-first` before the first merge runs
  replaces it (the engine's meta holds one task).
- The mark is per project; another repo's worker with the same key still runs
  its own merge (it is a different branch).
- `- merge-first` moves a merge that is queued (`Intended`, `Executing` or
  `Unknown`); it does not queue one — that is what `- remerge` does for a failed
  merge.

# T-588 — report

One meaning of "the current voyage", at its root.

## What changed

- `crates/gear-app/src/plan.rs`, `current_voyage(tx, project)` now answers with
  open work first, then the last departure:
  1. among the voyages that departed, the last departed one that still has a
     task that is not terminal (`!state.is_terminal()`, the same test as
     `gear_board::stations::voyage_open`);
  2. when no departed voyage has open work but a milestone has, that milestone
     — the one with the most open tasks, ties by name (a `BTreeMap` in name
     order, so a tie keeps the first name);
  3. when nothing is open, the last departed voyage (the previous answer);
  4. empty when the project never departed and no task is open.
  Its doc comment says why: GEAR M6.2 ran without a depart line while M6.1 was
  finished and departed, so a "last departure" rule answered M6.1 and every
  surface took the finished voyage; the rule lives here so no caller decides it
  on its own (T-586 taught one caller and the surfaces drifted).
- Every caller reads that one function and needed no change: the captain page
  (`home.rs`), captain take and handover facts (`captain.rs`), the charter, the
  admin config decision log and `staffing_voyage`, the stalled-voyage feed, the
  doorbell's `goal_line`, the reviewer raise (`release.rs`), the packet/charter
  facts in `plan.rs` itself and `gear report voyage` (`main.rs`).
- `crates/gear-app/src/home.rs` drops its own `open_voyages` (T-586) and asks
  `plan::current_voyage` again in the two places T-586 had replaced it: a
  captain is sailing when the plan names no voyage or the named voyage has open
  work, and the goal line is that voyage's. T-586's test stays green because the
  rule now answers M2 (undeclared, running) over the finished M6.1/M1, which is
  what that test asks for.
- Tests:
  - `crates/gear-app/src/plan.rs`, next to the function:
    `the_current_voyage_is_the_last_departed_one_that_is_still_open` (M2
    departed last and finished, M1 still open → M1),
    `nothing_open_gives_the_last_departed_voyage` (empty with no voyage; M2
    when both are finished), and
    `a_milestone_without_a_depart_line_is_the_voyage_while_it_has_the_most_open_tasks`
    (no departures: M2 and M3 tie at two open tasks → M2 by name; one M2 task
    lands → M3).
  - `crates/gear-engine/tests/it/doorbell_contract.rs`:
    `the_goal_line_names_the_open_voyage_not_the_finished_departure` — M1
    departed and done, M2 undeclared and open; the goal line carries
    `voyage M2` and not `voyage M1`.

## Noted

- The packet's rule, read literally, would let a finished last-departed voyage
  beat an undeclared milestone that still runs ("when none has [open work], the
  last departed one"), which is exactly the GEAR M6.2 fault and would redden
  T-586's test that the acceptance asks to keep green. Resolved as open work
  first: a departed voyage with open work, else a milestone with open work,
  else the last departure. The acceptance cases all hold either way; it is this
  one mixed case that decided it.
- `gear_board`'s snapshot/totals still pick their own voyage
  (`workload_voyage`, T-350/T-246) and are not on the packet's caller list, so
  they were left alone; the page's snapshot can name a different voyage than
  the goal line when a departed voyage and an undeclared one are both open.

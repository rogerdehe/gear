# T-566 — one merge-wait item per cause

## What changed

`crates/gear-engine/src/merge.rs` only.

The merge step told the captain that a merge waits with
`tell_captain(store, project, None, "merge waits: …", now)`, and `tell_captain`
writes on the thread `merge:<now>` — a **fresh thread every tick**. The `now` of
a retry is a new value, so one worktree that git could not create opened 47
items (M-7808…M-7859) in two minutes, and their doorbells kept arriving after
the fix.

- **One thread per project and cause class**: `merge-wait:<project>:worktree`
  and `merge-wait:<project>:other`. `MergeWaitCause::of(reason)` classes the
  reason: a reason that names the worktree (`worktree_create: refused …`, `the
  worktree … belongs to another repository …`) is `worktree`; anything else the
  step names is `other`.
- **`tell_captain_merge_wait`**: the thread's open item is found and its body
  set to `merge waits: <latest reason>` — updated, never duplicated. With no
  open item, one is inserted on that thread (`kind = Question`, the captain as
  sender and recipient, as before).
- **`close_merge_waits`**: when a merge of the project next starts, the item
  closes with `a merge of this project started, so the wait is over`. It is
  called where the merge actually begins — after `integration_worktree` (single
  merge), after the batch's worktree, after the train's first stage worktree —
  and closes **every** cause class, because a merge that starts has left every
  cause behind.
- No new table, no schema change; the three `tell_captain(… "merge waits: …")`
  call sites use the new function.

## Test

`crates/gear-engine/src/merge.rs` tests
(`make check CRATE=gear-engine TESTS='test(merge::)'`: **111/111 passed**):

`a_repeating_worktree_failure_keeps_one_item_and_a_merge_that_starts_closes_it`
— a merge worktree of another repository stands where `p/merge/home` goes, and
five ticks of `merge_passed` follow: after three with the first foreign
repository and two with a second one, the project has **one** item on
`merge-wait:p:worktree`, still open, whose body carries the **latest** reason and
not the earlier one. The right worktree is then registered, the merge starts,
and the same item resolves with `a merge of this project started, so the wait is
over`. Nothing about the run is per-tick any more.

## Decisions and deviations

- **Two classes, not a class per message**: the packet's example is
  `merge-wait:<project>:worktree`; every other reason the step can name lands in
  `other`, so a project can hold at most two such items.
- **The item is still a `Question` with no task**, exactly as before: the
  captain's home page keeps suggesting what it suggested for these items.
- **Closed on a start, not on a success**: the packet asks for "closed by the
  engine when a merge op next starts for that project", and the close runs right
  after the worktree is obtained, before the merge itself can still fail.

## Out of scope, logged

- The older `merge:<ts>` items a previous engine left open are not swept up by
  this change; they age out in the captain's inbox as before.
- `tell_captain` still writes its other one-off notices on `merge:<now>` (the
  rare ones); only the retried wait became one thread.
- `docs/design/` is untouched.

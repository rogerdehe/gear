# T-592 — report

The feature's full review sees what its members' light checks found, and its
rework goes to one owner lane, on the feature branch.

## What changed

`crates/gear-engine/src/review.rs`

- `feature_review_section` (new), called from `review_packet_for` when the task
  is a feature's integration task (`carrier_feature`, T-590): the review packet
  of the carrier now carries a section that
  - says, in the contract's words, `This is the feature's full review: judge the
    whole branch against the integration branch; a fail names every finding,
    the owner lane fixes them in one rework.`
  - lists every member of the feature in task order — the ones that carry
    `task_feature:<F>`, the carrier itself and cancelled members left out — each
    with the goal of its current contract and what its light check found.
- `light_check_findings` (new): the last attempt of the member with a stage
  marker for this feature, and the bodies of the direction results on it, read
  through the direction job's `checked_sha`/`sha` and seat when the record still
  names them (a closed job keeps only `checked_sha`, which is what the result
  names). A result that names another push is not the member's finding. A
  member with no check says `none ran`; a check with no result says so.
- `review_packet` takes the section as its last parameter and prints it after
  the diff line; for every other task the packet is byte-for-byte as before (an
  empty section adds nothing).

`crates/gear-engine/src/dispatch.rs`

- `ready_tasks_of`: a feature's integration task stays out of delivery while it
  has no attempt — attempt 1 is the engine's hand-in (T-581) — and IS the lane's
  work once it has one: the review's fail or the merge gate's reopen leaves the
  task `Ready` with an attempt, and the owner lane gets the next one.
- `intend_dispatch`: the delivery's branch is the task's own branch when it
  names one (`task_branch_override`, T-577), else the lane's task branch. So the
  integration task's rework packet says `Branch: p/feature/f-1` and
  `git switch p/feature/f-1`, the fix lands on the feature branch, and the
  hand-in reads that branch's tip (the hand-in's push check already reads the
  same override through `base::pushed_branch`).

`crates/gear-engine/src/feature.rs`

- `hand_in` yields while an attempt of the integration task is still in flight
  (`AttemptState::occupies_seat`). Dispatch runs earlier in the tick and has
  just delivered the rework, so the engine never opens a second attempt beside
  the lane's. The same-tip guard of T-581 is kept: an unchanged feature branch
  is not handed in again.

The owner lane is the one the plan set at creation (the lane with most members)
and it is the task's `lane`, so the captain moves it with `lane=` like any task.

## Tests

`cargo test -p gear-engine --lib <name>` (all pass):

- `review::tests::the_integration_tasks_review_packet_lists_the_members_and_their_findings`
  — two members, the first light-checked with a finding, the second `ok`; the
  integration task's review packet carries the full-review sentence, `T-1 — the
  goal` with `light check (attempt 1): F1: …`, and `T-2 — the second goal` with
  its own check (a distinct goal per member, so one goal cannot stand for all).
- `dispatch::tests::an_integration_tasks_rework_is_delivered_to_the_owner_lane_on_the_feature_branch`
  — with no attempt the lane's ready work is `T-1` only (attempt 1 is never
  delivered); with attempt 1 failed, `T-9` is delivered as `Rework T-9 attempt
  2` with `Branch: p/feature/f-1.` and `git switch p/feature/f-1`, never
  `heat/t9`.
- `dispatch::tests::an_integration_tasks_merge_gate_rework_is_the_owner_lanes_on_the_feature_branch`
  — the same after a failed merge gate: the task `Ready` with its accepted
  attempt kept (what the captain's settle leaves) is the owner lane's rework on
  the feature branch.
- `feature::tests::a_rework_in_the_lanes_hands_holds_the_hand_in` — with an
  attempt in flight the engine's hand-in hands nothing in and opens no attempt
  beside the lane's.

## Out of scope (logged, not fixed)

- The integration task's `base` is the integration branch, so the lane's
  hand-in of its rework must contain that branch's tip, while the rework packet
  only says to `git pull` the feature branch. A feature branch cut long ago is
  refused with the base rule's own message (`merge origin/dev into your
  branch`); the packet does not name that merge in advance.
- A rework delivered to a lane that then abandons it leaves the task `Ready`
  with an abandoned attempt; the engine's hand-in takes it again only if the
  feature branch moved and the last attempt was not `Rejected`, as T-581 wrote.

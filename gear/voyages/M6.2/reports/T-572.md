# T-572 — report

A red merge round tells the captain why, and a refusal that repeats stops the
splitting (user, 2026-11-05: Prometheus batches went red six times in an hour —
8, 3, 2, 1 members — every time for the same two browser cases missing cost
declarations, a cause on dev that no split could fix, and the captain heard
nothing).

## What changed

`crates/gear-engine/src/merge.rs`:

1. **The round is reported.** `run_batch` returns a third value,
   `Option<RedRound>`: the members it gated, the gate's refusal as the gate
   printed it, a **normalized** copy (shas, run ids and timings masked by
   `normalize_refusal`), and the cap it asks for. A round that named its
   culprit, or whose gate could not run (a reason that clears), is not a red
   round. `Finished` carries it to `collect_finished`, which calls
   `note_red_round`.
2. **One item per project** on the thread `merge-red:<project>`, **urgent from
   the first red round on** (contract v2): opened at once, body updated by every
   round with the refusal, the members, how many red rounds and minutes the line
   has spent, and what the captain can do — `send the cause back to a lane, take
   a member out (a `fail` verdict or a cancel), or let GEAR split the batch`.
   The halving goes on meanwhile as the fallback. Resolved by the next merge
   that lands (`close_red_line`, from `settle_report`'s `Report::Merged`), which
   also clears the line's counters.
3. **A refusal that repeats with different members stops the splitting.** When
   the last round's normalized refusal equals this one's and the members differ,
   the line is set waiting (`engine.merge_red.wait.<project>` holds the project's
   merge-op count) and the item becomes **urgent** with `the same refusal with
   different members: the cause is on <integration>, not in the batch`. Every
   member was already requeued by the red round. `red_line_waits` skips the
   merge step for the project while the wait stands, and a merge op queued anew
   — a remerge or a new pass, i.e. one more merge op than when the line stopped —
   clears it and the line runs again.

## Acceptance

- `make check CRATE=gear-engine TESTS='test(merge::)'` — 123 tests run, 123
  passed.
- `the_same_refusal_with_different_members_stops_the_splitting`: three tasks,
  `merge_batch = 3`, a gate that prints the same refusal whatever it gated —
  round 1 gates T-1, T-2, T-3 and round 2 gates T-1, T-2. One item, open and
  urgent, carrying the gate's refusal, `the same refusal with different
  members: the cause is on dev, not in the batch`, the members `T-1, T-2` and
  `2 red rounds`; all three ops back in the queue (`Unknown`); exactly two gate
  runs and no third while the line waits; a merge op queued anew lets the gate
  run again.
- `a_merge_that_lands_closes_the_red_item`: a red round of two, then T-2 lands
  alone — the item is resolved.
- `different_refusals_keep_the_halving`: three members refuse for T-3's file,
  two for none — the item is urgent (every red round is) but carries no "same
  refusal" sentence, it records 2 rounds, the cap halves to 1 and the line does
  not wait.
- The item's "what you can do" line is asserted in the first test, as contract
  v2 asks.

Fixtures added: `Shape::TrioFlat` (three tasks cut from `dev`), `Trio`,
`trio_world`, `batch_of(gate, size)`, and `quiet_ticks` (a merge step that runs
nothing is fine once a line waits).

## Out of scope

- The wait is per project (the item is per project), not per worker key: a
  second repo of the same project waits with it.
- A single merge that fails the gate alone is not a red *round*: it fails as it
  always did (its `merge-failed` item names it).
- The normalized refusal masks only what a gate commonly varies (shas, long
  numbers, durations); a gate whose wording changes per run still reads as two
  refusals and keeps halving.
- No release note: the packet does not name one.

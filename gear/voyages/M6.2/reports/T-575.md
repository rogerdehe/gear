# T-575 — the stall check never calls a delivered task queued

Prometheus 2026-11-05: M-10694, M-10699, M-10700 said **"T-748 is queued"**
every few minutes while T-748 attempt 1 was **delivered** and `gear queue`
showed "platform working T-748".

## Where those words came from

`crates/gear-engine/src/feed.rs`:

1. `startable_tasks` counts the ready tasks whose attempt does **not** occupy a
   seat. T-748's attempt was `Delivered`, so it took the task out of the count —
   correctly — and with no other task ready the project had **zero startable
   tasks**, which is the "voyage is stopped" branch (T-560).
2. `stalled()` then took every live task of the voyage as work nothing can
   start, and `wait_words()` described T-748. The lane was **working**
   (`gear_board::idle::idle_reason` counts `Delivered` as working), so the lane
   had no idle reason, and `wait_words` fell to its last line:
   `is {state_word(task.state)}` = **"is queued"**.
3. The item is urgent and is re-opened as the state flickers, so the captain was
   rung again and again for work that was simply in flight.

## The fix — `crates/gear-engine/src/feed.rs`

**`in_progress(tx, project, task)`** — the task has an attempt the seat still
holds: `Delivered | Started | Stopped | Unknown` (`AttemptState::occupies_seat`,
the rule `gear queue` prints "lane working T-x" by).

- **`stalled()`** splits the voyage's remaining tasks into work in progress and
  stuck work. Only the stuck ones are named, counted and shown; an urgent item
  for a voyage whose tasks are all in flight is never written. When every task
  left is in progress the open item closes with **"a task is in progress"**
  (a new reason, `IN_PROGRESS`) — not `NO_TASK_LEFT`, which would claim the
  voyage is empty.
- **`wait_words()`** says **`is in progress`** for such a task before any lane,
  dependency or queue reasoning, so a mixed voyage (one stuck task next to a
  delivered one) never prints "is queued" for the one being worked on.

## Tests — `make check CRATE=gear-engine TESTS='test(stall) | test(feed)'` → 55/55

In `crates/gear-engine/tests/it/feed_contract.rs`, on a voyage whose one task
sits on a held lane (no lane can start it):

- **`a_delivered_task_is_work_in_progress_not_a_stalled_queue`** (the
  acceptance): the task's attempt 1 is `Delivered` and the task is still `Ready`.
  `feed::keep_lanes_fed` opens **no** `stalled` item — no change on that thread
  and nothing written.
- **`a_task_with_no_attempt_is_still_named`** (the acceptance's second half):
  the same task with no attempt gets the item, and it says
  `T-1 waits for lane review (held: …)`, never "is queued".

Also run: the whole `gear-engine` crate **1044/1044**, so no other tick test
depends on the old wording.

## Decisions

- **Which attempts count.** `occupies_seat()` — the same predicate the feed's
  own `ready` count and `gear queue` use, so the two cannot drift apart. A
  `Submitted` attempt (waiting for review) is not work in progress here; its
  task is not `Ready` either, so it never reaches `wait_words`.
- **The item closes, it is not merely left alone.** A captain who already had
  the (wrong) urgent item gets it closed with the fact, rather than a stale item
  that rings forever.
- **A voyage with both kinds still rings**, naming only the stuck tasks: that is
  a real stoppage, and the in-progress tasks are not evidence of one.

## Out of scope, logged

- The `feed.rs` lane items and `gear_board::idle` already treated `Delivered` as
  working, so only the stalled-voyage item was wrong; nothing else changed.
- A task whose attempt is `Submitted` (the lane finished, the review has not
  started) is still not "in progress"; if such a task ever holds a voyage alone,
  the item names it with its state as before.
- `docs/design/` is untouched.

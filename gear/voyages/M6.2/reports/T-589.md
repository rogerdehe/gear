# T-589 — report

A feature member's hand-in is accepted without a blocking review.

## What changed

`crates/gear-engine/src/review.rs`:

- **The settlement.** `start_hand_in_reviews` now settles a member of a feature
  as accepted at hand-in, in the tick its result arrives, with no reviewer: the
  attempt is `Accepted`, the task `Done`, and the merge step queues its op in
  the same tick or the next (the merge path a captain's pass takes). It runs
  before both the mechanical branch and the `[temps]` guard, so a member is
  settled in a project without reviewers too, and no `verdict:<task>:<attempt>`
  manual-settlement request is raised for it. Its merge is the light one stage 1
  built: the task's `base` is the feature's branch and its `gate` is
  `feature_check`, so the merge is a conflict check plus that check, never the
  project gate.
- `feature_member()` — the rule, one read: a task that stores a feature
  (`Tx::task_feature`, non-empty, already filtered by the store) **and** is not
  that feature's integration task (`Tx::feature_carrier`). The carrier's hand-in
  is not touched: it still waits for a review, which is how the feature reaches
  the integration branch through one review and one full gate (stage 1). A task
  with no feature is reviewed as today. No attempt number is consulted, so a
  rework (the captain's attempt n >= 2) settles exactly the same way.
- `settle_mechanical` and the new `settle_feature_member` now share
  `settle_without_review`: one verdict write (`gear_app::tasks::settle`, exactly
  a captain's pass) and one Info line to the captain, once per task, on
  `feature:<task>` for a member (the mechanical line keeps its wording and its
  `mechanical:<task>` thread, and its meta key is unchanged). The evidence note
  is `feature F-<n>: accepted at hand-in without a review` — deliberately not
  `mechanical:`, so the merge keeps requiring the task branch and the T-564
  check on it (a member had a lane push; a mechanical task never does).
- A settlement that errors is reported in `ReviewReport::settle_failed` (never
  fatal) and the hand-in falls through to a review, as T-273's contract v2 has
  it. `ReviewReport::settled` / `settle_failed` docs name both sources now.

`mod tests` — four new tests:

- `a_feature_members_hand_in_is_accepted_without_a_review` — no seat, worktree
  or agent; attempt `Accepted`; verdict passed with the feature evidence,
  `by_seat = engine`; `merge_passed` queues one op for `T-1/1`; one Info line on
  `feature:T-1`, and a second tick adds nothing.
- `a_feature_members_rework_is_accepted_without_a_review` — attempt 2 settles
  the same way and its merge queues as attempt 2.
- `a_feature_integration_tasks_hand_in_still_waits_for_a_review` — with
  `feature_carrier:F-1 = T-1` the same task is not settled: the attempt stays
  `Submitted` and a temp seat takes it.
- `a_task_with_no_feature_is_reviewed_as_today` — no feature mark: as before.

## Noted (edge cases outside the contract's normal use)

- A member whose attempt works to an older contract than the task carries now
  still settles (the packet says "an attempt of a task with a stored feature"),
  but `passed_tasks` only queues a merge for a verdict written against the
  task's **current** contract version, so such an attempt is accepted and
  unmerged: T-397's "lost attempt" item names it to the captain. T-273 met the
  same case by not settling (a mechanical reason belongs to the contract text);
  a feature mark belongs to the task, so the packet's rule is applied as written
  here. Rare: a captain re-plans a contract while its attempt is in flight.
- A member's push still starts a direction check (`start_direction_checks`): the
  packet is about the hand-in, and a direction check blocks nothing. Mechanical
  tasks skip it; if a member's push should too, that is stage 2's call.

# T-573 — a merge that carries only reports skips the gate

The user, 2026-11-05: prometheus/web/t732 held one review record, and its merge
would still pay a four-to-five-minute CI round.

## What changed — `crates/gear-engine/src/merge.rs`

**The rule.** A merge is report-only when every file it changes — the approved
candidate **and** the review commits, against the integration branch it is built
on — lies under the project's voyage folder. The folder comes from
`[conventions].voyage_dir` (new `Repo.voyage_dir`, filled in `crates/gear-app/
src/config.rs`), with `{project}` filled and **`{milestone}` matching any one
folder**. A merge that changes nothing at all is **not** report-only (a `diff`
that failed to read must never buy a merge without a gate).

- `changed_paths(git, dir, base, head)` — `git diff --name-only base head`, the
  paths the merge adds.
- `reports_only(paths, voyage_dir, project)` / `is_under_voyage(...)` — the rule
  itself, pure and unit-tested: prefix with `{project}` filled, one folder for
  `{milestone}`, then the template's own suffix and the file.

**Single merge** (`merge_one_locked`): after the merge is built (steps 1–7: the
fetch, the candidate, the conflict check) and before the gate, it computes the
changed paths and sets `Prepared.no_gate`. A report-only merge runs **no gate**;
the push and the branch closing are exactly as before. `Prepared` now carries
`base` (what it was built on) so the diff needs no second guess.

**Batch** (`run_batch`):

- the members are **built report-only first**: before the build loop, each op's
  candidate is read against the remote integration branch, and a candidate that
  is not here yet counts as **gated**, never as a report;
- each built member is marked from its own `changed` paths (its review commit
  included), so a member whose real diff grew past a report is gated;
- **one gate still judges the rest**, as today; a batch whose members are all
  report-only runs **no gate at all** and goes straight to the push.

**The merge result says so**: every green line carries `no gate: reports only`
right under `merged <task> into <integration>: <commit>` — single merge and
batch member alike (`closed_and_line`).

## Tests — `make check CRATE=gear-engine TESTS='test(merge::)'` → 123/123

- **`a_merge_that_carries_only_reports_skips_the_gate`** (the acceptance): a
  candidate that adds only `gear/p/voyages/M1/reviews/T-6.md` and a review
  commit on top of it, merged with the gate command `false` — the merge lands,
  its line says `no gate: reports only`, and dev holds both commits. The gate
  would have failed, so landing proves it never ran.
- **`a_merge_that_touches_another_file_still_gates`** (the acceptance's second
  half): the same candidate plus `notes.txt`; the gate runs, fails, and nothing
  lands.
- `only_a_file_under_the_voyage_folder_is_a_report`: the path rule — the
  acceptance's path with `{project}` filled, any milestone folder, another
  project's folder no, the folder itself no, the default template, and a merge
  that changed nothing no.
- The existing batch tests (`two_merges_are_merged_together_and_gated_once`,
  `two_merges_gate_side_by_side_and_land_in_order`,
  `waiting_merges_take_turns_and_a_chain_lands_in_order`) still pass unchanged.

Also run: whole `gear-app` crate **692/692** (the `Repo` field is new there).

## Decisions

- **`{milestone}` matches any one folder, never a prefix of a path**: `rest` is
  split at the first `/` after the prefix, so `gear/p/voyages/M1` (a folder, not
  a file) is not a report and `gear/other/voyages/M1/...` is another project's.
- **A candidate git cannot read is gated.** The batch's pre-check runs before the
  fetch; a candidate that is not here yet must not buy a gate-less merge.
- **A red gate still requeues the whole batch**, report-only members included:
  they were built into the same tree, and the next tick merges them without a
  gate. Halving and culprit naming are unchanged.

## Out of scope, logged

- A batch mixing report-only and gated members runs the gate over the whole
  stack, so the gate sees the report files too. That is what today's one-gate
  batch already does; the packet asks only that the report-only members need no
  gate, which they do not (no gate runs when none of the members is gated).
- The train path (`merge_parallel` above 1) is untouched: it gates every stage
  on its own base, and the packet names single and batch merges.
- `docs/design/` is untouched.

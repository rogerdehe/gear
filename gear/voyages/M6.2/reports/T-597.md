# T-597 — report

The feature branch catches up with the integration branch before its own full
review (M6.2, feature stage 3, 1/3).

## What changed

- `crates/gear-engine/src/feature.rs`:
  - `hand_in` now refreshes the feature branch before it hands the integration
    task in: after the fetch (which now names every branch of the remote, as a
    merge's fetch does) it asks `git merge-base --is-ancestor
    <remote>/<integration> <remote>/<feature>`; a branch that already holds the
    integration branch is handed in exactly as before, with the same report
    (`the feature branch <branch> at <sha>`).
  - New `refresh` (`Refresh` = `NotNeeded` | `Refreshed` | `Wait`): it opens the
    merge worktree as `merge.rs` opens it (`merge::open_integration_worktree`,
    seat `merge`), takes `merge::merge_lock` so the merge queue and this step
    never share it, resets the worktree to `<remote>/<feature>`, merges
    `--no-ff <remote>/<integration> -m "refresh(<feature>): <integration>"`,
    pushes `HEAD:refs/heads/<feature>`, and hands in the new tip. The report
    names the refresh commit: `the feature branch <branch> at <tip>, refreshed
    with the integration branch (refresh(F-1): dev)`. A push the remote rejects
    pushes nothing and the next tick fetches and merges again; a worktree busy
    with another merge is a later attempt, not a failure.
  - A conflict aborts the merge (`merge --abort` + `reset --hard` to the
    feature tip), pushes nothing and hands nothing in. It records the two tips
    it found in `feature_refresh_conflict:<project>:<feature>` and opens one
    captain item on `feature-refresh:<feature>` (an open item of the same
    feature is updated, never duplicated), naming the conflicting files
    (`git diff --name-only --diff-filter=U`), saying "Settle a fail of T-<n>
    with a rework; its owner lane resolves the conflict on the feature branch",
    and naming the two tips. A later tick tries again only when one of the two
    tips differs from the recorded pair.
  - `start_features`/`hand_in` take `herdr` (the worktree is Herdr's, as a
    merge's is); `feature_of_carrier` reads the feature id through the plan's
    `feature_carrier:<project>:<feature>` meta (the carrier itself carries no
    `task_feature`), falling back to the branch name.
- `crates/gear-engine/src/lib.rs`: the tick's step 6f passes `herdr`.
- Tests in `feature.rs mod tests` (real bare remote + a real merge worktree
  registered in `FakeHerdr`, as the merge tests build one): the feature branch
  behind `dev` is refreshed, the remote branch holds `dev` under the subject
  `refresh(F-1): dev`, and the hand-in names the refresh commit and the new tip;
  a conflicting refresh opens one item naming `f.txt` and the rework sentence,
  pushes nothing, hands nothing in, does not try again on the next tick, and
  hands the feature in once the owner lane resolves it on the feature branch;
  a feature branch that already holds `dev` is handed in as before, with a
  herdr that has no merge worktree (proving no refresh ran). The three T-581
  tests are unchanged apart from the `herdr` argument.

## Out of scope

- The feature id in the commit subject and the item thread is the stored form
  (`F-1`), not the branch's lowercased one (`f-1`); the plan's
  `feature_branch` template does that lowercasing for the branch name only.
- The `feature-refresh:<feature>` item is left for the captain to resolve; a
  later refresh that merges does not close it (the item says what was found at
  those two tips).
- A refresh whose push fails reports through the tick's `feature_failed` list
  rather than opening an item; it is transient and the next tick merges again.

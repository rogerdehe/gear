# T-551 — report

`gear admin init` never moves a Herdr session to another store without being
told.

## Where the code lives

The packet puts `targets.tsv` and the refusal in `crates/gear-app` and the tests
in gear-app's tests, but gear-app holds no registry code: the registry
(`targets_path_in`, `registered_store`, `register_store`) and the init-time
write are in `crates/gear-cli/src/main.rs` (`cmd_admin_init`), and the init and
registry tests are in `crates/gear-cli/tests/it/admin_init_contract.rs`. I sent
this as a question with options (a) implement in gear-cli where the code is, or
(b) move the registry into gear-app first; the captain answered **(a)**, which
is what was done.

## What changed

- `crates/gear-cli/src/main.rs`:
  - new `fn refuse_a_store_move(move_store: bool)`: when the caller is inside a
    Herdr session (`HERDR_SOCKET_PATH`), the session has a line in
    `~/.config/gear/targets.tsv`, that line names another store **and** that
    store file still exists, and `--move-store` was not given, it returns
    `BadFormat` before anything is written. The message names the session (its
    socket), the registered store path, the new one, and the flag:
    "session <socket> is registered on the store <registered>, and this init
    names another one (<db>): init does not move a Herdr session to another
    store without being told; run `gear admin init --move-store <config>` to
    move it, or unset GEAR_DB to keep the session's store".
  - it is called after the foreign-session and fixture refusals, by `--check`
    (so a check says it early, as the foreign-session refusal does) and by a
    real init before `open_store()`, so the new store file is never created on
    a refusal.
  - `AdminOp::Init` gains `#[arg(long)] move_store: bool` (`--move-store`), with
    its doc; `cmd_admin_init` takes it as a parameter.
  - the same store (compared canonical), a session with no line, and a
    registered store file that is gone are allowed, exactly as today.
- `crates/gear-cli/tests/it/admin_init_contract.rs`:
  - `init_from_session` now goes through `run_init(home, socket, config, check,
    move_store, db)`; `init_moving_the_store(...)` runs the same init with
    `--move-store`; `registered_store_of(home, socket)` and `canonical(path)`
    read the registry line.
  - new `init_refuses_to_move_a_sessions_store_without_the_flag`: the session
    registers on its own store, the same store named explicitly passes
    (`--check` and init), another store is refused by `--check` and by init with
    an `ERROR BAD_FORMAT` naming the socket, both paths and `--move-store`, with
    no file created and the line unchanged; `--move-store` writes the project
    into the new store and replaces the line; after the registered store file is
    removed, another store registers as it always did.
  - `init_refuses_a_config_for_another_herdr_session`'s `alpha` + explicit
    `GEAR_DB` block asserted the old silent move. It now expects the refusal
    (`--check` too) and then `--move-store` moving the line, which is the
    behaviour this task asks for.

## Acceptance

The packet's acceptance names gear-app's tests, which cannot reach this code (see
above); the analogous tests are the gear-cli ones:

- init with a different store for a session whose registered store exists is
  refused and the error names both paths and `--move-store`:
  `init_refuses_to_move_a_sessions_store_without_the_flag`.
- with `--move-store` the line is replaced: same test.
- the same store, and a registered store that is gone, change nothing from
  today: same test.
- the two other init tests that register from a session still pass:
  `init_refuses_a_config_for_another_herdr_session`,
  `init_refuses_a_fixture_into_the_sessions_store`.
- `make check CRATE=gear-cli TESTS='test(init)'` — 32 tests run, 32 passed.
  The whole crate, since this touches the init path other tests use:
  `make check CRATE=gear-cli` — 201 tests run, 201 passed.

## Out of scope

- No doc or skill text was changed: `--move-store` is documented by its clap
  help only, as the packet asks for the flag, not for a skill line. The skill
  (`skills/gear/references/`) still says "`gear admin init`" without its flags.
- The release note for v0.6.52 (T-549) does not name this item; it was written
  from its own packet.
- The change does not touch `crates/gear-app`: there is no registry code there to
  change.

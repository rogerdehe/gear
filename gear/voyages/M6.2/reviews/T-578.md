## Findings
- F1 [P1, blocking] An existing task whose feature changes keeps its old base and gate — `crates/gear-app/src/plan.rs:998` and `:1020`. The `feature:` field is stored first (`tx.set_task_feature(project, id, feature)` at line 998), and only then `let before = tx.task_feature(project, id)?` is read (line 1020), so `before` already equals the new value: `before.as_deref() != Some(feature)` is always false for a non-empty change and `before.is_some()` is always false for a clear (`feature: -`). The base/gate move (lines 1024-1036) is dead code. Repro: apply a plan that creates an unfeatured task, then re-apply a block naming it with `feature: F-1`; the mark is stored but `task.base`/`task.gate` stay the lane's integration branch and full gate, so the task merges to the wrong branch and runs the full gate instead of the feature's. This breaks contract requirement (1) "on existing tasks when their feature changes". Fix: read the old value before the first set — move `let before = tx.task_feature(project, id)?;` to just above the `if let Some(feature) = &item.feature { tx.set_task_feature(...) }` block at line 996-999 and delete the now-duplicate set at line 1032 (about 3 lines).
- F2 [P1, blocking] A terminal carrier is treated as absent, so a landed feature is re-minted on every later apply — `crates/gear-app/src/plan.rs:2048-2061`. `feature_work` builds members from *all* tasks' stored marks (no terminal filter, plan.rs:1913-1945), so after the carrier merges (Done) its members are Done but still marked. `tx.feature_carrier` still names the Done carrier, but the `!task.state.is_terminal()` guard fails, `new_carrier` becomes true and a brand-new integration task is created for the same feature — with deps = the already-Done members — on every subsequent apply, even one whose plan file contains no `feature:` line at all. Repro: apply feature F-1 with one member (creates carrier); mark member Done and carrier Done; apply any later plan (e.g. one unrelated NEW task); `result.created` contains an extra NEW "Integrate feature F-1" task. This breaks (4) "when a feature has no carrier yet (`feature_carrier`)" — a Done carrier is still the feature's carrier — and mints a duplicate of the "one integration task" the feature is supposed to have. Fix: reuse the stored carrier whenever `feature_carrier` returns a task that exists — change the guard to `Some(carrier) if existing.contains_key(&carrier)` (drop the terminal test), leaving `_` for a dangling name. If the captain later wants "a new member after the feature finished gets a fresh carrier", that belongs to the semantics the captain should decide; as written the code regenerates unconditionally for a completed feature.
- F3 [P2, logged] Lane tie-break is "lowest task number", not "first in the draft" — `crates/gear-app/src/plan.rs:1969-1990` (lanes collected in member-number order) and `:2015-2022` (first strictly-greater count wins). For NEW-only features number order equals draft order, so the common case matches the contract; but a feature that mixes an existing low-numbered member with a higher-numbered one named earlier in the draft ties to the wrong lane. Edge case (ties only); does not block.

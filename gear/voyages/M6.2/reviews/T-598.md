## Findings
- F1 [P2, logged] The request meta is marked `started` before the bisect worktree is obtained and the thread spawned — `merge.rs:2063` (`set_meta(&key, BISECT_STARTED)`), with `Err(_) => continue` at `merge.rs:2069` and `if spawned.is_ok()` at `merge.rs:2097`. If `bisect_worktree` fails (seat-branch settle, herdr open/create, `check_worktree`) or the thread spawn fails, the request is consumed, never retried, and no line or note reaches the merge-failed item: the feature's red gate is never named and the captain cannot tell "could not start" from "still running". This is an edge case outside normal use, so it does not block, but it is silently dropped rather than logged. Smallest fix (~6 lines): move the `set_meta(BISECT_STARTED)` after a successful worktree open and a successful spawn; on a worktree-open failure leave the key `pending` for a bounded number of ticks (or append a one-line "bisect could not start: <reason>" note to the item), so the failure is visible instead of swallowed.

## Findings
- F1 [P2, logged] `- remerge` of an `Unknown` op both requeues the old op (`plan.rs:2711-2721`) and queues a fresh one (`plan.rs:2797`), leaving two active `Intended` merge ops for the same task and candidate. In a single-merge project this settles cleanly (the first lands, the second is voided by `attempt_already_merged`); in a batched/trained project both join the same batch/train, and the second member's `prepare_merge` finds its candidate already on the staged base and merges the task branch tip again (`merge.rs:3163-3168`, `only_the_candidate` is false when the review commit sits on the candidate), producing a spurious empty `--no-ff` merge commit. The task still lands and nothing is lost or double-merged, so this is not blocking; the smallest fix, if the captain wants it, is to not requeue the old op when a new one is queued (drop the `Unknown` arm's `set_op_state` in `plan.rs`, or leave the old op to be voided).

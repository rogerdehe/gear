## Findings
- F1 [P3, logged] `feature::branch_override` duplicates `gear_store`'s `task_branch_override` accessor (now merged by T-577) — `feature.rs:41-45`. Same meta key and empty-means-none semantics, so behaviour is identical and the merge is clean only because the names differ. The report already flags it as the one line to switch once T-577 lands; nothing to change for this task.
- F2 [P2, logged] the mandated `tasks::start_attempt` carries a precondition the audit step avoids: the writer lane seat must have no in-progress attempt (`tasks.rs:63-77`). If the integration task's lane is still working another task when the last member merges, the hand-in is refused (`seat already has an attempt in progress`) and reported as `feature_failed`, then retried next tick — it self-heals once the lane is idle, so no wrong data and no lost work, only a delay. This is inherent to the contract's own choice of store calls, not a writer deviation; flagging so the captain can note it. The smallest change if wanted would be an idle seat fallback, but that would depart from the contract's "the same store calls".
- F3 [P3, logged] `hand_in` fetches the remote but reads the tip from the `RepoTips` cache, whose `entry().or_insert_with` returns a value cached earlier in the same tick — e.g. by the audit step, which runs immediately before and shares the repo path in a single-repo project (`feature.rs:127-129`). The candidate can be up to one sub-tick fetch stale; both fetches are milliseconds apart, so only a member pushing in that window differs. Not normal use.
- F4 [P3, logged] the acceptance's "no delivery op" is asserted via `ready_tasks_of` excluding the override task (the source of the delivery decision), not by running `plan_dispatch`/`intend_dispatch` and checking the store has no `Deliver` op. A reasonable proxy given the filter is the one place every assignment reads; a stricter test would close the gap but nothing in the code suggests the op could appear another way.

## Findings
- F1 [P1, blocking] The foreign check rejects the documented conflict-resolution flow for a task-branch merge — `crates/gear-engine/src/merge.rs:3019` (the `git log` at 3022 and the `foreign` test at 3035). When a task-branch merge conflicts, the captain's playbook (skills/gear/references/course.md line 56) is "merge the integration branch into the task's branch, resolve it there, push, then `- remerge T-<n>`". That merge pulls dev's own commits into the range: after `git merge dev` on the task branch, `git log --no-merges <candidate>..<tip>` lists the review commit *and* every dev commit merged in, and those dev subjects do not start with the review prefix, so the remerge fails `stuck` naming dev's already-reviewed commits as "not the review". Reproduction: `candidate + review(T-5): pass` on `heat/t5`, then `git merge dev` into it, remerge → `stuck`: "…not the review: <dev sha> dev moved; a change after hand-in needs a new attempt". This is normal use (a merge conflict, and the engine's own failure message still tells the captain "to retry it: `- remerge {task}`"), so it breaks the milestone bar. Smallest fix: judge only commits the merge would newly introduce — add `--not {base_ref}` to that `git log` call (e.g. `["log", "--no-merges", "--format=%H%x09%s", &format!("{sha}..{tip}"), "--not", base_ref]`, `base_ref` is already computed at the top of `prepare_merge`). Lane commits are never on the integration branch, so all three acceptance tests still pass, and dev's conflict-resolution commits are no longer foreign. Add a test: a task branch of candidate + review commit with `git merge dev` resolved on it merges (or at least does not fail as foreign).

## Set aside
- A lane commit whose subject happens to start with the review prefix is not caught — that is the contract's own design (subject prefix is the signal), not a defect to fix here.
- A lane commit pushed on top of a *mechanical* settle's task branch is not merged: the mechanical path merges only the pinned candidate (`else if !already { merges.push((sha, sha)) }`), never the task tip, so there is no hole there.
- The fallback `task_tip.clone().unwrap_or_else(|| task_ref.clone())` can merge the unresolved branch name only if `rev-parse` succeeded for the existence check and failed for the sha read (a branch deleted between the two calls); the merge then fails on the missing branch, and a normal push-after-read is pinned and caught. Edge case outside normal use — logged, not flagged.
- The `git log` read failure is `clear` (retried) rather than `stuck`: the sha is pinned, so this only happens on a transient/repo fault, and retrying is right.

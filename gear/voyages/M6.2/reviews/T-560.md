## Findings
- F1 [P2, logged] the stalled item has no re-open gate: a captain who resolves the alert while the stall lasts is rung again on the next tick — `crates/gear-engine/src/feed.rs:625` (`stalled`, the `None` arm of the `open_stalled` match) — `open_stalled` sees only Open|Waiting, so a resolved item is re-inserted as a fresh urgent message every engine tick, unlike the lane items (`feed.rs:260`) and the balance item (`feed.rs:428`), which stay quiet for one `attention::period` after a resolution. Fix (about 3 lines, mirroring `imbalance`): in `stalled`, before `tx.insert_message(&NewMessage { … })` in the `None` arm, add `if !crate::attention::due(tx, project, STALLED_THREAD, captain, now)? { return Ok(None); }`.
- F2 [P3, logged] a `Failed` task is neither counted nor named — `crates/gear-engine/src/feed.rs:574` — the filter `!task.state.is_terminal()` also drops `TaskState::Failed`, while the contract counts "tasks not done and not cancelled"; a voyage whose only remaining task is `Failed` stays quiet. Edge case (Failed is terminal in the store; tasks are normally reopened or cancelled), but the literal wording differs. Fix (1 line): `!matches!(task.state, TaskState::Done | TaskState::Cancelled)` instead of `!task.state.is_terminal()`.
- F3 [P3, logged] stray tasks with no milestone count under the current voyage — `crates/gear-engine/src/feed.rs:575-579` — `milestone == None` is treated as "left", so with a departed voyage plus un-voyaged tasks the `<n> tasks left` count and the named list describe work outside that voyage. Edge case (tasks normally belong to a voyage); the report documents it as a decision.

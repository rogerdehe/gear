## Findings

- **R1 [P1, blocking; prior F7 and startup recovery] Confirmation clears the durable plan before its caller commits completion** — `crates/gear-engine/src/switch.rs:228`, `crates/gear-engine/src/quota.rs:317`, `crates/gear-engine/src/onboard.rs:180`. `switch_in_place` commits `clear_pending` and returns Done; only afterward does quota finish_switch record the new model and Continue. A restart between these calls leaves neither a plan nor Continue. When the quota marker has cleared, subsequent quota ticks do nothing. For startup, the same boundary leaves a Starting lane with no plan, which onboard_queued skips forever. These are reachable with one restart, even though finish_switch itself now uses one transaction. **Reproduction:** with an active lane/open T-1, store `engine.switch.p:heat = confirm|0|0|DeepSeek V4.1 Flash OpenCode Go`, put the target status bar on the pane, call switch_in_place and stop after Done (the crash boundary). Run quota policy four times with idle/non-quota observations: zero Continue ops, expected one. Repeat with the lane Starting and its binding Pending; four onboarding calls leave Starting, expected Active. Tests: `restart_after_status_confirmation_keeps_the_quota_completion_intent`, `restart_after_lane_confirmation_finishes_starting_seat`. **Smallest fix:** in switch.rs, retain the plan on successful confirmation and let the owning caller clear it in its completion transaction. quota::finish_switch already has the correct clear inside its transaction. Add the clear to both lane finish_onboard transactions and the review start completion transaction, so success is committed with startup/packet delivery. Keep a success plan recoverable until that transaction commits; update helper expectations accordingly. About 20–35 implementation lines across switch.rs/onboard.rs/review.rs, plus the two boundary tests. Verify recovery before completion sends no keys and yields one Continue or a completed startup, and recovery after completion creates no duplicate.

- **R2 [P1, blocking] Ordinary conversation text is mistaken for an open picker** — `crates/gear-engine/src/switch.rs:224`, `:253`. `picker_open` is true for any occurrence of Search, Recent, Select model, or No results anywhere on the visible screen. A stopped agent whose visible answer says `Search for the matching tests.` above the wrong-model bar gets repeated Esc instead of /model. Esc closes overlays but does not erase conversation text; after the two bounded tries this seat is flagged without attempting the switch. The new tests hide this by making Esc replace the entire conversation with `Ask anything…`. **Reproduction:** idle OpenCode; screen `Search for the matching tests.\nBuild auto · MiniMax-M3.1-Flash MiniMax · high`; no fake screen replacement on Esc. Five calls record five Esc and no /model. Test: `conversation_word_search_does_not_prevent_opening_model_picker`. **Smallest fix:** replace the unanchored single-word checks with recognition of the actual picker layout/title and anchored UI rows, requiring positive modal evidence rather than a word inside prose; apply the same discipline to Select variant. Keep bounded waiting and the whole visible read. About 20–30 lines in switch.rs and a regression that preserves conversation text across Esc. Verify quoted picker/variant instructions do not create dialogs, while real picker and variant fixtures still advance.

- **R3 [P1, blocking; prior F6] Doorbells and existing Intended ops still prompt into the model dialog** — `crates/gear-engine/src/dispatch.rs:91` (the guard's limited scope), `crates/gear-engine/src/lib.rs:325`, `crates/gear-engine/src/ops.rs:82`. The new switch_pending guard covers task-dispatch decisions only. doorbell_inputs still marks an idle seat reachable during a switch, and execute_intended ignores the pending plan. A single incoming instruction during a quota switch causes a GEAR doorbell to be prompted into the picker/variant search box. A delivery already Intended before switching also bypasses the guard. This corrupts UI input and can leave the lane unable to continue. **Reproductions:** (1) seed pending step filter and an actual picker, insert one Open instruction addressed to the lane, then run a full engine tick: FakeHerdr records the model filter followed by `Prompt("GEAR: 1 item(s) waiting...")` while the plan is still pending; (2) seed a pending variant step plus one Intended Deliver for the lane's open attempt, call execute_intended: it records `Prompt("Continue T-1")`. Tests: `a_message_does_not_prompt_into_an_open_picker`, `an_existing_delivery_is_held_while_the_picker_is_open`. **Smallest fix:** in doorbell_inputs, make a pending-switch seat ineligible for ringing; in execute_intended's preparation loop, defer (leave Intended, do not Void or execute) prompt ops for seats with a nonempty switch plan. About 10–20 implementation lines in lib.rs/ops.rs, retaining the dispatch guard. Add the two tests and verify the held message/op is delivered once after successful completion clears the plan.

- **R4 [P1, blocking] A variant dialog that renders one tick late is never answered** — `crates/gear-engine/src/switch.rs:282`. A delayed render after model selection therefore waits out a failed try rather than selecting the requested variant. **Reproduction:** Esc, /model opens the picker, the filter submits but the next read still shows the old bar; call the Variant step once, then render `Select variant / Search / Default / none / low / high / max`. Test: `a_variant_rendered_one_tick_late_is_answered`. **Smallest fix:** let confirmation handle a newly visible variant dialog and return to the variant-answer step; do not treat a single absent-dialog read as proof that this model has no variants. Retain bounded polling and only advance after a successful variant submission. Ensure a transient target bar does not prematurely finish before a pending variant can render. About 10–20 lines in switch.rs plus a delayed-variant test (including target-bar-before-dialog rendering), alongside the existing no-variant and immediate-variant tests.

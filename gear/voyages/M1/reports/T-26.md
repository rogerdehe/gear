What was wrong or missing, and what it says now:
1. **The PATH line pointed at a directory that does not exist.** It built the path from `herdr plugin config-dir` (`…/plugins/config/herdr-gear`) plus `../../github/rogerdehe/gear/bin`; Herdr installs a GitHub plugin at `~/.config/herdr/plugins/github/<plugin_id>-<hash>/` (verified with the file-viewer plugin on this machine), not at `<owner>/<repo>`. It now takes the plugin's `plugin_root` from `herdr plugin list --json` (the JSON shows `plugin_root`), then `/bin`, and shows the real shape (`~/.config/herdr/plugins/github/herdr-gear-<hash>/bin`). Verified on this machine: the one-liner prints the plugin root (here `/Volumes/Data/myai/gear`, a local link); the wrapper `bin/gear` runs from any directory.
2. **`gear admin kickoff > gear.toml` did not produce a config.** The kickoff prints the inventory first and the `gear.toml` skeleton after it, so the redirect wrote prose before the TOML and `gear admin init` would not parse it. It now extracts the skeleton (`gear admin kickoff | sed -n '/^# gear.toml/,$p' > gear.toml`). Verified: the extracted file is 36 lines of TOML; `gear admin init` on it reports the first TODO (`project.id "TODO"`), which is what "fill in the TODOs" means.
3. **The skill install was vague** ("install it as a skill for your captain's CLI"). It now names the command and every location: `gear admin install-skill --agent claude|codex|opencode|grok` writes `SKILL.md` plus the references to `~/.claude/skills/gear`, `~/.codex/skills/gear`, `~/.config/opencode/skills/gear`, `~/.grok/skills/gear`, and prints the paths. Verified for all four in this task's predecessor (T-30).
4. **The quality bars were missing.** The start-a-project section now has the short table the captain guide has: FASTEST / DELIVERABLE / STRICT (for, what blocks, rework), chosen by the user at kickoff, written into the milestone's `bar:`, never raised mid-voyage.

## Rework after the review of attempt 1 (R1–R4)

**R1 (P1, blocking) — the quickstart never started or identified its captain.** `init` binds the configured pane to generation 1, but it does not launch the captain or put `GEAR_CTX` into its process; a captain started without it got `NOT_REGISTERED` on `gear plan apply`. The README now has a **Start the captain** step between registration and planning: in the Herdr pane named in `gear.toml`, in the project directory, `export GEAR_CTX=<project.id>:captain:1` (and the same `GEAR_DB` if it was changed) and start the captain CLI (`claude`, or `codex`/`opencode`/`grok`); `init` still runs from the user's own shell without `GEAR_CTX`. It tells the captain to read the skill and write/apply the first plan. *Verified* with this candidate's binary on a scratch store: the export + pane identity + `gear plan apply` produced plan version 1, `created T-1`, and no engine ran on the unregistered store. *Not verifiable here* (labelled): starting a real agent in a fresh install.

**R2 (P1, blocking) — an unsupported command was labelled Verified.** `install-skill`, `gear --skill` and the captain guide are the T-30 release work and are not in this build; the block was labelled Verified from T-30's proof. The skill block is now **Not verifiable here**, says exactly why (that release work is not in this build of `gear`), and keeps the intended command and the four destinations. The plan step separates the two facts: `gear plan apply` itself is verified on a scratch store; the plan format is described by the captain guide of that same release work.

**R3 (P2)** — "the project's own build/test command" → "the project's own checks" in the DELIVERABLE row.

**R4 (P2)** — the registration step no longer claims the engine starts at `init`: "After registration, the next `gear` call (the captain's first one, below) starts the engine and brings the lanes up in their own Herdr worktrees." The new bootstrap step supplies that call.

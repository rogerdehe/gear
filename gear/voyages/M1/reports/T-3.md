# T-3 — `gear board`: a read-only full-screen view of the plan

Scope: T-3 — `gear board`: the plan as a full-screen text view, redrawn every 2 s, `q` quits; new crate `crates/gear-board`, wired into `gear-cli` with one subcommand.

Branch: board/t3 @ e52d723 (round 2: the rework); the first hand-in was 65c9a4f (code 572446f).

## Round 2 — the rework of the review of round 1

The review (`ops/reviews/T-3.md` on `origin/review/t3`, verdict fail) was right about the P1: `cfmakeraw` clears `OPOST`, so the frame's bare `\n` moved down a row without returning to column 0 — the plan drifted right and wrapped. The board was unusable as a full-screen view even though the string assertions passed.

- **P1 fixed** (`crates/gear-board/src/screen.rs`): the raw mode keeps `OPOST` with `ONLCR`, so the terminal gives the line feed its carriage return back. The frame is drawn as plain text; the terminal does what a terminal does.
- **P1 covered** (`crates/gear-board/tests/board_contract.rs`): a new contract test runs the **real raw-mode path on a pty** — the board draws on the slave side, the test reads the master side and checks that every row starts at column 0 (warning line, project line and task rows included). The test fails on the old raw mode (the rows drift: 10, 54, 54, 63, …) and passes on the new one.
- **P3 fixed** (`crates/gear-board/src/lib.rs`): one waiting item is `1 item`, not `1 items`.
- **The board not starting the engine stays** (the captain's decision), and the question about PRD §16 is closed.

Verification of round 2:
- `cargo test --workspace` → 276 tests, all ok; `cargo build --workspace --all-targets` → no warnings.
- The pty test was run against the old raw mode on purpose: it fails (`the rows drift right: [0, 10, 54, 54, 63, …]`) and passes with the fix.
- The real binary in a pty: 17 CRLF, 0 bare LF — every row starts at column 0 on a real terminal.

## Round 1 — the first hand-in

Files:
- `crates/gear-board/src/lib.rs` — the board itself: the model (totals, lanes, waiting, temp slots), the builder that reads the store, the text and JSON renderers, and the frame loop. Read-only: it never writes and never observes Herdr.
- `crates/gear-board/src/screen.rs` — the terminal: ANSI clear, the alternate screen buffer, raw mode and one key at a time (`q` leaves, Ctrl-C too, because raw mode has no SIGINT).
- `crates/gear-board/tests/board_contract.rs` — the contract: 2 lanes and 4 tasks from an in-memory store, the warning line, the captain's inbox, the temp slots, the JSON shape, `q` leaves.
- `crates/gear-cli/src/main.rs` — the `board` subcommand only: it opens the store, names the project and hands the terminal over.
- `Cargo.toml`, `crates/gear-cli/Cargo.toml` — the new crate in the workspace and the one dependency.

Verification:
- `cargo test --workspace` → 49 test targets, all ok; `cargo build --workspace --all-targets` → no warnings.
- `cargo test -p gear-board` → 15 tests ok (4 unit, 11 contract) after round 2.
- `GEAR_DB=~/.local/state/gear/gear.db gear board` → shows the gear project: 5 tasks, the three lanes with their queues, the captain's inbox, the temp slots.
- `GEAR_DB=<copy without engine.lock> gear board` → the same board plus `! engine down — the next gear call starts it`.
- In a pty: the frame is redrawn every 2 s (3 frames in 5 s) and `q` leaves the view at once (1.0 s after the key).
- `gear board --json` → the same view as JSON.

Open questions:
- **The board does not start the engine.** PRD §16 says "any `gear` call starts it when its lock is free"; the board is the one exception, because a view that revives what it reports on could never show that the engine is down (the warning line the packet asks for). The next `gear` call still starts it. The captain confirmed this in the review of round 1; one line in `crates/gear-cli/src/main.rs` flips it back.
- **Two states beyond the packet's five.** The packet names done / in review / in progress / queued / waiting. A task can also end as `failed` or `cancelled` (design/02); those two are shown with their own word rather than hidden, so the lane queues stay complete.
- **The totals count "in progress" as running only.** A task in review is therefore in "tasks" but in none of the three counters; it is visible in its lane's queue. The packet names exactly four totals, so nothing else was added.

Out of scope:
- The Herdr plugin, the `herdr-plugin.toml` and the README section — that is T-4.
- The task dependency graph (PRD §15, "later") and the per-project board of `gear --all`.
- The captain's own review snapshot (design/11) — the board shows the plan only, as PRD §15 asks.

Notes for the reviewer:
- Without a terminal (a pipe, a test) the board prints one frame and returns: a full-screen view must not hang a caller that cannot see it. `gear board --json` prints the machine-readable shape of the same view.
- A frame that cannot be read is drawn as the failure it is (`! the plan could not be read: …`), never as an unchanged plan; only the very first frame can end the command with an error.
- The board reads the engine's lock file next to the database (`<dir of GEAR_DB>/engine.lock`), the same file `gear run` locks.

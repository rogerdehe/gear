# T-532 — report (attempt 1, contract v2)

A remerge carries the captain's conflict fix on the review branch
(decision 03:55).

## `crates/gear-engine/src/merge.rs` (only file changed)

Step 6 now reads `"remerge": true` from the op's payload. When the op is a
remerge, the review branch `<remote>/<review>` exists, the attempt is not
mechanical, and `git merge-base --is-ancestor <candidate sha> <review ref>`
succeeds, the review ref is resolved to its sha once
(`rev-parse --verify <ref>^{commit}`) and **only that sha** is merged: the
candidate is inside it, and the candidate alone would conflict again. The merge
commit's `source` still names the review ref (`merge(T-5): origin/review/t5`).

In every other case the merge targets are built as today: the candidate by sha
(unless it is already on the integration branch), then the review ref by name.
The loop now carries `(target, source)` pairs so the remerge case can merge a sha
while naming the ref; the conflict refusal still reads
`conflict merging <target>`. Steps 7–9 (markers, gate, push, closing the
branches) are untouched.

## Tests (`mod tests`, the conflict fixtures' Scratch repos)

- `a_remerge_carries_the_captains_conflict_fix_on_the_review_branch` — dev moves
  the line the candidate appends to; the review branch merged dev and kept the
  captain's resolution. A remerge op (payload `remerge: true`, `review:
  review/t5`) merges through the store path: the gate runs (its marker file
  exists), the op is Confirmed, dev's log holds `task` and `resolution` with
  `merge(T-5): origin/review/t5`, and dev's README is `dev / other / task`.
- `a_first_merge_of_the_same_repos_still_conflicts` — the same repos with an op
  that has no `remerge`: `merge_one` fails with
  `conflict merging <candidate sha>`, `Blocker::Stuck`, and dev is untouched.
- `a_remerge_whose_review_branch_lacks_the_candidate_merges_both_as_today` — the
  review branch is reset to dev and carries its own `reviewed` commit (it does
  not contain the candidate): the remerge merges the candidate and then the
  review branch, both landing with the review ref named as the source.

The `queued_merge_candidate` test helper now delegates to
`queued_merge_payload` (same behaviour; the new helper takes the op payload), so
the remerge op can carry `review` and `remerge`.

## Out of scope

- The remerge condition is not applied to a mechanical attempt or to an op
  without `review` (they merge as today), and the `already` case resolves the
  review ref to its sha the same way as a first merge would merge the ref by
  name — same result, no behaviour change.
- A remerge whose review ref cannot be resolved falls back to today's targets
  (the candidate, then the ref).

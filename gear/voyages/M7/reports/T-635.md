# T-635 — the lost-work scan names a carried task whose carrier landed without its work

## What changed

`crates/gear-engine/src/merge.rs` (`tell_captain_lost`):

- For a task marked `carried-by: T-m` whose carrier has a merge time, the scan
  now reads the carrier's merged candidate and asks
  `git merge-base --is-ancestor <carried candidate> <carrier's merged
  candidate>`:
  - contained: the work landed with that merge. The attempt takes the carrier's
    merge time (if it has none yet), the landed key is set, and an open
    merge-lost item is resolved as landed. No item is opened.
  - not contained: the work is lost. The existing merge-lost item is opened
    with a body that names the carrier and the way out:
    `<task> attempt <n> was accepted but is not merged: its carrier <T-m>
    landed without its work. Set `carried-by: -` on <task> and `- remerge
    <task>` under `# Staff` retries it`.
- `Lost` carries the carrier; the generic ancestor check against the
  integration branch is unchanged for tasks that are not carried.

## Tests

`make check CRATE=gear-engine TESTS='test(lost)'` passes (18 tests). The whole
`merge::` suite passes too (133 tests).

New test in `merge.rs mod tests`:
`a_carried_task_whose_carrier_landed_without_it_is_named_lost`: a real repo
where the carrier merged a commit that does not contain the carried candidate
gets one merge-lost item naming `T-9`, `carried-by: -` and `- remerge T-5`;
a second carried task whose candidate is inside the carrier's merged candidate
gets none.

## Out of scope

- The carried-specific check runs only for tasks whose carrier has a merge
  time; a carrier still active keeps today's `carried_active` wait.
- A carried candidate inside the carrier's candidate is marked merged even when
  the carrier merged into a feature branch (not the integration branch), which
  `land_carried` alone does not cover.

# T-637 — [F-4 4/7] The engine creates the voyage label at departure

## What changed

`crates/gear-forge/src/sync.rs`:

- The crate's own config parse now reads `[github.issues] voyage_label`
  (`IssuesSection`): the default is `{project}/{milestone}` when `[github]` is
  set, and `""` turns it off. `voyage_label(template, project, milestone)`
  substitutes `{project}` and `{milestone}` and answers `None` for `""`.
- `departure_voyage` picks the project's voyage with the latest departure
  (`tx.voyages_of_project`); a voyage whose `station:<project>:<milestone>:land`
  meta names a Resolved message (landed) is skipped.
- `label_plan` asks for the label call when the project has a forge, the voyage
  departed, the label is not `""`, and `forge.label.<project>.<milestone>` is
  not `created`.
- `sync_with` runs that call through `run_call` with key `label:<milestone>`
  (`What::Label` → `create_label(repo, label, "GEAR voyage <milestone> of
  <project>")`, T-636). On `Done` or `Already` it sets the meta to `created`;
  a failed call stays `Failed` and is retried on a later tick, as other calls
  are. The label step runs even when no task of the project has an issue.

## Tests

`make check CRATE=gear-forge` passes (52 tests).

New `sync.rs mod tests` with a recording forge:
- `a_departed_voyage_gets_its_label_once`: one `create_label` call with the
  exact arguments, meta `created`, and none on the next tick.
- `an_undeparted_voyage_gets_no_label`.
- `an_empty_voyage_label_gets_no_label`.
- `a_failed_label_call_is_retried`: the first tick fails and leaves the meta
  unset; the next tick calls again and confirms.
- `a_landed_voyage_gets_no_label`: the latest voyage's land order is Resolved.

## Out of scope

- Only the project-root `[github]` is used for the label; a child repo's own
  `[github]` gets no voyage label.
- A non-empty template without `{milestone}` is not refused here (gear-app's
  config validation does that); it is substituted as written.

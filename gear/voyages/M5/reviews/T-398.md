## Findings

F1 [P1, blocking] Normal source rebuilds can embed the preceding commit's SHA — `crates/gear-cli/build.rs:11`. The script watches `../../.git/HEAD`, which contains the branch name and does not change when a commit advances that branch. Once rerun-if-changed directives are present, a changed Rust source can rebuild the binary without rerunning this script. Reproduced in an isolated regular Git checkout using an unchanged copy of this build.rs, a minimal gear-cli package, and the repository Makefile: the first `make check CRATE=gear-cli` passed a test comparing env!("GEAR_BUILD_SHA") with `git rev-parse --short HEAD` at commit 8fcd099; after editing src/lib.rs and committing a45aeb8 on the same branch, the second identical check recompiled gear-cli but failed with embedded SHA "8fcd099" versus actual HEAD "a45aeb8". The .git/HEAD modification time was unchanged. This breaks goal (1), identifying the commit the binary was built from, and the DELIVERABLE bar because ordinary commit/rebuild operation reports the wrong build. Smallest fix: in build.rs, resolve the actual Git paths (including linked worktrees), and emit rerun dependencies for HEAD, the current symbolic branch ref when present, and packed-refs (approximately 15–25 lines); retain the git-absent fallback. Add a regression that builds, commits a source change on the same branch, rebuilds without cleaning, and checks the embedded SHA against the new HEAD.

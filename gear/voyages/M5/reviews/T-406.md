## Findings
F1 [P1, blocking] Avoid scanning the project's entire message history once per ended round — `crates/gear-store/src/lib.rs:2874`. The new correlated EXISTS uses only the project prefix of `messages_recipient`; it has no indexed lookup for thread/attempt. Every ended round therefore scans that project's messages inside the write transaction. On a read-only backup of the actual store (519 rounds, 5381 messages), the candidate store library selected only 3 rounds but held the write for 27.162 s. This reproduces the task's original failure under normal project history. It breaks the DELIVERABLE bar and the explicit goal that a tick not hold the store for seconds.

Reproduction:
1. Open the current GEAR database read-only and use SQLite's backup API to copy it to a temporary database; leave the live database untouched. The reviewed snapshot had 519 rounds (3 open) and 5381 messages.
2. Link a temporary Rust driver to the candidate's `gear_store` library produced by `make check CRATE=gear-engine`. Open the copy with `Store::open`, then time `store.write(|tx| tx.rounds_to_process("gear").map(|rows| rows.len()))`.
3. Actual output: `candidate store query inside write: 3 rounds in 27.166441959s`; the store's own diagnostic says `a write held the store for 27162 ms`.
4. Independently execute EXPLAIN QUERY PLAN for the SQL: `CORRELATED SCALAR SUBQUERY` followed by `SEARCH m USING INDEX messages_recipient (project=?)`. The full candidate SELECT took 7.2285 s on an in-memory backup. A second snapshot comparison took 4.3469 s with the same predicate versus 0.0043 s for the uncorrelated predicate below; both returned identical round identities. Absolute times vary under shared load; the repeated project-wide message scans explain the cost.

Smallest fix: change only this query's EXISTS predicate (about 6 lines) to an uncorrelated membership query, so the eligible message keys are read once:

```sql
end_at IS NULL OR ('overrun:' || task || ':' || role, attempt) IN (
  SELECT m.thread, m.attempt FROM messages m
  WHERE m.project = ?1 AND m.kind = 'system'
    AND m.state IN ('open', 'waiting')
)
```

Keep the outer project filter and ordering. This needs no schema change and preserves the existing selected rows. Extend the performance regression to include representative message history and bound SQLite work (for example a statement/VM-step counter); the current test counts only `process` calls and misses the expensive filtering query.

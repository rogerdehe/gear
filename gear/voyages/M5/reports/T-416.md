# T-416 — report

A friction report reaches the captain while it is busy: the ring no longer
waits for an idle captain, the item names each open report with its task, role
and the start of its body, and an item resolved while its reports are still
open comes back after the cooldown.

## What changed

`crates/gear-engine/src/friction.rs` only (the module doc, `ring_in`, the new
`body`/`snippet`/`id_no` helpers and `State`), plus the tests the crate keeps
in `crates/gear-engine/tests/it/friction_ring_contract.rs`.

**The ring's conditions.** The `actionable_for(...).is_empty()` gate is gone
(call removed, so `ring_in` no longer asks the store for the captain's work).
The item opens whenever reports are open and the 30-minute gap since the last
ring (`State::at`) has passed. The "a report the captain has not been told
about yet" gate (`State::listed`) is gone too: it was what made a resolved item
count as handled, and T-416 (3) says the opposite. `State::listed` and
`with_listed` are deleted; an old state JSON with `"listed"` still reads back
(the field is simply ignored).

**The item's text** (`fn body`, `SNIPPET_CHARS = 160`, `MAX_LISTED = 10`), the
reports newest first:

```
13 friction reports:
F-13 T-13 dev: slowdown number 13
...
F-4 T-4 dev: slowdown number 4
and 3 more: run gear friction
```

One report per line, `F-<n> <task> <role>: <the first 160 characters of its
body>`; with ten or fewer the tail is `run gear friction` instead of
`and <k> more: run gear friction`. Newest first is `created` descending, ties
within a second by the number in the id descending (`fn id_no`): the store
orders by `created, id` with the id compared as text, so `F-13` sorts before
`F-4`, and a plain reverse did not give the newest report first.

**A resolved item comes back.** With `State::item` no longer open the code
falls through to the opening path; only the cooldown (`now - at < 30 min`)
holds it back, so the next ring after the window names the reports still open
again. Closing every report still closes the item by itself, and an item that
stays open is still updated in place when a report arrives (the 30-minute rule
covers rings, not list updates).

## Tests (`crates/gear-engine/tests/it/friction_ring_contract.rs`)

- `a_busy_captain_still_gets_the_ring` — replaces
  `a_captain_with_an_open_item_gets_no_ring`: with a result open in the
  captain's inbox the friction item opens at once, names `F-1 T-1 dev: the
  build took forever`, and the captain's own result still waits.
- `a_resolved_item_comes_back_with_the_reports_still_open` — replaces
  `a_resolved_item_rings_again_only_for_a_new_report`: ring at T0+1, the
  captain resolves the item at T0+2, T0+60 rings nothing, a store reopen keeps
  the cooldown (T0+1000 still nothing), T0+1801 opens a second item naming F-1
  again, T0+1810 rings nothing (one ring per window), closing F-1 closes the
  item.
- `the_item_names_at_most_ten_reports` — 13 reports: ten lines, `F-13` first
  down to `F-4`, then `and 3 more: run gear friction`.
- `the_item_quotes_the_start_of_a_body` — a 168-character body is quoted up to
  character 160 and the tail is absent.
- The existing tests now assert the new text
  (`an_idle_captain_gets_one_item_naming_the_open_reports`,
  `a_new_report_updates_the_item`, `closing_every_report_closes_the_item`,
  `the_ring_waits_thirty_minutes_before_it_rings_again`); the stale-reminder
  test passes unchanged.

## Out of scope (noticed, not changed)

- A report whose body has newlines (a `--friction` text typed over several
  lines) puts them inside its line of the item, so one report can span several
  lines. The packet said "the first 160 characters of its body"; collapsing
  whitespace would be a design choice I did not make.
- The quote is cut at 160 characters with no ellipsis.
- While the item stays open, a report that arrives updates it at once (no
  cooldown); only rings are limited to one per 30 minutes, as the packet's (1)
  says.
- A captain who keeps resolving the item and never closes its reports is rung
  once per 30 minutes for good. That is what T-416 (3) asks for; whether it
  should stop after some count is not in this packet.

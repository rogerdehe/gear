# T-400 — report

Changing a lane's model mid-voyage is documented, and proven for a lane that
was held: the hold takes it out of the reconciliation without losing the
change, and the release applies it.

## What changed

Two files, both named by the packet; no other design.

**`crates/gear-engine/src/restart.rs`, `fn reconcile_config`.** The behaviour
the packet describes was already the code's behaviour: the loop skips a seat
that is not `Active` or `Standby` before anything is computed or written, so
its stored `engine.restart_config.<seat>` stays exactly as it was, and when the
seat is `Active` again the comparison with the registered chain runs for it
like for any other seat. The one change here is the comment at that skip, which
now says that this is the point: a change made while a lane was held is still
stored as a change when the lane comes back. Editing the code to "do nothing
differently" would have been a lie; the proof is the test (below), which I
wrote first and ran against the unmodified function and it passed on the first
run — so I sent the captain a question rather than invent a change.

**`skills/gear/references/captain.md`**, a subsection "Changing a lane's model
mid-voyage" (in §3, after the daily loop): change a lane's model or CLI only
when the user asks and has confirmed it in the conversation; write the new
chain and re-init (`GEAR_ADMIN=1 gear admin init gear/gear.toml`); leave the
lane `Active` — the engine restarts it in place on the new chain's head and it
continues its open task (`Continue T-<n>`); check the seat's
`engine.model.<seat>`; never hold, kill or release a lane for this. It ends
with the held case: a lane held while the config changed gets the change when
it is released and `Active` again.

## The tests (both in `restart.rs`, `mod config_change_tests`)

- `model_change_made_while_the_lane_was_held_is_applied_on_release` — the
  packet's (1): seed the config at v1 and reconcile, hold `heat`, change the
  config to another model, reconcile: the stored `engine.restart_config` is
  byte-for-byte what it was and no restart plan exists; release the seat
  `Active` (its agent alive, as `- release` does), reconcile: the restart plan
  appears; the agent exits, the next step starts it with `--model new-model`
  and `engine.model.p:heat` is `new-model`.
- `re_init_with_an_open_attempt_restarts_on_the_new_model_and_continues` — the
  packet's (2): the attempt of `T-1` is `Started`, the config changes the
  lane's model: the lane restarts with `--model new-model`,
  `engine.model.p:heat` is `new-model`, and a `Deliver` op carries the
  `Continue T-1` line to the new generation.

## Out of scope

- The packet's (3) names `--confirmed` for the re-init after departure. No such
  flag exists in this tree (`gear admin init` takes `--check` and `--models`
  only, and the packet limits the code change to `restart.rs` and
  `captain.md`, so a CLI flag was not mine to add). The subsection says instead
  that after departure the user's confirmed word is what allows the change, and
  names the command that exists. I asked the captain about this too.
- The incident's own sequence, if it differs from the packet's: a change
  *detected while the seat was Active* (so `engine.restart_config` was already
  advanced to the new chain head) whose restart plan then waits, followed by a
  hold, would still leave the stored key saying "applied" if the plan does not
  survive the hold. That wants a different fix (compare against what the seat
  actually runs, not against the stored intent), which the packet does not ask
  for.

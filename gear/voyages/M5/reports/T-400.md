# T-400 — report

Changing a lane's model mid-voyage is documented, and proven: for a lane that
was held, and for the incident's lane that came back on its old model.

## What changed

**`crates/gear-engine/src/restart.rs`, `fn reconcile_config`.** A re-apply now
compares the registered chain **head** with what the seat actually runs —
`engine.model.<seat>` and the binding's CLI — instead of only the stored
`engine.restart_config.<seat>` key:

    let runs_other = current_cli != target_cli || match current_model.as_deref() {
        Some(running) => running != model,
        None => false,
    };
    let stale = reapply && !on_later_entry && runs_other;

`stale` triggers the same in-place restart as a changed key. `on_later_entry`
is the quota exception, taken from the old `quota_fallback` condition and now
applied whenever the seat runs a later entry of its **own** chain (not only on
the first sight of the seat): the quota step brings the lane back to the head at
the reset, so reconciliation must not fight it. The old key comparison
(`kind_changed`, `model_changed`) stays, so an arguments-only change (e.g. a
thinking level) still restarts, and a chain whose head names no model still
removes the `--model` flag. A seat that is not `Active` or `Standby` is still
skipped before any of this, so its stored key stays untouched and the change is
applied when the seat is back (T-400(1)); the skip now says so.

Why the extra comparison: a restart planned while the seat was Active advances
the stored key as soon as it is planned (`meta_set` after `advance`). If the
plan is then lost — the captain holds the lane, the agent exits, the lane is
released — the key says "applied" while the lane runs the old model, and nothing
would ever restart it. That is the incident in the packet.

**`skills/gear/references/captain.md`**, a subsection "Changing a lane's model
mid-voyage" (§3, before "Becoming the captain"), in the words contract v5
names: change a lane's model or CLI only when the user asks and has confirmed it
in a dialog; re-init with the new chain (`--confirmed` after departure); leave
the lane `Active` — the engine restarts it in place on the new model and it
continues its task (`Continue T-<n>` when an attempt is open); check
`engine.model.<seat>`; never hold, kill or release a lane for this. It ends with
the held case: a change made while the lane was held is applied when it is
released and `Active` again.

**`skills/gear/references/conventions.md`** (§9, after the `[[lanes]]`
example): a lane may run its own model and CLI with
`models = [{ model = "<id>", cli = "<pi|codex|opencode|claude>" }]` in its
`[[lanes]]` block, which overrides `[models] lanes` for that lane alone — its
first entry is the model the engine starts and restarts it on, and the one the
quota policy walks — with an example of two lanes on one model and one on
another CLI. (`gear_app::config::lane_chain` already reads it; this is the
documentation the packet asks for.)

## The tests (all in `restart.rs`, `mod config_change_tests`)

- `model_change_made_while_the_lane_was_held_is_applied_on_release` — the
  packet's (1): seeded at v1, hold `heat`, re-init to another model, reconcile:
  the stored `engine.restart_config` is unchanged and no plan exists; release
  `Active` with the agent alive, reconcile: the plan appears; the agent exits,
  the next step starts it with `--model new-model`, `engine.model.p:heat` is
  `new-model`.
- `re_init_to_another_cli_with_an_open_attempt_restarts_on_the_new_model_and_continues`
  — the packet's (2), with the CLI switch the acceptance names (pi → codex):
  `T-1`'s attempt is `Started`; after the re-init the `pi` agent is asked to
  exit and a `codex` agent starts with `-m new-model`; `engine.model.p:heat` is
  `new-model`; a `Deliver` op carries `Continue T-1`.
- `a_lane_that_came_back_on_its_old_model_is_restarted_again` — the incident:
  the restart is planned (key already `new-model`), then held, the plan gone,
  released with the agent alive; `engine.model.p:heat` is `old-model`, and
  reconciliation restarts it onto `new-model` anyway. This test fails with
  `stale` disabled (`let stale = false && …`) and passes with the fix.
- `a_lane_on_a_later_chain_entry_is_left_to_the_quota_step` — the exception: a
  lane on the second entry of a two-entry chain, after a config version bump, is
  not restarted back to the head.

## Out of scope

- The subsection names `--confirmed` for the re-init after departure and the
  dialog confirmation, as contract v5 and the direction check of attempt 1
  require (the direction check said not to substitute the older workflow).
  `gear admin init` in this tree takes `--check` and `--models` only, so the
  flag is not implemented yet: no CLI change was mine to make (the packet's
  allowed files exclude the CLI). captain.md §1.3 still tells the captain not
  to ask through a dialog tool; the subsection follows the contract's wording —
  if the two must agree, that is the captain's call.
- A lane whose `[[lanes]]` block names its own `models` chain (documented in
  conventions.md by this task) is read by `reconcile_config` through
  `role_chain` already, so the comparison uses the lane's own head; no code
  change was needed for that.
- A restart plan that hangs for a lane that is `Active` again with its agent
  alive (the plan is not advanced for a live agent, and the pending guard then
  keeps reconciliation out of it) is a separate hole: after the held release
  the lane could sit with the plan pending instead of running the old model.
  The packet's fix (compare what the seat runs) covers the case where the plan
  is gone; a plan that exists is still trusted to reach the head.
- `make gate` was not run (the merge gate runs it).

# T-411 — report

A long view scrolls with the mouse wheel and the page keys: the wheel moves the
selection three picks a notch, `PgUp` / `PgDn` move it a screenful, both are
clamped, neither is ever a click, and the viewport keeps following the
selection through `offset_of` as an arrow's does.

## What changed

Two files of code, as the packet says, plus the tests the crate keeps.

**`crates/gear-board/src/screen.rs`** —

- `Event` gains `PageUp` and `PageDown`.
- `read_sequence` also ends after `~`, so a page key is one sequence like an
  arrow is.
- `next_event` maps `[5~` to `PageUp` and `[6~` to `PageDown` before the
  one-letter sequences; everything else (the arrows, the shift-tab, the mouse)
  keeps its path. The SGR mouse sequence is untouched, so the wheel (`[<64;x;yM`
  and `[<65;x;yM`) is still an `Event::Mouse` with its own button.

**`crates/gear-board/src/lib.rs`** —

- `pub const WHEEL_PICKS: usize = 3` — the picks one notch moves.
- In the run loop, before the inner event loop: `let page = screen.size.1.saturating_sub(frame::VIEW_ROW + 2).max(1)`.
  The view rows the screen shows are the rows from the view's first row
  (`VIEW_ROW` = 5) up to the footer's spacer (`height - 2`): `height - 7`, and
  never less than one.
- Next to the `Up`/`Down` arms: `Event::Mouse { button: 64, .. }` moves the
  selection up `WHEEL_PICKS`, `65` down `WHEEL_PICKS`, both clamped to the
  picks (`saturating_sub` / `min(picks.len() - 1)`), and neither falls through
  to the click arm (`button: 0`); `Event::PageUp` / `Event::PageDown` move it by
  `page`, clamped the same way. Each closes the panel and breaks, exactly as an
  arrow's arm does — and a notch that arrives while a panel is open is spent
  closing it by the panel branch that already sits above the match, so it never
  opens anything.
- The doc of `run_with` names the wheel and the page keys.

The viewport needed no change: the frame and the hit testing both read
`frame::offset_of(&picks, screen.selected, …)`, which already keeps the selected
pick on the screen.

**The footer did not change.** The packet allows "wheel/PgUp/PgDn scroll" only
if it fits the golden frames unchanged. The footer is already longer than the
golden frames are wide (the last row of `tasks-folded.txt` is cut at "a lane's
t"), so any text inserted before the cut changes the golden text plane, and any
text appended after it is off the frame and invisible. The footer stays as it
is, and every golden-frame test passes unchanged.

## Tests

`crates/gear-board/tests/it/board_contract.rs`:

- `world_with_a_hundred_tasks()` — the packet's 100 tasks on one lane.
- `Events` now carries the screen size it reports (it was fixed at 80x12) so a
  test can drive a 40-row screen; the two existing users pass `(80, 12)`.
  `run_events` / `run_events_output` run the board over a list of events and
  return the last frame, or every frame written.
- `the_wheel_and_the_page_keys_move_the_selection_over_a_long_view` — 80x40:
  ten wheel-down notches from the first pick select pick 30 (T-31), drawn on
  `FIRST_ROW + 30` and lit (reverse video); ten wheel-up notches at the top stay
  at pick 0 (T-01, lit); `PageDown` from the first pick selects the 34th task
  (`page` = 33), its row is lit one row above the footer's spacer, and the
  viewport moved with it — the view's first row holds T-02 and the heading's
  row (`dev`) has scrolled away; `PageUp` comes back to T-01 with the heading
  back.
- `a_wheel_notch_is_never_a_click` — `Enter` opens the task panel (ROUNDS is in
  the frames written), the next notch closes it and opens none, and the
  selection has not moved; a notch at `y = 4` — where the `1 Now` tab is drawn
  — does not switch the view but scrolls three picks (T-04, lit).
- `the_page_keys_parse_and_the_wheel_is_still_a_mouse` — on a pty, the real
  raw-mode path: `\x1b[5~` is `PageUp`, `\x1b[6~` is `PageDown`,
  `\x1b[<64;10;20M` and `\x1b[<65;10;20M` are `Mouse { button: 64 | 65, .. }`,
  and `\x1b[<0;1;7M` still has button 0.

## Out of scope (noticed, not changed)

- `Event::Mouse` carries no press/release: an SGR wheel release (`…m`) with
  button 64/65 moves the selection like the press does. No terminal the board
  runs on sends a wheel release, and the packet names the press only.
- The wheel is handled in every view, including the Log view whose picks are
  the starred decisions only; there the notch walks decisions, not rows.
- A 100-task board build costs about a second in a test, so the new board tests
  add ~10 s to the crate's suite. It is the existing build cost, not a wheel
  path.

# T-299 — report

Commit messages are configuration now; GEAR's forms are only the defaults. A new pure module
`gear_model::commit` holds the three templates and one `fill`; `[conventions]` gains
`merge_message`, `review_message` and `plan_message`, checked in `validate` the way the branch
templates are; `gear plan apply` names the captain's plan commit in the project's own form; the
conventions and review skills say so. (Contract v3: the JSON field holds the filled message
itself — the captain answered M-4649.)

## What changed

**`crates/gear-model/src/commit.rs`** (new; `pub mod commit;` in `lib.rs`):

- `MERGE_MESSAGE = "merge({task}): {source}"`, `REVIEW_MESSAGE = "review({task}): {what}"`,
  `PLAN_MESSAGE = "{milestone}: {what}"`.
- `fill(template, values) -> String`: scans the template for `{name}` and substitutes the pairs it
  is given; every other text stays as it is, an unknown `{…}` and an unclosed `{` included (the
  rest is literal). A value is inserted literally — it is never rescanned for placeholders.
- Tests: each default filled; all / some / none of the placeholders; an unknown `{x}` left as it
  is; a value containing `{task}` stays literal; an unclosed brace is literal.

**`crates/gear-app/src/config.rs`**:

- `Conventions` gains `merge_message`, `review_message`, `plan_message` (`String`, read from
  `[conventions]` like `task_branch`), defaulting to the three constants.
- New `fn message_template_issues(field, template, required, allowed, issues)` beside
  `branch_template_issues`: an empty template is an issue; a placeholder outside `allowed` is an
  issue; a missing `required` is an issue (`merge`/`review` require `{task}`, `plan` requires
  none). Each text names the template and the `{…}` placeholders GEAR fills in.
- `validate` calls it for `conventions.merge_message` (allowed `{project}`, `{task}`, `{source}`),
  `conventions.review_message` (`{project}`, `{task}`, `{attempt}`, `{what}`) and
  `conventions.plan_message` (`{project}`, `{milestone}`, `{what}`).

**`crates/gear-cli/src/main.rs`** `fn run_plan`: after a successful apply, when the draft's last
`# Milestone` block exists, the text output ends with
`commit the plan as: <plan_message with {project} and {milestone} filled, {what} left>`, and the
JSON output carries the same message on its own under `"commit"` (`"M2: {what}"` — data for a
script, not the sentence; the field is absent without a milestone block). The template comes from
`gear_app::config::conventions_or_default(store, …)`.

**`crates/gear-app/tests/it/config_contract.rs`**: the three defaults; a project naming all three
parses and validates; `merge_message = "merged"`, `= ""`, `= "merge({task}): {branch}"`,
`review_message = "{who} reviewed"`, `review_message = "reviewed {attempt}"`,
`plan_message = ""` and `plan_message = "{task}: {what}"` each give their issue (and the texts name
the template and the placeholders). The existing `Conventions { … }` literal in the first test
gained the three fields.

**`crates/gear-cli/src/main.rs` tests**: `plan_apply_names_the_plan_commit` — a plan with
`# Milestone M2: two` prints `commit the plan as: M2: {what}`; with
`plan_message = "PROJ-1 {milestone} {what}"` it prints `commit the plan as: PROJ-1 M2 {what}`; the
JSON carries the filled template only (`"M2: {what}"`); a staff-only plan has no `commit` field and
no line.

**`skills/gear/references/conventions.md`**: three rows in the `[conventions]` table —
`merge_message`, `review_message`, `plan_message` with their defaults and placeholders.
**`skills/gear/references/review.md`**: the `review/t<n>` sentence now says the review is
committed with the message the packet names.

# T-395 — report

A merge that lost its push race (the op stays `unknown`) is no longer starved
by newer merges.

## What changed

Two edits in `crates/gear-engine/src/merge.rs`.

**`fn ready_merges`** — still reads the `Intended` and `Unknown` states and
keeps only `OpKind::Merge`, but the result is now one queue: sorted by the op's
`created` time, oldest first, with the op's number breaking ties
(`id.split_once('-')`, so `O-999` sorts before `O-1000`, not after it as a
string). Before, every `Intended` op came before any `Unknown` one, so while
new merges kept arriving an `Unknown` op never ran — and `- remerge` refuses an
`Unknown` op, so nothing else could move it.

`merge_order` (the waiting/running split) and the caller are untouched.

**`merge::tests::a_refused_land_is_retried_by_a_remerge`** — one stray pair of
lines removed (`let first = merge_op_in(&mut store, &candidate, OpState::Unknown);
let _ = first;`, added in T-178 and never used). That fixture queued an
`Unknown` merge op for T-5 attempt 1 and then the captain's `remerge` of the
same attempt; in a real project the two cannot coexist, because `- remerge`
refuses an `Unknown` op. With the new order the stray op ran first and the
remerge was voided as already merged, so the test's `Confirmed` assertion saw
`Void`. Its assertions and its intent are unchanged. I asked the captain
(`hull:198`) and went on with this as the default.

## Test

New, in `merge.rs`'s own test module:
`an_unknown_merge_is_not_starved_by_newer_intended_ones`. It queues two
`Intended` merge ops (`created` 200 and 300), an older `Unknown` merge op
(`created` 100) and an `Intended` `Doorbell` op (`created` 50), then asserts
`ready_merges` returns exactly `[raced, newer_a, newer_b]`: the raced op first,
the non-merge op left out.

## Out of scope

- `merge_order` sorts the waiting merges by `updated` and is unchanged; a
  waiting (T-62) op therefore still goes last regardless of `created`.
- The other id-number parsers (`gear-app/src/plan.rs` `op_number`,
  `gear-board/src/graph.rs` `op_number`) are untouched; `ready_merges` carries
  its own small closure since the change stays inside that function.

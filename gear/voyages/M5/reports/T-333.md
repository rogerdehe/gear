# T-333 — report

A plan that names a milestone in its `# Queue` now carries that milestone's
`# Milestone` block: the words come back from the store into the file, and a
milestone the store has no words for is refused.

## What changed

Four files, as the packet allows.

**`crates/gear-app/src/goal.rs`** (new, `pub mod goal;` in `lib.rs`) —
`pub fn missing_blocks(tx: &Tx<'_>, project: &str, draft: &Draft) ->
GearResult<Vec<String>>`: for every milestone a `draft.queue` item's
`milestone` names (items with `state: cancelled` excluded, first-named order,
each milestone once) that has no block in `draft.milestones`, it returns the
block text

```
# Milestone <id>: <title>
done: <done>
bar: <bar>
eta: <eta>
```

followed by one `station <id>: <needs>` line per `tx.voyage_stations` entry,
built from the stored voyage. With no stored `done` it is `BadFormat`:
"the plan names milestone <M> (<first task id or NEW>) but has no
`# Milestone <M>: <title>` block with its done:, bar: and eta: lines (T-22)".

**`crates/gear-app/src/plan.rs`** — `ApplyResult` gains
`#[serde(default)] pub milestone_blocks: Vec<String>`; `apply_queue` fills it
from `crate::goal::missing_blocks(tx, project, draft)?` at the end of its
validation (after `find_cycle`, before the writes) and pushes one warning per
block: "the # Milestone <M> block was written back into the plan file from the
store".

**`crates/gear-app/src/draft.rs`** — `rewrite_applied` takes `blocks: &[String]`
as its last parameter. Each block, with an empty line after it, is spliced in
before the first section header that is neither `# Goal` nor a milestone header
(`# Milestone …`, and `# Voyage …` which the parser reads as one); with no such
section the blocks close the file after an empty line. With `&[]` the output is
byte-for-byte today's.

**`crates/gear-cli/src/main.rs`** — the `plan apply` passes
`&result.milestone_blocks` to `rewrite_applied`.

Two points the packet left open, both asked (`gear send --kind question`,
answered in M-5704, followed as answered): the call sits at the end of
`apply_queue`'s validation (there is no "goal check" in `apply_queue` on
`dev` — T-331 put the departed-voyage guard in `record_voyages`), and the
refusal prints `<title>` literally when the store has no title to offer.

## Not done, and out of scope

- A stored voyage with a `done:` but no `bar:`/`eta:` would be written back with
  empty `bar:`/`eta:` lines, which the next apply then refuses (`record_voyages`
  wants all three). `record_voyages` never stores such a row, so this is outside
  normal use; I left it as is.
- The milestone header the parser also accepts, `# Voyage …`, is skipped by the
  insertion rule too (a block written before a `# Voyage` section would put the
  current voyage, the last block, in the wrong place). The packet said
  `# Milestone …`; I read the two forms as one header.
- `an_untouched_old_milestone_keeps_applying` no longer shows what its name said
  (a plan that names a milestone and describes nothing is now refused — that is
  this task). I kept the name for the board's sake; a rename is the captain's
  call.

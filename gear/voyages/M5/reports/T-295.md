# T-295 — report (contract v3)

The live proof, through `gear_engine::tick`, that a lane parked on a quota wait
resumes **its own session** at the reset, plus the one code change the contract
allows so the proof holds.

- Code: `crates/gear-engine/src/quota.rs` — a `wait`-policy park now writes a
  `Wait`, so `wake_from_source` continues the lane in place at the reset.
- Test: `crates/gear-engine/tests/it/quota_wait_resume_contract.rs` (new) plus
  its `mod` line in `tests/it/main.rs`, as v1 wrote it: **no**
  `[[quota.sources]]`.

## The test

`a_lane_parked_on_a_quota_wait_resumes_its_own_session_at_the_reset`:

- A project with one pi lane (`kind = "pi"`, `profile = "pi"`),
  `[models] lanes = ["tokenrhythm/deepseek-v4.1-flash-1017"]`,
  `on_quota = { lanes = "wait" }`, `quota_reset_h = 1`, no `[[quota.sources]]`
  (`sources_of` reads only the config — no reader, no network). The lane has
  T-1 Started (`start_attempt` + `on_delivery_confirmed`) and the binding's
  `session_ref` is `sess-before-park`. `FakeHerdr` runs the pi agent in the
  lane's pane with that session and the pi quota marker
  (`429: … "You exceeded your current quota" … "insufficient_quota"`).
- Tick at T0+10: one marker is no fact — the seat stays Active.
- Tick at T0+20: the second marker confirms it — the seat is Parked, its
  reason carries the deadline T0+3620 (`quota_reset_h = 1`), no delivery.
- Two ticks before the reset (T0+100, T0+700): the seat stays Parked and
  nothing is delivered.
- Tick at T0+3620 with the marker gone: the seat is Active, the one delivery
  text is `Continue T-1: your quota is back.`, the seat generation is the one
  from before the park and the binding's `session_ref` is still
  `sess-before-park`; `herdr.calls` after the park hold no
  `Call::AgentStart`, no `ctrl+c`/`ctrl+d` keys and no `/quit` (pi's exit
  command).

## The code change

`crates/gear-engine/src/quota.rs`, the `None =>` (park) arm of
`apply_quota_policy_with`, right after a successful `park(…)`: when the policy
is `QuotaPolicy::Wait`, write

    Wait { kind: "policy", until, started_at: now,
           provider: <current model before its first '/', or "">,
           window: String::new(), task: <open_attempt's task>, pause: true }

with `write_wait` in a store write. At the reset the existing
`wake_from_source` branch clears it and continues the lane in its own session
(the same generation, the same `session_ref`, the §9.2 Continue). The
`parked_until` + `change_model` branch stays for a seat that has no wait.

### One deviation from v2's wording, and why (asked)

v2 names "the `None =>` arm … that calls fn park", which is shared by the
`wait` policy and by a `fallback` chain-exhausted park. Writing the Wait for
both made three existing T-33/T-35 unit tests fail, because at the reset those
lanes then continue in place instead of restarting back to the original model:

- `reset_returns_to_the_original_cli_and_confirms_its_model`
  (`left: "codex", right: "opencode"`) — T-35's cross-CLI reset-back lost.
- `a_restart_onto_a_model_without_labels_rings_the_captain_once`
  (`left: Active, right: NeedsCheck`) — the missing-labels alert unreachable
  on that route.
- `an_exhausted_chain_parks_until_the_reset`
  (`["p:heat: continues after the wait (policy)"]`).

This was sent to the captain as a `question` (request
`r-1793234480206-48460`, thread T-295:2) and contract **v3** takes exactly
option 2: the Wait is written only when `policy == QuotaPolicy::Wait` — the
case v2 names ("a lane parked by the `on_quota = wait` policy with no quota
source"); the `fallback` chain-exhausted park keeps its restart back to the
original model and every existing quota.rs test stays as it is.

(The earlier v1 question — no sources vs. the unreadable-source park — is
request `r-1793233260464-32146`, thread T-295:1; v2 superseded it.)

## Out of scope

- The `fallback` chain-exhausted park is unchanged: at the reset it still
  restarts back to the first chain entry (`change_model`). Only the `wait`
  policy writes the new `Wait`.
- The pre-reset ticks assert Parked + no delivery; the pane assertions are the
  packet's own (`AgentStart`, exit keys) over everything after the park.
- The Continue is read from the lane's delivery ops whatever state the
  delivery reached; how that op settles is not asserted.

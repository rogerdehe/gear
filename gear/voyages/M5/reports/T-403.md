# T-403 — report

The board no longer flashes: each frame overwrites the last one in place,
inside a synchronized update, and a frame that says what the last one said is
not written at all.

## What changed

`crates/gear-board/src/screen.rs` and two call sites in
`crates/gear-board/src/lib.rs`, as the packet says.

**`screen::draw(out, text)`** wrote `\x1b[H\x1b[2J{text}` (home and clear the
whole screen before every frame: the blink). It now writes

    \x1b[?2026h            begin the synchronized update
    \x1b[H                 home
    <line>\x1b[K\n …       every line, its rest erased, the newlines between
    <line>\x1b[K           the last line, erased, without a newline (F2)
    \x1b[J                 erase below the frame
    \x1b[?2026l            end the synchronized update

and never `\x1b[2J`. The terminal shows all of the frame or none of it, and a
line that got shorter leaves nothing of the old one behind. A terminal that
does not know `2026` ignores the pair: the frame is still a full overwrite
from the home position.

**`run_with`** keeps `written: Option<String>`, the frame text it wrote last.
A frame whose text is that one is not written (the screen already shows it),
so a refresh that finds nothing changed writes nothing and the page cannot
blink. On a size change (`keys.size()` differs from `screen.size`) the board
writes `\x1b[2J` once in the run loop and draws the frame whatever it says:
the resize has thrown away what the screen showed. That is the only `2J` in
the crate. The "the plan could not be read" frame records itself as written
too, so a repeated failure frame is not rewritten either.

Design question sent (`gear send --kind question`, M-5290) about what "a full
clear" means when `fn draw` may never write `\x1b[2J`; the default taken is
the one above (the run loop writes the clear, `draw` does not).

## Tests

`screen.rs`, its own module: `draw_overwrites_the_screen_in_place` (starts with
`\x1b[?2026h\x1b[H`, no `\x1b[2J`, `\x1b[K` at the end of every line — which is
"before every newline" — and the last line without a newline, ends with
`\x1b[J\x1b[?2026l`) and `an_empty_frame_is_a_whole_update`.

`tests/it/quiet_contract.rs`: `ten_refresh_periods_build_the_board_once` now
asserts the frame is written **once** in eleven frames of unchanged data
(it asserted eleven writes: the blink, in a test); new
`a_resize_draws_once_over_a_full_clear` — the board draws the frame of the new
size and clears the screen exactly once. `a_key_press_redraws_without_building_the_board`
counts the frames a change writes.

`tests/it/board_contract.rs`: the frame reader is told the new frame start
(`\x1b[?2026h\x1b[H`), `q_leaves_the_board` asserts the update, the per-line
`\x1b[K`, the `\x1b[J` and that no `\x1b[2J` is written at all, and the two pty
tests use a new `Frames::quiet` where a key or a click changes nothing (the
frame on the screen is not written again, so no frame arrives). Where a test
waited for a *second* identical frame, it now reads the frame the board kept or
moves the selection first, so the click it tests is still a click that picks.
`tests/it/decisions_contract.rs`: the last-frame reader's marker.

## Out of scope

- `screen::enter` / `leave` are unchanged: the alternate buffer is taken and
  given back as before (the packet named `draw` and the run loop only).
- The board still asks the store for `data_version` every refresh period
  (T-384's rule); this task only stops the *writes* when the frame is the
  same.
- A pty test that wants to see a frame arrive while nothing changes can no
  longer have one; `Frames::quiet` is the way to say so.

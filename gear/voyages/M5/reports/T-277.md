# T-277 — report

A lane's delivery is confirmed by the lane's own work on it, not only by a
check-in view. The change is confined to `fn shown_delivery` in
`crates/gear-engine/src/ops.rs` (after T-267, same file) and its tests.

## What it does

`shown_delivery` already returned evidence in two cases: a view of the seat
and generation at or after the op showing the op's task and attempt, and a
hand-in recorded for the attempt by that seat. It now has a third:

- **The seat's own word about this very attempt.** `tx.messages_from_since
  (project, op.seat, op.created)` is scanned for the first message whose
  `sender_gen` is the op's generation, whose `task` and `attempt` are the
  op's, and whose kind is `progress`, `question` or `result` (a `gear send`).
  That message's `created` is returned as the evidence time.

So a lane that starts working on the task without running `gear` first — the
M5 case behind O-3473, T-257 and T-261 — is no longer re-delivered in a new
session: its first progress answer, question or result proves it received
the delivery. A message on another task or attempt, from another seat, from
an older generation, or of another kind proves nothing.

The view and hand-in cases are unchanged, and the view/hand-in checks keep
their precedence: a view that shows the task and attempt, and a recorded
hand-in, still settle the delivery as before. `confirm_pending_with` and the
rest of the file are untouched (per the packet: no other design).

## Out of scope (noticed, not changed)

- The evidence string for a delivery settled by a message is written by
  `confirm_pending_with`, which this packet forbids touching: with no
  matching view it takes the `hand_in` branch and the stored result reads
  `hand-in T-1 attempt 1 @ <ts>`. The time is the message's time; only the
  label says hand-in. Giving a message its own label is a one-line change
  in `confirm_pending_with` if the captain wants it.
- Only `progress`, `question` and `result` count, as the packet lists them.
  A `blocked` message from the lane (a report that it found a problem) also
  proves receipt but does not confirm the delivery, so such a lane can still
  be re-delivered.
- `cargo fmt --check` and `cargo clippy -D warnings` are not clean on the
  integration branch already (`attention.rs`, `gear-store`), so neither was
  used as a gate; the new code follows the file's own style.

# T-351 — report

A task moved to another voyage is recorded in the voyage it left, so that
voyage's board can name it (README change 6: "moved out: T-n", not counted).

## What changed

`crates/gear-app/src/plan.rs` and `crates/gear-board/src/lib.rs` only; tests
where the crates keep them.

- `fn apply_queue`, at the assignment `task.milestone = item.milestone.clone()`
  for an existing task: before the assignment, when the stored milestone is
  `Some(old)` and the item's is `Some(new)` and they differ,
  `record_gear_decision(tx, project, old, applied_version, "move",
  "{id} moved to {new}", None, "move|{id}|{old}|{new}", now)`. The entry is
  written to voyage `old`, its `source` is `gear`, it is never starred, and
  its key makes a second apply of the same move a no-op.
- `ProjectBoard` gains `pub moved_out: Vec<(String, String)>` (task, the voyage
  it moved to), filled from the shown voyage's decisions of kind `move` whose
  `what` is `"<id> moved to <milestone>"`, in the order the voyage recorded
  them (helper `fn moved_out_of`). A moved task carries the new voyage's
  milestone, so the shown voyage's tasks, lanes, graph and totals leave it out
  and it is counted nowhere; no filter is added on top of the milestone rule.

`crates/gear-app/tests/it/decision_contract.rs`,

M1's decisions then hold exactly one `move`, `what == "T-1 moved to M2"`,
`source == "gear"`, `star == false`; M2's decisions hold no `move`; the task
carries `M2`. Applying the same move again leaves the count at one.

`crates/gear-board/tests/it/voyage_select_contract.rs`,
`a_task_that_left_the_voyage_is_named_but_not_counted`: the T-350 fixture
(M1 landed with T-1 done/merged and T-4 cancelled, M2 sailing) plus T-1's
milestone set to M2 and the move decision recorded on M1. The board of M1 has
`moved_out == [("T-1", "M2")]`, and T-1 is absent from `token_tasks`, from the
graph, from its lane's queue and from `totals.tasks` (0); the board of M2 has
an empty `moved_out`. The fixture's `moved` helper writes the line as the
engine does (key `move|<id>|<old>|<new>`, kind `move`, source `gear`).

## Out of scope

- No frame or view draws `moved_out` yet: the packet adds the field, not the
  "moved out: T-n" line of the board. The golden fixture already carries
  `T-182 moved to M5` on M4.2, so a board built for M4.2 now reports
  `moved_out == [("T-182", "M5")]`; no golden-frame test compares it yet.
- `to_json` does not carry `moved_out`, for the same reason.
- The move is only recorded when both milestones are present; a task that
  goes from `None` to a milestone, or to `None`, leaves no `move` line (the
  packet names `Some(old)` → `Some(new)` only).

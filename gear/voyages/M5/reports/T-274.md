# T-274 — report

The engine suite's fixtures, not its code: a merge test copies its repo instead
of building one with git processes, and a test that needs two answers from git
asks for both in one shell. No engine behaviour, no test deleted or ignored, no
assertion removed, no `--test-threads` change.

**Acceptance is not met.** `make check CRATE=gear-engine` is 157.6 s (was
245.6 s) and 39 of the 640 tests are still over 3 s (58 were; 27 of those 58
came under 3 s, and the eight-test difference is tests that crossed the line the
other way under the heavier load of the after run). What did get faster is 1.5-2.4x
faster per test, and the suite is 36 % shorter. Why the
target is out of reach on this machine is in "Why 60 s is not reachable" - it is
not the fixtures.

## What changed

**`crates/gear-engine/src/merge.rs` (tests module only).**

- `copy_tree`: the per-test scratch dir is now an in-process copy of the
  shape's template instead of `sh -c cp -R` (a shell and a `cp` per test).
- `Scratch::prepared`: the merge worktree and the head of `heat/t5` - what a
  test asks for together - come from one `sh` (one shell plus two git, not two
  shells plus two git). Eight tests use it.
- `Scratch::state` / `State::has_task_commit`: the post-merge assertions that
  read the integration branch and the branch list pay one shell plus two git
  instead of one shell and one git per question. Three tests use it.

**`crates/gear-engine/tests/it/parallel_contract.rs`.** `Repo::new` ran eight
git processes per test (`init`, four `config`, `add`, `commit`, `rev-parse`);
the base repo is now built once per test process (`template()` behind a
`OnceLock`) and copied per test (`copy_tree`), with the base commit read from
the copy. Sixteen tests use it.

Unchanged: every test, every assertion, the test count (640 before and after),
the `HOME_LOCK` serialisation, the fixtures' once-per-process templates.

## Why 60 s is not reachable here, and what would get there

Every spawn on this machine costs 40-86 ms: `git --version` alone is 41-86 ms
(`/bin/echo` is 6 ms), while the box carries `XprotectService` and
`corespotlightd` (macOS rescans each new binary), another project's work - and
for a while a runaway `bfs` at 561 % CPU; load average was 20-58 all session.
The engine suite is spawn-bound: a merge is 13 git processes of its own, and a
count of one converted test showed 34 processes end to end (24 git, 10 shell).

So the floor per merge test is the engine's own git work - 13 processes, about
1 s here - and the fixture work cuts only the test-side spawns (34 -> 26
processes). Without this machine's tax that floor is 13 x 8 ms, i.e. a tenth of
a second. That is why the 3 s line reads as reachable in the task and not here.

What is left, in the order I would take it (each is the same pattern, one test
file at a time):

1. `parallel_contract` (13 still over 3 s): each test creates its branches with
   `switch`/`add`/`commit` per branch - a shape template per test case, as
   `merge.rs` does, would remove most of it.
2. `review::tests` (most of the 10 build their own origin and work clone with
   ~10 git each; the same once-per-process template applies).
3. `branch_templates_contract` (2), `multi_repo_contract` (1), `remote_contract`
   (1), and `merge::tests`' chain tests (3 merges each, ~39 processes - they
   cannot go much lower without changing what they assert).

The other lever is the machine, and it is not mine to change: the same suite
would be several times faster on a box where a spawn costs 10 ms instead of 50.

## What I tried and did not keep

- **A `git clone` for the merge template's checkout** (one process instead of
  `init` + `remote add` + `fetch` + `reset`, ~3 processes less per merge test):
  it changes the fixture's branch layout — the old checkout has a local branch
  for every origin branch, a clone only `origin/*` — and four fixture scripts
  (`publish`, the racer gate) read the local refs. Reverted rather than reshaping
  the fixture's semantics with minutes left; it is the next 3 spawns per merge
  test if someone wants them.
- **A shared template across a test file** is not available under nextest: it
  runs every test in its own process, so a `OnceLock` template is built once per
  *test*, not once per file. That is why `merge.rs`'s six-process template is paid
  by every merge test, and why the remaining work is *shrinking* the per-test
  fixture (fast-import instead of `init`/`add`/`commit`, one `clone`), not sharing
  it. This is worth knowing before the next round: the `OnceLock` half of the
  task's suggestion buys nothing under `cargo nextest`.

# T-352 — report

The board's model carries the shown voyage's stations: `ProjectBoard.stations`
is `Vec<StationBoard>` (`Reached`, `Now`, `Next`, with `what` and `at_min`), in
the voyage's order, filled for the shown voyage. The golden fixture seeds each
voyage's `STATIONS` and the M5 board holds the prototype's three stations.

wiring", but the line was empty, and the merged Batch C code does not carry the
fields the packet names: C4 (T-329) keeps only `VoyageStation { id, needs }`,
and C10 (T-334) computes progress but no `at_min`. So I sent
`gear send --kind question` (M-6014) with options and went on with the default,
(a): the smallest wiring that satisfies the acceptance.

## What changed

- `crates/gear-board/src/lib.rs`:
  - `pub enum StationState { Reached, Now, Next }` and
    `pub struct StationBoard { id, what, state, at_min }`.
  - `ProjectBoard.stations: Vec<StationBoard>`, filled at the constructor by
    `fn station_boards(tx, project, voyage)`: the shown voyage's station plans,
    in plan order, `"done"` → `Reached`, `"now"` → `Now`, `"next"` → `Next`
    (another state is not drawn); empty without a shown voyage.
  - T-334's progress list moves to `ProjectBoard.station_progress` (same data,
    same fill) so the packet's `stations` type is not lost.
- `crates/gear-board/tests/it/golden_fixture.rs`: `FixtureVoyage` reads
  `STATIONS`, and `load()` seeds each voyage's `(id, what, state, at_m)` with
  `tx.set_voyage_station_plans`.
- `crates/gear-board/tests/it/stations_contract.rs`: three new tests — S1
  reached 180, S2 now 330, S3 next 480 give those three `StationBoard`s in
  order; a voyage without station plans gives none; after
  `golden_fixture::load()` the M5 board has the prototype's three stations.
  The T-334 assertion follows the rename to `station_progress`.

# T-408 — report

The lost-merge check no longer names work of finished voyages, and no longer
names a candidate the task's repository does not hold.

## What changed

One file of code, `crates/gear-engine/src/merge.rs`, and its tests in the same
file (the crate keeps its unit tests there).

**The read pass of `tell_captain_lost`** now takes the project's tasks once and
first builds the open voyages: a voyage is its milestone, and it is open while
one of its tasks is not terminal (`TaskState::is_terminal`). A task of no
milestone has no voyage to be finished, so it is checked as before (T-397's
own tests carry `milestone = None` and must keep passing).

Each task that passes the T-397 filters is carried out of the read as a
`Lost { task, attempt, candidate, repo, told, voyage }`. `told` is the old
"told or landed already" pair of meta keys, kept (rather than `continue`d
early) so that an item that is still _open_ can be closed by the new rule.

**The git phase, per `Lost`**:

- `!voyage` → the task is skipped;
- else `candidate_held(&repo, &candidate)` answers `git cat-file -e
  <sha>^{commit}` in the task's repo: `Some(false)` → skipped, `None` → the
  repo path is not a directory, so git was not asked (see "Decision" below),
  and the task is checked as before;
- a skip calls the new `resolve_lost`, which resolves every **open** item on
  `merge-lost:<task>` with the result
  `LOST_SKIPPED` = "no longer checked: its voyage is finished or its candidate
  is gone";
- `told` → nothing more (the item was named once already, and the T-408 skips
  are the only thing that can still close it);
- the rest is unchanged: the ancestor check, the landed key, then the item.

## Decision I had to take (asked as a question, went on with the default)

T-397's own tests use `repo = /repo`, a path that is not on the machine, and
the acceptance says they must pass; so a repo git cannot be asked cannot mean
"the candidate is gone". `candidate_held` returns `None` for a path that is
not a directory and nothing is skipped on it — a missing repo path is the
project's trouble, not evidence that the commit is gone. A repo that _is_
there and does not hold the commit is `Some(false)` and skips the task.

## Tests

Three, in the crate's own test module (`merge.rs`):

- `a_task_of_a_finished_voyage_is_not_named_lost` — T-5 (Done) is the only
  task of M1: an accepted, unmerged attempt with a failed merge op gets no
  item.
- `a_candidate_the_repository_no_longer_holds_is_not_named_lost` — a scratch
  repo the scan can ask (`config_text_in`), candidate `6e555b1` which is no
  object in it: no item, and no landed key either (the skip is not a landing).
- `an_open_lost_item_of_a_skipped_task_is_resolved` — a real candidate names
  the work on the first tick; the voyage then finishes (T-5 becomes M1's only
  task) and the next tick resolves the open item, with `LOST_SKIPPED` in its
  result, and opens no second one.

`make check CRATE=gear-engine`: 745 tests, 745 passed. T-397's own tests pass
unchanged.

## Out of scope

- An open `merge-lost` item whose task stops being a candidate for a reason
  the packet did not name — the task was reopened (no longer `Done`), or a
  merge op was queued after the item was opened — is still left open. The
  packet only asks for the tasks "the new rule skips".
- The scan still asks git once per tick for each accepted-but-unmerged attempt
  whose repo holds the candidate and which is not yet told or landed; the
  landed answer (and, once resolved, the told key) is what stops the repeat.

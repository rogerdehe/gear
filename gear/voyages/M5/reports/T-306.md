# T-306 — report

`- remerge T-<n>` of a candidate that is already on the integration branch now
queues no merge op, resolves the task's open `merge-failed:<task>` and
`push:<task>` items, and the apply says so in its warnings. The code change is
`crates/gear-app/src/plan.rs` only; the tests are in the crate's
`tests/it/remerge_contract.rs`.

## What changed

**`crates/gear-app/src/plan.rs`**

- `fn remerges_already_merged(store, draft) -> GearResult<BTreeSet<String>>`,
  new, called from `fn apply` beside `cancellable_done_tasks` — i.e. before
  the write transaction, so git never runs while the store is held. For each
  `StaffItem::Remerge { task, .. }` it reads, in one `store.read`: the task's
  lane and the candidate of its last **Accepted** attempt
  (`rev().find(Accepted)`, as `cancellable_done_tasks` reads it), and the
  project's stored `config_toml`. Empty text → empty set (nothing to ask git
  with); text that does not parse → empty set (`crate::config::parse` skipped).
  With a parsed config, `on_integration(&config, task.lane.as_deref(),
  &candidate)` decides: `Ok(true)` inserts the task, `Ok(false)` and `Err(_)`
  do not — a git failure leaves the remerge exactly as it was, and the
  engine's merge confirms an already-merged candidate itself.
- `fn apply_queue` takes the set as `already_merged: &BTreeSet<String>` right
  after `cancellable: &BTreeSet<String>`, the way `cancellable` is taken.
- `fn remerge` gets `already: bool` and returns `GearResult<Option<String>>`.
  The last-op checks (last attempt accepted, last merge op `Failed`) run
  first and are unchanged; then, when `already` is true, it inserts **no** op,
  calls `resolve_merge_items(tx, project, task, "the candidate <sha> is
  already on the integration branch", now)` and returns
  `Some("remerge <task>: <sha> is already on the integration branch: no merge
  queued, its failed-merge item resolved")`. Otherwise it queues the op as
  today (same payload) and returns `None`.
- `fn resolve_merge_items` takes the result text as a parameter `result:
  &str`; the cancel path passes `"cancelled by the captain"` as before.
- The staff loop pushes a `Some` note from `remerge` into `warnings`.

## Tests

**`crates/gear-app/tests/it/remerge_contract.rs`**

- A git fixture built once per file (two `OnceLock`s: merged / unmerged, as
  `cancel_contract.rs` builds them): a bare `origin.git`, a repo with `dev`,
  a `heat/t1` commit (`candidate`), and — for the merged variant — that
  commit merged into `dev`; every branch is published into the bare origin's
  refs (`git fetch` from the source + `update-ref`, no test pushes). `repo()`
  copies both trees with `crate::copy_tree` and points the copy at its own
  origin with `crate::point_at`, and the project's config names the copy as
  its `repo` with `integration = "dev"`.
- `a_remerge_of_a_candidate_already_on_the_integration_branch_queues_nothing`
  — accepted attempt on the fixture's sha, a failed merge op and an open
  `merge-failed:T-1` item, then `- remerge T-1`: exactly one merge op still on
  the store (no new one), `warnings == ["remerge T-1: <sha> is already on the
  integration branch: no merge queued, its failed-merge item resolved"]`, and
  the item is `Resolved` with result `the candidate <sha> is already on the
  integration branch`.
- `a_remerge_of_a_candidate_not_on_the_integration_branch_queues_the_op` — the
  same world against the unmerged fixture: a second merge op is queued with
  that candidate, no warning, and the item stays `Open` for the engine's retry.
- The three existing remerge tests (`a_remerge_names_the_projects_review_branch`,
  `the_default_config_still_writes_review_t_n`,
  `the_last_merge_is_the_higher_op_number_not_the_larger_string`,
  `a_confirmed_four_digit_merge_is_named_in_the_refusal`) pass unchanged: their
  projects' `repo` is `/repo`, so `on_integration` errors and the remerge runs
  as before.
- `accepted_task` now delegates to a new `accepted_task_on(s, candidate)` so a
  test can accept the fixture's sha instead of `c1`.

## Out of scope

- `- remerge` of a task whose last attempt is not Accepted (or that has no
  merge op) still refuses before the `already` answer is used, as the packet
  orders ("after the last-op checks"). A candidate could be on the branch in
  that state too, but the packet keeps the refusal.
- `remerges_already_merged` reads the **last Accepted** attempt, while
  `fn remerge` reads the last attempt and demands it be Accepted; where those
  differ (a newer, non-accepted attempt) `remerge` refuses and the set is
  unused, so the two never disagree about what is merged.
- A config that does not parse yields an empty set and the old remerge path;
  no warning is added about the unread config (the packet says skip).

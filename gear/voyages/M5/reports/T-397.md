# T-397 — report

No accepted work is lost without a word: an accepted attempt whose candidate is
not on the integration branch always has a pending merge or an open captain
item.

## What changed

One file of code, `crates/gear-engine/src/merge.rs`, and its tests in the same
file (the crate keeps its unit tests there).

**`tell_captain_lost`** runs once per tick from `merge_passed`, after the queue
step (so a merge queued in the same tick already counts as in flight). In one
read it takes the merge ops that are `Intended`, `Executing`, `Submitted` or
`Unknown`, then for each `Done` task of the project whose latest attempt is
accepted, has a candidate and no `Merged` attempt time, and which has

- no merge op in flight,
- no open item on thread `merge-failed:<task>`,
- no meta key for this attempt,

the engine opens one item on thread `merge-lost:<task>`:

    <task> attempt <n> was accepted but is not merged and nothing will merge it:
    `- remerge <task>` under `# Staff` retries it

and remembers it in `engine.merge_lost_told.<project>.<task>.<attempt>`, so a
resolved item does not come back on the next tick.

**The ancestor check** (`is_ancestor` on the task's repo, against
`refs/remotes/<conventions.remote>/<repo.integration>`) leaves a candidate that
already landed alone; its answer is kept in
`engine.merge_lost_landed.<project>.<task>.<attempt>` so git is asked once per
attempt, not every tick. No fetch runs on the tick's path: a remote-tracking
ref that lags can only answer "not merged", and the remerge the item names
settles that case (the remerge path fetches). A git that cannot answer counts
as "not merged", so the work is named rather than silently dropped.

The four new tests:

- `an_accepted_attempt_that_nothing_merges_is_named_once` — a Failed merge op
  and its failed item resolved: one `merge-lost:T-5` item whose body is the
  line above, and a second tick adds none.
- `an_attempt_with_a_queued_merge_is_not_named_lost` — an `Intended` merge op
  gets no item.
- `a_merged_attempt_is_not_named_lost` — an attempt carrying its merge time
  gets no item.
- `a_candidate_on_the_integration_branch_is_not_named_lost` — a real scratch
  repo, the candidate at `dev`'s tip: no item, and the ancestor answer kept.

## Out of scope

- No `resolve_lost`/`resolve_failed` twin: the packet asks for the item, not
  for closing it when the work lands later. A merge that later goes through
  leaves the open `merge-lost:<task>` item for the captain to settle.
- The ancestor answer is cached per attempt (an internal meta key, next to the
  "told" key the packet names), to keep a hand-merged task from costing one git
  process per tick. It is a cache of "left alone", not new behaviour.
- `make gate` was not run (the merge gate runs it).

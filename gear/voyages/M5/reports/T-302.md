# T-302 — report

`crates/gear-app/src/admin.rs` `fn branch_clash` (T-256) now refuses three kinds
of overlap between two projects of one store instead of only the branch names:
two projects on one GitHub repository that would take the same issues, and two
projects whose `conventions.voyage_dir` expands to one folder. The two callers
(`check_other_projects` for register/re_register, and `--check` in
`crates/gear-cli/src/main.rs`) are unchanged; the fix is in `admin.rs` only.

## What changed

**`crates/gear-app/src/admin.rs`**

- `fn branch_clash` keeps its signature and its `repo_paths` comparison, and for
  each other project that parses runs the four checks in the packet's order:
  - **(a) GitHub issues**, before any path question: a repo of this config and
    a repo of the other that both have `github: Some(g)` with the same
    `g.repo` (`eq_ignore_ascii_case`) — whatever their local paths — clash when
    either side's `issues_labels` is empty (`every open issue would be taken
    twice`) or when the two lists share a label.
  - **(b)** no shared repository path → the next project.
  - **(c)** today's branch check, unchanged: three templates not all naming
    `{project}` → today's text.
  - **(d) voyage folder**: `gear_model::layout::voyage_dir` of both templates,
    each with its own project id and `"{milestone}"` left in place; equal →
    the voyage text.
- `fn github_clash(other_id, our_repos, other)` — the (a) check over every pair
  of `ProjectConfig::repos()`; the shared labels are named in this config's own
  order (deduplicated, joined by `", "`).
- The doc comment of `fn branch_clash` now says branches, voyage folders and
  GitHub labels, and spells the four steps out.

## Tests

**`crates/gear-app/tests/it/admin_init_contract.rs`**

- `project_on` keeps its signature and delegates to a new `project_on_with(id,
  repo, conventions, tail)`, so the T-302 tests can append whole sections.
- `a_second_project_on_one_repo_needs_its_own_voyage_folder` — beta on alpha's
  repository with all three branch templates templated but the default
  `gear/voyages/{milestone}`: refused, and the text is asserted exactly
  (`… keeps its voyages in the same folder gear/voyages/{milestone}: put
  {project} in conventions.voyage_dir …`); with
  `voyage_dir = "gear/{project}/voyages/{milestone}"` it registers.
- `two_projects_on_one_github_repo_need_their_own_issue_labels` — alpha on a
  first repo with `repo = "o/r"`, labels `["a"]`; beta on a **second** local
  repo with `repo = "O/R"`, labels `["b"]` registers (one repository,
  case-insensitively, labels of its own); gamma `["a", "c"]` is refused naming
  `a` and `alpha`; delta `[]` is refused with the non-empty text.
- `shared_issue_labels_are_named_together` — alpha `["a", "z"]`, beta
  `["z", "a", "q"]`: refused with `labelled z, a`.
- `a_second_project_on_one_repo_needs_project_in_its_branch_templates` (T-256)
  gains `voyage_dir = "gear/{project}/voyages/{milestone}"` in its templated
  config — the branch check still fires for the default templates (its first
  two assertions are unchanged) — and otherwise passes as before.

**`crates/gear-cli/tests/it/admin_init_contract.rs`** needed no change: its
`also works in` cases use the default branch templates, so the branch check
still answers first; both check runs are green.

## Out of scope

- The GitHub check reads a repo's resolved `[github]` only; a `[[repos]]` entry
  never inherits the project's section (T-79), so a child repo without its own
  `[github]` is not compared — as the packet says, no other design.
- The refusal is about a shared `owner/name` only: two projects whose local
  checkouts are different clones of the same GitHub repository but one of them
  is local-only are not refused (nothing is taken twice).
- An existing store whose projects already share a voyage folder or a GitHub
  repository is not re-checked until one of them re-registers; no migration was
  asked for.

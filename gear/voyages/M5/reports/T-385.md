# T-385 — report

The store reuses its prepared statements, so a tick or a board frame does not
re-parse every query (sampling of the engine and the board, 2026-10-29: after
waiting, the largest cost is SQLite parsing — `sqlite3RunParser` and
`sqlite3GetToken` — because `crates/gear-store/src/lib.rs` called
`self.tx.prepare(…)` on every query).

## What changed

**`crates/gear-store/src/lib.rs`** only; no other design, no query text, no
result changed.

- Every `prepare(` on the connection or transaction is now `prepare_cached(`
  — 30 call sites, a call-for-call rename; the SQL string handed in is the
  same at each site.
- New `pub const STATEMENT_CACHE_CAPACITY: usize = 256` with a doc comment
  naming T-385 and why the cache exists.
- The connection sets that capacity where it is opened:
  - `Store::prepare_connection` (called by `Store::open` and
    `Store::open_in_memory`) calls
    `set_prepared_statement_cache_capacity(STATEMENT_CACHE_CAPACITY)` before
    the pragmas, with a short comment pointing at `prepare_cached`;
  - `Store::open_read_only`, which is the one opener that does not go through
    `prepare_connection`, sets the same capacity right after building the
    store and before its busy timeout.

## Acceptance

- `grep -c "\.prepare(" crates/gear-store/src/lib.rs` prints **0** (the file
  holds no `prepare(` any more, test code included — the two test-only
  `Connection::open` calls never prepared directly).
- `make check CRATE=gear-store`: **76 tests run, 76 passed, 0 skipped**, the
  existing store suite unchanged — no test file was touched.
- Also ran the merge gate's build step for the whole tree
  (`cargo build --workspace --all-targets`): clean, **no warnings and no
  errors**, so the rename compiles in every crate that reaches the store, not
  only in `gear-store` itself. The merge gate (`make gate`) still runs the
  full suite.

No behaviour is meant to change: `rusqlite`'s cached statement derefs to
`Statement`, so every `query`, `query_map`, `query_row` and `execute` call
reads the same as before. A second `prepare_cached` of the same SQL while the
first statement is still checked out simply gets a fresh statement (rusqlite
only returns one to the cache on drop), so nested use cannot fail either.

## Out of scope (noticed, not changed)

- `crates/gear-store/src/lib.rs` is 4099 lines with several query bodies
  already reaching it through `*_select(…)` helpers; nothing here suggests a
  further change, just a note that the file is large.
- While sending progress, `gear` itself printed its slow-write line
  (`crates/gear-app/src/mail.rs:202` held the store 1240 ms). Unrelated to
  this diff — the cache change does not touch `gear-app` — so it is reported
  and not pursued here.

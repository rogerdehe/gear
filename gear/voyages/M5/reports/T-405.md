# T-405 — report

A task the engine settled as mechanical (T-273: no reviewer ever ran) merges
without a review branch. Before this, its merge op claimed a `review` branch
that never existed, so `merge_one_locked` failed with "the review branch
origin/review/t<n> is missing on origin" — and `- remerge` failed the same way
(T-385, 2026-10-29).

## What changed

`crates/gear-engine/src/merge.rs` and `crates/gear-app/src/plan.rs` only.

**How a merge knows it is mechanical.** The attempt's verdict row is the
marker: the engine's own pass (`by_seat = "engine"`) whose note
(`evidence`) starts with `mechanical:` — exactly what `review.rs`'s
`settle_mechanical` writes. Two small local predicates read it:

- `fn settled_mechanically(verdict: &gear_store::VerdictRow) -> bool` in
  `merge.rs`, used by `passed_tasks`;
- `fn settled_mechanically(tx, project, task, attempt) -> bool` in `plan.rs`,
  used by `remerge` (the accepted attempt's pass verdict).

Both files keep their own copy because the packet limits the change to them
(`gear-app`'s `tasks.rs` was not to be touched).

**Queuing the op (`merge.rs::merge_passed`).** `passed_tasks` now also returns
whether the pass is mechanical; the payload it writes carries
`"mechanical": true` for such an attempt. A reviewed attempt's payload is
unchanged (no key).

**Retrying the op (`plan.rs::remerge`).** The same payload the remerge builds
carries `"mechanical": true` when the accepted attempt was settled
mechanically, `"remerge": true` as before.

**Merging (`merge.rs::merge_one_locked`, step 6).** A `"mechanical": true`
payload merges the pinned candidate alone: the review branch is not looked up
and not merged, and a missing one is not an error. The guard
`if !has_review && !already` became `if !has_review && !mechanical && !already`;
`has_review` is `false` for a mechanical op even if a branch of that name
happens to exist, so no unreviewed branch is merged into the candidate's
merge. Every other merge still requires its review branch and still fails, with
the same message, when it is missing.

`close_branches` needed no change: it already closes only branches it saw on
the remote, so the absent review branch is simply skipped, and the task branch
whose tip is the candidate is closed as for any merge.

## Tests

`crates/gear-engine/src/merge.rs` (the crate's own test module):

- `a_mechanical_task_merges_without_a_review_branch` — the full engine path:
  a passing verdict by `engine` whose note is `mechanical: …`, the attempt
  accepted, `merge_passed` queues the op (it carries `"mechanical": true`),
  the review branch is deleted on origin, and the merge lands the candidate on
  `dev`, closes `heat/t5`, and merges nothing named `review`.

`crates/gear-app/tests/it/remerge_contract.rs` (where the crate keeps its plan
tests):

- `a_remerge_of_a_mechanical_task_queues_no_review_branch` — a mechanical
  settlement (the `engine`'s pass verdict), a failed merge op, `- remerge T-1`
  queues a payload with `"mechanical": true` and the accepted candidate.
- `a_remerge_names_the_projects_review_branch` — extended: a captain's pass is
  a reviewed merge, so its remerge payload has no `mechanical` key.

The reviewed task that lost its review branch is still covered, unchanged, by
`a_missing_review_branch_does_not_publish_a_partial_merge` and
`a_missing_review_branch_fails_the_op_and_tells_the_captain` (both pass).

## Out of scope (noticed, not changed)

- Ops already queued before this change still carry no `mechanical` key, so a
  mechanical merge that failed for the missing review branch keeps failing until
  the captain's `- remerge` re-queues it — and that remerge now says
  `mechanical: true`. A backfill of queued merge ops was not in the packet.
- A mechanical verdict's note is the only marker; a captain who hand-writes
  `evidence=mechanical: …` in a plan verdict would not be honoured (the seat is
  not `engine`), and an engine pass with any other note is a normal review-less
  pass only by that note. The packet names the note as the marker, so that is
  what is read.
- `merge_one_locked` still derives a review branch name for a mechanical op
  (from the payload's `review`) only to name it in messages; nothing looks it
  up. Leaving the key out of mechanical payloads would be a payload-shape
  change the packet did not ask for.

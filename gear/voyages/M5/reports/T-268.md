# T-268 — `- remerge` names the project's review branch and reads ops by number

Attempt 1, contract v1.

Two defects in `crates/gear-app/src/plan.rs` `fn remerge` (T-92's plan line),
both found while writing M5's contracts:

1. the queued merge op's payload carried `"review": format!("review/{slug}")`,
   the built-in default, while every other path expands the project's
   `[conventions].review_branch` (T-252). A project with its own template
   remerged a review branch that does not exist, so the merge could not find
   what the review left there.
2. the task's **last** merge op was found by sorting on `(created, id)` with the
   id compared **as a string**, where `O-999` sorts after `O-1000` when both
   were created in the same second. The line then judged the wrong op: it could
   refuse "already merged" for a task whose newest merge had failed, or queue a
   retry for one whose merge was in flight.

## What changed

`crates/gear-app/src/plan.rs`, `fn remerge` only:

- the payload's `"review"` is
  `gear_model::branch::expand(&conventions.review_branch, project, &lane, task_id)`
  — the same `conventions` the function already reads for `"branch"`; the
  now-unused `slug` local is gone. The default template still gives
  `review/t<n>`.
- the sort key is `(created, <the number after "O-" as u64, 0 when it does not
  parse>)`, a closure inside the function. No design outside this function
  changed.

## Tests

New `crates/gear-app/tests/it/remerge_contract.rs` (registered in
`tests/it/main.rs`):

- `a_remerge_names_the_projects_review_branch` — a project with
  `review_branch = "{project}/review/t{n}"` remerges T-1 and the queued op's
  payload is `review = "p/review/t1"`, `candidate = "c1"`, `branch = "heat/t1"`,
  `remerge = true`.
- `the_default_config_still_writes_review_t_n` — the same task with no stored
  config writes `review/t1`.
- `the_last_merge_is_the_higher_op_number_not_the_larger_string` — ops
  `O-999` (Confirmed) and `O-1000` (Failed) of one task, created in the same
  second: the remerge is allowed and the queued retry is attempt 1 on `c1`.
  With the old string sort the function read `O-999` as last and refused with
  "already merged".

Mutation check on the same tests (each mutation reverted afterwards):

- `"review": format!("review/{slug}")` restored → the template test fails
  (`left: "review/t1", right: "p/review/t1"`).
- `(a.created, &a.id)` string sort restored → the op-order test fails (the
  remerge is refused "already merged (O-999)").
- The default-template test passes either way, as it must.

## Validation

`cargo build -p gear-app --all-targets` → exit 0, no warnings.
`git diff --check` → clean. `origin/dev` merged in before the run.

## Out of scope

- The packet's acceptance said "two failed merge ops … the remerge is allowed
  and judged on O-1000"; two *Failed* ops give the same verdict whichever one
  the sort picks, so that shape cannot see the bug. Asked as a question
  (thread T-268:1) with options; the default taken is the one the phrase
  "allowed and judged on O-1000" supports — `O-999` Confirmed, `O-1000` Failed,
  remerge allowed. If the captain wants the literal both-failed shape too, it
  is one more test and proves nothing about the order.
- The engine writes the same payload when a review passes
  (`crates/gear-engine/src/merge.rs`) and already uses the template; only the
  plan's retry path had the two defects.
- Reaching four-digit op ids in a test needs ~1000 inserted ops; the test
  inserts 998 in one transaction (`O-1`…`O-998`), which costs ~0.3 s for the
  file. No store helper sets `id_seq`, and adding one would be a change
  outside `fn remerge`.

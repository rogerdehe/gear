# T-273 — report

The engine half of the small-task procedure (T-272 added
`ContractRow.mechanical`): a task whose contract says it is mechanical is
judged by its merge gate alone — no reviewer, no direction check — and a
hand-in is settled as a pass in the same tick. A task without `mechanical` is
reviewed exactly as before.

## What changed

Only `crates/gear-engine/src/review.rs`. `crates/gear-engine/src/lib.rs` needed
no change: the tick already calls `review::start_reviews`, and both changes fit
inside the two functions the packet names.

**`fn start_hand_in_reviews`.** For each handed-in task (Submitted attempt,
task Verifying, no verdict — the list `tasks_to_review` builds), the first
thing the loop does now is `mechanical_reason(...)`: the attempt's **adopted**
contract (`tx.get_contract(project, task, attempt.adopted_version)`) has a
`mechanical` reason. If it does, the task is settled in this tick by
`settle_mechanical` and the loop goes on — no checkout check, no model choice,
no seat, no packet.

**`fn settle_mechanical`** (new). One write:
- `gear_app::tasks::settle` with `pass: true`, `evidence: Some("mechanical:
  <reason>")`, `by_seat: "engine"`, the attempt's own candidate and its adopted
  `contract_version` — written against the contract `mechanical_reason` read, as
  the packet says. The task goes Done and the attempt Accepted, so the merge
  step (`merge::passed_tasks`) queues the merge op from the pass verdict exactly
  as it does for a captain's pass.
- The captain gets one `System`/`Info` line on the thread `mechanical:<task>`:
  `<task> settled without review: mechanical (<reason>); the merge gate
  decides`. Guarded by the meta key `engine.mechanical_told.<project>.<task>`,
  so a second tick (or a settle that is replayed) adds no second line.

**`fn start_direction_checks`.** Before anything else in its task loop: the
task's **current** contract (`tx.get_contract(project, task,
task.contract_version)`, as the packet names it) with a `mechanical` reason
skips the task, so a push of a mechanical task starts no direction check. A
contract row that is missing is not mechanical (unchanged behaviour).

## Out of scope

- **A mechanical hand-in adopted an older contract.** `settle` refuses a pass
  whose contract is not the task's current one (`BadFormat: a pass needs the
  task's current contract`), and `start_reviews`' error reaches the tick, so a
  mechanical task whose contract moved on mid-attempt would fail the project's
  tick every tick. The packet says "the attempt's own … contract", so that is
  what is written; the edge is reported to the captain as a question (asked,
  with the literal reading as the default) rather than invented around.
- **A project without `[temps]`.** `start_reviews` returns before
  `start_hand_in_reviews` and tells the captain to settle the hand-in
  (`verdict:<task>:<attempt>`, v0.4.8). A mechanical hand-in in such a project
  gets that line instead of the mechanical settlement. The packet puts the
  change inside `start_hand_in_reviews`; moving the early return was not asked
  for.
- **A reviewer already bound to the task.** `tasks_to_review` does not list a
  task whose reviewer is queued/starting/active, so a mechanical task that
  somehow has one is still reviewed by it; the mechanical path only sees the
  tasks the packet describes (no reviewer yet).
- The plan/draft side (writing `mechanical` into a contract) and the packet
  text (`Review: none — mechanical (…)`) are T-272's and already on `dev`.

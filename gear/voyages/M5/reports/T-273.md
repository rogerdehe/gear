# T-273 — report

The engine half of the small-task procedure (T-272 added
`ContractRow.mechanical`): a task whose contract says it is mechanical is
judged by its merge gate alone — no reviewer, no direction check — and a
hand-in is settled as a pass in the same tick. A task without `mechanical` is
reviewed exactly as today, and so is a mechanical hand-in that no longer works
to the task's current contract (contract v2, the captain's answer to hull's
question M-4507); no error of this step stops the tick.

## What changed

**`crates/gear-engine/src/review.rs`.**

- `ReviewReport` gains `settled` (`project:task/attempt`) and `settle_failed`
  (`project:task/attempt: CODE: detail`), the two facts the tick reports once
  the mechanical step runs.
- **`fn start_hand_in_reviews`.** For each handed-in task (Submitted attempt,
  task Verifying, no verdict — the list `tasks_to_review` builds), the first
  thing the loop does is `mechanical_reason(...)`. With a reason, the task is
  settled in this tick by `settle_mechanical` and the loop goes on — no
  checkout check, no model choice, no seat, no packet. A settlement that fails
  is pushed onto `report.settle_failed` and the loop **falls through to the
  normal review**, so the hand-in is judged as today and the tick never dies on
  it (contract v2: no error of this step stops the tick).
- **`fn mechanical_reason`** (new). The reason of the attempt's adopted
  contract, but only while `attempt.adopted_version == task.contract_version`:
  a task whose contract moved on during the attempt is not mechanical this
  round. The pass could not be written anyway (`a pass needs the task's current
  contract`), and the change the newer contract asks for is exactly what a
  reviewer must judge. A missing contract row is not mechanical.
- **`fn settle_mechanical`** (new). One write:
  - `gear_app::tasks::settle` with `pass: true`, `evidence: Some("mechanical:
    <reason>")`, `by_seat: "engine"`, the attempt's own candidate and its
    adopted `contract_version` (equal to the task's, from the check above). The
    task goes Done and the attempt Accepted, so the merge step
    (`merge::passed_tasks`) queues the merge op from the pass verdict exactly as
    it does for a captain's pass.
  - The captain gets one `System`/`Info` line on the thread `mechanical:<task>`:
    `<task> settled without review: mechanical (<reason>); the merge gate
    decides`. Guarded by the meta key `engine.mechanical_told.<project>.<task>`,
    so a second tick (or a replayed settle) adds no second line.
- **`fn start_direction_checks.`** Before anything else in its task loop: the
  task's **current** contract (`tx.get_contract(project, task,
  task.contract_version)`, as the packet names it) with a `mechanical` reason
  skips the task, so a push of a mechanical task starts no direction check. A
  missing contract row is not mechanical (unchanged behaviour).

**`crates/gear-engine/src/lib.rs`**, where the tick calls `review::start_reviews`:
the two new report lists go into the tick report's existing `settled` and
`settle_failed` fields — the same fields `settle_reviews` fills — so a
mechanical settlement (and a failed one) is visible in the tick like a
review's. No other behaviour there.

## Out of scope

- **A project without `[temps]`.** `start_reviews` returns before
  `start_hand_in_reviews` and tells the captain to settle the hand-in
  (`verdict:<task>:<attempt>`, v0.4.8). A mechanical hand-in in such a project
  gets that line instead of the mechanical settlement. The packet puts the
  change inside `start_hand_in_reviews`; moving the early return was not asked
  for.
- **A reviewer already bound to the task.** `tasks_to_review` does not list a
  task whose reviewer is queued/starting/active, so a mechanical task that
  somehow has one is still reviewed by it; the mechanical path only sees the
  tasks the packet describes (no reviewer yet).
- **A failed settlement has no test of its own.** The guard is there and is
  reported (`report.settle_failed`, then the review runs), but every path that
  makes `settle` refuse is now unreachable from this code: the contract version
  is checked first, and the candidate is the attempt's own. It would need a
  hand-built store that lies about one of them.
- The plan/draft side (writing `mechanical` into a contract) and the packet
  text (`Review: none — mechanical (…)`) are T-272's and already on `dev`.

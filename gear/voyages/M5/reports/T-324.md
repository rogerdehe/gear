# T-324 — report

The engine no longer treats a lane that helps on an unanswered captain
instruction as idle, as run-dry/busy, or as stuck: `gear_board::idle::helping`
(T-323) now guards the three places the contract names. Nothing else changed.

## What changed

**`crates/gear-engine/src/feed.rs`, `fn feed`** — in the seat loop, right after
the parked/held/tail check: when `gear_board::idle::helping(…)` is `Some(h)`,
the `feed-severity:<seat>` meta is set to `"0"`, the lane's open item is closed
with `the lane is <h.text()>` (a `FeedChange` with action `closed`, as for a
parked lane) and the seat is skipped. A helping lane therefore opens no IDLE
item, and the open one is resolved with the reason.

**`crates/gear-engine/src/busy.rs`, `fn check`** — a lane for which
`gear_board::idle::helping(…)` is `Some` does not qualify: it goes the same
`recover` way as any lane that does not qualify (`:since` and an open alert are
cleared), so no "lane is busy with no task" item is raised for it.

**`crates/gear-engine/src/lib.rs`, the flagged-seat loop over `report.flagged`**
— the seat row is now read once (`tx.get_seat(&seat)?`) and its `project` used;
when the seat is not missing and it is a lane for which
`gear_board::idle::helping(tx, &row.project, row, now)` is `Some`, no stall item
is written. A missing agent still gets its item ("its agent is gone from its
pane"), and the T-287 "exited again after the engine restarted it once" fact is
unchanged.

## Tests (where the crate keeps them)

- `feed_contract::a_lane_helping_on_an_unanswered_instruction_is_not_idle`:
  the IDLE item opens, an unanswered captain instruction closes it with
  `the lane is helping the captain: please look at the merge`, no new item
  opens while the help lasts, and after the lane's `reply_to` the IDLE item
  opens again on the next feed pass.
- `busy_contract::a_lane_helping_on_an_unanswered_instruction_raises_no_busy_item`:
  a Working helping lane with ready work raises no busy item; after the reply
  the condition counts as before and alerts ten minutes on.
- `stall_contract::a_flagged_helping_lane_whose_agent_is_present_gets_no_stall_item`
  and `…_whose_agent_is_missing_still_gets_the_stall_item`: a flagged helping
  lane (a doorbell whose check budget runs out) whose agent is present gets no
  stall item; with its pane closed the "its agent is gone from its pane" item
  is written.

## One existing test had to move (question sent, default taken)

`busy_contract::a_lane_helping_on_an_unanswered_instruction_is_not_interrupted`
(T-323) expected the `due_interrupts` esc on the tick right after the reply.
`due_interrupts` shares the `lane-busy-idle:<seat>:since` timer with `check`,
and the contract sends a helping lane through `recover`, which clears that
timer — so the condition can only start at the reply now. The test's
"no esc while helping" assertions are untouched; only its post-reply timing
moved: no esc on the reply tick, the esc five minutes later. Reported as a
question (M-5070, r-1793239580934) with the default taken per the packet.

## Out of scope

- `gear_board::idle::helping` itself (the board half, T-323) is untouched.
- The board's own `helping` row and the `gear queue`/imbalance views were
  already showing the help; the imbalance item already skips a helping lane
  through `idle_reason`.
- An open stall item of a lane that starts helping, and later stops answering
  after `HELP_LIMIT_S`, is left to the existing rules: the contract only says
  no new alert is written.

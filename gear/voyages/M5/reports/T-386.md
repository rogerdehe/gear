# T-386 — report

The engine now says what each tick costs, and a tick reads a repository's
branches with one git process instead of one per task and one per lane: the
direction checks and the no-push clock take their sha and time from a single
`git for-each-ref` per repository and tick.

## What changed

**(1) `crates/gear-engine/src/review.rs`.** New

```rust
pub(crate) fn branch_tips(cfg: &EngineCfg, repo: &str, remote: &str) -> HashMap<String, (String, Ts)>
```

runs one `git for-each-ref --format=%(refname:short) %(objectname)
%(committerdate:unix) refs/remotes/<remote>/` through `review_git` as the
per-branch calls went through it, and answers a map keyed by the branch alone
(`heat/t1`), holding the tip's sha and its commit time. `%(committerdate:unix)`
is the same time the old `git log -1 --format=%ct` read; a read that fails is
an empty map, so a caller keeps its behaviour on a branch it cannot read.

`fn start_direction_checks` no longer runs `git rev-parse --verify
refs/remotes/<remote>/<branch>` per started attempt: it takes the sha from the
tips. `fn finish_direction_results`, the other per-`rev-parse`-per-running-check
read of the same step (T-283's tip comparison), does the same. `merge-base` and
`diff` are still per task: they are the diff, not the branch read, and the
packet does not ask for those.

The map is filled once per repository by `pub(crate) fn repo_tips`, whose
`RepoTips` type (`HashMap<repo path, HashMap<branch, (sha, time)>>`) is the one
map the whole tick shares:

- `start_reviews` keeps its signature and makes its own map (one read per
  repository for that step);
- `pub fn start_reviews_with_tips` is the same step reading a caller's map, and
  `lib.rs`'s tick calls it with the tick's map.

**(2) `crates/gear-engine/src/quiet.rs`.** `fn last_push` — the push-time read
of the no-push clock — takes the branch's time from the tips map instead of
`git log -1 --format=%ct refs/remotes/<remote>/<branch>` per lane per tick.
`fn tick` and `fn loops` take the tick's `RepoTips` and the engine's cfg (they
need `cfg.review_git`; `lib.rs` had both). The `git log` per lane per tick is
gone.

**(3) `crates/gear-engine/src/lib.rs`.** `fn tick` and its per-project step
function time each of their steps with `std::time::Instant`; a step past 200 ms
(`SLOW_STEP_MS`) adds `<step>: <ms> ms` to the new `TickReport.slow:
Vec<String>`. The report is printed as today (`tick: {report:?}`), so the slow
lines come with it. The steps timed are the tick's own steps (reconcile
rebinds, rebind, onboard, settle reviews, waits, parallel check, forge sync,
stations, observe, names, each project, rounds, waits after, overrun, reviewer
nudge flags) and the per-project steps (`names restore`, `observe seats`, `park
end and busy`, `busy interrupt`, `blocked`, `guardrails`, `backoff`, `captain
quota`, `restart missing jobs`, `silent`, `restart config`, `quota`, `quiet`,
`confirm`, `resubmit`, `late confirm`, `attention`, `dispatch`, `feed`, `dead
temps`, `tail`, `friction`, `review`, `reviewer nudge`, `lane nudge`, `release`,
`retire`, `doorbell decide`, `doorbell intend`, `execute`, `merge`). The tick
creates the one `RepoTips` map and hands it to both the quiet step and the
review step, so a repository is read exactly once per tick however many tasks
and lanes ask for it.

Behaviour is unchanged: the same shas, the same commit times, the same quiet
decisions; only the number of git processes changes.

## Tests

- `crates/gear-engine/src/review.rs` (unit tests):
  - `branch_tips_reads_every_remote_branch_once` — a real fixture repository
    with two remote branches: the map holds each branch's tip sha and the time
    `git log -1 --format=%ct` gives for that ref, and nothing else.
  - `a_tick_reads_each_repositorys_branches_once_for_two_attempts` — two lanes
    with started attempts in one repository and two pushed branches; a whole
    `crate::tick` records exactly one `for-each-ref` call and no `rev-parse`
    (a recording `ReviewGit` fixture), and the direction check that got the
    free seat carries the first lane's branch tip. The test asserts both
    attempts are `Started` before the tick.
- `crates/gear-engine/src/lib.rs` (new `t386_tick_tests`):
  `a_step_over_the_budget_is_named_in_the_report` — an injected `ReviewGit`
  that sleeps 250 ms per call: the tick's report names the step (the quiet step
  read the tips first, then the review step), each line is `<step>: <ms> ms`
  with `<ms>` over 200.
- `crates/gear-engine/src/quiet.rs` (unit tests): the test module gained a
  local `cfg()` and one-shot `tick`/`loops` wrappers (a tick shares one map);
  the tests themselves are unchanged and still read real repositories.

## Out of scope

- The first run of the new tick test failed for a reason outside the code: the
  fixture wrote the second branch's file before checking the branch out. Fixed
  in the test (`git checkout` first, then the write).
- `%(refname:short)` is ambiguous only if the repository also has a local
  branch literally named `<remote>/<branch>`; git then prints the full
  unambiguous name and that ref is skipped, so the caller sees the branch it
  cannot read (the fallback the old failing `rev-parse` gave). No test: it
  needs a local branch named `origin/…`.
- The `merge-base` and `diff` of the direction step are still one git process
  per started attempt. They read the diff range, not the branch list, and the
  packet names only the branch read.
- `crates/gear-engine/src/dispatch.rs` still runs `git status --porcelain`
  through `cfg.review_git` per call for the "dirty tree" line of a packet; not
  a branch read, and outside the files this task names.
- I asked the captain (thread `T-386:1`) whether `finish_direction_results` was
  in scope and defaulted to converting it and sharing one map per tick (the
  acceptance's "one for-each-ref call per repository" in a tick).

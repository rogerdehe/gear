# T-321 — report

The home page warns when the config file differs from the config the project
runs on (design §10.7 row "B03 config"): the store keeps only the applied text
(`projects.config_toml`) and its version, never where it came from, so nothing
could compare. No schema change — the path is a meta row.

## What changed

**`crates/gear-app/src/admin.rs`** — the key, as the packet words it:

- `pub fn config_path_key(project: &str) -> String` → `"config.path.<project>"`,
  with the doc comment that says why the store needs it (the applied text has
  no path).

**`crates/gear-cli/src/main.rs`, `fn cmd_admin_init`** — right after a
successful real `init_checked` (the `--check` path returns long before):

```rust
let path = canonical(&config.to_string_lossy());
store.write(|tx| tx.set_meta(&gear_app::admin::config_path_key(&r.project), &path))?;
```

`canonical` is the file's existing helper (`std::fs::canonicalize`, the input
spelling when that fails), so a `gear admin init …/nested/../gear.toml` and a
`gear admin init …/gear.toml` store the same row. A failed meta write is
reported: the command exits non-zero rather than claim a registration it could
not remember.

**`crates/gear-app/src/home.rs`**

- `fn snapshot` pushes `config_drift(tx, project)?` right after the totals
  line, so the warning is the snapshot's **second** line, before the lanes and
  the inbox (T-321's position).
- New `fn config_drift(tx, project) -> GearResult<Option<String>>`: `None`
  when the meta row is unset (a project registered before T-321, or one
  registered without the CLI) or the project row is missing; then
  `std::fs::read_to_string` of the recorded path:
  - text equal to `config_toml` → `None`;
  - text differs → `! config drift: <path> differs from the applied config
    v<n>: re-apply it with GEAR_ADMIN=1 gear admin init <path>, or restore the
    file`;
  - unreadable (gone, or not a file) → `! config file <path> cannot be read
    (config v<n> still runs)`.

The page stays read-only: one `stat`+read of the config file and two rows of
the store, no write, no engine.

## Out of scope

- Nothing watches the file: the drift is computed when the captain reads
  `gear`, not pushed. A captain who never opens the page sees nothing (the
  packet asks for the home page).
- The comparison is the whole text, verbatim: a trailing newline added by an
  editor is drift, and a comment-only edit is drift too — the file is no
  longer byte-for-byte what was applied, which is exactly what the message
  offers to fix.
- No line for the lanes: the snapshot is the captain's (`home::build` shows it
  only for `SeatRole::Captain`), and the packet asks for the snapshot's line.
- A re-registration without the CLI (an `admin::init` call from another
  program) does not write the meta row; only `cmd_admin_init` does, as the
  packet says. Such a store keeps comparing against whatever path the last CLI
  init recorded — which is still the file the user edits.
- Nothing in `gear-board`, `gear-engine` or the frame: the line lives in the
  home snapshot only.

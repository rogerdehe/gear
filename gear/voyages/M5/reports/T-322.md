# T-322 — report

One view across Herdr sessions: since v0.4.5 each Herdr session has its own
store and nothing listed them together. The smallest form, as decided — a
read-only command that lists every store on this machine and the projects in
it. No shared quota scheduling, no writes, no engine.

## What changed

**`crates/gear-cli/src/main.rs`**

- `AdminOp::Projects` (`gear admin projects`, global `--json` applies):
  `cmd_admin_projects` prints one block per store.
- `fn stores_in(home)` — the stores, in path order: the shared store
  `~/.local/state/gear/gear.db`, every `~/.local/state/gear/*/gear.db`, and
  every store named in `targets_path_in(home)` (second column of the registry).
  Only existing files, each once: every candidate is canonicalized and put in a
  `BTreeSet<PathBuf>`, which dedups a store reached twice (a session directory
  and a registry line) **and** gives the path order. The canonical path is what
  is printed, so the header is the same path the dedup was made on.
- `fn projects_in_store(path)` — opens the store with
  `gear_store::Store::open_read_only` and reads, per project, `id`,
  `herdr_session`, `config_version` and `gear_app::plan::current_voyage`; its
  `Err` is the detail text (`GearError::detail`) and the command goes on with
  the next store.
- `fn render_stores` — `<path>` then one line per project
  `  <id> · session <herdr_session> · config v<n> · voyage <M-n or ->`, or
  `  (no projects)`, or `  cannot read: <detail>`. An empty list prints nothing.
- `fn stores_json` — `[{"store", "projects": [{"id", "session",
  "config_version", "voyage"}], "error"}]`; `voyage` is `-` for a project in no
  voyage, the same value the text form prints.
- `fn starts_engine` returns false for `Projects`, with the reason in its doc
  comment (an engine would open one of these stores and write it).
- `fn checks_a_config` became `fn writes_nothing` and covers `Projects` too, so
  `main` does not call `default_store_path` for it: the command creates no
  directory either (the packet's "nothing is written" — it would otherwise
  create `~/.local/state/gear` just by running). Its one call site is updated.

**`crates/gear-cli/tests/it/projects_contract.rs`** (new; registered in
`tests/it/main.rs`), five contract tests through the real binary and
`scratch::gear`:

- `every_store_on_this_machine_is_listed` — a scratch `HOME` with the shared
  store holding `a` (voyage `M2`), `~/.local/state/gear/s1/gear.db` holding `b`,
  an empty registered store, a registry that names that registered store,
  names the session store a second time and names a file that is not there:
  exactly the three existing stores print, in path order, each once, with its
  project line (and `voyage -` for `b`) or `(no projects)`.
- `json_names_every_store_its_projects_and_the_error` — two entries, the good
  one with `error: null` and the four project fields, the broken one with its
  `error` detail and no projects.
- `a_store_that_does_not_open_is_reported_and_the_others_still_print` — a file
  that is not a database gives `cannot read: <detail>` and the good store still
  prints; the exit code stays 0.
- `it_writes_nothing_and_starts_no_engine` — a `HOME` with no store at all
  prints nothing and creates no `.local`; a `HOME` whose store is registered
  for the `HERDR_SOCKET_PATH` the caller runs in (so a command that started the
  engine would leave `engine.lock` beside it) leaves no `engine.lock` and no
  `engine.log`, and the store still reads the same.
- `a_home_that_is_not_there_lists_nothing` — no `HOME`: no stores to list,
  `[]`, no complaint.

## Out of scope

- `GEAR_DB` is not one of the stores: the packet lists the shared store, the
  session stores and the registry, and says nothing about the caller's own
  store. A `GEAR_DB` store that is not registered is therefore not shown (in
  normal use `admin init` registers it).
- No documentation update (`docs/`, the skill's command list): the packet keeps
  the code change in `crates/gear-cli/src/main.rs` and the tests.
- A store whose schema is older than the binary reads as it is (read-only, like
  `admin init --check`): a missing table then shows as `cannot read: <detail>`
  rather than being migrated.

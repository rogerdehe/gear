# T-280 — report

A merge that loses the push race on every try of a tick is no longer a failed
merge: the integration branch moved under each attempt (another fleet's or
another project's merge landed), so the op goes back to the queue and merges
again from the new tip on the next tick. No `OpState::Failed`, no captain item,
no `- remerge` by hand.

## What changed

**`crates/gear-engine/src/merge.rs`** (the only file of the code change)

- `enum Report` gains `Raced(String)` — the merge lost the push race on every
  try.
- `enum Step` gains `Raced(String)` — the same, inside one worker run.
- `fn lost_the_race(reason: &str) -> bool` (private, next to `step_result`):
  `reason.starts_with(RACE)` and the reason names a moved remote
  (`non-fast-forward` or `fetch first`). A `cannot lock ref` failure is
  deliberately not a race here: it can be a stale local lock, not a move on the
  remote.
- `fn merge_with_retries`: the branch that would return `Step::Failed` after
  `attempt >= MERGE_RETRIES` now returns `Step::Raced(reason)` instead when
  `pr.is_none() && lost_the_race(&failed.reason)`. The reason keeps the
  existing `(retried N time(s), …)` note of that branch and still starts with
  `push race: `. Every other clear failure keeps today's three retries and its
  `Failed` end; PR mode (the push in `fn pr_head`, `pr` Some) is untouched and
  keeps its `Failed` end.
- The worker closure maps `Step::Raced(reason)` to `Report::Raced(reason)`,
  where it maps the other steps.
- `fn merge_passed` collects `Report::Raced(reason)` with
  `retry_merge(store, project, op, &format!("{first} — the integration branch
  moved during each of {} tries; it merges again from the new tip on the next
  tick", MERGE_RETRIES + 1), finished.at)` — `<first>` is the first line of the
  reason (`reason.lines().next()`), `MERGE_RETRIES + 1` is 4 and matches the
  tries the worker made (attempt 0..=3). The op goes back to `Unknown`, so
  `ready_merges` runs it again next tick: fetch, merge, gate, push as on every
  run. No `fail_merge`, no captain item, and no `failed_thread` message.
- `fn step_result` (test helper) maps `Step::Raced(reason)` to
  `Err(Failed::clear(reason))`.

Nothing else in the crate changed; the race is not counted across ticks.

## Tests (in `merge::tests`, next to the existing race tests)

- `struct RaceRemote` (next to `FailOnceRemote`), modelled on it: refuses its
  first N pushes with a given reason and then behaves like `FetchRemote`; it
  also counts every push so a test can assert how many tries it cost.
  `const REJECTED: &str = "! [rejected] dev -> dev (non-fast-forward)"`.
- `a_merge_that_loses_the_push_race_on_every_try_is_raced`: `merge_retried_with`
  with `RaceRemote::new(4, REJECTED)` returns `Err` (the `step_result` mapping
  of `Step::Raced`) whose reason starts with `push race: ` and whose blocker is
  `Clear`; the runner was pushed exactly 4 times (`MERGE_RETRIES + 1`) and
  nothing of T-5 reached `dev`.
- `a_merge_that_races_every_try_goes_back_to_the_queue_and_lands`: driven by the
  existing `drive` helper over `queued_merge`, with `cfg.remote` set to
  `RaceRemote::new(4, REJECTED)`. The first launch races 4 times, the op goes
  back to `Unknown`, the second launch's push succeeds; the `drive` closure
  asserts after every tick that the op is never `Failed`. Ends `Confirmed`, 5
  pushes in all (4 refused + 1 landed), T-5 on `dev`, and
  `failed_items(store, "T-5")` empty (no message on the task's `failed_thread`).
- `a_push_a_hook_declines_every_try_still_fails_and_rings_the_captain`: the same
  runner refusing every push with `hook declined` (`usize::MAX`). Driven to
  `Failed`; exactly one captain item, its body naming
  `push failed: hook declined`; nothing pushed. Today's path is unchanged.

## Out of scope

- The `Raced` message keeps the worker's `(retried N time(s), each with a
  growing wait)` note in `op.result`'s tail; `merge_passed` names only the first
  line, as the packet says. Harmless, but a reader of `op.result` sees both the
  count and the note.
- A race that runs through `MERGE_RETRIES + 1` tries in *one tick* is reported,
  not counted across ticks (as the packet requires). If the branch moved every
  single try for many ticks, the op would keep re-queueing on every tick and the
  engine would re-run the gate each time — no test covers that pathological
  case.
- `REJECTED`/`RaceRemote` live in the crate's test module only; no integration
  test in `crates/gear-engine/tests/` uses them.

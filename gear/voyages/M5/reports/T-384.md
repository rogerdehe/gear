# T-384 — report

The board stops rebuilding itself when nothing changed. `run_with` now keeps the
board it built, the store's `PRAGMA data_version` and Herdr's agent list, and
rebuilds only when the version moved, the agent list moved, or the kept board is
a minute old. Every other refresh — and every key — redraws what it has. Herdr
is asked for its agents at most every ten seconds instead of every two seconds
and after every key.

Nothing the board shows changes: the kept board is the same model, the same
`frame::view`/`frame::canvas` draw it, and the only staleness the design accepts
is a clock and a few age/deadline texts that are rebuilt after 60 s.

## What changed

`crates/gear-store/src/lib.rs` (the allowed edit):

- `Tx::data_version(&self) -> GearResult<i64>` — one `PRAGMA data_version`
  query. SQLite moves the value when **another** connection commits and leaves
  it alone for this connection's own writes; the board only reads, so every
  write it has to notice arrives through another connection (the engine, the
  CLI).

`crates/gear-board/src/lib.rs`:

- `fn run_with` keeps, across frames, the built `Board`, the `data_version` it
  was built on, when it was built, and the last agent list with the time it was
  asked for. At the top of each frame it asks Herdr only when the last ask is
  `AGENTS_EVERY` old, reads `data_version` with one `store.read`, and rebuilds
  when the version differs, the agent list differs, or `REBUILD_AFTER` passed;
  otherwise it redraws from the kept board. `p` walks the kept board one project
  on (`rotate_left(1)`) instead of rebuilding for the next project, which is the
  same rotation the old rebuild applied. The failure path is unchanged: the
  first frame still decides whether the board can start, a later failure is
  shown as the error frame it is, and the kept board is dropped so the next
  period tries again.
- `pub const REBUILD_AFTER` (60 s) and `pub const AGENTS_EVERY` (10 s) name the
  two intervals.
- `pub mod hook` is the test hook the acceptance allows: it counts the builds
  and, for a test only, shortens the two intervals. It is thread-local (a test
  runs on its own thread, so no test can shorten another's minute) and its
  defaults are exactly the two constants above, so a board that never calls it
  behaves as specified. It is the only thing added outside `run_with` in that
  file.

The two intervals are read through the hook both in production and in tests
(`hook::stale_after()`, `hook::agents_every()`), so a test exercises the same
code path the user runs, only with shorter waits.

## Tests

`crates/gear-board/tests/it/quiet_contract.rs` (new module, registered in
`tests/it/main.rs`) — one test per acceptance point:

- `ten_refresh_periods_build_the_board_once` — a keyboard that lets ten refresh
  periods time out (each waits its whole timeout, as a terminal does) and then
  quits: `hook::builds() == 1`, and the output holds eleven frames, so the board
  was redrawn each period without being built.
- `a_write_from_another_connection_builds_the_board_again` — the board reads a
  file-backed store; the keyboard's first period opens a second `Store` on the
  same path and writes, then times out: `hook::builds() == 2`.
- `a_key_press_redraws_without_building_the_board` — `2`, `Down`, `Down`, `q`:
  `hook::builds() == 1`, four frames, and the last frame differs from the first
  (the selection moved).
- `an_old_board_is_built_again_once` — `set_stale_after(25 ms)` and one 40 ms
  period: `hook::builds() == 2` (the first frame and the one rebuild of an old
  board).
- `herdr_is_asked_for_its_agents_at_most_every_interval` — a `HerdrRead` that
  counts `agents()` calls, `set_agents_every(25 ms)` and one 40 ms period: two
  asks, one build.
- `a_changed_agent_list_builds_the_board_again` — the same, with the fake
  handing out a different agent list on its second ask: two asks, two builds.

`crates/gear-store/tests/it/data_version_contract.rs` (new module, registered in
`tests/it/main.rs`):

- `data_version_moves_when_another_connection_writes` — two connections on one
  file: reading twice does not move the value, a write from the other
  connection moves it, a second commit moves it again, and this connection's own
  write does not move the value it sees.

## Rework (attempt 2, review F1)

The selected project could change on its own. `shown` counted the `p` presses
since the board opened while the kept board was rotated by one per press, so
after a full cycle back to the first project `shown` was a multiple of the
count, not `0`. A rebuild then rotated by `shown % count` — harmless at the
same count, wrong once the count grew: with two projects and two presses
(`shown == 2`), registering a third project rebuilt the board and rotated by
`2`, showing project `c` where the user had left `a`.

Fix, in `fn run_with` only (`crates/gear-board/src/lib.rs`):

- `shown` is now the index of the project the board shows. `p` normalizes it
  to the current project count after the press's rotation, and the rebuild
  branch normalizes it again before rotating, so a rebuild against a different
  count starts from the project that was on screen. Two to four lines each;
  the model, the triggers, the intervals and every frame are unchanged.

Test (`crates/gear-board/tests/it/quiet_contract.rs`):

- `a_project_registered_later_does_not_move_the_shown_one` — a file-backed
  store with projects `a` and `b`, the board opened with no project, `p`
  twice (a full cycle), then a third project `c` registered from a second
  `Store` connection and one refresh period let by. The titles read `a`, `b`,
  `a`, and — after exactly one rebuild (`hook::builds() == 2`) — `a` again,
  now `p: next of 3 projects`. Red before the fix: the same test read `c` in
  the last frame.

# T-373 — report

A re-applied config that changes `conventions.seat_branch` now says which seat
worktrees GEAR no longer uses: one line per seat that has a worktree in meta,
naming the path, the branch it was made for, the branch new agents of that seat
get, and the command that removes the old tree. Nothing is removed.

## What changed

**`crates/gear-app/src/admin.rs`**

- `InitResult` gains `stale_worktrees: Vec<String>` — the display lines, empty
  when the `seat_branch` did not change (`#[serde(default)]`, so an older JSON
  still reads).
- `const WORKTREE_PATH_KEY: &str = "engine.worktree_path."` beside
  `re_register`, documented as the same key string
  `gear_engine::onboard::worktree_path_key` builds. The app sits below the
  engine and cannot call it, so the shape is named on both sides.
- `fn stale_seat_worktrees(tx, project, config)`: parses the stored config
  text; equal `conventions.seat_branch` → no lines; otherwise, for every seat
  of the project with a non-empty worktree path in meta, one line
  ``seat <name>: its worktree <path> was made for branch <old expansion>; new
  agents of this seat get a worktree on <new expansion>; remove the old one
  with `herdr worktree remove` once the seat runs in the new one`` — both
  expansions from `gear_model::branch::expand_seat`.
- `re_register` returns those lines in its `InitResult` and lists the rule in
  its doc comment; `register` (a first registration) returns nothing, there is
  no old `seat_branch`.

**`crates/gear-cli/src/main.rs`** — the text output of `gear admin init`
prints `r.stale_worktrees` right after `project <id> (config v<n>)`, before the
seat lines.

**Tests**

- `crates/gear-app/tests/it/admin_init_contract.rs`:
  `a_changed_seat_branch_names_the_worktree_it_leaves_behind` — a project whose
  lane `heat` has `/work/harbor-heat` in meta re-applied with
  `{project}/seat/{seat}` → `{project}/home/{seat}` gives exactly that one
  line (both expansions, the path), the other lane and the captain say nothing,
  the meta still holds the path, and an unchanged `seat_branch` gives no line.
- `crates/gear-cli/tests/it/admin_init_contract.rs`:
  `a_changed_seat_branch_prints_the_worktree_it_leaves_behind` — the same
  change on a real store prints the line directly after `project p (config v2)`.

## Out of scope

- The packet's contract v1 named the meta key `onboard.worktree.<seat id>`;
  `gear_engine::onboard::worktree_path_key` builds `engine.worktree_path.<seat
  id>`, which is what this code reads. The captain settled it in contract v2
  (question M-4837, answer M-4839). Because the key is now spelled in two
  crates, a shared constant (in `gear_model`, which both read) would remove the
  duplication — a small task.
- A seat's meta path that is empty is skipped (no path to name), as
  `gear_engine::rebind` does for the same key.
- The line is emitted for every seat with a path, as the packet says, even in
  the rare case where the two templates differ but expand to the same branch
  for that seat (`{project}/x` → `{project}/{seat}` for a seat named `x`): that
  line would name the same branch twice.

# T-323 — report

A lane that holds an unanswered instruction of the captain is busy, not idle:
the board, the frame and the plan's idle warning now say `helping <lane>: …`
instead of `no current task` / `idle: nothing left planned` (trial B04-01: a
lane giving read-only evidence to another lane looked idle and drew IDLE and
stall alerts).

## What changed

**`crates/gear-board/src/idle.rs`** — the one predicate, as the packet words it:

- `pub const HELP_LIMIT_S: i64 = 1800;`
- `pub struct Helping { message, lane: Option<String>, words, since }` and
  `Helping::text()` → `helping <lane>: <words>` when `lane` is Some, else
  `helping the captain: <words>`.
- `pub fn helping(tx, project, seat, now) -> GearResult<Option<Helping>>`:
  `None` unless the seat is a `SeatRole::Lane` with no
  `in_progress_attempts_of_seat` and the project has a captain; then the newest
  `MsgKind::Instruction` sent by the captain's seat id to the lane within
  `HELP_LIMIT_S` that has no answer — no message of the lane since the
  instruction's `created` with `reply_to == Some(instruction.id)` — gives the
  help. `lane` is the lane of the instruction's task when it is not the lane's
  own name; `words` is the first six whitespace words plus ` …` when the body
  has more.
- `fn idle_reason`: right after the `is_working` check, a seat for which
  `helping(…)` is Some has no reason (`None`).
- `fn has_reply` and `fn words_of` are the two small helpers the predicate
  needs.

**`crates/gear-board/src/lib.rs`**

- `LaneBoard` gains `pub helping: Option<String>` (`None` in both places that
  build a `LaneBoard`), filled in the loop that sets `idle_text` from
  `idle::helping(…)?.map(|h| h.text())` of the lane's seat `<project>:<lane>`.
- `fn lane_line` shows that text in place of `no current task` when the lane
  has no current task and `helping` is Some.

**`crates/gear-board/src/frame.rs`, `fn view_now`** — a new first arm: a lane
with `helping` Some and no current task shows the text in the middle column
with `Style::fg(Color::Acc)`, before the `idle_text` arm.

**`crates/gear-app/src/plan.rs`, `fn idle_lanes`** — a lane seat for which
`gear_board::idle::helping(…)` is Some is skipped (the allowed edit; after the
tail check, before the queue is read).

## Question sent, and answered by contract v2

The v1 packet's rule said `words` is the first **6** whitespace words; its own
acceptance expected `helping mast: Read the log of T-2 and send …`, the first
**7**. `gear send --kind question` M-4593 asked which the acceptance meant; the
implementation and the test followed the explicit rule. The captain answered
(M-4595) that the 6-word rule stands and that the example was a miscount, and
contract v2 carries it: its acceptance now expects
`helping mast: Read the log of T-2 and …` — exactly what the code and the test
produce, so v2 needed no further change. The attempt adopted v2 (`gear` printed
it) and this hand-in names contract v2.

## Out of scope

- No engine change: the packet says the predicate is what the next hull task
  uses; nothing in `gear-engine` was touched here (so the engine's own stall
  alerts still read only attempts and tasks).
- `idle_reason` keeps its order otherwise: a quota/parked/held/waiting seat
  still answers before the help, so a parked lane with an unanswered
  instruction is parked, not helping (the packet's position for the check).
- A lane whose instruction's task has no lane (or no task row) reads as
  `helping the captain: …`; a deleted task does not make the help vanish.
- `frame.rs`'s help line is not truncated to the 44-column middle field like
  the task title is — the whole `helping …: …` text is printed, as the packet
  asks for the text, not a shortened one.

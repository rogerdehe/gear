# T-387 — report

A voyage whose `eta:` is not a duration does not depart. A milestone block
could carry a style word or a sentence as its `eta:` (`eta: do it properly`),
which applied cleanly and left a voyage the board, the stations and the
forecast cannot measure (the station code kept working, at a "-" pace and no
eta quarter stations, but the voyage's eta was silently meaningless). Apply now
refuses such a block.

## What changed

**`crates/gear-app/src/station.rs`**

- `fn eta_seconds` is now `pub(crate)` (its body untouched: still strict, one
  or more `<number><unit>` groups and nothing else, `None` for anything else).
  Its doc comment says apply refuses a milestone whose eta it cannot read.

**`crates/gear-app/src/plan.rs`, `fn record_voyages` only**

- After the existing "done, bar and eta make a voyage" check, a block whose
  `eta:` `crate::station::eta_seconds` reads as `None` returns
  `bad(0, "milestone <M>: eta must be a duration GEAR measures the voyage
  against, e.g. `eta: 8h` or `eta: 1d 4h`; reasons go in # Decisions; got
  \"<first 40 characters>\"")` (`BadFormat`), before that block is written.
  The check runs for every block the draft carries, departed or not, so an
  existing voyage cannot be edited to a prose eta either; because it is inside
  the apply transaction, a refusal writes nothing at all (no task, no voyage,
  no departure) and leaves the plan version where it was.
- The first 40 characters are taken by `chars()` (never mid-character), and a
  block with no `eta:` line is still refused by the earlier missing-field
  check, which runs first.

The refusal reads `line 0: …` because `plan.rs`'s `bad(line, detail)` prefixes
the line and a milestone block is stored as `(header, body)` with no line; `0`
is the crate's existing "no line" value (`bad(0, "project not found")`).

**`skills/gear/references/captain.md`** (the `# Voyage` field line): `eta:` is
now "a duration (`8h`, `1d 4h`) and nothing else: apply refuses any other
text, since the board, the stations and the forecast measure against it".

## Tests (`crates/gear-app/tests/it/`)

- `voyage_contract.rs`, new `an_eta_that_is_not_a_duration_is_refused`:
  `eta: 8h` then `eta: 1d 4h` apply and the voyage stores them; `eta: 8h, hard`
  and `eta: do it properly` are refused with the text above (asserted
  verbatim, including the `got "…"` part) and the stored voyage keeps the eta
  it had; on a fresh project each refusal writes nothing — no voyage, no task,
  plan version still `0` (the voyage cannot depart); a 46-character eta shows
  exactly its first 40 characters in `got` and nothing past them.
- `station_contract.rs`, fixture only: `unknown_eta_keeps_task_stations_and
  _unknown_measurements_honest` used to seed `world("soon", 5)` through apply,
  which this task now refuses. It seeds `world("4h", 5)` and writes the prose
  eta straight into the voyage row, the way a row older than T-387 carries it —
  the station-level tolerance the test exercises (no eta station, `pace - ·
  projected finish -`, the course station still rings) is unchanged and still
  covered.
- No other fixture used a style word as eta (all others are durations).

## Out of scope

- `skills/gear/references/captain.md:11` ("its `eta:` as a style (\"quick
  landing\" or \"do it properly\")") and `skills/gear/references/course.md:23`
  ("the eta number only sets that style") still describe eta as a style word.
  The packet's allowed edit is the `eta:` description in the `# Voyage` field
  line, so those two lines were left alone; they now contradict the new rule
  and want a task of their own.
- The station layer still tolerates a prose eta in a voyage row (`and_then
  (eta_seconds)`), as the packet requires (`fn eta_seconds` stays strict); the
  fixture above is the only way such a row can still exist.
- Voyage rows already stored with a prose eta are not migrated or invalidated:
  they keep their eta until their block is applied again, which is now refused
  until the captain writes a duration. Nothing in the packet asked for a
  migration.

# T-428 — report

A plan never leaves a task depending on a cancelled one. When a plan is
applied, every task of the project that is still to be worked on (not
`Cancelled`, `Done` or `Failed`) whose deps name a task that is — or becomes
in that same plan — `Cancelled` makes the apply fail with one line per pair:

```
T-3 depends on cancelled T-2: drop or replace that dependency
```

Nothing is applied. Two tasks that both wait on the cancelled one give two
lines in the same refusal, tasks in id order, deps in the order the task lists
them.

## What changed

`crates/gear-app/src/plan.rs` only (plus the tests):

- step 5 of `fn apply_queue`, after the dependency cycle check: a map of the
  task states the plan leaves behind (the stored state, overridden by
  `state=` of the draft's blocks, `Ready` for a `## NEW` block), matched
  against the final deps graph the cycle check already builds (`graph`: the
  stored deps, replaced by the block's `deps:` for every mentioned task). A
  live task with a dep whose final state is `Cancelled` is collected as
  `"<id> depends on cancelled <dep>: drop or replace that dependency"`; a
  non-empty list is one `BadFormat` whose detail is the lines joined by
  `\n`. The check runs before any write, so the plan version, the states and
  the deps are untouched on refusal.
- The doc comment of `apply` names the new rule in step 5.
- `crates/gear-app/tests/it/cancel_contract.rs`: the file's fixture plan
  `CANCEL_T1` cancelled `T-1` while `T-2` still said `deps: T-1`. That is
  exactly what is refused now, so the fixture drops the dep (`deps: -`, i.e.
  the captain's "drop or replace" move) and the T-93 tests keep testing the
  cancel, not the new rule; the old text is kept as `CANCEL_T1_WITH_DEPS` for
  the first new test.

## Tests

New in `crates/gear-app/tests/it/cancel_contract.rs` (`world()` has `T-1` and
`T-2 deps T-1`):

- `a_plan_that_cancels_a_dep_is_refused_and_names_the_pair` — cancel `T-1`
  while `T-2` keeps `deps: T-1`: `BadFormat`, detail exactly
  `T-2 depends on cancelled T-1: drop or replace that dependency`, `T-1` still
  Ready and the plan version still 1.
- `a_live_task_newly_depending_on_an_already_cancelled_task_is_refused` — a
  cancelled `T-1` in the store, a plan that gives `T-2` `deps: T-1`: the same
  refusal, the dep was not written, the plan did not apply.
- `dropping_the_dependency_lets_the_cancel_apply` — the plan that cancels
  `T-1` and gives `T-2` `deps: -` applies; `cancelled == ["T-1"]`, `T-2` has
  no dep.
- `a_done_task_keeping_a_cancelled_dep_is_not_refused` — a Done `T-2` with
  `deps: [T-1]` (cancelled) applies fine.
- `every_pair_gets_its_own_line` — `T-2` and `T-3` both wait on the `T-1` the
  plan cancels: the refusal carries both lines, in id order, and nothing was
  applied.

## Out of scope (noticed, not changed)

- The rule covers every task of the project, as the packet says, not only the
  tasks the draft lists: a plan that changes something else still fails while
  a live task in the store waits on a cancelled one, and the captain has to
  mention that task and drop the dep in the same plan. That is the intended
  "drop or replace" flow, but an existing project that already has such a
  dependency (the other project's `T-140`/`T-178` on `T-186`) needs one plan
  line per task; nothing repairs them on its own.
- `crates/gear-engine/src/dispatch.rs` still counts a dependency only when it
  is Done and merged, so a dependency on a `Failed` task keeps a task
  undelivered with nothing said. The packet asked for `Cancelled` only; a
  `Failed` dep is the same dead end and would be a separate task.

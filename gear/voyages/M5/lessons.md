# M5 lessons (recorded lightly; distilled into the skill only at a release review)

0. **Important: decompose the whole voyage before departure.** I departed M5 with 5 tasks and a decision of my own to "write the queue in waves"; after an hour the plan held 21 tasks and the user read it, rightly, as a voyage of 21 tasks. Decomposing as you go drops work along the way (). Every item taken at kickoff becomes tasks in the plan before the lanes start; a cut that proves wrong is adjusted later. The skill never said so (captain.md, decompose.md): T-275 adds it. I was teaching another project's captain how to use GEAR while getting this basic step of it wrong.

1. 2026-10-28, first hour: the 4.2-era delivery problems are still there. (a) The direction packet of T-260 (O-3422) reached a fresh Codex session of review-11 that sat at 0% context; the review packet came through later, but O-3422 stays "submitted" and three more deliveries to the same seat (O-3424..O-3426) stay "submitted" too, so "deliveries not confirmed" climbs on the home page. (b) mast's first packets (O-3411 T-257, O-3423 T-261) were "not confirmed within 180s" although mast did the work: it did not run `gear` first, and each time the engine re-delivered in a new agent session. Both are the backlog's lost-packet and confirm-by-first-action items: they become tasks in a later S1 wave.
2. T-263: a contract that says "change <file> only" and asks for tests makes the reviewer fail a test placed where the crate keeps its tests (tests/it). Write the scope as "the code change is in <file> only; tests go where the crate keeps them". Captain's wording error, settled by a pass over the review.
3. M-4365: a "name is held by another pane" item for a name a finished reviewer gives back later in the same tick; fixed at the root by T-270.
4. F-122, F-123: review rounds get 10-min budgets while one `make check CRATE=gear-engine` takes ~3 min (build 30-55 s, tests up to 152 s) and a redelivered packet starts with the timer already running. Engine test speed becomes an S1 task; the redelivery is T-267's family.
5. T-276: the contract said "run without the flag it behaves as today" and named no check, so mast designed one (a pty harness that starts the prototype and quits it) and spent minutes on it. A contract that says a behaviour must not change also says how that is checked (here: the diff touches no drawing function).
6. F-124 (T-267): the v1 rule "confirming a delivery voids the older ones" could not hold, because the tick confirms the oldest first with the same view; and "starts with X as the review packet does" was false (the review packet starts with "Review T-n"). Two contract errors of mine from writing without reading the order the engine walks things in. Read the loop before writing a rule about its order.
7. Decomposing the rest of M5 took four agents over 20 minutes each: one agent per 20 items, each item needing its code read so the contract names only what exists. Cut such work into batches of 7-8 items, more agents in parallel, and put the item → task map in the plan first so the user sees the whole voyage at once.
8. Two captains, two opposite cuts, both from a skill with no number: I departed with 5 tasks and wrote the rest in waves (lesson 0); another project's captain cut four 300-minute tasks, one per lane. Decomposition needs hard rules a captain cannot read his own way: the whole voyage before departure (T-275) and at most 60 minutes per task, refused by apply (T-279).
9. T-274: an absolute speed threshold on a machine shared with another project cannot be met or judged; a speed task's accept compares before and after in one run, or names no number.
10. F-127: nextest runs each test in its own process, so 'build the fixture once per test file' (OnceLock) shares nothing; a fixture shared across tests has to be on disk (built once, copied) or the tests must not need it. The conventions' test rule says 'once per file' and is wrong under nextest: correct it at S1's release review.
11. F-129: a reviewer's `gear --show` got LOCKED from the store once and passed on retry (the store was busy with the engine's tick). M4.2 saw "database is locked" too (O-3206). One more sighting makes it a task: a read waits on the lock with a bound instead of failing.
12. T-322: 'no new file appears' in an accept is read literally by the reviewer (SQLite's -wal/-shm count); say what must not appear (a store, a directory).
13. F-130/F-131 (T-318): an accept that runs a release build costs a cold release build per worktree (7-10 min here) for the writer and again for the reviewer; size the budget for it, or prove the step with `make -n` and one existing build.
14. M-4616: re-splitting the lanes after decomposition turned same-lane order into cross-lane order with no deps (T-334 mast needs T-329, which moved to hull). After a re-split, every former 'after:' between two tasks that now sit on different lanes becomes a deps: line.
15. M-4774: a merge that conflicts is a rework (merge dev, resolve), not a remerge, though the item's hint offers only `- remerge`; and a fail on an accepted attempt must name the candidate exactly as stored (here the short sha the lane handed in), or settle refuses it as a different verdict.
16. [now] in a queue header does not move a task up a lane's queue; the block's place in the file does. T-371 waited behind 10 hull tasks while lost Enters recurred.
17. The board batch was drafted as one serial chain of 21 tasks (most touch frame.rs), so mast idles at every step while the previous one is reviewed and merged. A file shared by many tasks is cut so tasks touch different functions or files, or the lane gets other work interleaved; a long same-lane deps chain is the shape decompose rule 3 forbids.
18. I rebuilt the engine "for T-371" when T-371 showed done, but done means its verdict passed, not that it is merged: the build had no T-371, and the fifth lost Enter came after. Before a rebuild, check the merge commit is on origin/dev (git log origin/dev --grep 'merge(T-n)') and the binary carries the change.
19. At 50 % of the eta I proposed moving the eta out to 24 h because the station forecast said 20.8 h. The user refused: a short clock is answered by working faster, never by moving the eta, or every voyage slips for ever. The forecast itself was wrong: it summed each task's start-to-merge span, but review and merge run beside the lane's next task, so minutes counted twice; lane throughput (estimate done per lane wall minute) put the finish at about 845 of 960 min (T-390). Before proposing any eta change, measure throughput and look for the speed-up.
20. I put `make check … TESTS=<filter>` into 14 queued contracts before T-393 (the Makefile half) was merged, so every lane and reviewer met a command that silently ran the whole crate and worked around it (F-147..F-151). A contract names only what exists on the integration branch; a new tool goes into contracts after its merge.
21. M-5012..M-5061: I pushed a plan commit after nearly every item while merges were queued, and each push moved dev under the engine's merge: T-381 lost its push race four times (merge op unknown) and T-382 took 33 min. The standing rule "push only when no merge op is pending" holds even for one-line station answers: commit locally, and push when the merge queue is empty.
22. At 21:42 I stopped the engine to push the review-loop fix, and a lane's next gear call restarted it within seconds on the old binary; v0.4.11 finished building three minutes later, so our engine never ran the fix. I then chased a "third path" for an hour while the cause was the old binary (lsof showed the replaced inode). The rebuild order is: build, check the binary, then stop; and after any restart, verify the running engine's binary (lsof txt inode equals target/release/gear's) before reading its behaviour as the new code's.
23. Eight friction reports (F-150, F-157, F-158, F-163, F-166, F-167, F-169, F-174) are my contracts: a file name dev already had, a rule pair with no winner, a rework that said "keep both sides" when dev had changed a helper's signature, a version bump after the work was done. Each cost a question or a round. A packet names files as they are on dev now, says which rule wins when two meet, and names what a dev merge breaks; a contract is bumped mid-task only when the old one cannot be met.
24. I hand-wrote two releases (v0.4.12, v0.4.13) while the voyage was stopped; resuming, I checked first that dev's full gate passes in a clean checkout outside the temp directory, that every accepted attempt is in dev or queued as rework, and which lane and rework branches conflict with dev, then had each lane merge dev and push while still held, and released it after. Resume in that order after any hand fix.
25. T-366's rework pointed mast at "the text the captain gave in M-5524"; a lane cannot read a captain's message by id, so it had to ask again. A packet or rework carries the text itself, never a message id.
